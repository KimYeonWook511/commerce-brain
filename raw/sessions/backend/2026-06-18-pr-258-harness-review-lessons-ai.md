## 배운 것 (AI/harness 운영)

**구현 전 별도 에이전트로 설계 전제 검증의 가치**
- 설계 문서 초안을 별도 검토 에이전트에 돌렸더니 치명 결함을 잡음: 설계 전체가 기댄 안전망(기존 결제
  대사가 미완 환불을 재시도해 줌)이 코드상 존재하지 않았음. 직접 코드로 재확인해 확정.
  → 내가 짠 설계의 "전제"를 구현 전에 적대적으로 검증시키면 돈 유실급 결함을 미리 잡는다.

**리뷰 봇 제안은 blind accept 금지**
- 봇이 "distinct 제거"를 제안했는데 그 쿼리의 join fetch 구조를 놓친 틀린 제안이었음(그대로 적용하면
  버그 — 상세 메커니즘은 도메인 메모). LLM 코드 리뷰는 쿼리의 한 부분만 보고 다른 부분의 효과를 놓치는
  실수를 사람처럼 한다. → 봇 제안의 근거를 코드로 검증하고, 틀리면 다른 해법으로 고친다(blind accept
  금지).

**harness committer/recorder 실행 순서·문서 drift**
- 흐름은 개발→리뷰→커밋(committer)→기록(recorder). recorder는 phase index(step status 정본 파일)에
  step 상태를 쓰기만 하고 git 권한이 없어 커밋을 못 함. 그래서 한 step의 상태 파일 변경은 "다음 step의
  커밋 에이전트"가 뒤늦게 커밋함(git log가 뒤섞여 보이는 이유).
- harness-v4 레퍼런스 문서는 "phase 상태 파일은 마지막 마무리 단계가 일괄 커밋, 커밋 에이전트는
  건드리지 않음"이라 적혀 있는데 실제론 커밋 에이전트가 step별로 커밋함 → 문서-실제동작 불일치.
  (커밋 에이전트 제약 강화 + 문서 동기화는 하네스 PR 난립을 피하려 별도 chore로 배치 처리하기로 미룸.)

**실수 2건 (재발 방지)**
- 루트 문서 동기화 때 문서를 worktree가 아닌 메인 체크아웃(develop 브랜치)에 편집함(경로에
  worktrees/<브랜치>/ 가 빠짐). 메인을 원복하고 변경분을 worktree로 옮겨 수습. → worktree 작업 중 루트
  문서 편집은 경로 확인.
- 백그라운드로 빈 busy-loop(존재하지 않는 마커 파일을 무한 체크하는 셸 루프)를 띄워 CPU를 한 시간
  넘게 점유함. 에이전트 완료는 자동 알림되니 폴링 루프 자체가 불필요했음. → 백그라운드 작업 대기에 빈
  폴링 루프 쓰지 말 것(자동 완료 알림 신뢰).

**ADR 세분화 과다**
- task 단위 결정 6개를 전부 루트 결정 문서로 승격했는데, 사소한 것(응답 계약 디테일, "기존 unique가
  이미 충분"이라는 발견 등)까지 올리면 루트 결정 문서가 비대해짐. 진짜 cross-cutting/되돌리기 어려운
  결정만 루트에 두고 나머진 task 문서가 받치는 게 맞음. (이 저장소는 원래 결정을 잘게 쪼개 올리는 편 —
  한 task가 다수, 많게는 9개가량 올린 적도 — 이지만 그 관례 자체를 재고할 만함.)
