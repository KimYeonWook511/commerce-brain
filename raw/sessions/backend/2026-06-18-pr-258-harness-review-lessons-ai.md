# PAID 취소·환불을 하네스로 돌리며 얻은 AI 운영 교훈 — 설계 전제의 적대적 검증, 리뷰 봇 blind accept 금지, 커밋/기록 순서와 문서 drift

PAID(결제 완료) 주문의 사용자 취소·환불 흐름(PR #258)을 dynamic workflow 하네스로 자동 구현하면서 얻은, AI·도구 운영 측면의 교훈을 모았다. 이 작업은 한 phase(취소·환불)를 세 개의 순차 구현 단위(step)로 쪼개, 각 step이 개발 → 수용기준 검증 → 리뷰 → 커밋 → 상태 기록을 한 바퀴 돈 뒤 마무리(finalize)하는 방식으로 굴렸다. 도메인 설계 결정(단일 tx 환불 의도, append-only 원장, standalone CANCEL 대사, 락 전략 등)의 "왜"는 같은 PR의 도메인 설계 메모에 따로 있고, 여기는 하네스·리뷰 봇·프로세스 자체에서 배운 것에 국한한다.

## 배운 것

### 구현 전, 설계 전제를 별도 에이전트로 적대적으로 검증하는 것의 가치

설계 문서 초안을 별도 검토 에이전트에 돌렸더니 치명 결함을 잡았다. 설계 전체가 기댄 안전망 — "주문 취소와 단일 트랜잭션으로 영속화한 환불 의도를, 기존 결제 대사가 나중에 집어 재시도해 마무리해 준다" — 가 **코드상 존재하지 않았다.** 실제로 기존 결제 대사는 승인(APPROVE) 타입만 스캔하고 취소(CANCEL) 대사 분기는 건너뛰고 있어서, 승인 결제에 매달린 환불 의도를 구동하는 경로가 아예 없었다(글로만 있던 안전망). 검토 에이전트의 지적을 직접 코드로 재확인해 확정했고, 이 발견이 이번 작업에서 standalone CANCEL 대사를 신설하게 만든 진짜 핵심이 됐다.

- **핵심 교훈:** 내가 짠 설계의 "전제"를 구현 전에 별도 에이전트로 적대적으로 검증시키면, 돈 유실급 결함(취소는 됐는데 환불 기록이 없는 상태)을 코드를 쓰기 전에 잡을 수 있다.

### 리뷰 봇 제안은 blind accept 금지 — 근거를 코드로 검증한다

취소 흐름에서 주문을 잠그는 `distinct + join fetch + FOR UPDATE` 쿼리가 리뷰에 올랐고, 리뷰 봇이 "distinct 제거"를 제안했다. 그러나 이는 그 쿼리의 join fetch 구조를 놓친 틀린 제안이었다 — 그대로 적용하면 join fetch의 row 뻥튀기(주문 한 건이 자식 아이템 수만큼 행으로 복제됨)를 단건 매핑이 못 받아 예외가 나는 버그가 된다(상세 메커니즘은 도메인 설계 메모).

- **패턴:** LLM 코드 리뷰는 쿼리의 한 부분(distinct)만 보고 다른 부분(join fetch)의 효과를 놓치는 실수를, 사람처럼 한다.
- **대응:** 봇 제안의 근거를 코드로 검증하고, 틀리면 봇이 시킨 대로가 아니라 다른 해법으로 고친다. 이번엔 distinct 제거 대신 주문 행 하나만 잠그고 아이템은 별도로 로드하는 2단계 분리를 택했다(락 범위를 좁히는 이득이 진짜 문제였고, 봇 제안은 증상만 건드린 셈).

### 하네스의 커밋/기록 에이전트 실행 순서와 문서-동작 drift

step 한 바퀴의 흐름은 개발 → 리뷰 → 커밋(커밋 에이전트) → 상태 기록(기록 에이전트)이다. 기록 에이전트는 각 step의 진행/완료 상태를 정본 상태 파일(phase 상태 파일)에 쓰기만 하고 git 권한이 없어 스스로 커밋하지 못한다. 그래서 한 step의 상태 파일 변경은 **다음 step의 커밋 에이전트**가 뒤늦게 함께 커밋한다 — git log만 보면 커밋이 뒤섞여 보이는 이유가 이것이다.

- **문서 drift:** 하네스 레퍼런스 문서에는 "phase 상태 파일은 마지막 마무리(finalize) 단계가 일괄 커밋하고, 커밋 에이전트는 상태 파일을 건드리지 않는다"고 적혀 있는데, 실제로는 커밋 에이전트가 step별로 상태 파일을 커밋하고 있었다. 문서와 실제 동작이 어긋난 상태다.
- 어느 쪽으로 정합화할지(커밋 에이전트의 제약을 강화해 상태 파일을 안 건드리게 하거나, 문서를 실제 동작에 맞게 갱신하거나)는 이번에 결정하지 않고 미뤘다 — 하네스 자체를 고치는 PR이 난립하는 걸 피하려고 별도 chore로 묶어 배치 처리하기로 했다.

### 재발 방지 — 프로세스 실수 두 건

- **worktree 작업 중 루트 문서를 메인 체크아웃에 편집함.** 루트 문서 동기화를 하면서, 작업용 worktree(`worktrees/<브랜치>/` 아래 격리된 작업 트리)가 아니라 메인 체크아웃(develop 브랜치)에 직접 편집해 버렸다(편집 경로에서 `worktrees/<브랜치>/` 접두가 빠진 것). 메인 쪽 변경을 원복하고 변경분을 worktree로 옮겨 수습했다. → worktree 작업 중 루트 문서를 편집할 땐 경로부터 확인한다.
- **빈 busy-loop로 CPU를 한 시간 넘게 점유함.** 존재하지 않는 마커 파일을 무한히 체크하는 셸 폴링 루프를 백그라운드로 띄워 놓고 방치했다. 애초에 에이전트 완료는 자동으로 알림이 오므로 폴링 루프 자체가 불필요했다. → 백그라운드 작업 완료를 기다릴 때 빈 폴링 루프를 쓰지 말 것(자동 완료 알림을 신뢰).

### 결정 문서 승격 기준 — 잘게 쪼개 올리는 관례를 재고할 것

이 작업에서 나온 task 단위 결정 여섯 개를 전부 루트(cross-cutting) 결정 문서로 승격했는데, 그중엔 사소한 것도 섞여 있었다 — 취소 응답 계약의 디테일, "기존 4컬럼 unique가 CANCEL 멱등을 이미 하드 보장하고 있었다"는 발견 같은 것. 이런 것까지 루트로 올리면 루트 결정 문서가 비대해진다.

- **판단:** 진짜로 여러 도메인을 가로지르거나 되돌리기 어려운 결정만 루트에 두고, 나머지는 해당 task 문서가 받치게 하는 편이 맞다.
- **배경:** 이 저장소는 원래 결정을 잘게 쪼개 올리는 편이다 — 한 작업이 다수를, 많게는 아홉 개까지 루트 결정으로 올린 적도 있다(대사·후처리 루프를 크게 다룬 그 작업이 그랬다). 이번 여섯 개도 그 관례의 연장인데, 그 관례 자체를 재고할 만하다.

## 미해결·열린 질문

- **커밋 에이전트가 이전 step의 상태 파일을 커밋하는 실제 동작 vs 레퍼런스 문서의 정합화.** 커밋 에이전트의 제약을 강화하거나 문서를 갱신하거나 둘 중 하나로 맞춰야 한다. 하네스 PR 난립을 피하려 별도 chore로 배치 처리하기로 미룬 상태.
