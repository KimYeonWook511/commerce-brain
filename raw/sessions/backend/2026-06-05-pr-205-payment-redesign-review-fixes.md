## 결정한 것

정본은 commerce-backend/docs/tasks/payment-order-redesign/ 의 adr.md 와 retrospective.md.

### 단일 테이블 → 두 테이블 분리로 전환 — 내 이해
처음엔 tbl_payment 한 테이블에 결제 유형(예약/승인/취소)을 type 컬럼으로 다 담으려 했다. 근데 4가지 위화감이 누적됐다:
1. 예약(임시·만료·상태변화 영역)과 승인/취소(PG 에 보낸 불변 사건)는 본질이 다르다. 한 테이블에 두면 예약의 임시성이 사건 테이블을 오염시킨다.
2. 예약 단계엔 pg_payment_id 가 없어서, 그것 때문에 컬럼을 NULL 허용으로 완화하게 된다. 승인/취소만 보면 NOT NULL 이 자연스러운 보장인데 포기하게 됨.
3. status 컬럼에 예약 상태와 사건 상태 두 의미가 혼재 → "결제 시도 몇 건?" 같은 단순 조회마다 type 필터를 달아야 함.
4. "단일 테이블이 단순하다"는 착시였다. 테이블 수는 줄지만 NULL 컬럼과 쿼리 분기가 오히려 늘어난다.
→ 두 테이블로 쪼개니 pg_payment_id NOT NULL 이 복원되고, 두 status enum 이 각자 깔끔해졌다.

### NULL 트릭으로 partial unique 우회
MySQL InnoDB 는 PostgreSQL 의 조건부 unique 인덱스(CREATE UNIQUE INDEX ... WHERE)를 지원하지 않는다. 그래서 "조건 충족 시에만 값을 넣고 아니면 NULL" 인 컬럼 + 일반 unique 제약으로 우회한다 (InnoDB 가 NULL 을 unique 중복으로 치지 않는 특성 이용). 승인 성공 시에만 order_id 를 넣는 컬럼, 예약 RESERVED 상태일 때만 "{order_id}:{provider}" 를 넣는 컬럼. 핵심은 캡슐화 — 상태와 트릭 컬럼을 *같은 도메인 메서드 한 번의 호출에서 동시에* set 한다. 둘이 따로 변경되면(예: 상태만 바꾸고 트릭 컬럼은 안 비움) unique 가 무력화돼 정합성이 무너진다. 도메인 테스트로 "한 메서드 호출에서 두 필드 동시 변경"을 단언으로 박았다.

### 성공 결제 unique 는 PG(provider) 를 안 가린다 — 의도
한 주문에 성공한 승인은 네이버/카카오 등 전 PG 를 통틀어 1건만 허용. 사용자가 여러 PG 에 동시에 결제를 보내 둘 다 승인되는 cross-provider 이중결제를 막는 게 목적이다.

## 막힌 점 — 자동 구현 후 3회 리뷰에서 계단식으로 드러난 결함들

execute.py 워커가 자동 구현한 결과를, 3차례 코드리뷰(Gemini → Codex → Codex+Claude)로 검증하며 결함을 계단식으로 잡았다. 핵심 4개:

### 1. 취소 결제의 order_id 가 NULL 로 새던 문제 (1차 리뷰)
취소 결제 행을 만드는 팩토리가 orderId 를 받지 않아, 취소 결제의 order_id 가 NULL 로 저장됐다. 스키마 문서엔 NOT NULL 인데 마이그레이션 SQL(NULL 허용)·엔티티·팩토리가 서로 따로 놀았다. 취소 흐름이 후속 task 라 *실제로 DB 에 저장하는 실행 경로가 테스트에 없어서* 회귀로 안 잡힌 잠복 결함. → orderId 전파 + SQL NOT NULL + 엔티티 nullable=false 로 4곳 정합.

### 2. 이미 사용된 예약의 미완료 승인이 영구 차단되던 문제 (2차 리뷰)
같은 결제키로 redirect 가 다시 오면 기존 결제 결과를 멱등 응답하도록 했는데, 초기 구현은 *성공한 승인 행만* 찾아 반환하고 없으면 404 를 던졌다. PG 가 "처리 중"을 반환했거나 호출 직전 끊겨서 승인 시도가 미완료(요청됨) 상태로 남은 경우, redirect 재시도가 404 로 막혀 결제를 영영 못 끝낸다. → 기존 승인 시도를 상태별로 재처리(요청됨 → PG 재확인 / 성공 → 멱등 / 실패 → 실제 사유)하도록 고침. 교훈: "멱등 = 완료된 것 재반환"이라는 가정이 *진행 중* 상태를 빠뜨렸다.

### 3. 만료된 예약이 자리를 안 비워 재예약이 막히던 문제 (2차 리뷰 — 내 설계 맹점)
당시 설계 결정은 "만료된 예약은 EXPIRED 같은 상태로 따로 마킹하지 않고, 재사용 판단 시 만료 시각 필터로만 걸러낸다"였다. 마킹을 두면 "누가 언제 마킹하느냐"는 또 다른 박제 위험이 생긴다고 봤기 때문. 그런데 만료된 예약 행은 상태가 여전히 RESERVED 라 "{order_id}:{provider}" unique 키를 계속 점유한다. 만료 시각 필터는 *재사용*만 막을 뿐, *새 발급*은 같은 키로 unique 위반을 일으켜 **같은 주문이 영원히 재예약 불가**가 된다. "필터로 충분하다"가 재사용 한쪽만 본 결론이었다. → 만료 상태(EXPIRED)를 다시 도입하되, reserve 진입 시점에 만료/무효 예약을 그 자리에서 회수(상태=EXPIRED + 키 비움)한 뒤 새로 발급. reserve 호출 요청이 자기가 쓸 자리를 직접 정리하므로 별도 배치/스케줄러의 박제 위험은 안 생긴다. 교훈: 상태/필드를 단순화로 제거할 때 영향을 *모든 경로(재사용 + 재발급)에서* 따져야 한다. 한쪽만 보고 단순화하면 정합성 구멍이 생긴다.

### 4. 결과 불명 오류를 '실패'로 분류해 이중결제가 열려 있던 문제 (3차 리뷰 — 가장 심각)
PG 승인 호출의 timeout/네트워크 오류를 PG 클라이언트가 네트워크 예외로 감싸는데, 게이트웨이가 이를 '실패(FAILED)'로 반환하고 있었다 (그 아래에 결과 불명(UNKNOWN)으로 보내는 분기가 있었지만 위에서 다 잡혀서 도달 못 하는 죽은 코드였다). timeout 은 *PG 가 승인을 처리했는지 불명*인데 '실패'로 기록하면, 그 주문에 결과 불명 결제가 있는지 검사해 재시도를 차단하는 로직이 안 걸린다 → 재결제가 허용되고, PG 가 이미 승인한 상태였다면 **이중결제**가 난다. → 결과가 불명한 오류(네트워크/PG 서버 오류/응답 해석 불가)는 결과 불명(UNKNOWN)으로, 처리되지 않음이 확실한 거절(인증 실패/잘못된 요청)만 '실패'로 분류하도록 정정. 교훈: 외부 호출 예외를 '실패'로 뭉뚱그리면 *결과 모름* 과 *처리 안 됨* 이 섞여 정합성이 깨진다 — 성공/실패 외에 '결과 모름'이라는 세 번째 상태가 필요한 이유다.

## 배운 것

- **잠복 결함은 "후속 task 라 실행 경로가 테스트에 없는" 곳에 숨는다.** 취소 결제의 order_id, 취소 흐름 등. 수용 기준(단위/통합 테스트)을 통과해도 미구현 경로의 정합성은 안 잡힌다.
- **단순화의 영향은 모든 경로에서 따진다.** 만료 상태를 없앤 게 재사용 판단은 단순화했지만 재발급을 깼다.
- **외부 연동 예외 분류는 '결과 모름' vs '처리 안 됨'을 반드시 구분.** 돈이 두 번 빠지느냐가 여기서 갈린다.
- **여러 AI 리뷰어가 서로 다른 결을 잡는다** (어떤 리뷰어가 무엇에 강했는지의 비교는 같은 PR 의 harness 운영 메모에 별도 정리).
