# 유일 제약을 비웠다가 같은 값으로 다시 잡을 때의 쓰기 순서

## 배경 — 어떤 설계에서 이 문제가 나오나

결제 모델을 다시 설계하면서 **"한 주문에 살아 있는 결제는 최대 하나"** 를 DB 유일 제약으로 지키기로
했다. 그런데 결제는 실패하면 회원이 다시 시도할 수 있어야 한다. 그러면 **한 번 잡았던 주문 식별자를
놓았다가 같은 값으로 다시 잡는** 흐름이 생긴다.

이 모양은 결제에만 있는 게 아니다. "**어떤 자원을 한 번에 하나만 점유하되, 점유를 풀고 다시 잡을 수
있어야 한다**" 는 조건이면 어디서나 같은 문제가 나온다 — 좌석 선점, 배타적 작업 잠금, 예약 슬롯.

## 결정한 것

### 1. 점유를 나타내는 컬럼을 **따로** 두고, 비울 때 NULL 로 만든다

컬럼이 둘이다. **이 둘을 하나로 합치지 않는 것이 이 설계의 절반이다.**

| 컬럼 | 성질 | 무슨 일을 하나 |
| --- | --- | --- |
| 자원 참조 | `NOT NULL` | **이력.** 이 행이 어느 주문의 시도였는지. 끝나도 안 지운다 |
| 점유 표시 | `UNIQUE`, NULL 허용 | **배타 점유.** 살아 있으면 자원 식별자, 끝나면 NULL |

- **왜 나누나**: 합쳐서 하나로 두고 끝날 때 NULL 로 만들면 **끝난 행이 어느 자원의 것이었는지가
  사라진다.** "이 주문에 지난 시도가 몇 번 있었나" 를 영영 못 찾는다. 결제는 시도 이력이 남아야
  하는 성격이라(원장) 이건 그냥 데이터 손실이다.
- **살아 있는 동안 두 컬럼에 같은 값이 중복으로 들어간다.** 정규화 관점에서는 중복이지만,
  **한쪽은 사실을 기록하고 다른 쪽은 제약을 표현하는 것**이라 목적이 다르다. 값이 같다고 합치면
  위의 손실이 따라온다.

### 2. "살아 있는 것만 유일" 을 NULL 허용으로 표현한다

- **왜 되나**: MySQL 은 유일 제약에서 **NULL 을 중복으로 치지 않는다.** 끝난 행이 아무리 쌓여도
  NULL 끼리는 충돌하지 않는다.
  - **DBMS 마다 다르므로 옮길 때 확인해야 한다.** SQL Server 는 유일 제약에 NULL 을 **하나만**
    허용한다(이 방법이 아예 안 통한다). PostgreSQL 은 기본은 같지만 15 부터 `NULLS NOT DISTINCT`
    로 이 성질을 끌 수 있어, 무심코 켜면 조용히 깨진다.
- **왜 이 우회를 쓰나**: PostgreSQL 이면 `CREATE UNIQUE INDEX ... WHERE status = 'ALIVE'` 라는
  **부분 인덱스**로 조건부 유일을 직접 표현할 수 있다. **InnoDB 에는 그게 없다.** 그래서 조건을
  인덱스가 아니라 **값에 담는** 우회를 쓴다.
- **대가**: 점유 컬럼 하나가 두 가지를 겸한다 — 무엇을 가리키는 값이면서 동시에 "살아 있는가" 의
  표시. 상태 컬럼과 어긋날 수 있다는 뜻이라, **둘을 같은 UPDATE 에 묶어** 도메인 객체 안에서만
  바뀌게 했다. 따로 두면 상태는 끝났는데 점유가 안 풀린 행이 생긴다.

### 3. 시도마다 새 행을 쌓는다 — 기존 행을 재사용하지 않는다

여기서 갈림길이 있었다. 재점유를 **기존 행의 UPDATE 로** 처리하면 아래 4번의 쓰기 순서 문제가
**아예 안 생긴다.** 그래도 새 행을 쌓기로 했다.

- **이유**: 이 테이블이 **시도 원장**이다. 몇 번 시도했고 각각 왜 실패했는지가 남아야 한다.
  행을 재사용하면 그 이력이 덮인다. 순서 문제는 해결할 수 있는 것이고 잃은 이력은 되찾을 수 없다.
- **검토하고 버린 것 — 끝난 행을 DELETE**: 점유가 풀리긴 하지만 **이력이 사라지는 데다,
  ORM 의 쓰기 순서상 DELETE 가 INSERT 보다 뒤라 순서 문제가 오히려 악화된다**(아래 4번).
  두 가지가 다 나쁘다.
- **검토하고 버린 것 — 유일 키에 시도 회차를 넣어 값이 안 겹치게**: 그러면 같은 주문에
  살아 있는 결제가 여럿 서도 제약이 안 막는다. **막으려던 것 자체가 사라진다.**
- **검토하고 버린 것 — 비움과 재점유를 두 트랜잭션으로 나누기**: 순서는 확실해지지만 사이에서
  끊기면 **아무도 점유하지 않은 채로 남는다.** 원자성을 잃는다.

### 4. 비우는 쪽이 새로 잡는 쪽보다 **먼저** DB 에 닿게 만든다

한 트랜잭션 안에서 "앞 것을 끝내고(비움) 새 것을 만든다(같은 값으로 점유)" 를 할 때가 문제다.
**순서가 뒤집히면 아직 차 있는 값에 부딪혀 유일 제약 위반이 난다.**

두 층을 갈라 봐야 한다.

**DB 층 — 순서만 맞으면 문제가 없다.**

| 보낸 순서 | 결과 |
| --- | --- |
| UPDATE(비움) → INSERT | 통과 |
| INSERT → UPDATE(비움) | 위반 |

- MySQL 은 유일 제약을 **행을 쓰는 그 순간마다** 검사하고 커밋까지 미룰 수 없다. 이를 미루는
  표준 SQL 의 `DEFERRABLE INITIALLY DEFERRED` 를 MySQL 은 지원하지 않는다.
  - **"문 단위" 가 아니라 "행 단위" 인 것이 중요하다.** 한 문으로 값을 밀어 올리는
    `UPDATE t SET slot = slot + 1` 은 **최종 상태가 유일해도 중간 행에서 위반이 난다.**
    "그럼 한 문으로 처리하면 되지 않나" 는 이 주제에서 자연스럽게 나오는 발상인데, 안 통한다.
  - `unique_checks = 0` 은 유예처럼 보이지만 **검사를 미루는 게 아니라 건너뛴다.** 중복이 그냥
    들어간다. 대안이 아니다.
- **옵티마이저가 문과 문 사이 순서를 바꾸는 일은 없다.** 옵티마이저가 고르는 것은 *한 문 안에서*
  어떤 인덱스를 탈지이지 실행 순서가 아니다. 이걸 헷갈리면 "DB 가 알아서 하겠지" 로 잘못 안심한다.

**ORM 층 — 코드에 적은 줄 순서는 아무 보장이 아니다.**

두 경로가 있고 **둘 다 같은 결론으로 간다.**

*경로 하나 — 기본키를 DB 가 매기는 전략*(`GenerationType.IDENTITY` / AUTO_INCREMENT).
키 값을 얻으려면 INSERT 를 보내야 하므로 **미룰 수가 없다.** 저장을 호출하는 그 자리에서 곧바로
나간다. MySQL 은 시퀀스가 없어 현실적으로 이 경로가 지배적이다.

*경로 둘 — 그 밖의 전략*. Hibernate 가 flush 할 때 코드 순서가 아니라 **작업 종류별로 모아
정해진 순서**로 내보낸다.

```
OrphanRemoval → INSERT → UPDATE → (컬렉션 작업들) → DELETE
                ^^^^^^   ^^^^^^
                이 순서가 고정.  코드에 무엇을 먼저 적었든 무관하다
```

비우는 코드를 위에 적고 새로 만드는 코드를 아래에 적어도 **실제로는 INSERT 가 먼저 나간다.**
정확히 우리가 피하려던 순서다.

→ 결론: **비우는 갱신을 명시적으로 먼저 flush 해야 한다.** 줄 순서로는 못 만든다.
어느 전략을 쓰든 성립하도록 이렇게 방어했다 — 기본키 전략을 아직 문서에 못 박지 않았기 때문이다.

**단, 먼저 flush 한다고 저절로 되는 게 아니다.** `flush()` 는 그 엔티티만이 아니라 **영속성
컨텍스트 전체**를 내보낸다. 새 점유 엔티티를 이미 영속화해 둔 뒤에 비우는 갱신을 flush 하면
**그 flush 안에서 INSERT 가 UPDATE 를 앞질러** 원래 버그가 그대로 재현된다. 즉 이 해법은
**"비우는 flush 시점에 새 엔티티가 아직 영속화되지 않았을 것"** 이라는 조건 위에서만 성립한다.

### 5. 그 순서 의존을 **메서드 이름으로** 드러낸다

영속성 어댑터에 전용 저장 메서드를 따로 두고, 이름이 "무엇에 기대는 자리인지" 를 말하게 했다.

| 성격 | 무엇에 기대나 |
| --- | --- |
| 평범한 저장 | 아무것도. 커밋 시점에 나가면 된다 |
| 충돌 확정용 저장 | 낙관 락 충돌을 이 호출 안에서 확정하는 것 |
| 순서 보장용 저장 | 이 저장이 뒤엣것보다 먼저 DB 에 나가는 것 |

- **왜 이름까지 가르나**: 셋 다 안에서는 똑같이 즉시 flush 를 부른다. **안이 같으니 이름 말고는
  구분이 안 드러난다.** 그러면 나중에 누가 "여기는 충돌을 안 잡네" 하고 평범한 저장으로 바꾸는
  순간 **쓰기 순서가 조용히 깨진다.**
- **주석으로는 부족하다**: 주석은 리팩터에서 지워지지만 **이름은 남는다.**
- **한 자리가 둘 다 필요하면** 충돌 확정용을 쓰면 된다(그게 이미 flush 를 당겨오므로 순서도 함께
  얻는다). **다만 그 자리에 순서도 걸려 있다는 걸 주석 한 줄로 남긴다** — 나중에 충돌 처리 방식이
  바뀌어 그 메서드가 빠질 때 순서 보장까지 같이 사라지는 걸 막으려고.
- **이름은 방어선이 아니라 신호다.** 실제 방어는 *비우고 같은 값으로 다시 잡는 경로를 진짜 DB 로
  도는 통합 테스트*다. 이름은 사람이 읽어야 작동하지만 테스트는 자동으로 작동한다. 이름의 역할은
  **그 테스트가 왜 있는지를 읽히게 하는 것**이다. 둘 중 하나만 두면 안 된다.

## 막힌 점·해결

이 결정들을 문서에 적는 과정에서 **설계 문서가 근거를 어디서 가져와야 하는가** 라는 별개의 문제가
드러났다 — 사라질 코드를 근거로 삼고 있었고, 문서에 없는 사실을 근거로 끌어오려 했다.
그건 이 주제와 독립적으로 재사용되는 얘기라 따로 적었다.

## 배운 것

- **"동시에 나가나?" 는 잘못된 질문이었다.** 한 커넥션에서 SQL 은 언제나 하나씩 순차로 나간다
  (JDBC 배치로 묶여도 순서는 보존된다). 진짜 질문은 **"어느 쪽이 먼저 나가나"** 다. "같은
  트랜잭션이니 한 덩어리로 처리되겠지" 라고 뭉뚱그리면 이 구분을 놓친다.
- **제약 검사 시점은 DBMS 마다 다르다.** 표준 SQL 에는 검사를 커밋까지 미루는 장치가 있지만
  MySQL 에는 없다. "커밋할 때 한꺼번에 보겠지" 라는 직관은 MySQL 에서 틀린다.
- **ORM 의 쓰기 순서는 코드 순서가 아니다.** 이 버그가 늦게 발견되는 이유는 **flush 순서가 흔들려서가
  아니다** — 그건 결정적이다. 늦게 발견되는 진짜 이유는 이렇다.
  - **비우고 *같은 값으로* 다시 잡는 경로를 테스트가 안 덮는다.** 값이 다르면 순서가 뒤집혀도 통과한다.
  - **중간에 조회 쿼리 한 줄이 끼면 auto-flush 가 일어나** 비우는 갱신이 먼저 나가 **우연히 통과한다.**
    이게 제일 고약하다 — 그 쿼리를 지우거나 옮기는 순간, 아무 상관없어 보이는 변경에서 깨진다.
  - 제약이 안 걸린 스키마나 인메모리 DB 로 도는 테스트.
- **"비우고 다시 잡기" 사이의 틈은 다른 트랜잭션에 안전하다.** 비우는 UPDATE 가 그 행에 배타 락을
  걸어서, 다른 트랜잭션이 같은 값을 넣으려 하면 **우리가 커밋할 때까지 대기**한다.
  - **다만 그 대기가 두 가지로 끝날 수 있고, 둘은 다르게 다뤄야 한다.** 하나는 **락 타임아웃**,
    다른 하나는 **데드락**이다 — InnoDB 의 중복 키 검사는 공유 락·갭 락을 잡아서 데드락의 고전적
    원천이다. 데드락은 한쪽이 즉시 롤백되므로 재시도 판단이 타임아웃과 다르다. **두 예외를 받는
    자리가 있어야 하고, 낙관 락 충돌과도 구분해야 한다.**

## 미해결·열린 질문

- **생성 컬럼(또는 함수 인덱스)으로 조건부 유일을 표현하는 방법을 검토하지 않았다.**
  MySQL 5.7+ 의 생성 컬럼, 8.0.13+ 의 함수 인덱스로 `CASE WHEN status='ALIVE' THEN 자원식별자 END`
  를 만들고 거기에 유일 제약을 걸 수 있다. 결과는 같은 NULL 이지만 **DB 가 스스로 파생시키므로
  애플리케이션이 점유 컬럼을 손으로 채우고 비울 필요가 없다** — 위 2번의 "상태와 점유가 어긋날 수
  있다" 는 대가가 사라진다. 대신 인덱스가 상태 값에 묶여 상태 어휘를 바꿀 때 스키마도 따라가야 하고,
  마이그레이션 비용이 든다. **이번엔 아예 검토 대상에 안 올렸다는 게 정확한 상태다.**
- **락 대기 시간을 재보지 않았다.** 비움과 재점유 사이가 짧으니 문제 없을 것으로 보지만, 같은
  자원에 재시도가 몰리는 상황을 부하로 확인한 적이 없다. 데드락 발생 빈도도 마찬가지다.
- **기본키 생성 전략을 문서에 명시할지 정하지 않았다.** 위에서 봤듯 그 전략이 쓰기 시점을 바꾼다.
  명시하는 게 나은지, 구현 선택으로 남기는 게 맞는지 결론이 안 났다. 지금은 **어느 쪽이든 성립하게**
  방어해 두었다.
