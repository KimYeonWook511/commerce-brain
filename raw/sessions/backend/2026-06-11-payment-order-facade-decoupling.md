# 결제-주문 결합을 facade 한 점으로 모으기 — 이진 분기·조율자 위치·order 없음 처리 구체화

결제가 주문 상태 머신을 대신 돌려(결제 안에서 `order.getStatus()`로 분기해서) 주문 상태 가짓수 × 결제 상태 가짓수만큼 분기가 폭발하던 결합을, 조율자(facade) 한 점으로 빼내는 설계 세션이다. 큰 방향 — Tell-Don't-Ask, 결제→주문 단방향 결합, facade 조율, 보상에서 "판단"과 "실행"의 분리, 이벤트 불필요 — 은 전날(2026-06-10) order-payment 결합 해소를 큰 틀로 잡은 세션에서 이미 정리했다. 이 세션은 그 위에서 더 나아가 구체화·교정한 부분만 담는다. 후속 작업은 facade 도입(#240)과 escalation 운영자 통지·종착(#238)으로 분리했다.

## 결정한 것

### 1. 결제 분기 축을 "주문 상태 N개"에서 "수용/거부 이진"으로 못박음

결제가 봐야 할 축을 "주문이 지금 어떤 상태냐"(가짓수가 N개)에서 "주문이 이 결제를 수용했나"(수용/거부의 이진)로 고정했다.

- **핵심:** 결제는 `order.completePayment()`(주문이 결제 완료를 받아 자신을 PAID로 전이시키는 주문 도메인 메서드) 하나를 시도하고 수용/거부만 돌려받는다. 주문 상태 해석은 주문 안에 갇히고, 결제는 주문 상태머신을 알 필요가 없다.
- **효과:** 주문 상태가 늘어도 결제 쪽 분기는 2개로 고정된다. 전날 세션에서 "단방향으로 끊으면 조합이 절반"이라고 잡았던 것을, 이번에 "이진"으로 확정한 것이다.

### 2. 조율자를 payment 응용 계층 facade 한 점에 둔다

여러 도메인을 엮는 승인 확정 흐름의 조율자를 결제 응용 계층의 facade(설계 시점 임시 이름은 `PaymentApprovalFacade` — 실시간 승인·대사 양 경로의 결제 확정을 조율하는 응용 서비스)에 두기로 확정했다.

- **왜 결제 계층인가:** 흐름의 트리거(PG 승인 응답, 대사 스캔)가 둘 다 결제 쪽에서 시작하니 조율자도 결제 계층에 두는 게 자연스럽다.
- **결합의 격리:** 결합은 facade 한 점에만 격리된다 — payment 도메인은 주문을 모르고, order 도메인은 결제를 모른다. 둘 다 아는 건 오직 facade다.
- **기각한 대안:** 조율 전용 별도 패키지를 두는 것 — 지금은 엮이는 흐름이 하나뿐이라 과한 설계(YAGNI)로 기각했다.

### 3. 두 진입점(실시간 승인·대사)을 한 코어로 통합한다

실시간 PG 승인과 대사(reconciliation)는 본질적으로 같은 "결제 확정"인데 분기 로직이 갈라져 있었다.

- **핵심:** facade의 한 코어(시도 → 수용/거부 → 확정 or 환불)로 두 경로를 통합한다.
- **통합 안 하면:** facade 클래스만 늘고 분기 중복은 그대로 남는다. 통합이 이 리팩터링의 진짜 이득이다.

### 4. 환불 "판단"만 facade로 올리고, 환불 "실행"은 결제가 한다

보상(결제가 뒤늦게 성공했는데 주문은 이미 취소·만료된 경우)에서 판단과 실행을 갈랐다.

- **문제의 진짜 위치:** order가 결제를 모른 채 스스로 취소/만료하고 payment가 뒷수습하는 비대칭 자체는 단방향 결합이면 당연한 필연이다. order가 payment를 보게 만들면 오히려 양방향이 되어 더 나쁘다. 틀렸던 건 비대칭이 아니라, payment가 "환불해야 하나"를 스스로 판단하던 것이다.
- **결정:** "환불해야 하나"라는 판단만 facade로 올린다. 환불 실행은 payment가 한다 — 외부 결제 ID로 PG를 취소하는 건 결제만 할 수 있는 일이라서다.

### 5. order 없음(주문 미존재)은 자동 환불 금지 + 운영자 통지로 교정

전날 세션은 "반영 불가 확정 예외(주문 종결/없음/중복)면 환불 종착"으로 order 없음을 환불 대상에 뭉쳐 넣었는데, 이번에 이를 교정했다.

- **왜 교정:** 주문 없음은 수용/거부 축 밖의 정합성 오류다. 주문은 hard delete가 없어 정상 흐름에선 도달 불가급 상태다. 원인 불명 상태에서 자동으로 PG를 취소하는 건 또 다른 오류를 부른다.
- **결정:** 자동 환불하지 않고, 운영자 통지로 escalation(#238)에 위임한다. (구현에서는 주문 없음이 FAILED 종착 + 운영자 통지로 처리된다.)

## 배운 것

- **결합은 "없애는" 게 아니라 "한 점에 모으는" 것.** 두 도메인을 엮는 판단은 누군가는 반드시 진다. 그게 도메인(payment)이 아니라 조율자(facade)인 게 핵심이다. payment가 order를 아는 게 문제였지, facade가 둘 다 아는 건 조율자의 정당한 역할이다.
- **비대칭은 단방향 결합의 필연이다.** 한쪽이 자기 일을 하고 다른 쪽이 결과를 뒷수습하는 비대칭을 없애려고 양쪽이 서로를 보게 만들면 양방향 결합이 되어 더 나빠진다. 비대칭을 탓하지 말고 "판단이 어느 쪽에 있느냐"를 봐야 한다.
- **외부 비동기 경합은 막지 말고 보상으로 정리하는 게 정공법이다.** PG가 외부 비동기라 주문 상태를 아무리 세분화해도 경합("취소된 주문에 뒤늦은 결제 성공")은 사라지지 않는다. 막으려 상태를 쪼개는 대신 보상으로 정리한다.

## 미해결·열린 질문

- **INIT 취소와 결제 승인의 경합.** 주문은 INIT(결제 전) 상태에서만 취소 가능하고, 결제완료(PAID) 후 취소(환불 동반)는 이 시점엔 미구현이다. INIT이 "결제 시작 전"과 "결제 진행 중(예약·승인 중)"을 한 상태로 뭉뚱그리고 있어서, 취소와 결제 승인이 같은 주문을 두고 경합한다. 이 경합이 곧 "취소된 주문에 뒤늦은 결제 성공 → 환불 보상"의 근원이다. (앞의 '배운 것'대로 막으려 하지 말고 보상으로 정리하는 방향.)
- **facade 구현과 escalation 상태모델의 선후.** facade 구현은 escalation(#238)의 상태모델 결정 이후에 한다. #238이 정하는 "결론/보상 축을 어떻게 표현하느냐"가 facade 설계의 입력이라 선후 의존이 있다. (이 세션과 같은 날, escalation 종착·통지를 새 상태 대신 직교 필드로 표현하는 방향의 후속 논의가 이어졌다.)

## 근거로 삼은 기존 결정

- 보상으로 거부된 승인 결제를 새 상태 없이 FAILED + 실패코드로 두기로 한 결정 — facade가 확정하는 "결론 표현"의 전제.
- 상한 초과 미확정 건을 새 상태 대신 대사 스캔의 시간 윈도우 상한으로 자동 제외하기로 한 결정 — escalation 운영 가시성(#238)이 그 위에 얹힌다.
