# 결제-주문 결합 끊기 방향 — 결제가 주문 상태 머신을 대신 돌리는 안티패턴을 Tell-Don't-Ask·facade 조율로 전환

UNKNOWN 결제 대사(reconciliation)와 그 보상 코드를 짜다가, 결제 쪽 로직이 복잡하게 폭발하는 뿌리가 "결제가 주문 상태 머신을 대신 돌리고 있다"는 데 있음이 드러난 세션이다. 이번 PR에서는 동작하는 형태로 일단 막고, 결합을 끊는 근본 개선의 방향만 정리해 후속 작업(#240)으로 분리했다. 여기 담는 건 그 방향의 "왜"와 검토한 대안, 그리고 이번에 근본 개선을 미룬 이유다.

## 문제 — 결제가 주문 상태 머신을 대신 돌린다

- **조합 폭발의 진짜 원인은 모놀리식이 아니라 결합이다.** 결제 로직 안에서 주문 상태를 직접 조회(`order.getStatus()`)해 if 분기를 치면, 처리해야 할 경우의 수가 "주문 상태 가짓수 × 결제 상태 가짓수"로 곱해진다. 한 도메인 안에 두 상태 머신이 섞여 조합이 터진다.
- **드러난 안티패턴 — 판단 중복.** 대사 서비스에서 주문 완료가 거부됐을 때 처리하는 분기(`handleOrderNotCompletable`)가, 주문을 다시 조회해 취소됨/PAID/주문 없음/기타 네 갈래로 나눠 환불 필요 여부를 판단한다. 그런데 주문을 결제완료로 전이시키는 도메인 메서드(`order.completePayment()`)는 이미 "주문이 결제 전 초기 상태(INIT)일 때만 허용하고 아니면 거부"라는 가드로 그 판단을 하고 있다. 즉 주문 안에서 한 번 판단한 것을, 거부를 받은 결제 쪽이 주문 상태를 되물어 다시 분석한다 — 같은 판단이 두 군데에 있다.

## 결정한 방향

이번 PR에서는 결합을 끊지 않고 동작하는 4분기로 두되, 근본 개선의 원칙을 다음과 같이 정했다.

- **Tell-Don't-Ask.** 결제가 주문 상태를 묻지(ask) 말고, `order.completePayment()`로 "결제 끝났으니 반영하라"고 시키고(tell) 반영 가능 여부 판단은 주문 도메인 안에 가둔다. 결제는 주문 상태 머신을 알 필요가 없어진다.
- **단방향 결합.** 결제→주문으로 결과를 통보하는 한 방향만 남긴다. 양방향(결제가 주문을 되묻는 쪽)을 끊으면 처리해야 할 조합이 절반으로 준다.
- **조율은 facade가 맡는다.** 여러 도메인을 엮는 흐름(승인 확정 + 거부 시 보상)은 결제 것도 주문 것도 아니다 — 그 위의 조율자(facade)에 둔다. 각 도메인은 자기 일만 하고, 도메인 간 결합은 facade 한 점에만 격리된다.
- **보상은 판단과 실행을 분리한다(Saga 보상).** "결제가 뒤늦게 성공했는데 주문은 이미 취소된" 경합에서 역할을 셋으로 가른다: (1) 결제는 "승인이 성공했다"는 사실만 확정한다. (2) 환불이 필요한지 판단은 주문/facade가 한다. (3) 환불 실행(PG 취소)은 다시 결제가 한다. 사실 확정과 정책 판단과 실행을 서로 다른 책임으로 떼어낸다.
- **이벤트로 가야 하나? — 아니다(이번엔).** 결합을 끊는 핵심은 "조율을 facade로 빼는 것"이지 이벤트 자체가 아니다. 모놀리식에서는 facade가 각 도메인을 직접 호출하는 것으로 충분하다. 반응자가 여럿(주문 + 알림 + 적립 …)이 되거나 MSA로 분리할 때가 이벤트를 도입할 시점이다. 지금 이벤트를 넣는 건 이득 없는 복잡도다.
- **facade까지 안 가는 중간 정리도 가능하다.** 완전한 facade 조율에 이르지 않더라도, 대사의 4분기는 "승인 확정을 시도한다 → 성공이면 확정, 주문에 반영이 불가능한 확정적 예외(주문 종결됨/없음/중복)면 환불로 종착, 일시적 예외면 재시도"로 재구성하면 제거된다. 주문 상태를 되묻는 대신 확정 시도의 결과(예외 종류)로 분기하는 형태다.
  - **단서: 일시적 실패는 환불하면 안 된다.** DB 오류 같은 일시적(transient) 실패를 확정적 거부와 뭉뚱그리면, 재시도로 풀릴 상황에 환불을 때려 정상 결제를 날린다. 그래서 "환불로 종착"과 "재시도"는 예외의 종류로 반드시 갈라야 한다.

## 미해결·열린 질문

- **근본 결합 제거는 후속(#240)으로 분리했다.** dead 분기 정리와 주문 상태 4분기 제거, Tell-Don't-Ask·facade·Saga 보상 적용은 거기서 한다. 이번엔 근본 해소를 미룬 채 동작하는 4분기로 둔 것 — 의도된 타협이지만, 다음 결제 작업에 들어가기 전 우선순위로 둔다(결합이 방치되면 다음 결제 기능마다 같은 조합 폭발을 다시 밟는다).
- 중간 정리(대사 4분기만 예외 종류 기반으로 재구성)로 갈지, 곧장 facade 조율까지 갈지는 후속 작업에서 범위를 정한다. 중간 정리는 싸지만 조율 책임의 소재를 여전히 대사 서비스에 남긴다.
