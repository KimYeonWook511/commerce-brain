# 복합 인덱스에서 range 조건 뒤 컬럼으로 정렬하면 filesort가 붙는다 (MySQL)

## 배경

주기 배치가 대상을 고르는 조회가 있다. 복합 인덱스는 `(상태, 회차카운터, 마지막처리시각)` 순이고, 조회 조건은 이 셋을 그대로 쓴다.

```sql
WHERE 상태 = 'UNKNOWN'
  AND 회차카운터 >= :min AND 회차카운터 <= :max
  AND (마지막처리시각 IS NULL OR 마지막처리시각 < :임계)
ORDER BY id ASC
```

회차 구간을 `>=` `<=` 쌍으로 받는 이유는, 마지막 구간만 위를 열어 둬야 하기 때문이다(표를 다 쓴 건이 어느 구간에도 안 들어 영영 안 잡히는 걸 막는다). 나머지 구간은 `min == max`라 사실상 등호다.

## 막힌 점 — 추측이 틀렸다

처리 개수 상한을 없앤 뒤(그 판단은 `2026-09-04-batch-round-cap-what-it-buys` 에 있다), `ORDER BY id ASC`가 아무 역할도 안 하면서 비용만 낸다는 걸 알았다. 그래서 "정렬을 `마지막처리시각` 순으로 바꾸면 인덱스가 이미 그 순서로 주니 filesort가 사라진다"고 판단했다.

**실측하니 틀렸다.** MySQL 8.4에 1만 행을 넣고 EXPLAIN을 돌렸다.

| WHERE | ORDER BY | Extra |
|---|---|---|
| `카운터 >= 0 AND <= 0` | `id` | Using index; **filesort** |
| `카운터 >= 0 AND <= 0` | `마지막처리시각` | Using index; **filesort** ← 기대와 다름 |
| `카운터 = 0` | `마지막처리시각` | Using index (filesort 없음) |
| `카운터 >= 4 AND <= MAX` | `마지막처리시각` | Using index; **filesort** |
| `카운터 >= 0 AND <= 0` | 없음 | Using index (filesort 없음) |
| `카운터 >= 4 AND <= MAX` | 없음 | Using index (filesort 없음) |

**`>= 0 AND <= 0`은 사람 눈에 `= 0`이지만 옵티마이저는 range로 분류한다.** range 뒤 컬럼으로 정렬하면 "카운터가 여러 값일 수 있다"는 전제라 그 안에서 시각이 전체적으로 정렬돼 있다고 보장할 수 없고, filesort가 붙는다. `= 0` 등호로 쓰면 카운터가 하나로 확정되어 정렬 보장이 생긴다.

그리고 마지막 구간은 진짜 range라 등호로 바꿀 수도 없다.

## 결정한 것 — 정렬을 바꾸는 대신 없앴다

상한이 없어 매칭 전체를 처리하므로 **정렬이 결과 집합을 바꾸지 않는다.** 순서만 정하고 비용을 낸다. 없애면 모든 구간에서 filesort가 사라지고, 인덱스가 주는 순서(카운터 낮은 것 먼저, 같은 카운터 안에서는 오래 안 본 것 먼저)가 오히려 자연스러운 처리 순서다.

**정렬이 더 무의미했던 이유가 하나 더 있다.** 구간별 조회 결과를 리스트에 이어붙이는 구조라, 각 블록 안에서만 정렬돼 있고 **전체 리스트는 애초에 정렬 상태가 아니었다.** 블록 경계에서 순서가 되감긴다.

## 배운 것

**"인덱스가 이 순서로 저장돼 있으니 정렬이 공짜"는 조건 형태에 달렸다.** 앞 컬럼이 등호로 고정돼야 뒤 컬럼 정렬이 인덱스로 해결된다. 범위 조건이 끼면 그 뒤로는 정렬 보장이 끊긴다. **`>= x AND <= x`처럼 논리적으로 등호인 것도 옵티마이저는 range로 본다.**

**실행 계획은 추측하지 말고 돌려봐야 한다.** 이번엔 컨테이너로 DB를 띄우고 실제 스키마와 1만 행을 넣어 확인했다. 조건 하나하나가 인덱스로 얼마나 좁혀지는지도 그때 함께 봤다 — 세 조건 모두가 인덱스에 먹혀 1만 행 중 712행만 읽고 그 712행을 그대로 반환했다(읽고 버리는 행이 없었다). 인덱스 컬럼 순서와 조건 순서가 맞으면 이렇게 된다.

조회가 읽는 컬럼을 줄이면서 생긴 **커버링 인덱스** 이야기와, 거기에 컬럼을 하나 더 얹으려다 겪은 일은 `2026-09-04-covering-index-broken-by-one-extra-column` 에 따로 적었다.

## 미해결·열린 질문

- 정렬을 없애 순서가 불확정이 됐다. 지금은 전부 처리하니 안전하지만, **나중에 처리 개수 상한이 다시 들어오면 "누가 잘리나"가 정렬에 달리므로 조용히 기아가 생길 수 있다.** 지금은 주석으로만 막아 뒀다.
- 구간별 조회를 등호와 범위로 나누면 앞 구간들은 filesort를 없앨 수 있지만, 마지막 구간은 어차피 안 되고 조회 메서드가 늘어난다. 이득이 작다고 판단해 안 했다.
