# 하네스 진입 게이트를 제거가 아니라 경량화 — 리뷰가 드러낸 인접 부채는 즉석 패치 대신 별도 이슈로 분리

후처리 정책 재설계(작업 #221)를 개발 하네스로 끝까지 굴리는 과정에서 두 가지 운영 판단이 나왔다. 하나는 하네스가 구현 실행 직전에 거는 승인 게이트를 무거운 Plan Mode 의식에서 가벼운 진행 확인으로 바꾼 것(#223), 다른 하나는 다각도 코드 리뷰가 정책 한 줄이 아니라 인접한 실시간 보상·예외 전략 부채까지 끌어냈을 때 그걸 본 PR에 섣불리 메우지 않고 별도 이슈로 분리한 것이다. 두 판단 모두 "규칙·모델은 기억이 아니라 문서·코드로 확인한다"는 같은 원칙에서 나왔다.

여기서 "하네스"는 태스크 문서 탐색·논의·step 설계·문서 초안·구현·리뷰·커밋·루트 문서 동기화를 9단계 워크플로우로 묶어 진행하는 개발 도구를 말한다. 그 안의 `execute.py`는 설계가 끝난 phase의 step들을 자동으로 실행하는 실행기다.

## 결정한 것

### 1. `execute.py` 진입 게이트를 Plan Mode 승인 의식에서 가벼운 확인으로 교체 (#223, 머지됨)

실행기를 돌리기 직전의 게이트가 원래는 "Plan Mode로 구현 계획을 제시 → `ExitPlanMode`로 사용자 승인을 받은 뒤에만 실행"이라는 무거운 절차였다. 이걸 "File Drafting 결과(작성한 태스크 문서·phase 경로)와 실행 계획을 보고하고 진행 의사를 가볍게 확인받은 뒤, 승인되면 실행 모델을 고르고 바로 실행"으로 경량화했다. 변경은 하네스 스킬 문서 2개뿐이고 실행기 코드나 협업 규칙 문서는 건드리지 않았다.

- **제거가 아니라 경량화로 정한 근거:** 팀 협업 규칙 정본 문서의 승인 게이트 항목은 "사용자 승인 전에는 파일을 생성·수정하지 않는다"는 큰 원칙 아래에서, 하네스 실행기(`execute.py`)에 대해서는 "진행 확인 후 실행한다"고만 적혀 있었다. 즉 정본이 요구하는 건 *진행 확인*이지 Plan Mode + `ExitPlanMode`라는 무거운 의식이 아니었다. 그 의식은 스킬 문서가 자체적으로 격상시킨 것이었다. 그래서 가벼운 확인(진행 동의 + 실행 모델 선택)이 오히려 협업 규칙 원문과 더 정합했고, 정본 규칙 문서는 그대로 두고 스킬 문서만 원문에 맞춰 내렸다.
- **게이트 자체를 없애지는 않은 이유:** 실행기에는 자동 코드 검증 게이트가 없어서 "진행 전 사용자 확인" 룰을 agent가 직접 지켜야 한다. 그래서 확인 단계는 남기되 형식만 가볍게 했다.

### 2. 리뷰가 드러낸 인접 부채는 본 PR에 즉석 패치하지 않고 처리처로 매핑해 분리

후처리 정책 재설계(#224)를 진행하며 코드 리뷰를 정확성 / 리팩터로 사라진 동작 / 테스트 커버리지 세 관점의 병렬 리뷰로 돌렸다. 그 리뷰가 정책 본체를 넘어 인접한 실시간 보상·예외 전략 부채를 함께 드러냈다.

- **결정:** 드러난 발견을 본 PR에 "한 줄"로 메우지 않고, 각 발견을 "이 PR / 후속 이슈 / Epic"이라는 처리처로 매핑해 분리했다. 결과적으로 정책 본체만 #224로 깨끗이 머지하고, 인접 부채는 후속 이슈(정상 승인 후 기록 실패 시 환불 대신 완료 재시도 + application 계층의 DB 무결성 예외 직접 catch 제거·이중결제 보상 순서 일관화가 #225, 주문 만료 취소와 결제 대사 타이밍 정합이 #222, 운영 배치·스캔 wiring이 Epic #208)로 떼어냈다.
- **왜 분리가 옳았나:** 처음엔 발견 하나를 본 PR에 즉석 패치로 메우려 했는데, 사용자가 그 처리 방향 자체가 틀렸음을 짚어 *모델이 잘못됐다*는 게 드러났다(정상 승인이 끝난 결제를 transient 기록 실패만으로 환불하는 건 "완료 재시도"여야 할 것을 "실패 처리"로 굳히는 잘못된 모델). 섣불리 패치했으면 잘못된 모델을 코드에 박제했을 것이다. 발견을 정확한 처리처로 매핑하는 디시플린이 핵심이었다.

## 막힌 점·해결

### 하네스 동작에 대한 기억이 문서와 어긋났다 — 방어하지 말고 검증

사용자는 이 하네스 버전(v2)을 "Plan Mode 게이트를 제거한 버전"으로 기억하고 있었다. 나는 처음에 스킬 문서를 인용하며 "임의로 Plan Mode에 들어간 게 아니라 규칙대로 한 것"이라고 방어했다. 사용자가 "원래 게이트가 제거된 버전 아니냐"고 되짚어서 스킬 문서를 grep해보니 — **게이트가 그대로 남아 있었다.** v2는 실행기와 agent 실행 계층만 다시 짰을 뿐, 그 앞뒤를 감싸는 9단계 워크플로우(그 사이의 진입 게이트 포함)는 이전 버전에서 그대로 계승한 것이었다. 즉 사용자의 기억이 틀렸고, 게이트는 살아 있었다. (이 확인이 위 결정 1의 출발점이 됐다 — 어차피 게이트가 살아 있으니 "제거" 대신 "경량화"가 실제 선택지였다.)

- **해결:** 도구/하네스 동작에 대한 기억이 문서와 어긋날 땐 방어하지 말고 스킬 문서·코드로 검증한다. 검증 결과 게이트가 남아 있음을 확인하고, 정본 협업 규칙과 대조해 스킬 쪽 격상분만 원문 수준으로 내리는 게 맞는 조치임을 정했다.

### 인접 부채를 본 PR에 메우려던 첫 시도가 틀린 모델을 굳힐 뻔했다

위 결정 2에서 적은 대로, 리뷰 발견을 본 PR에 즉석 패치로 흡수하려던 첫 방향이 잘못이었다. 사용자가 처리 방향의 오류를 짚으면서, 문제가 "한 줄로 메울 갭"이 아니라 실시간 보상·예외 전략 전반의 모델 부채임이 드러났다. 이걸 후속 이슈로 분리하고 본 PR은 정책 본체만 머지하는 것으로 방향을 틀었다.

## 배운 것

- **다각도 코드 리뷰는 "정책 한 줄"이 아니라 인접 부채를 드러낸다.** 정확성 / 리팩터로 사라진 동작 / 테스트 커버리지 세 관점을 병렬로 돌렸더니, 후처리 정책 리뷰가 인접한 실시간 보상·예외 전략 부채까지 끌어냈다(상세 발견은 같은 PR에서 별도로 남긴 도메인 메모 두 건 — 후처리 정책 UNKNOWN 재설계, 결제 보상·예외 전략 발견 — 에 있다).
- **리뷰에서 나온 인접 부채는 즉석 패치 금지, 처리처로 분리한다.** 발견을 "이 PR / 후속 이슈 / Epic"으로 매핑하는 디시플린이 핵심이고, 그게 후속 이슈 #225·#222·Epic #208 분리로 이어졌다. 섣불리 본 PR에 메웠으면 잘못된 모델을 굳혔을 것이다.
- **하네스 단계 게이트·예외 전략 정합 같은 "규칙"은 기억이 아니라 문서로 확인하고, 불일치하면 문서를 고친다.** 이번 게이트 경량화(#223)가 바로 그 예 — 스킬 문서가 협업 규칙 정본보다 무겁게 격상돼 있던 걸 정본에 맞춰 내렸다.

## 미해결·열린 질문

- 분리한 후속들의 처리처와 조건만 확정한 상태다(각각 후속 이슈·Epic으로 떼어 둠). 정상 승인 후 기록 실패를 환불이 아니라 완료 재시도로 바꾸는 재정합, 주문 만료 취소와 결제 대사 타이밍 정합, 운영 배치·스캔 wiring은 이번 PR 범위 밖으로 미뤘다.
