## 한 일

- harness-v2 스킬 문서의 `execute.py`(harness가 phase의 step을 자동 실행하는 실행기) 진입 게이트를 정리했다 (PR #223, 머지됨). 기존엔 실행 전 "Plan Mode 진입 → ExitPlanMode 승인"이라는 무거운 절차였는데, **가벼운 진행 확인**으로 교체. 스킬 문서 2개만 변경.
- 그 위에서 postprocess 재설계(#221)를 harness-v2의 9-stage 워크플로우로 끝까지 진행하고 다각도 코드 리뷰를 돌렸다.

## 결정/발견 — 도구 동작은 기억이 아니라 문서로 확인

- 사용자는 "harness-v2 = plan-mode 게이트를 제거한 버전"으로 기억했다. 내가 처음엔 스킬 문서를 인용하며 "임의로 plan 모드 들어간 게 아니라 규칙대로"라고 방어했는데, 사용자가 "원래 제거된 버전 아니냐"고 해서 스킬 문서를 grep → **게이트가 그대로 있었다.** v2는 *실행기와 agent 실행 계층만* 재설계했고 9-stage 워크플로우(그 사이의 진입 게이트 포함)는 계승한 것이었다. 기억이 틀렸다.
  - 교훈: 도구/하네스 동작에 대한 기억이 문서와 어긋날 땐, 방어하지 말고 스킬 문서/코드로 검증한다.
- 게이트를 *제거가 아니라 경량화*하기로 한 근거: 협업 규칙 정본(`commerce-backend/CLAUDE.md`의 승인 게이트 항목)의 execute.py 부분은 "진행 확인 후 실행"으로만 적혀 있고, 무거운 plan-mode 의식은 스킬 쪽이 격상시킨 것이었다 → 가벼운 확인(진행 동의 + 실행 모델 선택)이 오히려 협업 규칙 원문과 정합. CLAUDE.md는 안 건드림.

## 배운 것 (일반화)

- **다각도 코드 리뷰가 "정책 한 줄"이 아니라 인접 부채를 드러낸다.** 코드 리뷰를 *정확성 / 리팩터로 사라진 동작 / 테스트 커버리지* 세 관점의 병렬 agent로 돌렸더니, 후처리 정책 리뷰가 인접한 실시간 보상·예외 전략 부채까지 끌어냈다(상세는 도메인 메모).
- **리뷰에서 나온 인접 부채는 즉석 패치 금지 — 별도 이슈로 분리한다.** 처음에 한 발견을 본 PR에 "한 줄"로 메우려 했는데, 사용자가 그 처리 방향 자체가 틀렸음을 짚어 *모델이 잘못됐다*는 게 드러났다. 섣불리 패치했으면 잘못된 모델을 굳혔을 것이다. → 발견을 "처리처(이 PR / 후속 이슈 / Epic)"로 매핑하는 디시플린이 핵심이고, 그게 #222·#225·#208 분리로 이어졌다.
- 하네스 단계 게이트·예외 전략 정합 같은 "규칙"은 기억이 아니라 문서로 확인하고, 불일치하면 문서를 고친다(#223이 그 예).
