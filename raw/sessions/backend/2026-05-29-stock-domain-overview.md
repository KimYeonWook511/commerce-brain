# 재고(stock) 도메인 개요 — 비관적 락·관리자 이력 분리·Outbox 복구 흐름의 근거

상품별 재고를 별도 도메인으로 떼어내면서 확정한 세 축을 정리한 세션이다. (1) 주문 경로 차감의 동시성 전략을 비관적 락으로 두고, (2) 관리자 재고 조작과 변경 이력을 주문 흐름과 분리하며, (3) 재고 복구를 Outbox + Kafka 비동기 흐름으로 뺀 이유를 각각 "왜 이 선택이었나 / 무엇을 기각했나"까지 남긴다. 재고는 `Product`와 `1:1`로 대응하되 상품 테이블에 얹지 않고 별도 엔티티/테이블(`tbl_stock`)로 분리해, 재고 쪽에서 상품을 `product_id`로 가리킨다.

도메인이 담당하는 책임은 네 가지다 — 상품별 현재 재고 보관 / 주문 경로의 재고 차감·복구 / 관리자의 초기 재고 생성·수동 조정 / 재고 변경 이력. application 계층은 책임별로 세 서비스로 갈렸다: 주문 흐름 차감(단건/배치)을 맡는 `StockInventoryService`, 관리자 초기 생성·증가·감소·이력 조회를 맡는 `AdminStockService`, 동시성 전략을 격리하는 `StockConcurrencyService`. 재고 복구만은 `outbox/stock/` 서브 모듈에서 Outbox 패턴 + Kafka로 비동기 처리한다(주문 취소/만료 → 복구 Outbox 발행 → 스케줄러 relay → Kafka → consumer → 단건 재고 증가).

## 결정한 것

### 1. 주문 경로 재고 차감의 기본 전략은 비관적 락

주문 경로의 재고 차감은 비관적 락(`SELECT ... FOR UPDATE`)을 기본으로 둔다. 후보를 비교해 고른 결과다.

- **낙관적 락 ✗**: 재고는 인기 상품에 동시 주문이 몰려 충돌이 잦은 특성이라, 충돌 시 재시도로 처리하면 retry가 잦아 서버 부담만 커진다.
- **Redis 분산 락 ✗**: 지금은 단일 DB 환경이라 DB 밖의 외부 동기화 지점이 불필요하다. DB 부하가 심해지는 시점에 도입을 검토하는 후보로 남긴다.
- **atomic UPDATE(`WHERE quantity >= N`) ✗**: affected rows가 0일 때 "상품이 없음"과 "재고가 부족함"을 구분할 수 없어, 둘을 서로 다른 도메인 예외로 갈라 던질 수 없다. 구분하려고 사전 `SELECT`를 덧붙이면 결국 같은 row에 lock이 걸려 atomic의 이점이 사라진다.
- **비관적 락 ✓**: `SELECT FOR UPDATE`로 row를 잡은 상태에서 "상품 존재 여부 → 재고 충분 여부"를 도메인 객체 안에서 명시적으로 검증하고 각각 다른 예외로 던질 수 있다. 같은 트랜잭션 안이라 실패 시 자동 롤백된다.

- **트레이드오프:** 경쟁이 심해지면 락 대기와 DB 부담이 커진다. 임계에 닿으면 Redis 락으로 전환할 예정.

- **사실관계 정정 메모(내 초기 오해 교정):** 처음엔 "atomic UPDATE는 실패 시 보상 트랜잭션이 필요하다"라고 생각했는데 틀렸다. RDB 트랜잭션 안의 UPDATE는 다른 SQL과 똑같이 트랜잭션이 롤백되면 함께 되돌아간다. 보상 트랜잭션이 진짜 필요한 경우는 "트랜잭션 경계 밖의 외부 시스템 호출"이나 "트랜잭션 없이 즉시 반영되는 작업(Redis INCR 등)"이다. 따라서 비관적 락이 atomic UPDATE보다 나은 진짜 이유는 *원자성/롤백*이 아니라 *실패 원인을 도메인 예외로 정밀하게 구분할 수 있다*는 점이다.

### 2. 관리자 재고 조작은 별도 API로 분리하고 변경만 이력에 남긴다

관리자의 초기 재고 생성·수동 증가/감소는 상품 API가 아니라 별도의 재고 API로 제공하고, 그 변경은 `tbl_stock_history`에 감사 데이터로 남긴다. 이 이력 테이블의 핵심 컬럼은 *변경 수량(`quantityChange`) + 변경 사유 + 관리자 member id + 시점*이다.

**왜 주문 차감/복구는 이력에 안 남기는가** — "테이블 폭증" 우려보다 *테이블 목적 자체*가 이유다.

- **`tbl_stock_history`는 관리자 감사용으로 설계됐다.** 핵심 컬럼이 관리자 member id와 변경 사유다. 주문 차감은 관리자가 없고 사유도 단조로워서, 같은 테이블에 끼우면 NULL/sentinel 값이 늘고 "감사"라는 의미가 흐려진다.
- **주문 흐름은 이미 다른 도메인이 기록한다.** 주문 생성/취소/만료는 order 도메인이, 재고 복구는 outbox 이벤트(Kafka payload 포함)가 기록한다. 게다가 HTTP 요청에서 발급한 traceId가 Kafka 경계(producer/consumer 인터셉터)와 Outbox 경계(outbox 이벤트에 traceId를 컬럼으로 저장했다가 relay 시 MDC로 복원)를 지나 주문→재고 복구 흐름 전체를 단일 traceId로 잇는다. 같은 사실을 이력에도 또 적으면 기록의 원천(SoR)이 둘이 되어 일관성 부담만 는다.
- **변경의 성격이 다르다.** 관리자 변경은 *수동·의도적·외부 입력*이고, 주문 차감은 *자동·시스템 결과*다. 둘을 한 테이블에 섞으면 이력을 조회할 때마다 성격별 case-split이 필요해진다.

→ 이력 테이블의 *목적*과 *조회 동기*가 "관리자 책임 추적" 한 가지로 좁아서, 다른 변경원은 의도적으로 배제했다.

### 3. 재고 복구는 Outbox + Kafka 비동기 흐름(`outbox/stock/`)

이 구조는 한 번에 깐 over-engineering이 아니라, *각 단계가 그 단계에서 새로 생긴 문제를 풀려고* 누적된 결과다. 단계마다 도입 이유가 다르다.

1. **주문↔결제 트랜잭션 분리** — 결제는 외부 PG API 호출이라 같은 트랜잭션에 묶으면 트랜잭션 길이가 비현실적으로 길어진다. 분리하면 "주문은 생겼는데 결제가 미완료"인 *고아 주문*이 생길 수 있다.

2. **고아 주문 정리는 만료 배치(Spring Batch)** — polling 대신 배치를 택한 이유:
   - 시점 일관성(만료 cut-off 기준이 명확)
   - 운영 가시성(Spring Batch 메타데이터로 진행/실패/재시작 추적)
   - peak 부하 회피(오프피크에 몰아서 처리)
   - 장애 복구 spike가 정상 트래픽에 섞이지 않음

3. **그런데 배치 chunk = 하나의 트랜잭션** — chunk size만큼 read-process-write가 한 트랜잭션 안에서 commit된다. 재고 row에 걸린 배타 lock을 chunk가 잡으면 chunk가 끝날 때까지 유지되고, 그동안 정상 주문 흐름의 `SELECT FOR UPDATE`가 chunk 처리 시간 내내 대기한다. **락 보유 시간이 단건이 아니라 chunk 단위로 확대되는** 문제가 생긴다.

4. **그래서 비동기로 분리** — 배치는 *복구 명령만 발행*하고, 실제 재고 복구(증가)는 consumer가 *단건으로 처리*한다. 이러면 락 보유 시간이 다시 단건 처리 시간으로 줄어든다.

5. **비동기 = 유실 가능 → 메시지 큐(Kafka)** — 발행한 복구 명령이 확실히 소비되도록 큐를 끼운다.

6. **Kafka 발행 = 외부 시스템 호출 → "주문 취소 commit + Kafka 발행"의 원자성 필요 → Outbox** — 주문 취소 DB commit과 Kafka publish가 따로 놀면 "DB는 commit됐는데 Kafka 발행은 실패" → 복구 메시지가 영구 유실될 수 있다. Outbox row를 같은 DB 트랜잭션에 함께 박아 두고, 스케줄러가 그 row를 안정적으로 publish + 재시도한다.

- **핵심 사슬:** 외부 PG API → 고아 주문 → 만료 배치 정리 → chunk 락 확대 → 비동기 분리 → 유실 방지 → 메시지 큐 → 발행 보장 → Outbox. 각 단계가 앞 단계가 만든 새 문제를 받아 푼다.

## 막힌 점·해결

### 초기 재고 0 허용 vs 이력 quantityChange 0 불허 — 요구사항끼리 충돌

관리자 재고 관리 기능을 구현하는 중에 두 요구사항이 정면으로 부딪혔다.

- **충돌:** 요구사항은 초기 재고 수량 `0`을 허용한다. 동시에 이력의 변경 수량(`StockHistory.quantityChange`)은 `0`을 허용하지 않도록 설계돼 있었다. 초기 재고를 0으로 만들면 이력에 `quantityChange = 0`을 남겨야 하는데 그게 금지라 막혔다.
- **해결:** "초기 재고가 0이면 재고(stock) row만 생성하고 이력(history)은 저장하지 않는다"는 예외 정책을 두어 풀었다.
- 이 충돌은 구현 단계에서야 드러나 그 자리에서 봉합했다. 계획 단계에서 미리 잠갔어야 했다는 게 회고의 결론.

## 배운 것

### DDD 이관 회고에서 (도메인 경계·네이밍 기준)

- **DDD 이관 커밋과 legacy 삭제 커밋을 섞지 않는다.** 두 의도가 한 커밋에 섞이면 리뷰 부담과 변경량이 불필요하게 커진다. 새 구조 추가·핵심 흐름 전환·테스트 정리만 이관 커밋에 담고, legacy 패키지 이동/삭제는 별도 커밋으로 뺀다.
- **책임 중심 네이밍:** 주문에서 호출된다는 점을 드러내는 `OrderStockService`보다, 실제 책임(재고)을 앞세운 `StockInventoryService`를 택했다. "주문에서 호출되는" 관점보다 "재고 책임"이 우선.
- **구현 전략은 public method 이름에 노출하지 않는다:** `decreaseWithPessimisticLock` ✗ → `decrease` ○. 비관적 락은 구현 세부라 서비스 내부 주석으로 남기고, 호출부가 그 세부에 묶이지 않게 한다.
- **application 계층 클래스명에 계층 접미사(`ApplicationService`)를 반복하지 않는다.** 패키지 경로가 이미 계층을 표현하므로, 서비스는 유스케이스 책임 중심으로 이름 짓는다.
- **테스트는 application service 책임 단위로 분리한다** (Admin / Inventory / Concurrency). 어떤 서비스의 계약이 깨졌는지 더 빨리 파악되고, 후속 legacy 삭제 때 영향 범위도 좁아진다.

### 요구사항 충돌은 계획 단계에서 잠근다

위 "초기 재고 0 vs 이력 0" 충돌에서 얻은 일반 교훈 — 서로 충돌할 수 있는 요구사항·정책은 *구현 전 계획 단계*에서 먼저 명시하고 잠가야 한다. 구현 중에 부딪히면 임시 예외 정책으로 봉합하게 되고, 그 예외가 문서화되지 않으면 나중에 놀란다.

## 미해결·열린 질문

- **재고 이력 pagination 부재** — 관리자 재고 분리 결정의 트레이드오프로 명시해 둔 것. 이력 조회의 첫 버전은 pagination 없이 상품별 전체 목록을 반환한다. 데이터가 늘어나면 후속 작업으로 pagination을 붙여야 한다.
- **락 경쟁 모니터링** — 비관적 락을 "수용 가능"하다고 판단한 근거(단일 DB·현재 경쟁 수준)가 실제 부하에서 언제 깨지는지 측정이 필요하다. 임계에 닿으면 Redis 분산 락으로 전환.
