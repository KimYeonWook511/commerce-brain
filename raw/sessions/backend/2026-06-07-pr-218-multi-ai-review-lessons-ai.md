# 다중 AI 코드리뷰 종합 — 상반돼 보이면 "어느 층위를 보는가"로 통합하고, 심각도는 도메인으로 보정한다

NaverPay(PG) 결제 승인 경로의 예외 포착 범위를 좁히는 작은 단일 버그 fix(이슈 #206, PR #218)를 진행했다. 이 fix의 핵심은, 승인 호출을 감싸던 광범위한 `catch (Exception)`이 우리 코드의 NPE 같은 프로그래밍 버그까지 결제 결과 UNKNOWN으로 흡수하던 것을 좁힌 것이다 — 결과가 UNKNOWN으로 남은 결제가 걸린 주문은 재시도(reserve/approve)가 영구 차단(brick)되므로, 일시적 버그 한 번에 결제가 수동 개입 전까지 막혔다. 작업하면서 이 PR에 3개의 AI 코드리뷰(내가 돌린 gemini code assist, codex CLI, claude code review)를 받아 종합했다.

이 세션은 그 **다중 AI 리뷰를 다루며 얻은 운영 교훈**만 남긴다. 같은 PR의 도메인·설계 결정 — PG 호출 예외를 "요청 전송 시점"으로 갈라 전송 전 버그는 전파(가시화)하고 전송 후/불명은 UNKNOWN으로 보존(이중결제 방어)한 경계 — 은 별도 세션에 따로 기록했으므로 여기서는 반복하지 않는다.

## 배운 것

### 1. 다중 AI 리뷰어는 서로 다른 "층위"를 본다 — 상반돼 보이면 단일 상위 축으로 통합

같은 변경(승인 예외 catch)을 두고 세 리뷰어가 각기 다른 층을 봤다.

- **gemini**: catch 메커니즘의 **구현** — 어떻게 잡고 어떻게 변환하는가.
- **claude**: catch **타입/순서의 정확성** — 어떤 예외를 어떤 순서로 잡는지가 코드상 맞는가.
- **codex**: 결제 **도메인 안전성** — 이 catch가 이중결제를 부를 수 있는 경로인가.

claude의 "정확성 문제없음"과 codex의 "이중결제 위험"은 겉보기엔 모순이지만, 실은 **codex가 한 층 위(도메인 결과)를 본 것**이라 양립한다. claude는 코드 정확성 층에서 맞다고 했고, codex는 그 정확한 코드가 도메인에서 어떤 결과를 내는가를 봤다.

- **핵심 교훈:** 리뷰가 상반돼 보이면 심각도를 비교하기 전에 "**어느 층위를 보는가**"부터 구분하고, 그다음 단일 상위 축으로 통합한다. 여기서 그 상위 축은 "요청 전송 시점"이었다 — 전송 전에 난 버그는 PG 부작용이 0이라 전파해도 안전(claude의 정확성 관점)하고, 전송 후/불명이면 PG가 이미 처리했을 수 있어 보존해야 한다(codex의 도메인 안전성 관점). 두 관점이 이 하나의 경계 위에서 자리를 찾았다.

### 2. 리뷰어의 심각도를 그대로 수용하지 말 것 — 도메인 지식으로 보정

codex가 "이중결제 직결"이라고 심각도를 매긴 경로가 있었는데, 도메인 멱등성으로 재검증해보니 실제 위험은 그보다 낮았다.

- 그 경로(PG가 `AlreadyComplete`로 응답한 뒤 결제내역을 재확인하는 갈래)를 domain 관점에서 다시 보면, 직접적인 돈 이중출금이라기보다 **"박제" 수준**이었다 — PG는 승인했는데 우리 Payment는 미결제로 남아 생기는 **정합성 깨짐**. `AlreadyComplete`는 PG의 멱등 반환이라 같은 결제가 두 번 청구되는 게 아니라, 우리 쪽 상태만 어긋난 채 굳는다.
- 심각도가 한 단계 내려갔다고 무시한 건 아니다. 이 경로는 이번 PR에서 처리하지 않고 후속(#219)으로 분리해, 같은 "전송 후/불명 → UNKNOWN 보존" 원칙을 그쪽에도 적용하기로 했다.
- **핵심 교훈:** AI 리뷰어가 붙인 심각도(특히 "직결", "critical")는 입력 신호일 뿐, 그대로 우선순위로 승격하지 말고 **도메인 지식으로 재평가**해 보정한다.

### 3. 작은 fix에 무거운 개발 워크플로우는 과함

이 변경은 사실상 1 step짜리(예외 catch 범위 축소)였다. 여기에 무거운 개발 워크플로우(task 문서 5종 + 다단계 실행기)를 태우는 건 과했다.

- 이런 소규모 변경은 **경량 경로(worktree + plan + 직접 구현)**로 충분했다. 무거운 워크플로우 스킬은 여러 단계로 쪼개지는 큰 작업용으로 남긴다.
- **핵심 교훈:** 작업 규모에 맞춰 프로세스 무게를 고른다 — 단일 스텝 fix에 다단계 실행기를 끌어오면 산출물(문서·단계)이 변경보다 무거워진다.
