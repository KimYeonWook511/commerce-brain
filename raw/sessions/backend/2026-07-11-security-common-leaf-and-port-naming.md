# 인증/인가 진입점을 common의 leaf 하위 패키지로 재편 + 토큰 포트/어댑터 네이밍

배경: 백엔드는 JWT 기반 인증을 쓴다. HTTP 요청의 인증/인가를 웹 진입점에서 강제하는 코드(요청마다 토큰을 검증하는 서블릿 필터, 권한을 검사하는 MVC 인터셉터, 인증된 신원을 요청 스코프에 보관하는 컨텍스트, 컨트롤러 파라미터에 회원 id를 주입하는 argument resolver)가 원래 top-level의 독립 `security` 패키지에 있었다. 이번 작업은 그 패키지를 공통 인프라 패키지(`common`)의 하위(`common.security`)로 옮겨 "아무것도 의존하지 않는 leaf"로 만든 리팩터다. 외부 동작(HTTP 응답·에러코드·DB 스키마)은 바뀌지 않았다.

## 결정한 것

### 1. security를 common.security로 옮겨 leaf로 만든다
- 문제: 패키지 순환이 실재했다. 공통 웹 설정이 security를 빈으로 등록 → security가 인증 도메인(auth)을 호출 → auth의 예외가 공통 예외 베이스를 상속 → `공통 → security → auth → 공통` 3-패키지 순환.
- 또한 권한 애너테이션(`@RequireRole`)과 인증 컨텍스트는 거의 모든 도메인 컨트롤러가 import한다. 이렇게 "많은 곳이 의존하는" 패키지일수록 leaf(아무것도 의존 안 함)여야 안정적이다(안정 의존성 원칙).
- 결정: 인증/인가 진입점 전체를 공통 인프라 패키지의 하위(`common.security`)로 이동. 공통 패키지는 이미 전역 예외 처리·로깅 필터 같은 웹 인프라를 품고 있어서, 인증/인가 필터·인터셉터도 같은 부류다. 옮기면 순환이 사라지고 새 패키지 간 의존이 0이다(관련 패키지들이 이미 공통 패키지를 의존하고 있으므로).

### 2. 토큰 검증만 포트로 역전한다 (security는 JWT를 모른다)
- leaf는 토큰 기술(JWT)을 몰라야 한다. 그래서 "토큰 문자열 → 누구인가(신원)"라는 단 하나의 호출만 포트 인터페이스로 두고(`common.security`에 위치), 인증 도메인이 JWT로 그 포트를 구현한다. 방향은 "구현체 → 공통" 한 방향뿐이라 순환이 안 생긴다.
- 검증 실패의 전파: 구현체(인증 도메인)가 던지는 예외는 앱 전역 공통 예외 베이스를 상속한다. 필터는 그 예외를 **공통 베이스 타입으로** 잡아 안에 실린 에러코드를 응답에 쓴다. 필터는 인증 도메인의 구체 예외 타입을 이름으로 부르지 않는다(다형성) → 컴파일 타임 의존이 안 생겨 leaf가 유지된다.

### 3. 인가용 역할(Role)은 인가 leaf가 소유하고, 도메인 역할과는 분리한다
회원 도메인에는 "관리자/일반"을 나타내는 역할 enum이 원래 있었다. 인가 판정에도 같은 역할 개념이 필요하다.
- 대안 A(기각): 회원 도메인의 역할 enum을 인가 leaf로 옮겨 하나로 통일. 단점 — 회원 도메인이 인가 패키지를 역으로 의존하게 된다. 도메인이 가장 안쪽이어야 하는데 이 리팩터의 목적(의존 방향 바로잡기)과 정면으로 어긋난다.
- 대안 B(채택): 회원 도메인은 자기 역할 enum을 그대로 두고, 인가 leaf에 **별도의** 인가용 역할 enum을 신설한다. 두 enum은 서로 직접 참조하지 않고 **JWT의 role 문자열로만** 오간다(토큰 발급 시 enum 이름 → 문자열, 검증 시 문자열 → enum으로 복원). 상수 이름이 같아 문자열이 그대로 왕복한다.
- 통일하지 않은 진짜 이유: "중복 비용"이 실제로는 낮다. 두 enum 사이에 이미 JWT 문자열이라는 경계가 있어서 enum↔enum을 직접 변환하는 매퍼 코드가 생기지 않는다. 발급은 enum이름(문자열화), 검증은 문자열→enum이고 이 변환은 JWT를 쓰는 한 원래 존재하던 코드다. 유일한 대가: 역할을 새로 추가할 때 두 enum에 다 넣어야 한다. 하지만 빠뜨리면 문자열→enum 변환이 예외를 던져 시끄럽게 드러나므로(조용한 버그가 아님) 감수 가능하다.

### 4. 인가 진입점의 자체 에러코드를 두되, 코드 문자열은 인증/인가 계약을 보존한다
- leaf가 인증 도메인의 에러코드를 import하면 다시 의존이 생기므로, 인가 진입점 자체의 에러코드 타입을 새로 만들었다. 단 "토큰 없음(401)"·"권한 부족(403)"의 code/message 문자열은 기존 인증 계약(예: `AUTH-401`·`AUTH-403`)을 그대로 쓴다.
- 핵심 원칙: **에러코드는 "어느 클래스가 던졌나"가 아니라 "클라이언트에게 이게 무슨 종류의 문제인가"로 분류하는 계약이다.** 인가 진입점의 에러코드 클래스는 leaf를 지키려고 코드를 정의하는 자리일 뿐이고, 그 코드가 가리키는 문제 영역은 여전히 "인증/인가"다. 그래서 클래스가 security에 있어도 코드는 인증 접두를 쓴다.
- 새 접두(예: `SECURITY-401`)를 안 쓴 이유 둘: (1) 인증 실패 코드가 이미 API 스펙에 계약으로 게시돼 있어 클라이언트가 그 문자열로 분기한다 → 바꾸면 계약 파괴. (2) 토큰 만료·무효 세부 코드는 인증 도메인이 던져 포트를 통해 전파되므로 여전히 인증 접두다. 새 접두를 쓰면 같은 401 경계에서 "토큰 없음=SECURITY-401 vs 토큰 만료=AUTH-401-x"로 접두가 갈라져 오히려 더 나쁘다. → 접두는 문제 영역이 결정한다.
- 현업 근거: 실제 결제 게이트웨이(PG) 응답을 살펴보니, 실패 사유마다 **고유 code**를 주고 message는 사람용 설명이었다(백엔드가 그 고유 code로 프로그램 분기까지 함). 즉 "사유마다 고유 code, message는 설명"이 업계 표준이고, code를 공유하고 message로만 구분하는 방식은 실무에서 사실상 표준이 아니다. message는 문구가 바뀌고 다국어가 되니 계약이 아니기 때문. 우리의 명시적 code 문자열 방식도 이 원칙(사유별 고유 code)을 만족한다.

### 5. 포트↔어댑터 이름 짝맞춤, 그리고 하나의 JWT 어댑터로 병합
- 네이밍 원칙: 포트(인터페이스)는 기술을 모르는 추상 이름, 어댑터(구현체)는 `<기술>+<포트명>`으로 시각적 짝을 맞춘다. 이 프로젝트는 이미 이 패턴을 쓴다(토큰 발급 포트↔JWT 발급 어댑터, refresh 토큰 저장 포트↔Redis 저장 어댑터, 비밀번호 해시 포트↔Bcrypt 어댑터).
- 그래서 access 토큰 검증 포트를 `TokenValidator`, 그 JWT 구현을 `JwtTokenValidator`로 이름을 맞췄다(처음엔 "인증하다"에 가까운 이름(예: `TokenAuthenticator`)을 썼다가, 어댑터와 1:1로 짝이 맞고 검증기라는 어휘가 더 자연스러워 Validator로 통일).
- "왜 AccessTokenValidator는 없나": access 토큰 검증기가 곧 그 포트(`TokenValidator`, 신원을 반환)다. access와 refresh 검증이 대칭 쌍(`AccessTokenValidator`/`RefreshTokenValidator`)이 **될 수 없는** 이유는 leaf 경계다 — access 인증은 인가 진입점(leaf) 소관이라 그 포트가 leaf에 있고, refresh 검증은 재발급이라는 인증 도메인 내부 소관이라 그 포트가 인증 도메인에 있다. 둘을 한 포트로 합칠 수도 없다(leaf에 두면 security가 refresh를 알게 되고, 인증 도메인에 두면 필터가 인증 도메인을 의존해 다시 순환).
- 어댑터 병합: 처음엔 access/refresh 어댑터를 두 클래스로 쪼갰다. 그러자 둘이 똑같은 "JWT 서명·만료·타입 검증 + claims 추출" 코드를 공유하려고 별도 헬퍼 클래스가 하나 더 생겼다. 곧 "쪼갠 뒤 다시 공유하려 헬퍼를 만든" 꼴이라 클래스만 늘렸다고 판단해, **하나의 JWT 어댑터가 두 포트를 모두 구현**하고 공통 파싱은 그 클래스의 private 메서드로 두는 쪽으로 병합했다(헬퍼 제거). 교훈: 두 포트가 하나의 기술(JWT)을 공유하면, 그걸 억지로 두 어댑터로 쪼개지 말고 어댑터 하나가 두 포트를 구현하는 게 자연스럽다.

### 6. 토큰 실패 코드를 인증 도메인 예외가 실어나르는 이유
- 만료·무효·빈 토큰을 서로 다른 코드로 구분해 유지하기로 했다. 그러면 "어떤 종류의 토큰 실패인가"를 아는 쪽 = 인증 도메인(JWT를 실제로 파싱하는 쪽)이 그 코드를 소유해야 한다. leaf는 토큰 기술을 몰라야 하니까.
- 그래서 코드를 실은 예외는 인증 도메인의 예외 타입이고, 이건 "도메인 모델링"이 아니라 앱 전역의 "에러코드를 실어 응답으로 매핑되는" 공통 예외 베이스를 상속한 것뿐이다(모든 모듈이 이 방식). 필터는 이걸 공통 베이스로 받아 코드만 전파한다.
- 참고로 참조한 다른 서버 구현은 토큰 실패를 전부 단일 401 하나로 뭉개서 그 예외를 인가 leaf에 둘 수 있었다(구분이 없으니 leaf가 "무효" 하나만 알면 됨). 우리는 구분을 유지하기로 했기에 코드가 인증 도메인에 있는 게 그 결정의 필연적 귀결이다.

### 7. 참조한 다른 서버 구현과 비교 — 가져온 것/안 가져온 것
- 가져옴: 인가 골격을 공통 패키지의 security 하위에 두는 방향, 토큰 검증을 포트로 역전하는 구조, 포트가 신원 값 객체(record)를 반환하는 형태.
- 안 가져옴: (a) 에러코드를 enum 이름 그대로 내보내는 방식 — 우리는 명시적 code 문자열 컨벤션이라 그대로 쓰면 API 계약이 깨진다. (b) 모든 토큰 실패를 단일 401로 뭉개는 것 — 우리는 만료/무효 구분을 유지. (c) 비밀번호 해시를 인가 패키지에 두는 것 — 비밀번호 해시는 로그인/가입만 쓰는 인증 도메인 관심사라 거기 유지. (d) 인가 패키지를 전부 평평하게 두는 것 — 우리는 역할별 하위 패키지(필터/인터셉터/resolver/컨텍스트/포트/에러/설정)를 유지.

## 배운 것
- "많은 곳이 의존하는 패키지는 leaf여야 한다"(안정 의존성)를 실제 순환 제거에 적용한 사례. 진입점(필터·인가)을 공통 인프라 하위로 내리고, 도메인을 아는 유일한 지점(토큰→신원)만 포트로 역전하면 순환이 소멸한다.
- 에러코드 접두는 "던진 클래스"가 아니라 "문제 영역"으로 정한다. 클래스 위치(leaf 유지용)와 코드 네임스페이스(계약)는 별개 결정이다.
- 포트↔어댑터 1:1 네이밍은 1포트↔1어댑터일 때 자연스럽다. 두 포트가 한 기술을 공유하면 어댑터 하나가 두 포트를 구현하는 게 낫고, 억지 분리는 공유 헬퍼라는 군더더기를 부른다.

## 미해결·열린 질문
- 토큰 만료(예: `AUTH-401-2`)와 무효(예: `AUTH-401-3`) 구분 코드는 코드가 내보내지만 **API 스펙 문서엔 없다**(스펙엔 `AUTH-401`만 명시). 클라이언트가 실제로 그 구분에 의존하는지 불명확 — 구분 유지가 정말 필요한지 재논의 여지가 있다(현재는 유지).
- 토큰 검증 경로의 로그 레벨 정리(만료·빈 토큰은 운영 로그 스팸이라 warn→무로그/debug, 위조는 warn 유지, 그리고 "어댑터가 직접 로깅 vs 중앙에서 일괄"의 경계)는 이 리팩터 범위 밖이라 분리해 보류했다. 별도 작업 후보.
