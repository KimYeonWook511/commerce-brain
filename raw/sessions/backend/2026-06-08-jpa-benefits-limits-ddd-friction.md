# 결제 도메인에서 JPA의 이점과 한계, 그리고 DDD와의 근본 괴리 정리

같은 날 이어진 flush 타이밍·예외 경계 논의가 깊어지면서 "JPA는 변수가 너무 많은 것 아닌가, DDD를 지키려니 이렇게 되는 건가?"라는 질문에 부딪혔다. 그 답으로 JPA의 실제 이점과 한계, 그리고 DDD ↔ JPA의 근본 괴리를 정리했다. 결론부터: 결제 저장에서 flush 타이밍·예외 번역이 복잡한 건 **DDD 때문이 아니라 JPA의 영속성 컨텍스트(flush 지연) + 우리가 특수한 것을 하기 때문**이다. 그 특수한 것이란 (1) unique 위반을 사후 조회로 처리하지 않고 즉시 능동적으로 잡아 도메인 예외로 승격하는 것, (2) partial unique 제약을 MySQL NULL 트릭으로 구현한 것 둘이다. 반대로 JPA가 내세우는 자랑(1차 캐시·지연로딩·write-behind·batch)은 결제 같은 append-only 도메인에선 대부분 안 먹힌다. DDD ↔ JPA 괴리는 "한 클래스에 도메인·영속성 두 주인"이라는 잘 알려진 트레이드오프이고, 해결이 아니라 "어느 비용을 택하느냐"의 문제다.

## 결정한 것

프로젝트(commerce-backend) 차원에서 확정한 원칙.

- **flush 복잡함의 원인을 DDD가 아니라 JPA 영속성 컨텍스트 + 우리 특수 요구로 규정하고, 결제 한 지점에 격리한다.** 두 특수 요구가 flush 예민함의 실제 원인이다. 하나는 "unique 위반 즉시 능동 처리" — 결제 승인 저장 전용 경로가 `saveAndFlush`의 조기 flush로 unique 위반을 그 메서드 호출 안에서 즉시 확정시키고, adapter가 그 위반을 도메인 예외로 매핑한다(정상 흐름을 사전 조회에 맡기지 않는다). 다른 하나는 "MySQL NULL 트릭" — "한 주문에 성공 결제 하나"를 강제하는 부분 unique 제약을, MySQL InnoDB가 partial unique index를 지원하지 않아 조건을 만족하지 않는 행의 키 컬럼을 NULL로 두어 unique 대상에서 제외하는 방식으로 구현한 것이다. 이 두 요구가 결제 승인 저장 한 지점에만 있으므로 복잡함도 거기 가둔다.

- **DDD ↔ JPA 괴리는 "해결"이 아니라 "어느 비용을 택하느냐"임을 인정하고, 엔티티=도메인(실용 진영)을 유지하되 오염을 가둔다.** 순수 도메인 객체와 JPA 엔티티를 분리하는 순수 진영은 매핑 보일러플레이트가 폭발한다. 실무 대부분처럼 한 클래스가 도메인이자 엔티티인 실용 진영을 기본으로 두고, 그 오염을 (a) 도메인 메서드 캡슐화, (b) 명시적 save, (c) 예외 격리, (d) FK를 걸지 않고 ID 참조로 "가둔다". 이건 이 논의 내내 실제로 해온 방식이다.

- **더티 체킹의 암묵성에 기대지 않고 명시적 save를 컨벤션으로 둔다.** managed 엔티티에 대한 `repository.save()`는 JPA 내부에선 no-op이지만, "이 시점에 저장한다"는 의도를 코드 표면에 드러내고 응용 계층의 사고 모델을 특정 ORM에서 떼어낸다. save 계약은 "영속화한다"까지이고 flush 시점은 adapter/트랜잭션 정책이다. 즉시 검증이 필요한 특수 케이스만 별도 계약 메서드로 판다. "DDD 지키니 변수 많다"의 반전이 여기 있다 — 명시 save를 컨벤션으로 박으면 오히려 "save를 부를까 말까"라는 더티 체킹의 암묵성이 사라져 변수가 준다.

- **결제는 JPA 이점이 약한 도메인임을 인지하고, 당장은 다른 도메인과의 일관성을 위해 JPA + 격리를 유지한다.** 결제는 append-only + 단순 연관 + 재조회 없음 + 정합성 critical이라 JPA 자랑이 거의 다 비껴간다. 남는 이득은 "단순 조회의 편함 + 다른 도메인과의 일관성"뿐이다. 그리고 flush에 예민한 건 그 한 지점(unique 위반 즉시 처리)뿐이라, 선택지는 ① JPA + `saveAndFlush`(그 메서드만) ② 그 쿼리만 `JdbcTemplate` ③ 결제 전체를 JDBC/MyBatis로. 지금은 ①. 다른 도메인(주문/회원)이 JPA를 충분히 활용 중이라 일관성 위해 유지하되, "이득 없고 1차 캐시가 오히려 불편"이 강해지면 결제만 JDBC로 빼는 것도 정당하다. 도메인마다 ORM이 달라도 된다.

## 배운 것

### JPA 메커니즘 — 자주 헷갈리는 것들 (오해 → 정정)

- **1차 캐시 ≠ write-behind ≠ batch.** 셋은 다른 메커니즘이다.
  - 1차 캐시(영속성 컨텍스트): 같은 트랜잭션 안에서 같은 엔티티 재조회를 메모리로 처리.
  - 쓰기 지연(write-behind): 변경/INSERT를 flush(기본은 커밋 시점) 때 모아 전송.
  - batch: 모인 SQL을 JDBC batch로 묶어 1 RTT로. **별도 설정(`batch_size`)이 필요하고 기본은 OFF.**
- **batch insert는 `@GeneratedValue(IDENTITY)`면 불가능하다.** INSERT를 해야 ID를 받으니 모을 수가 없다. 우리 엔티티가 IDENTITY 전략이라 INSERT batch 이점은 못 누린다.
- **"flush 한 번" ≠ "1 RTT".** flush 시점에 UPDATE가 3개면 기본은 각각 3 RTT다. 1 RTT로 묶으려면 batching 설정 + 같은 종류로 정렬(`order_updates`)이 필요하다. UPDATE/DELETE는 IDENTITY와 무관하게 batching이 가능하지만 역시 설정이 있어야 한다.
- **같은 엔티티를 한 트랜잭션에서 여러 번 수정해도 flush가 한 번이면 UPDATE는 한 번.** 더티 체킹은 "변경할 때마다"가 아니라 flush 시점에 "최종 상태"를 스냅샷과 비교해 SQL을 만든다. 단 그 사이에 flush(`saveAndFlush`, JPQL 실행 등)가 끼면 쪼개진다. 기본 UPDATE는 전체 컬럼을 쓰고, `@DynamicUpdate`면 변경된 컬럼만 쓴다.

### 1차 캐시는 "성능 캐시"가 아니라 "트랜잭션 내 동일성 보장" (관점 전환)

- 흔한 불편 지적: "같은 엔티티를 재조회하면 그 사이 DB가 바뀌었어도 처음 스냅샷을 준다 → 최신값이 필요하면 방해가 된다." 이건 **맞는 단점**이다.
- 그러나 본질은 성능이 아니라 동일성이다. 같은 트랜잭션의 같은 행 = **같은 객체 인스턴스**(`o1 == o2`). 둘을 다 변경해도 한 객체이므로 **lost update가 방지된다.** 이게 성능보다 중요한 역할이다.
- 게다가 MySQL 기본 격리수준인 REPEATABLE READ에선 1차 캐시를 비우고 DB를 재조회해도 어차피 같은 스냅샷이라 같은 값이 나온다. 즉 1차 캐시는 "이상한 옛날 값"을 주는 게 아니라 "격리수준과 일관된 값"을 메모리로 빠르게 주는 것이다.
- 최신값이 꼭 필요하면 `em.refresh()` / `em.clear()` / 새 트랜잭션으로 탈출한다.

### "트랜잭션 안에서 row 존재를 계속 확인"이 안 되는 이유

- 1차 캐시를 비워도 **MVCC 스냅샷** 때문에 그 사이 다른 트랜잭션이 커밋한 INSERT는 안 보인다.
- 애초에 "한 트랜잭션 안에서 외부의 실시간 변화를 감지"하려는 것 자체가 트랜잭션(일관된 세계를 봄)의 목적과 충돌한다 → 보통 설계가 어긋난 신호다.
- 해법: "있으면 쓰고 없으면 생성"이면 SELECT로 확인하지 말고 **INSERT를 시도 + unique 제약**에 맡긴다(write는 현재 상태와 충돌하므로 정확하다). 정말 최신 조회가 필요하면 짧은 트랜잭션으로 쪼개거나 `FOR UPDATE`(current read) 또는 READ COMMITTED를 쓴다. 생길 때까지 대기해야 하면 앱 레벨 폴링/이벤트로 처리한다(트랜잭션을 열어둔 채 기다리지 않는다).

### JPA가 빛나는 곳 vs 안 먹히는 곳

| 이점 | 빛나는 조건 | 결제(append-only, IDENTITY, FK 없음) |
|---|---|---|
| 객체 그래프 탐색 | 연관이 풍부 | FK 안 걺 / ID 참조 → 탐색 없음 ✕ |
| 더티 체킹 | 부분 수정 잦음 | 상태 전이 몇 개, INSERT 위주 △ |
| 1차 캐시(동일성) | 같은 객체 재조회 | 트랜잭션당 조회 1번 → 이득 0 ✕ |
| 벤더 독립 | DB 바꿀 가능성 | NULL 트릭 등 MySQL 특화 ✕ |
| CRUD 생산성 | 단순 CRUD 많음 | 단순 조회만 누림 △ |
| 생명주기/cascade | 애그리거트 부모-자식 | 단순 구조 △ |

- JPA의 본질 = **"DB(테이블/SQL)를 객체(그래프/상태)로 다루게 해줌"**이다. 연관이 풍부하고, 상태 변경이 잦고, 재조회가 많고, 애그리거트 구조인 도메인(회원/주문/카탈로그/일반 CRUD)에서 강력하다.
- 결제는 append-only + 단순 연관 + 재조회 없음 + 정합성 critical이라 JPA 자랑이 거의 다 비껴간다. 오히려 SQL 명시성(JDBC/MyBatis)이 잘 맞는 도메인이다.

### DDD ↔ JPA 괴리의 뿌리 — 한 클래스에 두 주인

- 괴리의 뿌리는 **한 클래스에 두 주인**이다. DDD는 "도메인 객체는 영속화를 몰라야 한다"고 하는데, JPA는 "이 객체는 내가 관리하는 영속 엔티티다"라고 한다. 같은 `Payment`가 순수 도메인이면서 동시에 JPA 엔티티여야 한다.
- 증상이 전부 여기서 나온다: save를 부를까 말까(더티 체킹), `@Entity` 침투, `DataIntegrityViolationException` 번역, FK를 걸까 ID로 참조할까.
- 두 진영:
  - **실용 진영 (엔티티=도메인)**: 한 클래스가 둘 다. 단순하고 생산성이 높지만 도메인 오염을 감수한다. **실무 대부분.**
  - **순수 진영 (도메인 ≠ 영속성 모델)**: 순수 도메인 + JPA 엔티티를 분리하고 adapter에서 매핑한다. 순수하지만 매핑 보일러플레이트가 폭발한다.
- **둘 다 비용이 있어 "해결"이 아니라 트레이드오프다.** 실무의 중도는 실용 진영을 기본으로 두고 오염을 도메인 메서드 캡슐화 / 명시적 save / 예외 격리 / FK 안 걸고 ID 참조로 "가두는" 것이다.

### 명시적 save vs 더티 체킹 신뢰 — 실무 추세

- **A안 (더티 체킹 신뢰, save 생략)**: 전통적 정석. "영속 엔티티를 변경하면 커밋 때 반영된다."
- **B안 (명시적 save)**: 추세, 특히 DDD/헥사고날 팀에서. 반영 의도가 드러나고, detached 엔티티 사고를 막고, 흐름이 바뀌어도 안전하다.
- 권장은 **명시적 save를 컨벤션으로** 두는 것. save 계약은 "영속화한다"까지이고 flush는 adapter/트랜잭션 정책이다. 즉시 검증이 필요한 특수 케이스만 별도 계약 메서드로 분리한다.

## 미해결·열린 질문

- **batch insert를 누리려면 ID 전략을 IDENTITY → 시퀀스/테이블로 바꿔야 한다.** MySQL은 시퀀스가 없어 테이블 전략을 써야 하는데 그것도 나름의 비용이 있다. 다만 결제는 트랜잭션당 변경이 1~2행이라 어차피 batch 실익이 없어, 이 전환을 지금 할 이유는 없다.
- **결제만 JDBC/MyBatis로 뺄지 여부** — 다른 도메인(주문/회원)이 JPA를 충분히 활용 중이면 일관성을 위해 JPA 유지가 무난하다. "결제에서 JPA 이득이 거의 없고 1차 캐시가 오히려 불편"이 충분히 강해지는 시점에 재판단할 문제로 남긴다.
