## 출발 질문
flush/예외 경계 논의가 깊어지면서 "JPA가 변수가 너무 많은 거 아닌가? DDD를 지키려니 이렇게 되는 건가?"로 이어졌다. JPA의 실제 이점과 한계, DDD와의 근본 괴리를 정리했다.

## 핵심 결론
flush 타이밍·예외 번역의 복잡함은 **DDD 때문이 아니라 JPA의 영속성 컨텍스트(flush 지연) + 우리가 특수한 걸(unique 위반 즉시 능동처리 + MySQL NULL 트릭) 하기 때문**이다. JPA의 자랑(1차 캐시·지연로딩·write-behind·batch)은 대부분 **결제 같은 append-only 도메인에선 안 먹힌다**. DDD ↔ JPA 괴리는 "한 클래스에 도메인/영속성 두 주인"이라는 알려진 트레이드오프이며, 해결이 아니라 "어느 비용을 택하느냐"의 문제다.

## 정리한 개념

### 1. JPA 메커니즘 — 자주 헷갈리는 것들 (오해 → 정정)
- **1차 캐시 ≠ write-behind ≠ batch.** 셋이 다른 메커니즘.
  - 1차 캐시(영속성 컨텍스트): 같은 트랜잭션 내 같은 엔티티 재조회를 메모리로.
  - 쓰기 지연(write-behind): 변경/INSERT를 flush(기본=커밋) 때 모아 전송.
  - batch: 모인 SQL을 JDBC batch로 1 RTT로 묶음 — **별도 설정(batch_size) 필요, 기본 OFF.**
- **batch insert는 `@GeneratedValue(IDENTITY)`면 불가** — INSERT 해야 ID를 받으니 모을 수가 없음. (우리 코드가 IDENTITY라 이 이점 못 누림)
- **"flush 한 번" ≠ "1 RTT".** flush 시점에 UPDATE 3개면 기본은 각각 3 RTT. 1 RTT로 묶으려면 batching 설정 + 같은 종류 정렬(order_updates). UPDATE/DELETE는 IDENTITY 무관하게 batching 가능하지만 설정 필요.
- **같은 엔티티 한 트랜잭션에서 여러 번 수정 → flush가 한 번이면 UPDATE 한 번.** 더티 체킹은 "변경마다"가 아니라 flush 때 "최종 상태"를 스냅샷과 비교해 SQL 생성. 단 그 사이 flush(saveAndFlush, JPQL 실행)가 끼면 쪼개짐. (기본 UPDATE는 전체 컬럼, @DynamicUpdate면 변경 컬럼만)

### 2. 1차 캐시는 "성능 캐시"가 아니라 "트랜잭션 내 동일성 보장" (관점 전환)
- 불편 지적: "같은 엔티티 재조회 시 그 사이 DB가 바뀌었어도 처음 스냅샷을 준다 → 최신값 필요하면 방해." → **맞는 단점.**
- 그러나 본질은 동일성: 같은 트랜잭션의 같은 행 = **같은 객체 인스턴스**(`o1 == o2`). 둘 다 변경해도 한 객체라 **lost update 방지**. 이게 성능보다 중요한 역할.
- 또 REPEATABLE READ(MySQL 기본)에선 1차 캐시 비우고 DB 재조회해도 어차피 스냅샷이라 같은 값 → 1차 캐시가 "이상한 옛날 값"이 아니라 "격리수준과 일관된 값"을 메모리로 빠르게 주는 것.
- 최신값이 꼭 필요하면 `em.refresh()` / `em.clear()` / 새 트랜잭션으로 탈출.

### 3. "트랜잭션 안에서 row 존재를 계속 확인"이 안 되는 이유
- 1차 캐시 비워도 **MVCC 스냅샷** 때문에 그 사이 다른 트랜잭션이 커밋한 INSERT가 안 보임.
- 애초에 "한 트랜잭션 안에서 외부 실시간 변화를 감지"하려는 것 자체가 트랜잭션(일관된 세계를 봄) 목적과 충돌 → 보통 설계 어긋남.
- 해법: "있으면 쓰고 없으면 생성"이면 SELECT 확인 말고 **INSERT 시도 + unique 제약조건**(write는 현재 상태와 충돌해 정확). 정말 최신 조회면 짧은 트랜잭션으로 쪼개기 / `FOR UPDATE`(current read) / READ COMMITTED. 생길 때까지 대기면 앱 폴링/이벤트(트랜잭션 열어두기 금지).

### 4. JPA의 진짜 이점 — 빛나는 곳 vs 안 먹히는 곳
| 이점 | 빛나는 조건 | 결제(append-only, IDENTITY, FK 없음) |
|---|---|---|
| 객체 그래프 탐색 | 연관 풍부 | FK 안 걺/ID 참조 → 탐색 없음 ✕ |
| 더티 체킹 | 부분 수정 잦음 | 상태 전이 몇 개, INSERT 위주 △ |
| 1차 캐시(동일성) | 같은 객체 재조회 | 트랜잭션당 조회 1번 → 이득 0 ✕ |
| 벤더 독립 | DB 바꿀 가능성 | NULL 트릭 등 MySQL 특화 ✕ |
| CRUD 생산성 | 단순 CRUD 많음 | 단순 조회만 누림 △ |
| 생명주기/cascade | 애그리거트 부모-자식 | 단순 구조 △ |
- JPA 본질 = **"DB(테이블/SQL)를 객체(그래프/상태)로 다루게 해줌."** 연관 풍부 + 상태 변경 잦음 + 재조회 많음 + 애그리거트 구조인 도메인(회원/주문/카탈로그/일반 CRUD)에서 강력.
- 결제는 append-only + 단순 연관 + 재조회 없음 + 정합성 critical → JPA 자랑이 거의 다 비껴감. SQL 명시성(JDBC/MyBatis)이 오히려 잘 맞는 도메인.

### 5. DDD ↔ JPA 괴리 — 알려진 트레이드오프 (감 맞음)
- 뿌리: **한 클래스에 두 주인.** DDD는 "도메인 객체는 영속화를 몰라야"라는데, JPA는 "이 객체는 내가 관리하는 영속 엔티티"라 함. 같은 `Payment`가 순수 도메인이면서 JPA 엔티티여야 함.
- 증상이 다 여기서: save 부를까 말까(더티 체킹), @Entity 침투, DataIntegrityViolationException 번역, FK 걸까 ID 참조할까.
- 두 진영:
  - 진영1 (엔티티=도메인, 실용): 한 클래스가 둘 다. 단순/생산성, 도메인 오염 감수. **대부분 실무.**
  - 진영2 (도메인 ≠ 영속성 모델, 순수): 순수 도메인 + JPA 엔티티 분리, adapter 매핑. 순수하지만 매핑 보일러플레이트 폭발.
- **둘 다 비용 → 해결이 아니라 트레이드오프.** 실무는 중도: 진영1 기본 + 오염을 도메인 메서드 캡슐화 / 명시적 save / 예외 격리 / FK 안 걸고 ID 참조로 "가둔다". (우리가 대화 내내 한 것)
- "DDD 지키니 변수 많다"의 반전: 명시적 save를 컨벤션으로 박으면 오히려 더티 체킹의 암묵성을 제거해 변수가 준다.

### 6. 명시적 save vs 더티 체킹 신뢰 — 실무 추세
- A(더티 체킹 신뢰, save 생략): 전통 정석. "영속 엔티티 변경하면 커밋 때 반영."
- B(명시적 save): 추세, 특히 DDD/헥사고날 팀. 반영 의도 드러남 + detached 사고 방지 + 흐름 바뀌어도 안전.
- 권장: **명시적 save를 컨벤션으로.** save 계약은 "영속화한다"까지(flush는 adapter/트랜잭션 정책). 즉시 검증 필요한 특수 케이스만 별도 계약 메서드.

### 7. 결제에 JPA를 쓰는 게 맞나
- 결제는 JPA 이점 대부분 ✕/△. 남는 건 "단순 조회 편함 + 다른 도메인과의 일관성".
- 그 한 지점(unique 위반 즉시 능동처리)만 flush 예민. 선택지: ① JPA + saveAndFlush(그 메서드만) ② 그 쿼리만 JdbcTemplate ③ 결제 전체 JDBC/MyBatis.
- 도메인마다 ORM 달라도 됨. JPA로 통일된 팀이면 일관성 위해 유지 + 그 지점 격리, "이득 없고 1차 캐시 불편"이 강하면 결제만 JDBC도 정당.

## 결정/원칙 (commerce-backend 프로젝트)
- flush 복잡함의 원인은 DDD가 아니라 JPA 영속성 컨텍스트 + 우리 특수 요구(즉시 능동처리 + MySQL NULL 트릭). 결제 한 지점에 격리.
- 진영1(엔티티=도메인) 유지 + 오염을 캡슐화/명시 save/예외 격리/ID 참조로 가둠.
- 명시적 save 컨벤션 지향. 더티 체킹 암묵성에 기대지 않음.
- 결제는 JPA 이점이 약한 도메인임을 인지. 당장은 일관성 위해 JPA + 격리, 필요 시 그 지점만 JDBC 고려.

## 열린 질문 / 주의
- batch insert 누리려면 ID 전략을 IDENTITY → 시퀀스/테이블로 바꿔야(MySQL은 시퀀스 없어 테이블 전략, 그 나름 비용). 결제는 트랜잭션당 변경 1~2행이라 어차피 batch 실익 없음.
- 결제만 JDBC/MyBatis로 뺄지 여부 — 다른 도메인(주문/회원)이 JPA를 충분히 활용 중이면 일관성 위해 JPA 유지가 무난.
