# 명세 검증 회차와 에이전트 운영에서 배운 것 — 반쪽 수정, 헛도는 검증, 반증 탐색, 규약을 이기는 도구 지시

> 이 교훈들이 나온 작업은 `2026-09-07-close-pre-payment-cancel-policy`다.

명세를 먼저 확정하고 그 명세가 구현을 끌고 가게 하는 방식으로 한 작업이다. 구현 전에 문서 검증을 여섯 회차 돌렸다 — 회차마다 여러 관점의 검사 에이전트를 병렬로 띄우고, 나온 발견을 고친 뒤 다시 돌리는 식이다. 관점은 일곱이었다: 추적성(요구에서 검증까지 사슬이 이어지나), 도메인 정합, 동시성·실패, 접근 제어, 저장소 규약, 명료성, 그리고 도메인 모델링 관점의 설계 검토.

## 막힌 점·해결

### 회차를 거듭해도 발견이 줄지 않았다

각 회차에서 나온 발견 건수다. **"심각"은 그대로 두면 구현이 잘못될 등급이고, "계"는 표기 정정까지 포함한 전체다.**

| 회차 | 심각 | 계 | 성격 |
| --- | --- | --- | --- |
| 1 | 2 | 17 | 초안의 구멍 |
| 2 | 0 | 17 | **1회차 수정이 만든 것** |
| 3 | 0 | 23 | **2회차 수정이 만든 것** |
| 4 | 1 | 20 | 설계를 뒤집은 직후 (그 뒤집기는 3회차를 마치고 일어났다) |
| 5 | 1 | 14 | 4회차 수정이 만든 것 |
| 6 | 0 | 3 | — |

2·3회차 발견의 상당수가 **직전 회차에서 내가 고친 것이 만든 새 어긋남**이었다. 원인은 하나였다.

### 반쪽 수정 — 다섯 회차 연속 같은 실패

명세가 여러 문서로 갈라져 서로를 참조한다(요구·시나리오·설계·단계별 구현 지시·용어집·애그리거트 정의). 한 사실이 보통 세 곳 이상에 적혀 있다. 발견을 고칠 때 **한 문서만 고치고 짝을 안 고쳤다.**

실제로 반복된 형태들:

- 요구를 좁혔는데 그 요구를 재는 시나리오는 안 좁혔다.
- 시나리오를 하나 추가했는데 "시나리오 몇 개"라고 세는 요약 세 자리를 안 고쳤다. (같은 절의 다른 숫자는 앞 회차에 고쳤으면서.)
- 설계 문서 둘의 근거를 정정했는데 정본인 명세의 같은 문답은 옛 근거 그대로 뒀다. 그 결과 정본만 읽은 사람은 **존재하지 않는 규약 조항**을 찾게 됐다.
- 용어를 통일했는데 재작성하면서 **세 번째 변형**을 새로 만들었다.
- 시나리오 추적 표에 요구 태그를 더했는데 단계별 지시의 같은 줄은 옛 태그였다.

**내 검증 방식 자체도 틀렸다.** 용어 통일 후 "전수 검색으로 잔여 0 확인"이라고 보고했는데, 전체 문구로만 찾아서 (가) 앞말이 다른 변형 (나) 줄바꿈으로 갈린 것 둘을 놓쳤다. 핵심어로 찾았으면 바로 나왔다.

**여섯 회차째에 처음으로 "반쯤 반영된 것 없음" 판정을 받았다.** 그때 달라진 것은 검사 에이전트에게 "각 처리 기록이 무엇을 했다고 적는지 읽고 문서에 실제로 반영됐는지 대조하라"고 명시적으로 시킨 것이었다.

### 헛도는 검증 — 통과하지만 아무것도 확인 못 하는 테스트

가장 값진 발견은 "이 테스트는 통과하지만 아무것도 못 잡는다" 유형이었다. 셋이 나왔다.

**(1) 대역 위에서 도는 경합 검증.** 동시 실행 수렴을 확인하는 검증을 다른 경로(만료 배치 쪽)로 옮기라고 지시했는데, 옮길 목적지로 지목한 기존 테스트가 저장소와 이벤트 발행을 전부 대역(mock)으로 바꾼 단위 테스트였다. 거기에 메서드를 더하면 실제 행 버전 충돌도 트랜잭션 롤백도 없는 자리에서 "한 번만 처리됐다"를 대역에 대고 단언하게 된다. 그래도 통과한다.

**(2) 태그만으로는 실물 DB가 아니다.** (1)을 고치면서 "실물 위에서 돌린다"고 적고 테스트 태그만 지정했다. 그런데 그 저장소에서 실제 DB를 쓰게 만드는 것은 태그가 아니라 컨테이너 등록이고, 태그는 어느 실행 묶음에서 도는지만 고른다. 등록이 없으면 인메모리 DB로 돌아 행 잠금 경합이 재현되지 않는다. **동시 실행 검증이 원래 들어 있던 그 클래스가 바로 컨테이너 등록이 없는 자리였다.**

**(3) 단언이 원리적으로 실패할 수 없는 진입점.** "겹쳐도 예외용 환불이 하나도 생기지 않는다"를 확인하는 경합 테스트에서, 실행 순서를 강제하려고 붙잡아야 하는 지점이 그 환불을 만드는 코드보다 **호출 순서상 뒤쪽**이었다. 그 뒤쪽을 직접 붙잡으면 환불을 만드는 코드가 아예 실행되지 않아, 버그가 있어도 "하나도 안 생긴다"가 참이 된다.

셋 다 "그 단언을 만드는 것이 무엇인가"를 코드로 따라가야 보였다. 문서만 봐서는 다 통과로 보인다.

### 여섯 회차를 살아남은 원래 결함

5회차에 나온 심각 발견은 **1회차부터 있던 것**이었다. 학습·실험용으로 남겨 둔 비활성 테스트 클래스를 지우라고 지시했는데, 저장소의 테스트 규약이 정확히 그 반대를 정하고 있었다 — 회고 참고용으로 보존하고, 운영 코드를 리팩터할 때 컴파일 깨짐으로 알려 주는 안전망으로 남기라고.

게다가 전제도 틀렸다. 그 테스트 클래스는 지우려던 클래스를 **임포트만 하고 한 번도 쓰지 않았다.** 지울 필요가 없었고 임포트 한 줄만 정리하면 되는 일이었다.

앞선 네 회차의 규약 검사 에이전트가 같은 규약 문서를 읽고도 그 절을 대조하지 않았다. 5회차에 잡힌 계기는 "규약 문서를 훑지 말고 **절 단위로** 읽고, 단계별 지시가 무엇을 지우라고 하는 자리를 규약의 보존·유지 조항과 하나씩 맞대어 보라"고 시킨 것이었다.

### 도구가 주입하는 지시가 저장소 규약을 이겼다

저장소 규약과 개인 메모 양쪽에 "커밋 메시지에 공동 저자 줄을 붙이지 않는다"가 적혀 있는데, 하위 에이전트가 만든 커밋 셋에 그게 붙었다(넷 중 하나만 안 붙어서 일관성도 없었다). Claude Code가 세션에 주입하는 지시가 "이전 안내를 대체한다"고 명시하고 있었고, 하위 에이전트가 그쪽을 따랐다.

거기에 세션 링크(`claude.ai/code/session_...`)까지 커밋 메시지와 PR 본문에 붙고 있었다. **공개 저장소라 그대로 인터넷에 노출됐다.**

문서로 적어 둔 규칙은 **읽고 따라야 하는 것**이라 무시될 수 있다. 설정으로 끄면 **지시 자체가 생성되지 않아** 따를지 말지 고를 대상이 없어진다. 실제 설정은 `settings.json`의 `attribution` 객체이고 세 필드를 모두 꺼야 한다.

```json
{ "attribution": { "commit": "", "pr": "", "sessionUrl": false } }
```

- `commit` / `pr` — 커밋 메시지와 PR 본문에 붙일 텍스트. 빈 문자열이면 안 붙는다.
- `sessionUrl` — 세션 링크를 붙일지. **별도 키다.** 기본값이 `true`이고, 웹이나 원격 제어 세션에서 실행할 때 붙는다. 로컬 터미널 세션에는 애초에 안 붙어서, 다른 사람 커밋에는 이 줄이 없다.

여기서 두 번 헛짚었다. 처음엔 기억나는 대로 `includeCoAuthoredBy`를 댔는데 그건 이미 폐기된 키였고(`attribution`이 우선한다), `attribution`을 넣은 뒤에는 "세션 링크도 그 텍스트의 일부라 같이 사라진다"고 단정했다가 틀렸다. **문서 요약이 필드 둘만 뽑아 왔는데 거기서 멈추고 넘겨짚은 것이 원인이다.** 나머지 키는 사용자가 직접 문서에서 찾아냈다.

## 배운 것

- **검증 에이전트에게 "이전 처리가 실제로 반영됐는지 대조하라"를 명시적으로 시켜야 한다.** 안 시키면 새 발견만 찾고, 반쪽 수정은 다음 회차에 새 발견으로 되돌아온다.
- **전수 검색은 전체 문구가 아니라 핵심어로 한다.** 앞말이 다른 변형과 줄바꿈으로 갈린 것이 문구 검색을 빠져나간다. "잔여 0 확인"이라고 보고하기 전에 검색어가 무엇을 못 잡는지 먼저 생각한다.
- **경합 검증은 "그 단언을 만드는 것이 무엇인가"를 코드로 따라가야 한다.** 대역인지, 실물 DB인지, 순서를 강제하려 붙잡는 지점이 단언 대상보다 뒤쪽인지. 셋 중 하나만 어긋나도 통과하면서 아무것도 확인하지 못한다.
- **규약 문서는 훑으면 안 걸린다.** "이 지시가 무엇을 지우라고 하는가"를 규약의 보존 조항과 하나씩 맞대는 방식이라야 걸린다. 같은 문서를 네 번 읽고도 못 잡은 절이 있었다.
- **도달 불가를 근거로 뭘 지울 때는 반증을 찾으라고 시킨다.** "불가능함을 확인하라"보다 "가능한 경로를 찾아라"가 훨씬 잘 잡는다. 실제로 그렇게 시키니 가장 유력한 반례 후보와 그것이 왜 성립하지 않는지가 함께 나왔고, 확신도와 못 본 곳까지 스스로 밝혔다. (그래서 무엇을 결정했는지는 `2026-09-07-close-pre-payment-cancel-policy`에 있다 — 같은 사건의 다른 면이다.)
- **에이전트에게 규칙을 지키게 하려면 문서보다 설정이 확실하다.** 문서는 설득이고 설정은 차단이다. 규약을 읽고도 무시하는 일이 반복되면 그 지시를 만들지 않는 스위치가 있는지부터 찾는다.
- **문서를 요약해 읽고 단정하지 않는다.** 요약이 필드 둘만 뽑아 왔는데 거기서 멈추고 "나머지도 같은 스위치일 것"이라고 넘겨짚어 두 번 틀렸다.
- **회차를 무한히 돌릴 수는 없으니 수렴 기준을 미리 정한다.** "심각 발견이 없고, 남은 발견이 새 설계 판단을 요구하지 않으면 닫는다"로 정했다. 그리고 마지막 회차는 일곱 관점을 다 돌리지 않고 **저장소 규약 관점 하나만** 돌렸다 — 4·5회차에서 심각 발견을 낸 것이 그 관점뿐이었기 때문이다.

## 미해결·열린 질문

- 반쪽 수정을 구조적으로 막을 방법을 못 찾았다. 지금은 "고칠 때 그 사실이 적힌 모든 문서를 세어 본다"는 습관에 기대고 있는데, 회차마다 실패했다. 한 사실의 정본을 한 곳으로 정하고 나머지가 가리키게 하는 쪽이 답일 수 있지만, 각 문서가 독립적으로 읽혀야 한다는 요구와 부딪힌다.
- 검증 회차의 비용 대비 효과를 재 본 적이 없다. 여섯 회차에서 나온 발견 중 실제로 구현을 바꾼 것과 문서 표기만 고친 것의 비율을 세면 몇 회차가 적정인지 감이 잡힐 텐데, 안 셌다.
