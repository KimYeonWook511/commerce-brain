# 돈이 움직이는 외부 호출에서 결과를 모를 때 무엇을 하는가

## 배경

결제사에 승인·취소를 요청하고 **응답을 못 받는 일**이 생긴다. 타임아웃, 서버 오류, 우리 프로세스가 죽는 것. 이때 돈이 나갔는지 안 나갔는지 우리는 모른다.

이 상태를 어떻게 다루느냐가 이번 설계에서 가장 크고, 결론이 여러 번 뒤집힌 축이다. **뒤집힌 것들을 여기 다 적는다 — 처음 답이 왜 그럴듯했고 왜 틀렸는지가 이 기록의 본체다.**

먼저 이 글에서 계속 갈라 쓰는 말 셋을 밝힌다.

```
이력        결제사가 가진 거래 내역.  우리가 조회해서 읽는다
호출 기록    우리가 남기는 로그성 테이블.  언제 무엇을 보내고 무엇을 받았는지
회수 배치    결과를 못 받은 건을 주기적으로 다시 집어 확인·재전송하는 배치
```

키도 셋으로 갈라 쓴다. 그 설계 자체는 [[2026-08-16-idempotency-key-three-values-and-unique-scope]]에 있고, 여기서는 아래 구분만 알면 된다.

| 부르는 이름 | 무엇인가 | 언제 바뀌나 |
| --- | --- | --- |
| 사건 키 | 이 환불·결제 사건 하나를 가리키는 값 | 안 바뀐다 |
| 요청 멱등키 | 호출자가 준 값. 중복 요청을 막는다 | 안 바뀐다 |
| **결제사 호출 멱등키** | 사건 키 + 시도 번호. 결제사에 실어 보낸다 | **다시 시도할 수 있는 실패를 받았을 때만 교체** |

아래에서 "같은 키로 다시 부른다" / "새 키로 보낸다"는 전부 **세 번째 값**을 말한다.

## 결정한 것

### 1. 결과 어휘를 넷으로 둔다

처음엔 셋이었다 — 됐다 / 안 됐다 / 모른다. **그러면 다시 시도할 값이 있는 실패와 그렇지 않은 실패를 가를 수 없다.**

```
됐다
모른다
다시 시도할 수 있는 실패     ← 새 키로 다시 보낸다
다시 시도할 수 없는 실패     ← 종결한다
```

결제사 응답 코드를 이 넷으로 접는 일은 어댑터가 하고 **도메인은 넷만 안다.** ("접는다"는 결제사마다 제각각인 수십 개 응답 코드를 우리가 아는 소수의 결과값으로 대응시키는 것을 말한다.)

### 2. 응답 코드 표보다 전송 계층 판정을 먼저 본다

접는 규칙이 처음엔 **응답 코드 기준으로만** 적혀 있었다. "타임아웃도 서버 오류도 모르는 응답도 전부 하나로 접는다"고만 했지 어느 것으로 접는지가 없었다. **응답을 못 받은 경우가 바로 돈이 걸리는 경우인데 그쪽이 비어 있었다.**

호출 기록으로도 구분이 안 됐다. 응답 시각이 비어 있는 이유가 셋인데 기록상 똑같았다.

```
커넥션이 거부됐다          안 나갔다
보냈는데 응답을 못 읽었다    나갔다. 처리됐을 수 있다
우리 프로세스가 죽었다      모른다
```

그래서 **응답 코드 표는 응답을 받았을 때만 쓰고, 그 앞에 전송 계층 판정을 뒀다.** 판정 결과는 호출 기록에 실패 유형으로 남기되 **상태 분기에는 쓰지 않는다** — 분기는 호출 직후 그 자리에서 끝나고, 이 값은 사후에 되짚기 위한 것이다.

### 3. 서버 오류(5xx)를 "다시 시도할 수 있는 실패"가 아니라 "모른다"로 접는다

직관과 반대다. 5xx는 보통 재시도 대상으로 다룬다. 그러나 **결제사가 요청을 받아 처리하다가 내부 오류로 5xx를 낼 수 있다.** 미처리로 단정해 바로 다시 보내면 돈이 두 번 나간다.

같은 계열의 판단 셋:

| 응답 | 어떻게 접나 | 왜 |
| --- | --- | --- |
| 요청 제한(429) | 다시 시도할 수 있는 실패 | "안 받았다"가 그 코드의 뜻이다 |
| 인증 거절(401·403) | 다시 시도할 수 있는 실패 + **별도 통지** | 설정이 틀리면 모든 건이 그 코드를 받는다. 개별 건으로 사람에게 넘기면 고치면 다 풀릴 건들이 전부 손처리 대상이 된다 |
| **모르는 코드** | **모른다** | 실패로 접으면 실제로 나간 돈을 안 나간 것으로 다룬다 |

**성공·실패를 HTTP 상태로 가르면 안 된다.** 실측에서 실패 응답이 HTTP 200으로 왔다. 본문의 결과 코드로 갈라야 한다.

**그리고 "그 자리에서 확정하면 안 되는" 응답이 둘 있다** — "이미 취소된 결제"와 "잔여 금액을 넘음". 다시 시도할 수 없는 실패로 접되 **거기서 끝내지 않고 이력을 읽는다.**

> 우리가 그 요청을 보냈다는 것 자체가 **우리 기록이 결제사와 갈렸다는 뜻**이다. 그냥 성공으로 접으면 우리가 모르는 환불이 있는 경우를 성공으로 덮는다.

이력을 읽어 셋으로 간다 — 우리 시도가 이미 완료로 있으면 성공으로 확정, 결과를 모르던 **다른** 건이 완료된 것으로 설명되면 그 건을 확정하고 이번 건은 다음 주기에 다시 집기, 어느 쪽으로도 설명되지 않으면 사람에게 넘긴다.

### 4. "안 나갔다"를 별도 갈래로 만들지 않는다

커넥션 거부는 요청이 안 나갔음이 거의 확실하므로, 그것을 별도 갈래로 두면 이력 조회를 건너뛰고 바로 보낼 수 있다. 그런데 **중간에 프록시나 게이트웨이가 끼면 커넥션 거부가 정말 확실한지 장담할 수 없다.**

> **이력을 한 번 더 읽는 값이 이중환불보다 싸다.**

### 5. 결과를 모르는 동안은 **같은 멱등키로** 다시 부른다 ← 뒤집힌 결정

이 결정이 한 번 뒤집혔고, 그 과정이 가장 배울 만하다.

**처음 결론은 "재요청마다 새 키"였다.** 근거가 둘이었다.

1. 같은 값을 계속 실으면 **결제사가 그때 저장해 둔 응답을 재생한다**(실측). 그러면 첫 응답이 실패였던 승인은 **승인 가능 시간이 지나도** 그 답만 되풀이 돌아온다. 아래 §8이 말하는 **유일한 자동 확정 근거("승인 가능 시간이 지났다")가 영영 안 오는 것**이라, 그 결제는 영원히 결과 불명으로 남고 활성 슬롯을 쥔 채 그 주문을 막는다.
2. 재전송은 이력에 그 시도가 없음을 확인한 뒤에만 하므로, 그 시점에 돈은 나가지 않은 상태다.

**두 번째 전제가 성립하지 않았다.** 결제사 API 문서를 다시 읽어 확인했다 — 이력의 처리 결과 값에 **"처리 중"을 나타내는 값이 없고**, 취소 일시도 취소가 완료된 뒤에야 나타난다. 즉 **처리 중인 취소는 이력에서 "없음"으로 읽힌다.**

```
환불 30,000 요청 (시도 1)  →  응답 못 받음  →  결과 불명
                              결제사는 처리를 마쳐 잔액 70,000
이력 조회                  →  처리 중이었거나 반영이 늦어 "없음"
시도 2 로 30,000 재전송     →  앞 취소가 완료돼 "진행 중" 거절이 안 뜨고
                              잔액도 남아 거절 사유가 없다  →  총 60,000 이 나간다
```

**부분환불이라 잔액이 남는 것이 핵심이다.** 전액 환불이면 "이미 취소된 결제"로 막히지만 부분환불에서는 막을 것이 없다. "결국 한도 초과로 드러난다"는 옛 근거도, 10만 원 중 3만 원을 두 번 되돌리면 초과가 안 나므로 성립하지 않는다.

그러면 같은 키를 쓰면 되는데, 그것을 막던 근거가 **"멱등키 보관 기간을 모르므로 만료된 뒤에 보내면 새 요청으로 처리되어 돈이 두 번 나간다"**였다. 같은 키를 보내는 시점은 "이력에 없다"를 확인한 뒤이고, 그때 가능한 상태는 셋뿐이다.

```
① 요청이 안 갔다          새 요청으로 처리된다. 우리가 원하던 것이다
② 처리 중이다             멱등키가 살아 있다. 처리가 끝나기 전에 키가 먼저 사라지는
                         시스템은 멱등성 보장 자체가 성립하지 않는다
③ 완료됐는데 반영이 늦다    409 와 함께 이전 응답이 돌아와 성공으로 확정된다 (실측)
                         ★ 새 키로 보내면 이 경우에만 돈이 두 번 나간다
```

**막으려던 바로 그 사고가 새 키에서만 일어난다.** 근거가 뒤집혔다.

최종 규칙:

```
응답을 못 받았다             →  같은 키로 다시 부른다
이력에 우리 시도가 없다        →  같은 키로 다시 부른다
이력에 실패로 있다            →  같은 키로 다시 부른다.  왜 실패했는지를 모르기 때문이다

성공                        →  확정하고 끝
다시 시도할 수 없는 실패       →  종결하고 끝
다시 시도할 수 있는 실패       →  새 키로 보낸다.  ★ 시도 번호가 오르는 유일한 자리
```

**앞 셋에서 같은 키를 쓰는 이유가 갈린다.** 처음 둘은 이미 나갔을 수 있어서고, **세 번째는 그 응답이 사유를 알려주기 때문이다.** 이력에는 실패 사유가 없어 재시도 가능 여부를 가릴 수 없는데, 같은 키로 부르면 409와 함께 돌아오는 이전 응답이 그 사유를 알려준다. 그리고 세 번째는 **키가 만료돼도 안전하다** — 이력이 실패라고 말하는 것은 그 취소가 실행되지 않았다는 뜻이므로, 새 요청으로 처리되어 성공해도 그것은 원래 되었어야 할 환불이지 이중환불이 아니다.

**승인과 환불의 위험이 다른데도 규칙을 같게 뒀다.** 승인 요청은 식별자 하나를 보내므로 새 키로 불러도 이미 성립한 건은 "이미 완료됨"으로 답한다. **환불은 금액을 실어 보내는 누적 연산이라 새 키가 곧 두 번째 환불이 된다.** 같게 둔 것은 같은 키가 양쪽 모두에서 더 안전하기 때문이다.

### 6. 결과 회수를 멈추지 않는다

옛 정책은 결과 불명으로 여섯 시간이 지나면 사람에게 알리고 자동 회수를 그만뒀다. **멈추면 회원이 할 수 있는 일이 없다.**

- 환불이 멈추면 돈이 안 돌아간 채 남고 그 금액만큼 한도가 계속 막힌다.
- 승인이 멈추면 결과 불명 결제가 활성 슬롯을 쥔 채 남아 **그 주문을 영영 결제할 수 없다.**

"사람에게 알린다"고 했지만 그것은 로그 한 줄이고 받아서 처리할 경로가 없었다. **멈추면 사실상 아무도 풀지 않는다.**

그래서 **시간·횟수 상한을 전부 없앴다.** 재요청 횟수 상한도 두지 않는다 — 상한이 막으려던 것(반복 전송으로 돈이 여러 번 나가는 것)은 보내기 전 이력 확인이 이미 막고, **무엇보다 상한은 그 건을 풀지 못한다.** 재요청만 멈출 뿐 상태는 그대로다.

대신 **다시 집는 간격을 회차마다 벌리되 상한을 뒀다** — `10초 · 30초 · 2분 · 5분 · 10분`. 결제와 환불이 같은 표를 쓴다.

> 한 주기에 결제사 호출이 둘 나간다(이력 조회 + 취소 요청). 3시간 장애에 결과를 모르는 환불이 20건이면, 고정 10초로는 43,200회이고 이 표로는 720회다.

### 7. 회수 수단은 둘이고 순서가 있다

**이력 조회가 먼저이고, 거기서 정해지지 않는 것을 같은 키 재전송이 받는다. 둘 중 하나만 쓰지 않는다.**

이력 조회가 회수의 첫 수단이 될 수 있었던 근거는 실측이다 — **요청에 실어 보낸 시도 키가 결제사 이력 행에 그대로 실려 돌아온다.** 이력에서 우리 사건을 집어낼 수 있다는 뜻이다.

**이력에서 찾을 때는 구분자까지 포함한 접두어로 찾는다.** 그래야 한 사건 키가 다른 사건 키의 앞부분과 같을 때 섞이지 않는다.

### 8. 승인은 "다시 물어서" 확정한다

승인 쪽에는 이력 조회만으로 안 되는 문제가 있었다. **빈 이력은 "돈이 안 나갔다"와 "결제사가 아직 반영하지 않았다"를 구분하지 못한다.** 잘못 확정해 슬롯을 풀면 회원이 다시 결제하는데 앞 건도 사실은 성공이라 돈이 두 번 나간다.

승인 API를 다시 부르면 그 번호의 현재 상태를 결과 코드로 직접 답한다. 그중 **"승인 가능 시간이 지났다"**는 *지금 승인이 없고 앞으로도 생기지 않는다*를 함께 뜻해 확정적이고, **이력 반영 시점과 무관하다.**

그래서 **한 주기에 두 번 묻는다** — 이력을 먼저 읽고, 없으면 그 자리에서 승인을 다시 부른다. **자동으로 실패를 확정하는 답은 "승인 가능 시간이 지났다" 하나뿐이다.** "이번 요청이 실패했다"로는 확정하지 않는다 — 이번 호출에 대한 답이지 앞선 호출에 대한 답이 아니다.

**승인 재요청을 미루지 않는다.** "승인 가능 시간이 지난 뒤에 부르면 결제사가 새로 승인해 줄 수 없어 안전하다"는 안을 검토했으나 버렸다 — 그러면 **요청이 아예 결제사에 닿지 않았던 결제가 구제되지 않는다.** 다시 부르기만 하면 성립할 결제가 시간이 지난 뒤 "시간 초과" 답을 받고 실패로 닫힌다.

대가를 명시했다: **이 호출로 돈이 움직인다.** 승인 가능 시간 안에서 부르면 결제사가 새로 승인해 준다. 회원이 인증까지 마친 건이라 의도된 움직임이지만, **"배치가 부르는 호출은 안전하다"는 전제가 더 이상 성립하지 않는다.**

**겹쳐 승인되지 않는 것은 결제사가 "아직 처리 중"으로 답해 주기 때문이다.** 이 재요청이 앞선 승인과 겹칠 수 있는데, 그것을 막는 것이 **그 답 하나뿐**이다. 어댑터가 그 코드를 다른 실패와 뭉뚱그리면 **방어가 통째로 사라진다.**

부수 효과가 좋았다 — **승인 가능 시간의 길이가 코드에서 사라진다.** 첫 회차부터 부르면 그 값을 우리가 알 필요가 없어 결제사마다 달라도 바꿀 곳이 없다.

### 9. 환불에는 자동으로 도달하는 실패 종착을 두지 않는다

**결제와 환불의 실패는 성격이 반대다.**

> 결제가 실패하면 물건을 안 팔면 되니 정상 종료지만, **환불이 실패하면 회원 돈을 안 돌려준 것이라 정상이 아니다.** 주문이 이미 취소됐으면 돈은 돌아가야 하고, 회원이 다시 요청할 수도 없다. **"환불하지 않기로 한다"는 선택지가 없다.**

그래서 환불의 자동 종착은 **성공 하나뿐**이다. 자동 처리가 더 못 가는 건은 "사람이 봐야 함" 상태로 가는데, **그것은 종착이 아니다** — 다른 수단으로 돌려주면 성공으로, 조건을 고쳐 다시 보낼 수 있게 되면 처음 상태로 돌아간다.

**시도의 실패는 사건의 실패가 아니다.** 실패한 한 번의 요청은 호출 기록에만 남고 환불 사건은 진행 중에 머문다.

사람에게 넘길 때 **검토 코드**를 함께 채운다. 관리자가 알아야 하는 것은 결국 **돈이 나갔는가**인데, 상태보다 그 코드가 그것을 직접 알려준다.

| 검토 코드 | 돈은 | 관리자가 할 일 |
| --- | --- | --- |
| 취소 기한이 지나 결제사로는 못 돌려준다 | 안 나감 | 다른 수단으로 돌려주고 성공 처리 |
| 정책상 이 결제는 취소할 수 없다 | 안 나감 | 위와 같다 |
| 환불 가능 금액을 초과했다 | **모름** | 결제사 화면에서 실제로 무엇이 나갔는지 확인 |
| 우리가 보낸 요청이 결제사 기준에 안 맞는다 | 안 나감 | 값을 고쳐 다시 보낸다 |

**단, 이 표의 "할 일"을 아직 아무도 못 한다.** 사람이 봐야 할 건임을 상태와 검토 코드로 표시하는 데까지는 왔지만, **그것을 다룰 관리자 화면이 없다.** 관리자 기능이 있어야 제대로 만들 수 있어 후속으로 미뤘고, 그동안 그 환불은 표시만 된 채 남아 있다.

**"자동 처리를 멈춤"을 매번 계산하는 분류로 두지 않고 상태로 저장한다.** 계산으로 두면 정책 값을 바꾸는 순간 이미 멈춘 건들이 일제히 부활하는데, 관리자가 결제사 화면에서 직접 처리한 환불에는 우리 시도 키가 실리지 않아 이력으로 확인되지도 않는다. **배포 한 번이 이중환불이 된다.**

### 10. 다시 보낼 때 상태를 되돌리지 않는다

옛 설계는 재전송할 때 상태를 "부를 준비"로 되돌렸다. 그래서 그 상태의 뜻이 "한 번도 안 불렀다"가 아니게 됐고, 문제가 셋 따라왔다.

```
확인이 낡는다     되돌린 뒤 보내기까지 주기가 벌어져, 그 사이 결제사가 이력에 반영할 수 있다
                 그래서 보내기 직전에 한 번 더 읽어야 했다
백오프를 잃는다    상태가 바뀌면 첫 회차처럼 다뤄져 다시 집는 간격이 처음으로 돌아간다
결제와 갈린다     결제는 결과 불명에 머문 채 다시 부르는데 환불만 되돌아왔다
```

**상태를 그대로 두고 그 자리에서 부른다.** 바뀌는 것은 부른 시각뿐이다. 그러자 **첫 상태가 다시 "아직 안 나갔음이 확실하다"는 뜻을 회복했다** — 재시도가 그 상태를 지나가지 않으므로 거기 있는 건은 둘뿐이다(한 번도 안 부른 것, 사람이 되살린 것).

**첫 발송과 재전송의 가드가 다르다.** 첫 발송은 그 첫 상태일 때만 하지만, 재전송에는 그 조건을 쓸 수 없다 — 늘 응답 대기이거나 결과 불명이다.

그래서 **앞 주기가 아직 부르는 중에 다음 주기가 같은 건을 집는 것**을 상태로는 못 막는다. **그 겹침을 가르는 것은 낙관 락이고**, 이긴 쪽이 부른 시각을 갱신해 회수 유예가 다시 걸리는 것이 겹을 좁힌다.

### 11. 결제사가 주는 "잔액 대조" 옵션을 켜지 않는다

결제사는 취소 요청에 **가맹점이 예상하는 잔여 금액을 함께 보내는 옵션**을 제공한다. 켜면 자기 계산과 다를 때 거절한다. 결제사 문서가 "이중 환불을 방지하기 위해 가급적 연동하기를 권한다"고 두 곳에서 반복한다.

**그런데도 켜지 않았다.** 이 기능은 우리 기록과 결제사 기록이 늘 일치한다는 전제 위에 서는데, 우리 구조는 요청을 받아들이고 뒷단에서 처리하므로 **시차가 정상이다.** 대조 값에는 성공으로 확정된 환불만 담을 수 있어, **결과를 모르는 환불이 하나만 떠 있어도 우리가 말하는 잔액이 실제보다 커져 그 결제의 이후 환불이 전부 거절된다.**

> **지연을 오류로 취급하는 셈이고, 그 대가가 방어 한 겹보다 크다.**

**공급자가 권장한다고 해서 우리 구조에 맞는 것은 아니다.** 권장의 전제(동기적으로 처리해 기록이 즉시 일치)가 우리에게 성립하는지를 먼저 봐야 했다.

**과다 환불은 결제사가 항상 하는 검사 둘이 막는다** — 요청 금액이 남은 금액을 넘으면 거절, 잔여가 0이면 거절. 옵션이 추가로 잡는 것은 "금액은 남아 있는데 우리 계산과 다른" 경우뿐이고, 그 자리는 이력 조회와 같은 키 재전송이 메운다.

### 12. 회수 배치가 환불을 집행하기 전에 "그 주문 정말 취소됐어?"를 묻지 않는다

옛 모델에는 그 확인이 있었다. 환불 행의 존재와 그 주문이 취소됐다는 사실이 항상 함께 가지 않았기 때문이다 — 주문 취소 없이 환불 행만 만드는 문이 따로 있었다.

새 모델은 **환불이 만들어지는 자리를 정당한 조건과 같은 트랜잭션으로 묶어** 부당한 행이 아예 생기지 않게 했다.

| 환불이 만들어지는 자리 | 무엇과 함께 커밋되나 |
| --- | --- |
| 회원이 주문을 취소한다 | **주문 취소와 한 트랜잭션.** 취소가 롤백되면 환불도 없다 |
| 승인 반려 | **결제 종결과 한 트랜잭션.** 반려 판단을 한 그 자리에서 |

> **전제를 확인하는 대신 전제가 깨지지 않게 만든 것**이며, 원래 요구("부당한 환불이 집행되지 않는다")는 그대로 지켜진다. **확인은 수단이었을 뿐이다.**

반례를 셋 찾아봤는데 그 확인이 실제로 막는 것이 없었다.

```
환불 행이 생긴 뒤 주문 취소가 롤백된다     같은 트랜잭션이라 불가능하다
반려 판단이 나중에 뒤집힌다                뒤집을 근거가 없다
옛 데이터가 이관되어 들어온다              이관을 안 하기로 했다
```

**세 번째는 조건부라 남겨 둔다** — 이 결론이 "데이터 이관을 하지 않는다"에 걸려 있으므로, 이관을 하기로 바뀌면 이 자리를 다시 봐야 한다.

게다가 그 물음은 **부분환불에서 답을 주지 못한다** — 품목 일부만 취소하면 주문은 결제완료로 남기 때문이다.

### 13. 밖에서 취소된 승인을 발견하면 닫는다

이력을 읽었더니 **승인도 있고 그 뒤 취소도 있는데 그 취소가 우리 기록으로 설명되지 않는** 경우가 있다. 우리는 환불 행 없이 취소를 보낼 수 없으므로 그 취소는 확실히 밖에서 온 것이다(결제사 관리 화면에서 사람이 직접 취소).

우리가 먼저 쓴 설계 초안은 "이미 취소됐음을 알아본다"까지만 적고 **알아본 뒤 무엇을 하는지를 비워 두었다.**

**결제를 실패로 종결하고 슬롯을 반납한다.** 돈은 확실히 돌아갔고 그 결제는 성립하지 않았다.

**"돈이 나갔다 돌아오는 중"을 뜻하는 전용 종결 상태([[2026-08-16-payment-refund-aggregate-boundary]] 참고)에 넣지 않는다.** 그 상태의 존재 이유는 지금 되돌아오는 중인 건을 골라내는 것인데, **이 건은 이미 돌아갔고 우리가 할 일이 없다.** 그리고 그 상태에는 "환불이 딸려 있다"는 검증이 걸려 있어, 여기를 거기 넣으면 예외가 생겨 규칙으로 걸 수 없게 된다. **환불을 만들지 않는다** — 되돌릴 것이 없고, 환불은 언제나 접수 상태로 태어나 발송 배치가 집어 보내므로 이 경우만 "태어나자마자 완료"인 환불을 만들면 **자리를 하나만 잘못 써도 이미 취소된 건에 취소를 한 번 더 보낸다.**

**성공한 취소인지를 조건에 넣는다** — 실패한 취소도 이력에 한 줄로 남으므로, 그것을 근거로 닫으면 돈이 나가 있는 결제를 닫는 것이 된다.

**닫지 않는 선택지는 버렸다.** 그러면 슬롯을 쥔 채 남아 그 주문을 영영 결제할 수 없다.

**이 건의 통지는 발견한 그 자리에서 한 번뿐이다.** 아래 §14가 통지를 반복한다고 하지만 여기는 예외다 — **되돌릴 것이 없고 조사만 남는 일이라 반복할 대상이 아니다.**

### 14. 통지는 보낸 뒤에 시각을 남기고, 상태가 이어지는 동안 반복한다

옛 구조는 통지 시각을 별도 트랜잭션으로 **먼저** 커밋하고 그 뒤에 보내며, 실패하면 로그로 삼켰다. **통지가 한 번도 안 나갔는데 시각은 남아 다음 주기가 그 건을 다시 집지 않는다.** 시각을 먼저 찍은 것은 여러 배치가 동시에 돌 때 하나만 통지하게 하려는 장치였다.

**보낸 뒤에 남기는 쪽으로 바꿨다.** 못 보내면 시각이 안 남아 다음 주기가 다시 집는다.

> 돈이 얽힌 건은 **알림이 안 가는 것보다 두 번 가는 것이 낫다.**

**통지를 반복한다.** 한 번만 나가면 그 로그 한 줄이 흘러가고 아무도 다시 보지 않는다. 자동으로 안 풀리는 건은 사람이 개입해야 끝나는데, 알림이 한 번뿐이면 개입할 사람에게 닿지 않는다. **멈추는 일은 상태가 하게 두고 횟수로 멈추는 규칙을 만들지 않는다** — 사람이 처리하면 상태가 바뀌어 저절로 멈춘다.

이것은 지금 드러나지 않는 결함이었다. **통지가 로그 한 줄이라 보내다 실패할 일이 거의 없어서다. 실제 통지 수단이 붙는 순간 살아난다.**

## 막힌 점·해결

### 결제사 문서를 두 번 읽어야 했다

"같은 키냐 새 키냐"의 첫 결론은 **그 문서를 한 번 읽고 내린 것**이었고 틀렸다. 뒤집힌 계기는 *"이력의 처리 결과 값에 '처리 중'이 있는가"*를 다시 확인한 것이다. 없었다.

**전제로 삼은 문장이 그 문서 어디에 있는지 짚을 수 없으면 그것은 추측이다.** "이력에 없으면 안 나간 것"은 그럴듯했지만 문서가 보장한 적이 없다.

### 실측이 문서보다 정확했던 자리

몇 가지는 문서로 알 수 없어 개발 환경에서 직접 확인했다.

```
실패 응답이 HTTP 200 으로 온다               →  상태 코드로 성공·실패를 가르면 안 된다
같은 키를 다시 보내면 저장된 응답이 재생된다     →  이것이 처음 "새 키" 결론의 근거였다
409 와 함께 이전 응답이 돌아온다               →  같은 키가 안전한 이유가 됐다
요청에 실은 시도 키가 이력 행에 실려 돌아온다    →  이력 조회를 회수의 첫 수단으로 만들 수 있었다
```

**마지막 것에 회수 전략이 통째로 기대고 있다** — 이력에서 우리 건을 못 집어내면 이력 조회를 첫 수단으로 쓸 수 없다.

## 배운 것

- **"모른다"를 실패로 접지 마라.** 실패로 접으면 실제로 나간 돈을 안 나간 것으로 다룬다. 모르면 모른다고 저장하고, 확정은 나중에 확정적인 근거로만 한다.
- **재시도 정책의 안전성은 "이미 나갔을 가능성"으로 판단한다.** 5xx가 재시도 대상인지는 프로토콜이 아니라 **그 요청이 부작용을 갖는가**로 갈린다.
- **멱등키를 새로 만드는 것이 항상 안전한 게 아니다.** 상대가 멱등키로 중복을 막아 준다면, 같은 키를 유지하는 것이 그 보호를 계속 받는 길이다. 새 키는 그 보호를 스스로 포기하는 것이다.
- **자동 회수를 멈추는 정책은 "그다음 누가 푸나"가 있을 때만 성립한다.** 받아서 처리할 사람이 없으면 멈춤은 방치와 같다.
- **상태를 되돌리는 재시도는 부수 효과가 크다.** 그 상태에 기대던 백오프·의미·조회가 함께 무너진다. 상태는 두고 시각만 갱신하는 쪽이 대체로 안전하다.
- **공급자 권장 기능도 우리 구조의 전제와 맞는지 먼저 본다.** 동기 처리를 전제한 방어를 비동기 구조에 붙이면 정상 지연이 오류가 된다.
- **확인을 넣는 것과 확인이 필요 없게 만드는 것 중 후자가 낫다.** 확인은 그 시점의 진실만 말하고, 확인과 실행 사이에 창이 열린다.
- **실패가 정상 종료인 도메인과 아닌 도메인이 있다.** 결제 실패는 정상이지만 환불 실패는 아니다. 상태 기계를 복사하기 전에 그것부터 본다.
- **드러나지 않는 결함을 찾으려면 "지금 이게 왜 문제가 안 되지"를 물어야 한다.** 통지 결함은 통지가 로그 한 줄이라 숨어 있었다.

## 미해결·열린 질문

- **결제사 API 문서로 확인하지 못한 것이 셋 남았다** — 이력의 실패 값이 붙는 조건, 멱등키 보관 기간, **처리 중이거나 서버 오류라 결과가 안 난 응답도 저장돼 재생되는가.** 셋 다 결제사가 실패하도록 만들거나 시간을 흘려보내야 관측되는 것이라 재현할 수 없다.
- **같은 값을 두 번 보내도 되는지 결제사 API 문서로 확인하지 못했다.** 이력에 실리는 값에 유일성 제약이 없다는 것과 결제사가 실제로 거절하지 않는다는 것은 다르다.
- **위험이 하나 남는다 — 완료됐는데 이력 반영이 늦은 건에서 키까지 만료된 경우.** 이력 반영 지연과 키 보관 기간을 둘 다 재야 창의 크기를 아는데 둘 다 관측할 수 없어 "매우 좁을 것"이라고 짐작할 뿐이다. **그래도 새 키보다 낫다** — 새 키는 그 경우에 반드시 두 번 나가고 같은 키는 키까지 만료됐을 때만 그렇다.
- **"그런 확정적인 답을 주지 않는 결제사"를 붙이면 자동 실패 확정 경로가 없다.** 그때 무엇을 근거로 삼을지는 정하지 않았다.
- **결과 불명이 얼마나 자주 나는지 재지 않았다.** 회수 간격 표의 값도 그 빈도를 모르는 채로 정했다.
- **통지를 보낸 뒤에 시각을 남기기로 하면서 중복 방지 장치를 잃었다.** 시각을 먼저 찍어 하나만 통과시키던 방식이 그 역할을 겸하고 있었는데, 순서를 뒤집으면서 **동시에 도는 배치 둘이 같은 건에 각자 통지를 보낼 수 있게 됐다.** 지금은 통지가 로그 한 줄이라 드러나지 않지만, **실제 통지 수단을 붙일 때 중복을 견디게 만들거나 다른 방법으로 한 번만 나가게 해야 한다.**
