# 결제 부분환불 도입 — 현행 한계와 테이블 분리 결정 (issue #291)

## 결정한 것
- 현행 결제 취소 구조는 전액 환불만 지원한다. 부분환불(한 결제를 여러 번 나눠 일부 금액씩 환불)을 도입하려면 재설계가 필요하다고 판단해 issue #291로 발급했다.
- 부분환불이 막히는 지점 4가지(현행 한계 진단):
  1. 결제 유효성 판단이 "승인 성공 사건이 존재하는가"라는 존재여부(boolean)만 본다. 금액 축이 없어 "얼마 남았나"를 표현하지 못한다.
  2. 주문 상태가 결제완료/취소의 이진이라 "일부만 환불된 상태"를 표현할 수 없고, 환불액·잔액 필드도 없으며, 주문 취소가 한 번 일어나면 잠긴다.
  3. 결제 사건 테이블의 unique 제약이 (가맹점 결제키, 결제수단, PG 결제ID, 사건종류) 조합이라 한 승인당 취소 사건이 1건으로 강제된다. 취소 생성 로직도 기존 취소와 금액이 다르면 거부한다(전액취소 멱등 목적).
  4. 누적 환불액·잔액을 추적하는 로직이 없다.
- 외부 결제사(간편결제) 연동 어댑터는 이미 부분취소 금액 파라미터를 지원한다. 즉 외부 호출 계층은 준비돼 있고 그 위의 도메인·스키마·API만 전액 취소로 고정돼 있다.
- 이 전액취소 전제는 우발적 버그가 아니라 의도된 설계다. 기획 문서가 스코프를 전액환불로 못박았고, 설계 결정 문서가 부분취소를 미래 과제로 미루며 해법 방향(취소요청 단위 고유키 + 누적취소액 ≤ 승인액 한도검증)까지 적어뒀다.
- **테이블 분리 결정 (승인 테이블 / 취소 테이블로 물리 분리)**: 지금은 승인·취소를 한 테이블에 "사건종류" 컬럼으로 담는데, 이를 두 테이블로 나눈다. 이유는 두 가지다. (가) 부분환불로 취소 전용 컬럼(취소요청 키, 취소 사유, 부분 금액, 원 승인 참조)이 늘면 한 테이블 방식은 승인 행에선 취소 컬럼이, 취소 행에선 승인 컬럼이 항상 비어(NULL) 응집도가 나빠진다. (나) 승인:취소가 1:N 부모자식 관계가 되는데, 한 테이블 안에서 자기 자신을 참조하는 1:N은 어색하다. 별도 테이블이 도메인적으로 자연스럽다.
- 이 테이블 분리가 개편의 진짜 동기다. 과다환불 방지 같은 비즈니스 로직 필요성과는 별개의 축(순수 데이터 표현 문제)이다.

## 검토한 대안·트레이드오프
- "취소요청 고유키 컬럼만 추가하면 되지 않나?" → 아니다. 그건 취소를 여러 건 담을 그릇만 만들 뿐이다. 잔액검증 없이 취소가 쌓이면 오히려 과다환불(5만원 결제에 3만원+3만원 취소로 6만원 환불)이 나는 위험 구조가 된다. 테이블 분리(그릇)와 비즈니스 로직(잔액검증·동시성 잠금·취소금액 입력 API·주문 부분환불 표현·유효성 금액화)은 형제 관계지 서로 대체하지 못한다. 부분환불엔 둘 다 필요하다.
- 테이블 분리의 비용: 승인+취소를 함께 조회할 때 union·조인이 필요하고, append-only 사건 로그가 두 곳으로 분산된다. 그래도 부분환불 맥락에선 응집도·관계표현 이득이 이 비용보다 크다.

## 부분취소 메커니즘 이해
- 외부 결제사는 원결제(PG 결제ID) 하나에 대한 부분취소를 여러 번 지원한다. 원결제 식별자는 고정이고 그 위에 취소 요청을 N번 보낸다.
- 각 취소 요청은 고유 취소식별자(멱등키)로 구분해야 한다. 중복취소(같은 요청이 재전송됨)를 막고, 우리 DB에도 N개 행으로 구분 저장하기 위해서다. "같은 키로 두 번"이 아니라 "원결제는 같고 취소 요청마다 고유키"가 정확한 그림이다.
- 우리 쪽에서도 누적취소 ≤ 승인액 잔액검증을 해야 한다. 외부 결제사의 잔액초과 거부에만 의존하지 않고 선방어하는 이유는 돈 정합성 이중방어 + 화면에 환불가능액을 보여주기 위함이다.

## 개편 범위 결정 (작업 단위 구조)
- 작업 발급 단위(issue)는 목적 기준, 코드 변경 단위(PR)는 더 잘게 나눈다.
- 부분환불(도메인 분리 포함)은 한 issue(#291)로 묶고, 도메인 분리는 그 안에서 여러 PR로 쪼갠다. 테이블 분리를 부분환불 없이 먼저 하면 아직 쓰지 않는 구조를 미리 만드는 셈이라 부적절하다.
- 외부 PG(토스페이먼츠) 연동은 별도 issue다. 결제창 준비물(승인 전 결제 세션) 제거도 별도 트랙이다. 이 계층은 현재 구조에선 외부 결제 식별자 발급과 재시도 단위를 대표하는 역할이라 필요하지만, 외부 PG 위젯 방식으로 전환하면 결제창 준비 역할이 가벼워져 없앨 수 있다 — 그마저도 승인 준비 영역이라 부분환불(취소 영역)과는 무관하다. 이 세 가지(부분환불, 외부 PG 연동, 결제창 준비물 제거)를 한 PR로 뭉치지 않는다.

## 미해결·열린 질문
- 주문의 부분환불 표현 방법: 별도 상태값(부분환불됨)을 추가할지, 환불액·잔액 필드로 표현할지.
- 동시 부분취소의 잔액 경합: 두 취소가 동시에 들어올 때 누적취소 검증이 깨지지 않도록 하는 잠금(낙관/비관) 방식.
- 개편 순서: 부분환불을 먼저 할지, 외부 PG 연동을 먼저 할지.
