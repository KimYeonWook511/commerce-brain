# 네이버페이 환불 API 실측 — 이력에서 특정 환불을 지목하는 근거를 정하기까지

> **용어**
> - **대사**: 외부 결제사 호출이 끊기거나 결과가 불확실한 건을, 배치가 주기적으로 다시 조회해 확정·재시도하는 것.
> - **환불 사건**: "얼마를 왜 돌려준다"는 의도 하나의 기록. 그 의도로 결제사를 여러 번 부를 수 있다.
> - 우리가 발급하는 값이 둘이라 헷갈리기 쉽다. **환불 식별자**는 환불 사건 하나를 가리키려고 우리가
>   만들어 요청 파라미터에 싣는 값이고, **멱등키**는 "같은 요청이다"를 결제사에 알리려고 HTTP 헤더에
>   싣는 값이다. 전자는 안 바뀌고 후자는 재시도 정책에 따라 바뀐다. (형제 기록에 나오는 **취소요청
>   고유키**는 또 다른 것 — 그건 클라이언트가 우리에게 보내는 값이다.)

## 배경

네이버페이를 결제대행사 없이 직접 연동해 결제·환불을 처리하는 백엔드에서, 부분환불을 받을 수 있도록
결제·환불 모델과 연동을 다시 설계하던 중이었다.

**"어느 환불이 집행됐는지 외부 이력에서 판정할 근거가 없다"는 문제가 두 차례 미해결로 닫혔다**
(`2026-07-23-partial-cancel-balance-and-idempotency-pitfalls.md`,
`2026-08-08-partial-cancel-external-cancel-correlation-gap.md`). 뒤쪽 기록이 남긴 열린 질문이
**"이력 항목이 금액·시각 말고 우리 사건과 맞물릴 값을 담고 있는가"**였고, **이번 실측이 그 답이다.**

### 왜 이 기록을 남기나

재현 비용이 크다. 결제창 인증에 사람이 직접 네이버 로그인과 결제 비밀번호를 넣어야 해서 자동화로
다시 만들 수 없다.

### 실측 조건

- 2026-08-09, 네이버페이 **개발 환경**. API `dev-pay.paygate.naver.com`, 결제창 `test-m.pay.naver.com`
- 100원을 결제한 뒤 30원·30원·40원으로 나눠 환불하며 관측
- **포인트 전액 결제였다.** 등록된 카드와 머니 충전계좌가 모두 점검 중이었다. 응답이 카드·계좌
  금액(`primaryPay*`)과 포인트 금액(`npoint*`)을 나눠 다루고 카드에는 취소 기한 제약이
  따로 있으므로(`CancelDeadlineExpired`), **카드 결제의 부분취소도 같다는 보장은 없다.**
- 개발 환경 관측이며, 운영 환경도 같다는 보장은 명세에 없다

## 결정한 것

### 환불 사건을 이력에서 지목하는 근거를 "보내기 전에 우리가 정하는 값"으로 삼는다

네이버페이는 환불이 처리되면 이력 목록에 항목을 남기고 각 항목에 이력 번호(`payHistId`)를 준다.
그런데 **그 번호는 환불 응답 본문에서만 얻는다.** 응답을 받았다는 것은 결과 코드도 함께 받았다는
뜻이라, 번호가 있으면 결과를 이미 알아 이력을 볼 이유가 없다. 반대로 결과를 몰라 이력을 봐야 하는
상황에는 번호가 없다. **게다가 응답을 받고도 우리 쪽에 기록하기 전에 끊길 수 있어, 번호가 우리에게
남아 있으리라 기대할 수 없다.**

그래서 "보내기 전에 우리가 정하는 값"이어야 한다. 환불 요청 파라미터 중 그런 성격이면서 이력 항목에도
있는 필드는 `merchantPayTransactionKey` 하나뿐이었다.

**명세가 안 말하는 것은 좁고 정확하다.** 그 필드는 이력 항목 표에 **선택 필드로 올라와 있다.** 다만
설명이 "가맹점의 결제 트랜잭션 번호 또는 주문 트랜잭션 번호"라 **취소 요청에 실은 값이 그 취소 항목에
되돌아오는지**가 규정돼 있지 않다. 승인 때 보낸 값이 모든 항목에 복사될 가능성도 배제되지 않는다.

실측 결과 **취소별로 되돌아온다**(아래 관찰 1). 그래서 우리가 발급하는 환불 식별자를 그 자리에 실어
보내고, 이력에서 그 값으로 우리 환불을 집어내기로 했다.

**대가**

- **유일성을 결제사가 보장하지 않는다.** 선택 필드의 자유 문자열이라 같은 값이 두 항목에 실려도 막지
  않는다. **유일성은 전적으로 우리 책임**이고, 깨지면 판정 근거 자체가 무너진다.
- **128바이트 제한.** 우리 식별자 형식이 그 안에 들어가야 한다.
- **승인 항목에도 같은 이름 필드에 값이 실린다.** 이 값만으로는 승인인지 취소인지 못 가리고
  유형 코드(`admissionTypeCode`)와 함께 봐야 한다.

### 이중환불의 최종 방어선을 멱등키 보관 기간에 의존하지 않는 잔액 대조에 둔다

멱등키는 실제로 중복을 막는다(관찰 4). 문제는 **결제사가 그 기록을 얼마나 보관하는지 명세에 없다**는
것이다(아래 미해결). 보관 기간이 지난 뒤 같은 키로 보내면 새 요청으로 처리되어 두 번 환불될 수 있다.

그래서 **2중 방어로 가되, 최종 방어선은 시간에 좌우되지 않는 쪽**에 뒀다 — 환불 요청에 "이번 환불 뒤
남을 예상 금액"을 함께 보내 결제사가 자기 잔액과 다르면 거절하게 한다. 막는 주체가 결제사 자신이라
경과 시간과 무관하다.

**구현할 때 반드시 볼 것**: `expectedRestAmount`는 **`doCompareRest=1`을 함께 보낼 때만 동작한다.**
스위치를 빠뜨리면 **최종 방어선이 꺼진 채로 돌고 아무 에러도 안 난다.**

**대가**: 우리 잔액 계산이 결제사와 어긋나면 **정당한 환불도 거절된다.** 결과가 확정되지 않은 환불을
계산에 넣느냐 빼느냐에 따라 어긋나는 경로가 생기므로, 무엇을 기준으로 빼는지를 따로 정해야 한다.

## 배운 것 — 실측으로만 알 수 있던 것

**1. 취소 요청에 실은 `merchantPayTransactionKey`가 그 취소 이력 항목에 되돌아온다.**
환불마다 다른 값을 넣으니 그대로 구분되어 돌아왔다. 승인 항목에도 결제 시작 때 보낸 값이 실려 있다.
→ 명세는 필드의 존재만 말하고 항목별로 어느 값이 실리는지는 말하지 않는다. 그 좁은 질문의 답이다.

**2. 나눠 환불하면 마지막 잔액을 남김없이 턴 건까지 전부 부분취소 유형(`04`)으로 기록된다.**
전체취소 유형(`03`)은 처음부터 전액을 한 번에 취소할 때만 나오는 것으로 보인다. **명세는 두 코드의
의미만 적고 어느 쪽이 붙는지 선택 규칙을 말하지 않는다.**
→ 전체취소 유형만 찾는 코드는 부분환불이 한 번이라도 섞이면 그 결제의 취소를 하나도 인식하지 못한다.
**여섯 중 가장 값어치 있는 관찰이다.**

**3. 잔액 대조 거절 응답에 결제사가 계산한 잔액이 실려 온다.**
일부러 틀린 예상 잔액(999원)을 보내니 `RestAmountDiff`로 거절됐고, 메시지에
`naverExpectedPayRestAmount:40` 형태로 담겨 왔다.
→ 파라미터와 실패 코드 자체는 명세에 있고 문서가 연동을 권장까지 한다. **새로 안 것은 "거절당했을
때도" 결제사 쪽 잔액을 얻는다는 것**이다(성공 응답에는 `totalRestAmount` 등으로 이미 온다).
우리 기록과 결제사 기록이 갈렸을 때 대사가 쓸 수 있는 값이다.

**4. 같은 멱등키 재전송에서 환불이 두 번 일어나지 않는 것을 확인했다.**
HTTP 409와 이전 응답 본문 재전달, 응답 헤더로 같은 키 반환은 **명세에 그대로 적혀 있다.** 실측으로
확인한 것은 **잔액이 유지되어 실제로 중복 집행이 없었다**는 것이다.
→ 교훈은 따로 있다. **409를 확정적 실패로 처리하면 성공을 실패로 뒤집는다.** 본문이 이전 성공 응답
그대로이기 때문이다.

**5. 요청 검증 단계에서 거절된 시도는 이력에 남지 않는다.**
잔액 불일치로 튕긴 요청이 이력에 흔적이 없었다(성공 4건만). 명세는 항목 상태(`admissionState`)에
`FAIL` 값이 **있다고만** 하고 언제 생기는지는 말하지 않는다.
→ "실패한 시도도 이력에 한 줄 남는다"는 가정이 적어도 파라미터 검증 실패에는 해당하지 않는다.
`FAIL` 항목이 생기는 경우는 결제사 내부 처리까지 간 뒤 실패한 때로 좁혀졌다.

**6. 이력 목록 순서는 이번 관측에서 시간 오름차순이었다.**
승인이 첫 항목, 환불들이 시간순으로 뒤에 왔다.
→ **설계 근거로 쓰지 않았다.** 명세에 순서 보장 서술이 없고 관측이 한 번뿐이다. 한 번 그랬다는 것이
항상 그렇다는 뜻이 아니라, "순서에 의존하지 않는 판정"이라는 방침을 그대로 유지했다.

## 배운 것 — 실측을 하기까지 알아내야 했던 연동 방법

명세에 있지만 흩어져 있어 모으는 데 시간이 걸린 것 중, **명세를 봐도 잘 안 풀리는 것만** 남긴다.

- **이력 조회만 요청 형식이 다르다.** 승인·취소는 form 형식인데 이력 조회는 JSON이고, 결제번호를 URL
  경로에 넣는다(`POST .../v2.3/list/history/{결제번호}`, 본문 `{"pageNumber":1,"rowsPerPage":50}`).
- **틀리면 원인을 짐작할 수 없다.** form으로 보내거나 경로에서 결제번호를 빼면 EUC-KR 인코딩 HTML로
  "서버에러"만 돌아온다. 경로에 번호가 없으면 기간 조회 엔드포인트로 해석되어 필수 파라미터
  (`startTime`·`endTime`) 부재로 실패하는 것이다.
- **취소 API 타임아웃을 최소 60초로 두라고 명세가 경고한다.** 취소 완료까지 시간이 걸린다는 뜻이고,
  "결과가 불확실한 건"이 어디서 오는지 알려주는 문장이다.

## 이번 실측에서 만들어 보지 못한 것 (명세에는 있다)

다음 사람이 이미 답이 있는 것을 다시 실측하지 않도록 적어 둔다. 취소 API 명세에 아래 결과 코드가
있으나 이번에 그 상황을 만들지 못했다.

- `CancelNotComplete` — "취소 처리가 완료되지 않았지만 자동 재처리 예정. **가맹점은 재시도 필요 없이
  취소 성공 상태로 변경**하면 된다"
- `PreCancelNotComplete` — 위와 지시가 정반대다. 이전에 요청한 취소 정보로 재시도하라고 한다
- `AlreadyOnGoing`, `AlreadyCanceled`("이미 **전체** 취소된 결제"), `CancelDeadlineExpired`

앞의 둘은 지시가 반대인데 이름이 비슷해 같은 실패로 묶기 쉽다. 재시도 안전성과 직결된다.

또 하나 확인 못 한 것: **환불이 동기적으로 완료되는가.** 응답을 받은 시점에 이미 이력에 반영돼 있었는지
따로 검증하지 않았다. 대사 설계에 직결된다.

## 필드 이름 대응표

재현할 사람이 그대로 쓸 수 있게 남긴다.

| 이 글에서 부르는 말 | 실제 |
| --- | --- |
| 환불 식별자를 싣는 자리 | 취소 요청 `merchantPayTransactionKey` (128바이트, 선택). 이력 항목에도 동명 필드 |
| 결제사가 발급한 이력 번호 | `payHistId` |
| 취소 유형 | `admissionTypeCode` — `01` 원결제 승인 / `03` 전체취소 / `04` 부분취소 |
| 이력 항목 상태 | `admissionState` — `SUCCESS` / `FAIL` |
| 예상 잔액 대조 | `doCompareRest=1` + `expectedRestAmount`, 거절 코드 `RestAmountDiff` |
| 멱등키 | 요청·응답 헤더 `X-NaverPay-Idempotency-Key` (64자 이내, 영문·숫자·밑줄·붙임표) |
| 결제창 시간 초과 | `TimeExpired` (예약 번호 생성 후 30분) |

## 미해결·열린 질문

**멱등키 보관 기간.** 명세에 숫자가 없고 **실험 설계 자체가 성립하지 않는다** — 며칠에 걸쳐 같은 키로
재전송하며 언제부터 새 요청으로 처리되는지 봐야 하는데, 개발 환경 데이터가 7일이면 사라지고 개발과
운영의 보관 정책이 같다는 보장도 없다.

그래서 이 값을 알아내려 하지 않고 **"언제든 만료됐을 수 있다"를 전제로 삼는 쪽**을 골랐다. 알 수 없는
값에 안전장치를 걸지 않는다는 판단이다.

**실패 상태 이력 항목이 언제 생기는가.** 파라미터 검증 실패는 안 남는 것을 확인했으나, 결제사 내부
처리까지 갔다가 실패하는 경우를 만들지 못했다. 그래서 "실패 항목만 있으면 완료로 보지 않는다"는
보수적 규칙을 유지했다.

**카드 결제에서도 같은가.** 위 관측은 전부 포인트 전액 결제다. 결제수단별로 금액 필드가 나뉘고 카드에는
취소 기한 제약이 따로 있어, 부분취소 동작이 같다고 볼 근거가 없다.

**개발 환경과 운영 환경의 동작이 같은가.** 다르다는 서술도 같다는 보장도 명세에 없다.
