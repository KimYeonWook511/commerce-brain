# 도메인 전용 스케줄러 풀을 만들면 프레임워크가 공용 풀을 더 이상 만들지 않는다

## 용어

이 문서를 읽는 데 필요한 도메인 어휘를 먼저 적는다.

- **대사(對査)** — 우리 기록과 결제사 기록을 맞춰 보는 일. 결제사를 부르는 도중 응답을 못 받으면 돈이 나갔는지 모르는 상태가 남는데, 주기적으로 결제사의 거래 이력을 읽어 그 상태를 확정한다. 승인 대사와 환불 대사가 따로 있다.
- **이력 조회** — 결제사에게 "이 결제에 무슨 일이 있었나"를 묻는 읽기 전용 호출. 대사가 결과를 확정하는 근거다. 다시 승인/취소를 요청하는 것이 아니라 읽기만 하므로 돈이 두 번 나가지 않는다.
- **아웃박스** — 다른 시스템에 보낼 이벤트를 DB에 먼저 적어 두고, 별도 주기 실행이 그것을 읽어 메시지 브로커로 내보내는 방식. 여기서는 주문 취소 시 재고를 되돌리는 이벤트가 그렇게 나간다.

## 결정한 것

### 배경 — 주기 실행 열 개가 스레드 하나를 나눠 쓰고 있었다

스프링에서 스케줄링만 켜고 스케줄러를 따로 설정하지 않으면 **기본 풀 크기가 1이다.** 이 저장소는 그 상태였고, 주기 실행 열 개가 그 하나를 공유했다.

```
결제 후처리 6   결제 대사 · 환불 대사 · 환불 발송 · 결제 통지 · 환불 통지 · 결제 만료
주문 만료   1   배치 런타임을 동기로 실행해 잡이 끝날 때까지 스레드를 붙든다
재고 복구   3   아웃박스 발행 · 재발행 · 멈춘 건 회수
```

이 중 **결제사를 부르는 것은 셋뿐이다** — 결제 대사, 환불 대사, 환불 발송. 통지 둘은 운영자 알림 채널로 나가고, 만료는 DB만 만진다.

문제는 그 셋의 대기 시간이 길다는 것이다. 대사는 한 주기에 최대 100건을 차례로 처리하며 건마다 결제사 응답을 기다린다(배치용 제한 시간 5초). 결제사가 느려지면 한 주기가 수 분으로 늘어나고, **한 줄로 이어져 있으니 그동안 재고 복구와 주문 만료는 순서가 오지 않는다.**

재고 복구가 밀리면 취소된 주문의 재고가 안 돌아와 팔 수 있는 물건을 못 판다. 주문 만료가 밀리면 결제 안 된 주문이 재고를 계속 물고 있는다. **결제사 장애가 결제 도메인 밖으로 번지는 구조다.**

실제 장애를 겪고 시작한 게 아니라, 결제 도메인을 재구성하는 PR의 코드 리뷰에서 이 구조가 지적돼 나온 작업이다.

### 풀 크기를 올리는 대신 풀을 나눴다 — 다만 이유를 정확히 적어 둔다

두 안이 있었다.

- **공용 풀 크기를 올린다** — 설정 한 줄. 가장 싸다.
- **결제 후처리 전용 풀을 따로 둔다** — 설정 클래스가 하나 는다.

전용 풀을 골랐는데, **처음에 세운 근거는 틀렸다.** "결제 후처리 여섯이 같은 결제사를 부르므로 크기를 6으로 올려도 여섯 칸이 전부 결제 대기로 찬다"고 적었는데, 실제로 결제사를 부르는 것은 셋이다. 크기를 6으로 올리면 세 칸은 결제사 대기, 나머지 세 칸은 다른 도메인이 쓸 수 있다. **즉 크기 증설로도 실질적으로는 해결된다.**

남는 진짜 이유는 이것이다.

**공용 풀 하나로 가면 그 크기가 "결제 배치가 몇 개인가"에 묶인다.** 배치를 하나 추가할 때마다 공용 풀 크기를 같이 올려야 하고, 안 올리면 조용히 다시 밀린다. 그리고 그 연결이 코드 어디에도 드러나지 않는다 — 누가 배치를 추가하면서 공용 풀 크기를 떠올릴 이유가 없다.

풀을 나누면 결제 쪽 숫자를 바꿔도 다른 도메인이 영향을 받지 않는다. **원리적 불가능이 아니라 유지보수의 문제이고, 그렇게 적어야 나중에 되돌리려는 사람이 판단할 수 있다.**

### 전용 풀 크기는 2로 잡았고, 근거가 약하다

결제사를 부르는 셋이 전부 1분 주기다. 크기 1보다는 확실히 낫지만, **셋이 동시에 대기하면 하나는 밀린다.** 3으로 잡지 않은 것은 동시에 부르면 병목이 결제사로 옮겨갈 뿐이고 결제사 쪽 동시 호출 허용치를 모르기 때문인데, 이 역시 확인된 값이 아니다.

**실측이 아니라 추정이다.** 결제사 실제 응답 시간과 한 주기 처리 건수를 함께 보고 다시 정해야 한다.

검토하지 않은 대안도 있다. 한 주기에 집는 건수(100)를 줄이거나 제한 시간을 낮추는 것, 결제사 호출을 별도 프로세스로 빼는 것은 이번에 논의하지 않았다.

## 막힌 점·해결

### 전용 풀 하나를 만들자 공용 풀이 사라졌다

전용 풀만 만들고 끝냈다면 **의도한 격리가 하나도 서지 않은 채 머지될 뻔했다.** 코드 리뷰가 잡아냈다.

스프링 부트의 자동 설정에 이런 조건이 걸려 있다.

```
스케줄러 자동 설정
  @ConditionalOnMissingBean({TaskScheduler.class, ScheduledExecutorService.class})
```

**그 타입의 빈이 하나라도 있으면 프레임워크가 기본 스케줄러를 만들지 않는다.** 전용 풀을 등록하는 순간 공용 풀이 사라진다.

그다음 무슨 일이 벌어지는가. 자기 풀을 지정하지 않은 주기 실행은 이 순서로 풀을 찾는다.

```
1. 타입으로 찾는다 — 유일하면 그것을 쓴다
2. 여러 개라 모호하면 → 기본 이름("taskScheduler")으로 고른다
3. 아무것도 없으면 → 단일 스레드 로컬 executor 를 스스로 만든다
```

전용 풀이 **유일한** 스케줄러가 되므로 1번에서 걸린다. 주문 만료와 재고 복구가 결제 전용 풀로 흘러들고, **갈라놓으려던 것이 도로 한 풀에 합쳐진다.** 기존보다 나빠지지는 않지만(크기 1 → 2), 이 작업이 하려던 일은 아무것도 이뤄지지 않는다.

같이 넣은 공용 풀 크기 설정(`spring.task.scheduling.pool.size`)도 무효가 된다. 그 값을 읽는 빈이 만들어지지 않기 때문이다. 이 키는 이번 변경에서 처음 추가한 것이라 그전에는 존재하지 않았다.

**가장 나쁜 점은 아무 증상이 없다는 것이다.** 기동도 되고 모든 배치가 돌고 테스트도 통과한다. 결제사가 느려지는 그 순간에만 드러난다.

### 해결 — 공용 풀도 우리가 명시적으로 만든다

프레임워크가 만들어 주던 것을 직접 만든다. 두 가지가 중요하다.

- **빈 이름을 기본값으로 둔다.** 위 탐색 순서의 2번이 이 이름을 쓴다. 이름이 어긋나면 풀이 여럿일 때 어느 것이 뽑힐지 정해지지 않는다. 문자열을 손으로 적지 않고 프레임워크가 노출한 상수를 참조했다.
- **프레임워크가 제공하는 빌더를 거친다.** 인스턴스를 직접 만들면 크기·스레드 이름 접두사 같은 설정값이 그 풀에 닿지 않는다. 빌더를 쓰면 설정이 그대로 적용되고, 전용 풀은 크기와 접두사만 덮어쓴다.

### 이 결함이 테스트에 안 잡힌 이유

전용 풀 설정 클래스에 "테스트 프로파일에서는 등록하지 않는다"는 조건을 붙였었다. 테스트에서 배치가 돌지 않으니 풀도 필요 없다고 본 것이다.

그런데 그 조건 때문에 **테스트 컨텍스트의 빈 구성이 운영과 달라졌고**, 빈 하나로 자동 설정이 물러나는 상황이 테스트에서 재현되지 않았다. 조건을 없애 풀은 뜨되 아무 배치도 돌지 않게 했다 — 주기 실행 메서드를 담은 클래스 쪽에만 프로파일 조건을 남기면 된다. 그러자 컨텍스트를 띄워 "두 풀이 다 있는지" 검사할 수 있게 됐다.

## 배운 것

### 조건부 자동 설정은 "내가 하나 만들면 프레임워크가 물러난다"

`@ConditionalOnMissingBean`류는 편리하지만 **조건이 타입 단위라 하나만 만들어도 기본값 제공이 통째로 멈춘다.** 여러 개가 공존해야 하는 자원(스케줄러 풀, 작업 실행기, 컨버터 등)에서 특히 위험하다. 하나를 커스터마이즈하려다 프레임워크가 주던 기본까지 잃는다.

**커스텀 빈을 등록하기 전에 그 타입의 자동 설정이 어떤 조건을 달고 있는지 먼저 읽는다.** 조건이 타입 단위면 기본값도 내가 명시적으로 만들어야 한다.

### 증상 없는 회귀는 동작을 돌려 보는 테스트로 못 잡는다 — 설정 자체를 검사한다

배치마다 어느 풀을 쓸지 애노테이션 속성으로 지정하는 방식이라(`@Scheduled`의 `scheduler` 속성, 스프링 프레임워크 6.1부터), 하나를 빠뜨리면 그 배치만 조용히 공용 풀로 돌아간다. 실행 결과는 똑같아서 어떤 기능 테스트로도 안 잡힌다.

그래서 **설정 자체를 읽는 검사**를 뒀다.

- 주기 실행 메서드 전부에 풀 지정이 있는가 — 리플렉션으로 애노테이션 속성을 훑는다.
- 공용 풀 빈이 컨텍스트에 존재하는가 — 그것이 사라지면 격리가 무효가 되는데 다른 방법으로는 드러나지 않는다.

**두 검사가 실제로 잡는지 일부러 깨뜨려 확인했다.** 한 배치에서 풀 지정을 빼고 돌려 실패하는 것, 공용 풀 설정 클래스를 지우고 돌려 실패하는 것을 각각 확인한 뒤 되돌렸다. 검사를 추가만 하고 작동을 확인하지 않으면 그 검사가 실은 아무것도 안 잡을 수 있다.

### 스레드 이름이 격리의 증거가 된다

전용 풀에 이름 접두사를 붙이면 로그에서 어느 도메인이 스레드를 쥐고 있는지 보인다. **격리가 서 있는지를 실행 로그만으로 확인할 수 있다.** 접두사가 섞여 찍히면 어딘가 지정을 빠뜨린 것이다.

무엇이 도는지는 로거 이름이 알려주므로 스레드 번호까지 볼 일은 없다.

### 문서에 적는 근거는 사실 확인을 거쳐야 한다

이 작업의 근거로 "결제 후처리 여섯이 모두 결제사를 부른다"를 적었는데 실제로는 셋이었다. **결정 자체는 뒤집히지 않았지만 근거 하나가 거짓이었고**, 그것이 코드 주석·PR 설명·결정 기록 세 곳에 그대로 들어갔다.

"이 중 몇 개가 그런가"처럼 세면 확인되는 것은 세어 보고 적는다. 그런 문장이 나중에 판단의 근거로 쓰인다.

## 미해결·열린 질문

- **풀 크기 2는 추정이다.** 결제사를 부르는 셋이 동시에 대기하면 하나는 밀린다. 결제사 실제 응답 시간과 한 주기 처리 건수(현재 100)를 함께 보고 다시 정해야 한다.
- **같은 풀 안의 배치끼리는 여전히 서로 민다.** 도메인 간 번짐만 끊었고 도메인 안은 그대로다.
- **종료 시 대기를 넣을지 정하지 않았다.** 배포로 프로세스가 죽을 때 결제사를 부르던 건은 결과를 모르는 상태로 남는다. 대기를 주면 줄지만 적정 시간이 한 주기 실행 시간에 달려 있어 미뤘다. 지금은 그렇게 남은 건을 다음 대사가 이력 조회로 회수한다.
- **인스턴스를 여럿으로 늘릴 때의 중복 실행.** 서버가 한 대라 아직 오지 않은 문제다. 겹쳐 돌더라도 대사가 건마다 낙관 락으로 대상을 선점해 진 쪽이 물러나므로 결제사를 두 번 부르지는 않는다. 다만 처리량이 늘지도 않는다 — 두 인스턴스가 같은 목록을 조회해 앞에서부터 부딪히기만 한다. 확장이 필요하면 대상을 미리 나누는 장치가 따로 있어야 한다.
