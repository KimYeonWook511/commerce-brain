# MDC 정리 책임을 스코프-오너십 2-규칙으로 전환 — memberId 필터 간 릴레이 제거

요청 로그 상관용 MDC(Mapped Diagnostic Context — 요청 스레드에 붙는 키·값 로그 컨텍스트)의 "누가 언제 지우나"를 정리한 세션이다. 문제의 뿌리는 `memberId`(인증된 사용자 식별자) 키가 요청당 두 번 넣기·두 번 빼기로 돌면서 필터끼리 결합해 있던 것 — 안쪽 인증 필터가 넣고 지운 뒤, 바깥 접근 로그 필터가 그 값을 request attribute로 릴레이받아 종료 로그 직전 다시 넣고 직후 다시 뺐다. 이걸 "스코프 경계가 정리 책임을 진다"는 2-규칙 모델로 바꿔, memberId는 넣기만 하고 요청 경계에서 통째 비워지게 했다. 이슈 #267 → PR #275.

## 배경 — 겹친 필터 3개와 갈라진 지점

요청 하나는 바깥→안쪽으로 겹친 서블릿 필터 3개를 통과한다. `TraceIdFilter`(최외곽, 요청 추적 ID `traceId` 발급) → `AccessLogFilter`(접근 로그 — 요청 종료줄에 status·latency 기록) → `JwtAuthenticationFilter`(인증, 최안쪽). 이 순서는 Spring `Ordered` 상수로 매기는데 **값이 작을수록 바깥(우선순위 높음)**이고, 실제 order 는 각각 `HIGHEST_PRECEDENCE + 10` / `+20` / `+30`이다.

여기서 어긋남이 생긴다. **memberId는 가장 안쪽 인증 필터에서만** 알 수 있는데, 그 값을 실어야 할 "요청 종료" 접근 로그는 **그 바깥 필터**에서, 인증 필터의 `finally`가 이미 memberId를 지운 *뒤에* 찍힌다. 값을 아는 지점(안쪽)과 로그를 찍는 지점(바깥)이 갈려서, 종료 로그에 memberId를 실으려면 릴레이가 필요했다 — 인증 필터가 `request.setAttribute(...)`로 값을 넘기고, 접근 로그 필터가 종료 로그 직전 그 값을 MDC에 재삽입했다가 직후 재제거했다. 그 결과 요청당 put/remove 가 각 2회이고, 필터 간 request attribute 결합이 생겼다.

관측 가능한 동작(접근 로그 종료줄에 memberId 실림 + 요청 끝나면 그 스레드에 MDC 잔류 0)은 이미 맞게 나오고 있었다. 이번 작업은 그 관측 결과는 그대로 유지한 채 **구조만** 단순화한다.

## 결정한 것 — 스코프 경계가 정리 책임을 진다 (2-규칙 모델)

검토한 대안은 셋이었다.

- **A. 접근 로그 필터가 memberId를 지운다** (원래 이슈에 적혀 있던 안): 인증 필터는 넣기만, 접근 로그 필터가 종료 로그를 찍은 뒤 "마지막 소비자"로서 지운다. → 접근 로그 필터가 인증 관심사(memberId 정리)를 떠안아 여전히 결합이 남는다. 기각.
- **B. 필터 순서를 뒤집어 인증 필터를 최외곽으로**: 인증 필터가 넣고 자기가 지운다(대칭). → 인증 실패(401)에서 인증 필터가 조기 반환하면, 그 안쪽이 된 접근 로그 필터를 건너뛰어 **401 요청의 접근 로그가 사라진다**. memberId 소비 시점도 어긋난다. 탈락.
- **C. 채택 — 스코프 경계 기준 2-규칙**:
  - **(a) 최외곽 요청 필터가 요청 끝(`finally`)에서 MDC 전체를 `clear()`로 비운다.**
  - **(b) 그보다 안쪽 nested 스코프는 자기가 넣은 키만 remove 한다.**
  - memberId 는 (a)에 얹는다 — 안쪽 인증 필터가 넣기(populate)만 하고, 최외곽의 `clear()`가 정리한다. 접근 로그 필터는 memberId 를 안 건드리는 순수 로거로 남는다.

**왜 C인가.** 최외곽 필터의 `finally`는 **안쪽 스코프가 전부 풀린 요청 종료 지점**이라, 그때의 `clear()`는 바깥에 살아남은 스코프가 없어 남의 키를 조기 삭제하지 않는다 — 오히려 스레드 풀 반납 전 잔류를 막는 최종 보루다. 반대로 안쪽/중첩 스코프에서 `clear()`를 부르면 아직 살아있는 **바깥** 스코프의 키(예: 유스케이스가 진입 시 넣은 `orderId`·`pgPaymentId`)를 날린다. 단일 동기 요청 스레드에서 MDC 스코프는 호출 스택을 따라 엄격히 중첩되기 때문이다. 그래서 정리 책임이 "최외곽 = 통째 `clear`, 중첩 = 자기 키만"으로 갈린다.

**방향이 뒤집힌 지점.** 처음엔 "`clear()`는 뭉툭하니 무조건 피하고 키별로 지우자"는 쪽으로 봤다 — 최외곽 필터에도 그런 방어 주석(*중첩 스코프에서 push 될 다른 키(userId·orderId 등)를 같이 날리는 위험 차단*)이 붙어 있었다. 그런데 그 위험이 **중첩 스코프에서만** 성립하고 최외곽에서는 성립하지 않는다는 걸 짚고 나니, 최외곽의 `clear()`가 오히려 더 단순하고 잔류 방지에 더 견고하다고 정리됐다. 그 방어 주석은 "최외곽 스레드 경계라 `clear()`로 스코프 전체를 정리한다"는 취지로 교체했다.

**규약 정합화도 함께.** 로깅 컨벤션 문서가 표면적으로 모순돼 보였다 — 핵심 원칙 요약은 "자신이 push 한 키만 remove, `MDC.clear()` 주의"라는데, MDC 절은 "요청 종료 시 반드시 `MDC.clear()` 호출"이라 했다. 이 둘은 **적용 스코프가 다른 두 규칙**인데 한 문서 안에서 상충처럼 읽혔다. 이번에 규약을 위 (a)/(b) 두 규칙으로 재서술해 정합화했다. 운영 코드에서 nested 스코프의 `clear()`는 금지하고, 테스트 격리용 `clear()`(스레드 로컬을 그냥 비우는 용도)만 허용으로 명시했다.

**코드 구조로 강제.** 공용 MDC 유틸(`LogContext`)에 `removeTraceId()`는 남겨두되 **`removeMemberId()`는 삭제했다**(대신 `MDC.clear()`를 감싼 `clear()` 추가). memberId 의 teardown 을 키별 remove 로 열어두지 않고 최외곽 `clear()`만 소유하도록 API 자체를 비운 것 — "populate 은 안쪽, teardown 은 스코프 소유자"가 서술이 아니라 코드 구조로 강제된다. 릴레이용 request attribute 상수와 그 사용처(인증 필터의 setAttribute, 접근 로그 필터의 재삽입·재제거)도 모두 제거했다. (`removeTraceId()`를 남긴 이유는 비동기 경계가 규칙 (b)로 계속 쓰기 때문 — 아래 참조.)

## 배운 것

- **MDC 정리 소유권은 "누가 넣었나"가 아니라 "스코프 경계가 어디냐"로 가른다.** 스레드 로컬 로그 컨텍스트가 필터·유스케이스로 겹겹이 쌓일 때, 최외곽(스레드의 요청 경계)만 통째 비우기(`clear()`)가 안전하고, 나머지 중첩 스코프는 자기 키만 빼야 남의 살아있는 컨텍스트를 안 깨뜨린다.
- **값을 아는 지점(안쪽)과 값을 소비·정리하는 지점(바깥)이 갈릴 때**, 억지로 대칭(넣은 쪽이 뺀다)을 고집하기보다 "populate 은 값을 아는 안쪽, teardown 은 스코프 소유자"로 나누는 게 구조가 깔끔하다. 대칭을 고집한 대안 B는 401 접근 로그 유실이라는 부작용을 낳았다.

## 미해결·열린 질문

- 이 모델은 **최외곽 필터가 MDC 를 만지는 가장 바깥으로 유지됨**을 전제한다. 최외곽 필터 order 가 `HIGHEST_PRECEDENCE + 10`이라 그보다 더 작은 값(`+0~+9`)에 MDC 키를 넣는 필터를 추가하면, 최외곽의 `clear()`가 그 키를 그 바깥 필터의 `finally` 전에 지워버린다. 그런 필터를 도입하려면 이 정리 모델을 먼저 재검토해야 한다. (이 전제는 ADR·규약에 남겼다.)
- 비동기 경계(Kafka/Outbox)의 traceId 정리는 이 2-규칙의 (b)(자기 키만 remove)와 정합한다 — 그쪽은 남의 스레드에 얹혀 돌기 때문이다. 비동기/이벤트 경계 traceId 를 명시적으로 실어 보내고 받는 쪽에서 복원하기로 한 기존 결정(PR #157)과 충돌 없음.
