# MDC 정리를 스코프-오너십 2-규칙 모델로 전환 (PR #275)

## 한 일

- 요청 로그 상관용 MDC(Mapped Diagnostic Context — 요청 스레드에 붙는 키·값 로그 컨텍스트) 정리 방식을 바꿨다. 핵심은 `memberId`(인증된 사용자 식별자) 키의 우회 구조를 없앤 것: 예전엔 안쪽 인증 필터가 넣고 지운 뒤, 바깥 접근 로그 필터가 request attribute로 릴레이받아 다시 넣고 지웠다 — 요청당 넣기·빼기가 각 두 번, 필터 간 결합까지 있는 구조.
- 관련 필터 3개가 바깥→안쪽으로 겹쳐 있다: `TraceIdFilter`(최외곽, 요청 추적 ID 발급) → `AccessLogFilter`(접근 로그) → `JwtAuthenticationFilter`(인증, 최안쪽). 관측 결과(접근 로그 종료줄에 memberId 실림 + 요청 끝나면 스레드에 MDC 잔류 0)는 유지하면서 구조만 단순화했다.
- 정본: 결정은 `docs/adr/20260710-pr275-mdc-cleanup-scope-ownership.md`, 코딩 규칙은 `docs/logging-conventions.md`. 이슈 #267 → PR #275.

## 결정한 것 — MDC 정리 소유권 모델

문제의 뿌리: memberId는 **가장 안쪽 인증 필터에서만** 알 수 있는데, 그 값을 실어야 할 "요청 종료" 접근 로그는 **바깥 필터**에서, 인증 필터가 끝난 *뒤에* 찍힌다. 값을 아는 지점(안쪽)과 로그를 찍는 지점(바깥)이 갈려서 릴레이가 필요했던 것.

검토한 대안:
- **A. 접근 로그 필터가 memberId를 지운다** (원래 이슈 안): 인증 필터는 넣기만, 접근 로그 필터가 로그 찍은 뒤 "마지막 소비자"로 지움. → 접근 로그 필터가 인증 관심사(memberId 정리)를 떠안아 결합이 생김.
- **B. 필터 순서를 뒤집어 인증 필터를 최외곽으로**: 인증 필터가 넣고 자기가 지움(대칭). → 인증 실패(401)에서 인증 필터가 조기 반환하면, 그 안쪽이 된 접근 로그 필터를 건너뛰어 401 요청의 접근 로그가 사라짐. 탈락.
- **C. 채택 — 2-규칙 모델**: **(a) 최외곽 필터가 요청 끝에서 MDC 전체를 `clear()`로 비우고, (b) 그보다 안쪽 스코프는 자기가 넣은 키만 지운다.** memberId는 (a)에 얹혀 — 안쪽 인증 필터가 넣기만(populate) 하고, 최외곽의 `clear()`가 정리. 접근 로그 필터는 memberId를 안 건드리는 순수 로거로 남음.

왜 C인가: 최외곽 필터의 finally는 **안쪽 스코프가 전부 풀린 요청 종료 지점**이라, 그때의 `clear()`는 바깥에 남은 스코프가 없어 남의 키를 조기 삭제하지 않는다. 반대로 안쪽/중첩 스코프에서 `clear()`를 부르면 아직 살아있는 **바깥** 스코프의 키(예: 유스케이스가 진입 시 넣은 `orderId`)를 날린다(단일 동기 요청 스레드에서 MDC 스코프는 호출 스택을 따라 엄격히 중첩된다). 그래서 "최외곽 = clear, 중첩 = 자기 키만"으로 갈린다.

처음엔 "`clear()`는 뭉툭하니 무조건 피하고 키별로 지우자"는 방향으로 봤는데(중첩 스코프의 도메인 키를 날릴까 봐 = 기존 코드의 방어 주석), 그 위험이 **중첩 스코프에서만** 성립하고 최외곽에서는 성립하지 않는다는 걸 짚고 나니, 최외곽 `clear()`가 오히려 더 단순하고 잔류 방지에 견고하다고 정리됐다.

코드 방증: 공용 MDC 유틸(`LogContext`)에 `removeTraceId()`는 있어도 **`removeMemberId()`는 두지 않았다**(이번에 삭제). memberId의 teardown을 키별 remove로 열어두지 않고 최외곽 `clear()`만 소유하도록 API 자체를 비운 것 — "populate은 안쪽, teardown은 스코프 소유자"가 서술이 아니라 코드 구조로 강제된다.

## 배운 것

- **MDC 정리 소유권은 "누가 넣었나"가 아니라 "스코프 경계가 어디냐"로 가른다.** 스레드 로컬 로그 컨텍스트가 필터·유스케이스로 겹겹이 쌓일 때, 최외곽(스레드의 요청 경계)만 통째 비우기(`clear()`)가 안전하고, 나머지는 자기 키만 빼야 남의 살아있는 컨텍스트를 안 깨뜨린다.
- 값을 아는 지점(안쪽)과 값을 소비·정리하는 지점(바깥)이 갈릴 때, 억지로 대칭(넣은 쪽이 뺀다)을 고집하기보다 "populate은 값을 아는 안쪽, teardown은 스코프 소유자"로 나누는 게 구조가 깔끔하다.

## 다음 단계 (지식 가치 있는 열린 항목)

- 이 모델은 **최외곽 필터가 MDC를 만지는 가장 바깥으로 유지됨**을 전제한다. 필터 순서는 Spring `Ordered` 상수로 매기는데 **값이 작을수록 바깥(우선순위 높음)**이고, 최외곽 필터 order가 `HIGHEST_PRECEDENCE + 10`이라 그보다 더 작은 값(`+0~+9`)에 MDC 키를 넣는 필터를 추가하면, 최외곽 `clear()`가 그 키를 그 바깥 필터의 finally 전에 지워버린다. 그런 필터를 도입하면 이 정리 모델을 먼저 재검토해야 한다.
- 비동기 경계(Kafka/Outbox)의 traceId 정리는 이 2-규칙의 (b)(자기 키만)와 정합한다 — 그쪽은 남의 스레드에 얹혀 돌기 때문. 기존 비동기 traceId 전파 결정(PR#157)과 충돌 없음.
