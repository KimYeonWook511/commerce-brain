# 결제 status는 "일어난 사실"만 담고, 후처리 분류는 정책이 계산 — MANUAL_REVIEW 새 상태 철회

PR #237(UNKNOWN 결제 대사 루프 + 주문 만료 타이밍 가드)에서 결제 상태 모델을 정한 세션이다. 대사(reconciliation) 종착과 보상 종착을 표현하려고 `PaymentStatus`에 `MANUAL_REVIEW`(자동 처리 포기·운영자 확인) 새 상태를 넣었다가, 이미 내려져 있던 반대 방향 결정을 뒤늦게 발견하고 철회한 과정이 핵심이다. 결론은 "status는 사실만, 분류는 정책이 매번 계산"으로 수렴했다. 같은 PR의 결제-주문 결합 제거 방향과 코드 리뷰에서 나온 버그는 각각 별도 세션으로 남겼다.

## 결정한 것

### status는 "결제에 일어난 사실"만, 후처리 대상 분류는 정책이 계산

`PaymentStatus`는 결제에 실제로 일어난 사실만 담는다 — 요청(REQUESTED)·성공(SUCCEEDED)·실패(FAILED)·미상(UNKNOWN) 네 값뿐이다. "이 결제가 후처리 대상이냐, 어떤 대상이냐"(자동 대사 / 보상 / 수동 확인 / 없음)는 status에 박지 않고, 정책이 `(status + 실패코드 + 경과 시간 + 연계된 취소 행)` 조합으로 매번 계산한다.

- **핵심 원칙:** 분류 결과를 status에 박으면 "일어난 사실"과 "그로부터 파생된 판단"이 한 값에 섞여 상태의 의미가 흐려진다. status는 사실 축에 고정하고, 파생 분류는 정책 계산으로 분리해 둔다.
- **철회한 것 = 상태이지 정책 분류값이 아니다.** 이 세션에서 넣었다가 뺀 건 `PaymentStatus.MANUAL_REVIEW`라는 *상태값*이다. 정책이 후처리 대상을 가릴 때 쓰는 분류값(자동 대사 / 취소 대사 / 보상 / 수동 확인 / 없음) 중 "수동 확인"은 그대로 살아 있다 — 그건 status가 아니라 정책이 계산해 내놓는 결과값이라 사실/파생 혼선을 일으키지 않는다. 승격을 막은 대상은 정확히 "이 분류를 status enum으로 올리는 것"이다.

### MANUAL_REVIEW 새 상태 도입은 기각

처음엔 자동 처리를 포기한 건과 보상 종착을 상태로 드러내려고 `MANUAL_REVIEW`를 도입했다. 사용자가 "보상된 승인 결제 상태를 어떻게 표현할지는 이미 정한 결정이 있다"고 짚어줘서 그 결정을 다시 읽고 철회했다.

- **이미 있던 반대 방향 결정:** PG가 승인(과금)했으나 우리가 중복·금액불일치로 거부하고 보상(환불)한 승인 결제는, "과금됐지만 보상 대상"이라는 새 상태로 표현하지 않는다. 대신 기존대로 `FAILED` + 실패코드(중복결제 / 금액불일치) + 같은 PG결제ID를 가진 취소(CANCEL) 행으로 표현한다. 새 상태를 도입하자는 안은 그때 이미 기각돼 있었다.
- **기각 근거 1 — 무손실 복원:** "과금 후 보상" 여부는 `실패코드 ∈ {중복결제, 금액불일치}` + 같은 PG결제ID의 취소 행 존재로 결정적으로 되살릴 수 있다. FAILED가 표현상 부정확할 뿐(과금된 거부 건을 실패로 표기) 데이터를 잃지는 않는다.
- **기각 근거 2 — YAGNI:** "clean fail vs 과금 후 보상"을 구분해 실제로 소비하는 기능(정산 대조 / 분쟁 자동화 / 운영 대시보드)이 아직 없다. 소비처 없는 상태를 미리 만드는 건 가정된 미래 요구를 위한 부채다. 새 상태 도입은 그 구분을 실제로 쓰는 기능이 생길 때 정당화된다.
- **되돌리기 쉬움:** 새 상태를 나중에 추가하는 비용이 지금 추가하는 비용과 거의 같고(enum 값 추가 + 소비처 재검토), 과거 데이터도 `FAILED ∧ 실패코드 조건` 일괄 UPDATE로 결정적 backfill이 가능하다. 미뤄도 이자가 붙지 않는 결정이라 미루는 쪽이 안전하다.

### escalation은 새 상태 대신 스캔 시간 윈도우로 처리

PG가 정해진 시간을 넘도록 결론(승인/거부)을 못 내는 건(escalation)도 `MANUAL_REVIEW` 같은 새 상태로 표현하지 않는다. 자동 대사 스캔 쿼리를 시간 윈도우로 제한해, 상한을 넘긴 미확정 건을 자동 대사 대상에서 자연히 빼는 방식으로 처리한다.

- **윈도우:** 하한은 진입 지연(UNKNOWN은 약 1분, REQUESTED는 약 15분 — 승인 가능 시간 10분 + 마진 5분), 상한은 escalation 기준인 약 6시간. 이 값들은 정책 상수로 확정했다(운영 config화는 추후).
- **"자동 대사 대상이냐"를 status가 아니라 시간 윈도우가 정의한다.** 상한을 넘긴 건은 스캔에서 빠지고 상태는 그대로 `UNKNOWN`/`REQUESTED`로 남는다. 상태 enum을 늘리지 않고도 "더 이상 자동으로 손대지 않는다"를 표현한다.
- **하한을 둔 이유:** 하한을 UNKNOWN/REQUESTED 공통으로 두면 진입 지연이 긴 REQUESTED가 정렬 앞단을 차지해 뒤 후보가 고사(starvation)한다. 그래서 하한을 상태별로 갈라 대사 임계 정책과 일치시켰다. (스캔 하한 수치의 확정 경위는 같은 PR의 대사 리뷰 발견 세션에 남겼다.)
- **후속:** 6시간 상한을 넘긴 건의 운영 종착·통지(사람이 봐야 할 것으로 surface)는 이번 범위 밖이라 후속 이슈(#238)로 미뤘다. 이번엔 "자동 재시도를 멈춘다"까지만 하고, "운영자에게 알린다"는 나중.

## 막힌 점·해결

같은 문제(보상된 승인 결제를 어떻게 표현할지)를 이미 내려진 결정과 정반대 방향으로 다시 풀었다. 이 PR의 task 문서만 보고, 그 위 층에서 최신 결정들이 번호순으로 누적되던 루트 ADR 로그를 안 봤기 때문이다. 거기에 "보상된 승인은 새 상태 대신 FAILED + 실패코드 + 취소 행"이라는 결정이 이미 있었는데, 그걸 못 보고 `MANUAL_REVIEW`라는 새 상태를 도입하는 정반대 선택을 했다.

- **해결:** 사용자가 그 결정을 짚어줘서 다시 읽고 `MANUAL_REVIEW` 도입을 철회, 기존 방향(FAILED + 파생 복원)으로 되돌렸다.
- **교훈으로 굳힌 것:** 상태·도메인 정책을 바꾸려 할 땐 탐색 단계에서 task 범위 문서에 갇히지 말고, 최신 결정이 쌓이는 루트 ADR 로그를 변경 키워드로 먼저 grep해서 "이미 반대 결정이 있나"를 확인해야 한다.

## 배운 것

- **"상태"와 "그 상태로부터의 분류"를 한 enum에 섞지 마라.** status는 일어난 사실 축에만 고정하고, "후처리 대상이냐 / 어떤 대상이냐" 같은 파생 판단은 정책이 사실 + 실패코드 + 시간 + 연계 행으로 계산하게 둔다. 파생을 상태값으로 승격하는 순간 사실과 판단이 뒤섞여 상태의 의미가 무너진다.
- **소비처 없는 상태값은 만들지 마라.** 새 상태의 정당화는 "그 구분을 실제로 읽어 쓰는 기능"이 생길 때다. 되돌리기 쉽고 backfill이 결정적인 결정이라면, 미루는 쪽이 부채가 적다.
- **직교하는 두 축을 한 값에 뭉개면 애매함이 생긴다.** 여기서 `MANUAL_REVIEW`의 애매함은 "결론이 났나(확정 vs 미상)"와 "과금됐나 / 보상됐나"라는 서로 직교하는 두 축을 한 상태값에 섞은 데서 나왔다. 분해한다면 status는 결론 축만 담고, 보상 여부는 별도 필드나 취소 행으로 직교하게 표현하는 게 맞다.

## 미해결·열린 질문

- **결론 축 / 과금·보상 축의 명시적 직교 분해는 아직 안 했다.** 지금은 "과금 후 보상"을 FAILED + 실패코드 + 취소 행으로 복원하는 데 그친다. status(결론 축)와 보상(별도 필드/취소 행)을 명시적으로 직교 분해하는 건, 그 구분을 실제로 소비하는 기능이 생길 때 재검토한다.
- **escalation 상한 초과 건의 운영 가시성**(통지·조회 종착)은 후속 #238로 미뤘다. 지금은 자동 대사에서 빠지고 UNKNOWN/REQUESTED로 남을 뿐, 사람이 봐야 할 것으로 드러나지는 않는다.
- 새 상태(정산 대조 / 분쟁 자동화 / 운영 대시보드가 요구할 때)를 도입할지는 그 소비 기능이 생기는 시점의 재검토 trigger로 남겨 둔다.
