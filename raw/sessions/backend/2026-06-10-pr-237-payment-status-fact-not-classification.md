## 맥락
- PR #237(UNKNOWN 결제 대사 + 만료 타이밍 가드) 중 상태 모델 결정. 같은 PR의 결제-주문 결합 제거 방향, 코드 리뷰 버그 발견은 각각 별도 메모.

## 결정 — status는 "사실"만, 후처리 분류는 정책이 계산
- 정본: commerce-backend/docs/adr.md "보상된 APPROVE(승인) 결제 상태 결정". 보상(환불)된 승인은 새 상태가 아니라 FAILED + 실패코드 + 같은 PG결제ID의 취소 행으로 표현. "과금됐는데 보상대상" 새 상태는 기각 — 실패코드+취소행으로 무손실 복원되고, 쓰는 곳 없는 상태를 미리 만들지 않는다(YAGNI).
- 나는 이 결정을 안 보고 PaymentStatus에 MANUAL_REVIEW(자동 처리 포기·운영자 확인) 새 상태를 도입했다가, 사용자가 ADR을 짚어줘서 철회.
- 핵심: status는 결제에 일어난 사실(요청/성공/실패/미상)만 담는다. "후처리 대상이냐, 어떤 대상이냐"(자동 대사 / 보상 / 수동 / 없음)는 정책이 (status + 실패코드 + 경과시간 + 연계 취소행) 조합으로 매번 계산한다. 분류 결과를 status에 박으면 사실과 파생이 섞여 의미가 흐려진다.
- 새 상태 정당화 = 그 구분을 실제 소비하는 기능(정산 대조 / 분쟁 자동화 / 운영 대시보드)이 생길 때. 미리 만들면 부채.
- escalation(PG가 정해진 시간 넘게 결론 못 냄)도 새 상태 대신 스캔 시간 윈도우(하한~6시간 상한)로 자동 대사 제외. "자동 대상이냐"를 status가 아니라 시간 윈도우가 정의. 6시간 초과 운영 종착·통지는 후속(#238). (스캔 하한 수치는 같은 PR의 리뷰 발견 메모 참조)
- 두 직교 축: "결론 났나(확정 vs 미상)"와 "과금됐나/보상됐나". MANUAL_REVIEW 애매함은 이 둘을 한 값에 섞은 것. 분리한다면 status는 결론 축, 보상은 별도 필드/취소행으로 직교 분해.

## 막힌 점 — 왜 놓쳤나
- task 문서만 보고 루트 docs/adr.md의 최신 결정을 안 봐서 같은 문제에 정반대로 갔다. 상태/도메인 정책 변경은 탐색 단계에서 루트 ADR(최신·높은 번호)을 변경 키워드로 먼저 grep해야 했다.
