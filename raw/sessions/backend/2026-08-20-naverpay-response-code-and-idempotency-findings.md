# 네이버페이 응답 코드와 멱등성을 실제 sandbox로 재본 결과

## 이 글을 읽는 데 필요한 어휘

- **네 갈래** — 결제사가 보내는 응답 문자열(`Success`·`AlreadyComplete` 같은 것)을 우리는 네 가지 중 하나로 판정한다. **성공 / 결과 모름 / 다시 시도할 수 있는 실패 / 종착 실패**(더 해 볼 것이 없어 끝난 것). 이 판정을 이 글에서는 "접는다"고 쓴다.
- **매핑표** — 응답 문자열을 네 갈래 중 하나로 옮기는 표. 결제사마다 하나씩 있다.
- **대사(對査)** — 결제사가 가진 기록과 우리 결제 기록을 주기적으로 맞춰 보고 어긋난 건을 정리하는 배치. 결과를 모르는 결제·환불이 여기서 확정된다.
- **이력 조회** — 한 결제에 무슨 일이 있었는지(원결제·취소가 각각 언제 얼마) 결제사에 물어보는 API. 대사가 판정의 근거로 삼는 것이 이 응답이다.
- **잔액환불** — 이미 일부를 환불한 결제에서 **남은 금액 전부**를 마저 환불하는 것.

우리 매핑표는 **연동 명세서를 읽고 만든 것이며 실제 응답으로 확인된 적이 없었다.** 다른 테스트는 결제사를 흉내 낸 응답을 쓴다. 명세를 잘못 읽었으면 그 흉내도 똑같이 틀린 채로 만들어지고, 테스트는 통과하는데 운영에서 깨진다.

그래서 결제사 sandbox에 실제로 결제를 만들어 승인 → 부분환불 → 잔액환불 → 이력 조회를 태우고 응답을 눈으로 확인했다.

## 결정한 것

**흉내 응답만으로는 매핑을 검증할 수 없다고 보고, 실제 호출로 확인하는 자리를 만들기로 했다.** 대안은 명세서를 더 꼼꼼히 읽는 것이었는데, 그건 같은 사람이 같은 문서를 다시 읽는 것이라 처음 잘못 읽은 대목을 또 잘못 읽는다.

매핑이 틀리면 돈이 잘못 움직인다. 다시 시도할 수 있는 실패를 종착으로 읽으면 환불이 불필요하게 사람 손으로 넘어가고, 반대로 읽으면 같은 취소가 두 번 나가며, 결과를 모르는 것을 실패로 읽으면 회원이 다시 결제해 돈이 두 번 나간다.

**매핑이 실제와 다른 것이 발견되면 그 자체를 성과로 삼고, 수정은 별도 이슈로 나누기로 했다.** 발견과 수정을 한 변경에 섞으면 무엇이 확인된 사실이고 무엇이 그에 대한 대응인지 흐려진다.

## 검증 결과 총평

**매핑표는 대체로 맞았다.** 실제 응답과 어긋난 것은 두 건이고, 둘 다 판정이 틀린 것이 아니라 설명이 부족하거나 근거가 잘못 적혀 있던 경우다.

1. 이력 조회의 "유효하지 않은 결제번호" 응답이 매핑표에 없다 — 표에 없는 코드는 결과 모름으로 접히는데, 그 결과 모름이 곧 "다음 주기에 다시 읽는다"라 **동작은 옳다.** 로그에 "모르는 응답 코드"로 찍혀 원인을 못 본다는 것만 문제다. 별도 이슈로 등록했다(우선순위 낮음).
2. 승인 멱등키를 만드는 코드의 설명이 "같은 키로 다시 부르면 결제사가 이전 응답을 되돌려준다"를 근거로 들고 있었는데, 승인 API는 그렇게 동작하지 않는다(아래 참고). 설계 자체는 그 근거에 기대고 있지 않았고 설명만 사실과 달랐다. 그 문장을 고쳤다.

## 실측으로 확인한 매핑

직접 호출해 응답을 눈으로 본 것만 적는다.

| API | 응답 문자열 | 실제 의미 | 우리 판정 | 어떻게 재현했나 |
|---|---|---|---|---|
| 승인 | `Success` | 승인됨 | 성공 | 인증을 갓 마친 결제에 승인 |
| 승인 | `AlreadyComplete` | 이미 승인이 끝남 | 결과 모름 | 승인이 끝난 결제에 승인을 다시 |
| 승인 | `AlreadyOnGoing` | 앞선 시도가 정리 중 | 결과 모름 | 실패 응답을 받은 직후 1~2분 안에 다시 |
| 승인 | `TimeExpired` | 승인 가능 시간 지남 | 종착 실패 (+ 승인 창이 닫혔다는 표시) | 인증 후 10분을 넘긴 결제에 승인 |
| 승인 | `Fail` | 이번 호출이 실패 | 종착 실패 | 결제수단 쪽 오류(잔액 부족으로 자동 충전 시도 후 실패) |
| 취소 | `Success` | 취소됨 | 성공 | 승인된 결제에 부분·전액 취소 |
| 취소 | `InvalidPaymentId` | 없는 결제번호 | 종착 실패 (+ 사람이 조사할 근거) | 형식이 다른 가짜 결제번호로 취소 |
| 이력 조회 | `Success` | 조회됨 | 성공 | 승인된 결제의 이력 조회 |
| 이력 조회 | `InvalidPaymentId` | 없는 결제번호 | (표에 없음 → 결과 모름) | 승인 전 결제번호로 이력 조회 |
| 이력 조회 | (HTTP 401, 본문 코드 없음) | 자격증명 거절 | 다시 시도할 수 있는 실패 | 틀린 비밀키로 이력 조회 |

이력 항목의 종류 코드는 `01`(원결제)·`03`(전체취소)·`04`(부분취소) 셋을 다 봤다. 연동 문서에도 이 셋만 나오고 `02`는 등장하지 않는다.

**아래 둘은 연동 문서에서 읽었을 뿐 실측하지 못했다.** 그런데 테스트 설계에는 영향이 컸다.

- `PreCancelNotComplete` — 앞선 취소가 아직 처리되지 않아 다음 취소를 받지 않는다. 우리는 다시 시도할 수 있는 실패로 접는다. 문서가 "이전에 요청했던 취소 정보로 재시도해야 이전 취소가 완료되고 다음 취소를 수행할 수 있다"고 지시한다.
- `CancelNotComplete` — 취소 처리가 끝나지 않았지만 결제사가 곧 자동으로 재처리한다. 문서가 "가맹점은 재시도 필요 없이 취소 성공 상태로 변경하면 된다"고 지시해서 **성공으로 접는다.** 즉 성공 응답을 받아도 이력에는 아직 없을 수 있다.

## 배운 것

### 멱등키는 결과를 알아내는 수단이 아니다 (가장 크게 배운 것)

결제사 멱등성의 약속은 "같은 키로 다시 보내면 이전 응답을 그대로 돌려준다"이다. 응답을 못 받았을 때(타임아웃 등) 안전하게 다시 물어볼 수 있게 하는 장치다.

**실측 결과 이 약속이 API마다 다르게 지켜진다.**

```
승인 API   같은 키로 1초 뒤 다시 보냄 → HTTP 200 + 결제번호의 현재 상태
                                        이전 응답이 아니다
취소 API   같은 키로 1초 뒤 다시 보냄 → HTTP 409 + 이전 응답 본문 그대로
                                        거래 번호·처리 시각까지 동일. 문서가 약속한 그대로
```

같은 결제사인데 승인은 재생하지 않고 취소는 재생한다. 연동 문서에는 두 API 모두 멱등성 지원 대상이라 적혀 있고 재생 방식도 하나로만 설명돼 있다.

**응답 헤더가 단서를 준다.** 요청에 실은 멱등키를 응답 헤더에 되돌려 주는데, 그 헤더의 유무가 이렇게 갈렸다.

```
처음 쓰는 (멱등키, 결제번호) 조합        헤더가 붙는다
1초 뒤 같은 조합으로 다시                 헤더가 사라진다
3시간 44분 뒤 같은 조합으로 다시           헤더가 다시 붙는다   ← 조합 기록 자체가 사라진 것으로 보인다
멱등키는 재사용하되 결제번호를 바꿈        헤더가 붙는다        ← 조합 단위로 기록한다는 뜻
```

즉 결제사는 `(멱등키, 결제번호)` 조합을 **기록은 하되 승인에서는 재생하지 않는다.** 그리고 그 기록이 **몇 시간 뒤에는 사라진다** — 정확한 기간은 재지 않았다.

여기서 나오는 교훈이 셋이다.

- **결과를 알아내는 정본은 이력 조회여야 한다.** 멱등 재생은 결제사가 정하고 기록에 기간이 있어 시간이 지나면 깨진다. 며칠에 걸쳐 도는 대사가 그것에 기대면 안 된다.
- **이중 실행을 실제로 막는 것은 멱등키가 아니라 결제사의 상태 판정일 수 있다.** 승인은 "이미 진행 중"·"이미 완료" 응답으로 겹치는 요청을 거절한다. 우리 대사 코드는 이미 그쪽에 기대고 있었고, 멱등 재생을 근거로 든 설명만 사실과 달랐다.
- **환불처럼 돈이 빠지는 호출은 재생 여부를 반드시 재봐야 한다.** 우리 환불 재전송은 멱등키를 `(환불 건 + 시도 번호)`로 만드는데, 재전송할 때 시도 번호를 올리지 않아 **같은 키가 다시 나간다.** 그 근거가 "이미 나갔으면 이전 응답이 되돌아와 그대로 확정된다"였다. 취소 API가 실제로 재생하는 것을 확인해서야 그 근거가 섰다. 재생이 없었다면 같은 취소가 두 번 실행돼 돈이 두 배로 빠졌을 자리다.

**멱등키를 다른 결제번호에 붙여도 그 결제번호의 현재 상태로 답한다.** 다른 결제의 저장된 답을 끌어오지 않는다 — 만약 끌어왔다면 그것대로 심각한 문제였을 것이다.

### 전액을 환불해도 나누면 "부분취소"로만 기록된다

같은 10,000원을 전액 환불해도 **나누는지에 따라 이력 기록이 갈린다.**

```
한 번에 10,000 취소        →  03(전체취소) 한 건
3,000 + 7,000 으로 취소    →  04(부분취소) 두 건.  03 은 하나도 없다
```

전체취소만 보고 환불을 찾는 구현이었다면 **나눠 환불한 결제의 환불을 통째로 못 본다.** 부분환불을 도입하면 그런 결제가 흔해진다.

### 실패 응답이 성공 상태 코드로 오고 빈 목록을 함께 싣는다

이력 조회가 거절될 때 이렇게 온다.

```
HTTP 200
{ "code": "InvalidPaymentId",
  "message": "유효하지 않은 네이버페이 결제번호입니다.",
  "body": { "list": [], "totalCount": 0 } }
```

본문의 결과 코드를 안 보고 목록만 읽었다면 "이력에 아무것도 없다"로 읽었을 것이다. 그러면 돈이 나간 건을 없던 것으로 확정한다. **"조회가 거절된 것"과 "이력이 비어 있는 것"을 반드시 가른다는 설계 덕분에 이 응답에 속지 않았다.**

승인 실패도 마찬가지로 HTTP 200에 실려 온다. 상태 코드만으로 성패를 가를 수 없다.

### 승인 실패의 세 답이 서로 다른 뜻이다

한 결제를 시간순으로 따라가 보니 답이 이렇게 바뀌었다.

```
Fail             이번 호출이 실패했다. 결제번호는 아직 살아 있어 다시 승인할 수 있다
AlreadyOnGoing   앞선 시도가 결제사 안에서 정리되는 중이다 (1~2분)
TimeExpired      승인 가능 시간(10분)이 지났다. 이제 진짜 끝이다
```

**결제사 응답 코드 목록에 "이미 실패함"이라는 값이 없다.** "이미 진행 중"과 "이미 완료"는 있는데 실패는 없다. 승인 실패는 **머무는 상태가 아니라 사건**이기 때문이다 — 한 번 실패해도 시간 안에는 다시 시도할 수 있고, 결제번호가 죽는 것은 승인이 완료될 때와 시간이 지날 때뿐이다.

그래서 "이번 호출이 실패했다"를 "그 결제가 끝났다"로 읽으면 안 된다. 실제로 실패 응답을 받은 직후에도 결제사는 그 건을 진행 중으로 보고 있었다.

### 승인 완료 응답에는 금액이 없다

이미 승인된 결제에 승인을 다시 걸면 "이미 결제가 완료되었습니다"가 오는데 **응답 본문이 통째로 없다.** 금액도 거래 번호도 주지 않는다. 그 결제가 얼마짜리였는지는 이력을 읽어야 안다.

그리고 **전액 환불된 뒤에도 "이미 완료"라고 답한다.** 환불 여부를 보지 않고 승인이 한 번 났다는 사실만 본다. 지금 얼마가 남았는지는 역시 이력을 읽어야 한다.

### 시간 제한이 두 개다

```
결제 예약(결제창)   생성 후 30분 — 회원이 결제창에서 인증을 마쳐야 하는 시간
결제 승인          인증 후 10분 — 가맹점이 승인을 보내야 하는 시간
```

둘을 헷갈리면 "결제 시간이 초과되었습니다"가 어느 쪽인지 못 가린다.

## 막힌 점·해결

**sandbox 결제를 만들 방법이 우리 코드에 없었다.** 결제 예약 API를 서버가 부르지 않고, 결제 시작 응답으로 결제사 SDK에 넘길 값들을 클라이언트에 내려주는 구조다. SDK가 내부에서 예약과 결제창 열기를 대신한다. 그런데 프런트에 아직 그 SDK 연동이 없어서 결제창을 여는 경로가 어디에도 없었다.

→ 연동 문서의 **SDK 미사용 방식**으로 우회했다. 서버에서 결제 예약 API를 직접 호출해 예약 번호를 받고, 결제 페이지 주소에 그 번호를 붙여 브라우저로 열어 사람이 인증한다. 인증이 끝나면 콜백 주소로 결제번호가 실려 온다 — 앱이 안 떠 있어도 브라우저 주소창에서 읽을 수 있다.

**테스트용 결제번호가 하나도 없었고 이력 조회 주소도 비어 있었다.** 이 작업을 연 이슈(#314)에는 그것들이 준비돼 있다고 적혀 있었지만 실제로는 셋 다 빈 값이었고, 이력 조회 주소는 로컬·운영·sandbox 세 환경 설정 파일 모두 비어 있었다. **그 상태로는 대사 배치가 이력을 부를 주소 자체가 없다.** 결제번호는 회원이 결제창 인증을 마쳐야 발급되므로 코드로 만들 수 없다.

**포인트/머니로 결제하면 잔액이 모자랄 때 자동 충전을 시도하고, 그 충전이 실패하면 승인이 거절된다.** 처음 두 번의 결제가 이것으로 날아갔다. 잔액이 충분하면 충전을 안 하므로 그대로 결제된다. 카드는 충전 개념이 없어 이 문제를 안 만난다.

## 미해결·열린 질문

- **승인 응답 코드 11개 중 6개는 재현하지 못했다** — 가맹점 설정 오류, 서비스 점검, 원천사 시스템 점검, 충전 계좌 점검, 본인 카드 인증 실패, 충전 계좌 잔고 부족. 전부 그 상황을 만들어야 확인할 수 있다.
- **취소 응답 코드도 두 개만 실측했다.** 특히 앞선 취소가 처리 중일 때와 자동 재처리 예정일 때의 응답은 문서로만 안다.
- **멱등 기록의 유효 기간을 재지 않았다.** 승인에서 3시간 44분 뒤에는 조합 기록이 사라진 것으로 보이지만 정확한 경계는 모른다. 취소의 재생이 언제까지 유지되는지도 모른다.
- **운영 서버가 sandbox와 같게 동작하는지 모른다.** 연동 문서는 중복 요청에 충돌 상태 코드와 함께 이전 응답을 준다고 약속한다. 승인에서 그렇지 않은 것이 sandbox 한정인지 아닌지 확인할 방법이 없다. 그래서 **충돌 상태 코드로 이전 응답이 실려 오면 그 본문으로 결과를 정하는 분기를 코드에 그대로 남겨 두기로 했다** — 운영에서 그 경로가 살아날 수 있고, 지웠다가 다시 필요해지면 곤란하다.
