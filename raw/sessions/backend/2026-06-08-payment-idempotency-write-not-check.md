# 결제 멱등은 "확인 후 생성"이 아니라 "INSERT 시도 + unique 위반 시 기존 반환" — succeed() 선점은 성공의 의미를 뒤집어 금지

"PG 결과를 받아 우리 서버에 반영하는" 지금 방향 대신, 반대로 "우리 서버에서 먼저 중복 방지용으로 `payment.succeed()`(성공 기록)를 찍고 통과하면 그때 PG에 승인 요청을 보내면 안 되나, 더 안 좋나?"라는 질문에서 출발했다. 이 선점 발상을 따져보다 "멱등을 무엇으로 보장하는가"라는 패턴 전체를 정리한 논의 세션이다. 특정 PR로 굳힌 결정이라기보다, 결제 승인·예약 경로가 공유하는 멱등 원칙을 세운 자리다.

## 결정한 것

### 1. `succeed()` 선점은 금지 — 성공의 의미를 뒤집는다

`payment.succeed()`는 결제를 SUCCEEDED로 확정 기록하는 도메인 메서드다(우리 코드에서 `Payment.succeed()`는 PG 승인 응답을 받은 *뒤에* 호출된다). 이걸 PG 호출 *전에* 먼저 찍어 중복을 막자는 게 선점 제안인데, 기각했다.

- **핵심 문제:** `succeed()`는 "성공했다"는 사실 기록인데, PG에 물어보기도 전에 성공으로 단정하게 된다. 순서가 진실을 앞지른다.
- PG가 실패를 주면? 이미 SUCCEEDED + 주문 PAID로 적어버렸으니 되돌려야 한다.
- PG가 타임아웃이면? 거짓 성공이 박제된다 — 돈은 안 빠졌는데 결제 완료로 처리되니 매출 손실이고, 어떤 의미론 이중결제보다 더 나쁘다.
- **결론:** 결제는 외부(PG)가 진실의 원천이다. `succeed()`는 PG가 성공을 확인해준 뒤에 기록하는 것이지, 요청을 보내기 위한 선결 조건이 아니다.
- **선점 자체는 정당하다 — 단 무엇을 선점하느냐가 다르다.** "처리 중"을 뜻하는 REQUESTED 상태 선점은 이미 하고 있고 정당하다. 선점할 거면 SUCCEEDED가 아니라 REQUESTED를 선점해야 한다(= 진입에서 REQUESTED 행을 먼저 만들어 두는 것).

### 2. "확인 후 생성"은 동시성에 뚫린다 (MVCC 스냅샷)

```
T1: findByKey → 없음
T2: findByKey → 없음   (T1 미커밋 + REPEATABLE READ 스냅샷이라 T1의 INSERT 안 보임)
T1: save 성공 / T2: save 성공  → 둘 다 "없음"을 봐서 둘 다 생성
```

- SELECT는 MVCC 스냅샷이라 서로의 미커밋 INSERT를 못 본다. 그래서 "SELECT로 확인하고 없으면 INSERT"는 race에 뚫린다.
- 반면 write(INSERT)는 스냅샷이 아니라 현재 커밋 상태와 충돌한다 → unique 제약이 "이미 있음"을 정확히 잡아준다. 멱등의 진짜 보장은 여기에 있다.

### 3. 멱등 getOrCreate의 정석 — find는 1차 필터, 최종 보장은 unique

```java
// find-first + INSERT 폴백 + 위반 안전망
public Payment getOrCreate(String key, ...) {
    return repo.findByKey(key)                 // 1. 흔한 경우(이미 있음) 빠르게 흡수
        .orElseGet(() -> insertOrReread(key)); // 2. 없으면 생성, 3. race면 기존 반환
}
```

- find는 흔한 시간차 중복을 값싸게 흡수하는 **1차 필터**일 뿐이고, **진짜 보장은 unique 제약**이다. find가 "없음"을 봤어도 MVCC 때문에 진실이 아닐 수 있으므로, INSERT 위반을 최종 안전망으로 둔다.
- 우리 코드에서 이 패턴을 따르는 실제 예: 예약(reserve) 경로의 재사용 조회(`findReserved` — 같은 주문·provider의 재사용 가능한 예약을 먼저 찾음)와, 결제 생성부의 `getOrCreate`(키로 먼저 찾고 없으면 생성) 계열 메서드. 둘 다 "먼저 find, 없으면 만들고, 충돌은 unique가 최종 방어"라는 같은 골격이다.

### 4. 위반난 같은 트랜잭션에서 재조회하지 않는다

처음엔 "INSERT 위반나면 catch 안에서 `findByKey`로 기존 것을 반환"을 떠올렸지만, **같은 트랜잭션 안에서의 재조회는 못 믿는다**는 결론에 도달했다.

- **(a) MVCC:** 위반은 났지만(write는 현재 커밋 상태와 충돌) 같은 트랜잭션의 SELECT는 시작 시점 스냅샷이라 그 행을 **여전히 못 볼 수 있다** → 재조회가 빈 결과 → `orElseThrow`가 터진다. 2번에서 못 본 걸 재조회에서도 못 본다(스냅샷이 동일하니까).
- **(b) 세션 오염:** flush 중 예외가 나면 트랜잭션은 rollback-only로 마킹되고 Hibernate 세션은 "더 쓰지 마라"가 기본이다. 같은 세션 재조회가 항상 보장되지 않는다.
- **그래서:** 재조회로 수습하려면 **새 트랜잭션**(= 새 스냅샷, 예컨대 `REQUIRES_NEW` 같은 별도 전파)이라야 하고, 그 곡예가 싫으면 위반을 그냥 던진다.

### 5. 위반의 의미로 응답이 갈린다 — 노이즈 vs 돈

- **노이즈성 위반(예약 따닥, 돈 안 걸림)** → 위반 시 그냥 500. 재시도하면 find가 흡수한다. 곡예 불필요. 실제로 예약 경로가 택한 방식이다.
- **돈 걸린 멱등(승인)** → 사용자에게 500을 주면 "실패했나" 하고 재시도할 위험이 있어, 멱등 성공 응답이 필요하다.

### 6. 돈 걸린 곳의 멱등 성공 — "위반 처리"가 아니라 "위반 회피 + 안전망"

복잡함의 원인은 "위반난 자리에서 멱등 응답을 만들려는 것"이었다. 발상을 뒤집었다.

```
1차: 진입에서 사전 체크 (findApproveSucceeded(merchantPayKey))
     → 있으면 멱등 성공 응답, PG 호출 안 함. 끝.   (시간차 중복=대부분, 위반 자체를 회피)
2차: 그래도 동시 race로 unique 제약 위반
     → 도메인 예외 throw → 보상(별도 트랜잭션으로 PG 환불) + PAYMENT_DUPLICATE
     → 사용자는 에러받고 재시도 → 재시도 땐 1차가 멱등 성공으로 흡수
```

- 대부분의 중복은 **시간차**(콜백 재도착, 새로고침)다. 같은 순간에 겹치는 동시 race는 극히 드물다.
- 그래서 시간차는 1차 사전 체크의 if문 하나로 단순하게 잡고, 복잡한 처리(보상·새 트랜잭션)는 **거의 안 타는 2차 경로로 격리**한다.
- 2차에서 멱등 성공을 굳이 안 만들어도 된다 — 보상 + 에러로 두고 재시도가 1차에서 흡수되게 하는 게 가장 단순하다. (승인 처리가 택한 방식.)

## 배운 것

- **SELECT는 스냅샷, write는 현재 커밋 상태와의 충돌.** 이 비대칭이 "확인 후 생성"이 뚫리고 "INSERT + unique 위반"이 진짜 멱등 보장인 이유다. 멱등을 SELECT로 지키려는 시도는 근본적으로 race에 취약하다.
- **find-first는 조건부 패턴이다.** "트랜잭션 짧음 + 충돌 확률 낮음"이 만족될 때만 race window 비용이 안전망 500으로 값싸게 흡수된다. 충돌이 잦은 곳(예: 캐시 미스 후 동시 다발 insert)에는 안 맞는다.
- **시간차 중복과 동시 race를 갈라 복잡도를 격리한다.** 대부분인 시간차는 진입 사전 체크로 단순하게 흡수하고, 드문 동시 race만 보상·새 트랜잭션 같은 무거운 처리로 몰아넣으면, 흔한 경로가 단순해진다.

## 미해결·열린 질문

- 동시 race(2차)에서 멱등 성공 응답을 *만들지* 여부는 정책 결정으로 남겨뒀다. 안 만들고 재시도에 넘기는 게 단순하고, 만들려면 새 트랜잭션 재조회가 필요하다.
- 보상(PG 환불)이 또 실패하는 경우의 처리 — 배치 재처리 후보다(별도 논의: 배치·스케줄러).
