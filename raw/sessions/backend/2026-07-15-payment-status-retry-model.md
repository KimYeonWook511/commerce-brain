# 결제 상태·재시도 모델 이해 — 외부 결제 연동, 결과 불명 상태, append-only

## 배운 것 (도메인 이해)
- **결제대행사(PG)와 간편결제 서비스 구분**: 네이버페이는 카드 승인을 중개하는 결제대행사(PG)가 아니라 간편결제 서비스다. 우리 시스템은 그런 외부 결제 서비스에 요청을 보내는 가맹점 쪽 결제 조율자이지, 남의 결제를 대행하는 PG 서버를 만드는 게 아니다. 토스페이먼츠는 진짜 결제대행사다(토스페이라는 간편결제와 다름). 여러 간편결제를 직접 통합하더라도 우리 결제만 처리하는 한 우리는 가맹점이지 결제대행사가 되지 않는다.
- **결제대행사 연동 vs 직접 연동의 경제성**: 소규모에선 결제대행사를 빼도 카드사·간편결제 수수료가 대부분 남아 절감이 거의 없고, 카드사 직접 계약은 규제·인프라상 사실상 불가능하다. 결제대행사 통합이 정답이다. 개별 간편결제 직접 연동은 학습 가치는 있으나 결제수단마다 유지보수가 배가된다.
- **하이브리드 전략(간편결제 직접 + 카드는 결제대행사) 검토**: 기술적으로 성립한다 — 토스페이먼츠 결제위젯은 노출할 결제수단을 가맹점이 켜고 끌 수 있어 카드만 위젯으로 두고 간편결제를 뺄 수 있고, 간편결제 3종(네이버페이·카카오페이·토스페이)은 각자 직접 연동한다. 그러나 "직접 연동하면 수수료가 싸다"는 조건부다. 간편결제사 자체 수수료는 직접이든 결제대행사 경유든 어차피 내고, 직접으로 아끼는 건 결제대행사 중개 마진뿐이다. 게다가 소규모는 협상력이 없어 표준(높은) 요율을 받는 반면 결제대행사는 다수 가맹점을 묶어 더 낮은 통합 요율을 협상하므로, 소규모에선 직접 연동이 오히려 비쌀 수 있다. 절감은 거래 규모가 충분히 커야 유의미하다. 카드는 직접 계약이 불가능해 결제대행사 경유가 사실상 유일하다. 운영상으로도 결제수단이 여러 갈래로 갈려 승인·취소·부분환불·대사·정산을 각각 관리해야 하므로, 소규모에선 절감보다 복잡도 비용이 크다. 학습 목적이라면 "여러 연동 방식을 다뤄본다"가 수수료보다 정직한 근거다.
- **세 층 역할**: 주문(무엇을 사는가) / 결제창 준비물(이번 결제 시도를 대표, 결제수단당 재사용되고 만료 시간이 있음) / 결제 사건(외부에 실제로 보낸 요청 기록, append-only이고 승인·취소 종류가 있음). 앞의 둘은 결제가 일어나기 전의 세계이고, 결제 사건은 외부 경계에서 실제 벌어진 일이다.
- **도메인 주문 식별자 ≠ 외부 결제 식별자**: 우리 주문은 하나로 유지되지만, 외부 결제사로 보내는 결제 식별자는 재시도마다 새로 발급한다(외부 결제사가 같은 식별자 재사용을 막기 때문). 둘의 생명주기가 달라서, 이 매핑과 재시도 단위를 대표하는 계층(결제창 준비물)이 필요하다. 그래서 재시도해도 주문을 새로 만들지 않고 외부 결제 식별자만 새로 발급한다.

## 결정·이해 — 결제 상태 모델
- **결과 불명 상태는 성공도 실패도 아닌 제3의 상태다**: 외부에 승인 요청을 보냈는데 timeout이나 네트워크 단절로 응답을 못 받아 "돈이 나갔는지 모르는" 상태. 정상 대기(요청을 보내고 응답을 기다리는 중)와는 다르다. 정상 대기는 기다리면 되지만, 결과 불명은 확인(대사) 전까지 재결제를 막아야 이중청구를 방지한다.
- **재시도 두 종류**:
  1. 같은 결제 건의 승인확정을 다시 요청 — 외부 결제사의 승인확정이 멱등적이라 이미 승인된 건은 중복 승인되지 않는다(외부 결제사가 이중청구를 막아준다).
  2. 새 식별자로 새 결제 — 외부 결제사는 별개 건으로 보므로 막지 못한다. 우리 시스템이 "결과 불명 건이 있으면 새 결제를 차단"해서 막아야 한다.
- **append-only가 필요한 이유**: 시도마다 결제 사건 행을 새로 쌓으면(재시도 = 새 식별자 = 새 행) 이전 시도 흔적이 덮이지 않는다. 결과 불명 흔적이 보존돼야 (1)추적·확정과 (2)새 결제 차단이 둘 다 가능하다. 한 행을 재사용(수정)하면 결과 불명 흔적이 덮여 이중청구 방어 근거가 사라진다.

## 검토한 대안·트레이드오프 — 결과 불명을 명시 상태로 둘지
- 논점: "결과 불명"을 별도 상태로 둘지, 아니면 "처리 중" 하나로 두고 경과 시각으로 구분할지.
- 통합(별도 상태 없이 처리중+시각) 논거: 서버 크래시로 확정하지 못하고 멈춘 "처리 중" 행도 어차피 시간 기반으로 확인(대사)해야 하니, "미종료 = 확인 대상"이라는 단일 조건이 단순하다. 별도 결과불명 상태를 둬도 크래시 케이스는 처리중에 남아 확인 대상이 두 갈래가 된다.
- 이 프로젝트에서 명시 상태 유지가 나은 이유: 현행은 결과 불명 건만 즉시 재결제를 차단하고 확인 주기를 빠르게(1분) 돌리며, 정상 요청 흔적은 느린 주기(15분)로 확인한다. 크래시로 요청 흔적 상태에 멈춘 행도 시간 기반 확인으로 스스로 복구된다. 즉 이 프로젝트는 위험도별로 대응을 차등하기 때문에 결과 불명을 명시 상태로 두는 게 유리하다. 통합 논거의 "처리가 동일하다"는 전제가 이 프로젝트엔 맞지 않는다.
- 로그로는 대체 불가: 로그는 "왜 불명이 됐나"(사후 디버깅)를 남기고, 상태는 "지금 이 주문을 막을까"(실시간 정합성 판단)에 쓰인다. 서로 다른 일이라 로그가 상태를 대신하지 못한다.

## 미해결·열린 질문
- 결과 불명 상태 표현은 이 프로젝트에선 명시 유지가 결론이나, 새 결제(외부 PG 신규 도입 등)를 백지에서 설계한다면 "처리 중 + 시각" 통합도 선택지로 열려 있다.
