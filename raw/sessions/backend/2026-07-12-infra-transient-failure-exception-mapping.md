## 결정한 것
- 인프라(외부 캐시·저장소)의 일시적 사용 불가 장애를 HTTP 500이 아니라 **503(Service Unavailable)**으로 응답하기로 함. 이유: 500은 "예상 못한 서버 버그"의 의미고, 저장소가 잠깐 죽은 것은 재시도 가능한 일시 장애라 503이 정확하다. 이를 위해, 도메인 예외가 HTTP 상태 대신 드는 "의미 분류(카테고리)" 체계에 "일시적 사용 불가(→503)" 카테고리를 신설했다.
- **공통 인프라 장애 베이스 예외 클래스는 만들지 않기로 결정.** 원래 제안은 "공통 인프라-사용불가 베이스 예외를 만들어 도메인별 인프라 장애 예외를 그 아래로 통합"이었으나 기각했다. 이유: (1) 사내 예외 전략 문서가 "베이스 추출은 사용처가 3곳 이상이고 공통 catch 시나리오가 실제 필요할 때"라고 미리 정해뒀는데 현재 사용처가 2곳뿐이며, (2) 두 사용처(캐시가 곧 저장소라 대체 불가한 인증 토큰 저장소 vs 원본 DB로 대체 가능한 주문 멱등성 캐시)의 처리 방식이 근본적으로 달라 하나의 베이스로 묶어도 실질 이득이 적기 때문. 선례상으로도 공통 베이스 없이 도메인별로 처리하는 패턴이 문제없이 운영된다.
- 예외의 상속 전략을 정하는 **판단축**을 명확히 했다: "**application 계층이 그 예외를 catch해서 삼키느냐**"로 갈린다.
  - catch하지 않고 요청 끝단(응답 경계)까지 전파 → 자동 응답 매핑되는 공통 예외 베이스 계열로 던진다. 그러면 전역 예외 핸들러가 "의미 카테고리→HTTP 상태" 규칙으로 자동 매핑한다(동시성 충돌은 409, 인프라 일시 장애는 503). 이 경우 도메인마다 전용 응답 핸들러를 만들 필요가 없다.
  - catch해서 대체 경로로 진행(fallback)하거나 보상 처리 → 자동 매핑을 **회피**해야 하므로, 자동 매핑되지 않는 unchecked 전용 예외 타입으로 던진다. 이유: 이 예외는 삼켜서 대체 경로로 흘려보내는 게 정상 흐름인데, 자동 매핑되는 타입으로 두면 catch를 놓치거나 범위가 어긋나는 순간 원치 않는 응답이 클라이언트로 새어나간다.
- 두 실제 사례의 대비:
  - **인증 refresh 토큰 저장소** (캐시가 곧 저장소 자체라 원본으로 대체 불가): 아무도 catch하지 않는다 → 공통 도메인 예외로 던져 503 자동 매핑. 기존에 있던 "이 저장소 전용 예외 클래스 + 이 도메인 전용 응답 핸들러"를 폐기했다. 도메인이 늘 때마다 전용 응답 핸들러(우선순위 지정·핸들러·단위 테스트)가 반복 증가하는 부담이 사라진다.
  - **주문 멱등성 저장소** (캐시는 성능 최적화 레이어일 뿐, 원본 DB로 대체 가능): application이 catch해서 DB 유니크 제약 안전망 경로로 fallback한다 → 자동 매핑을 피하는 전용 unchecked 예외를 유지한다.
- **"도메인 예외 클래스를 따로 두느냐 vs 공통 예외를 그대로 던지느냐"의 판단축**: "그 예외를 타입으로 catch해서 구분·처리할 일이 있는가". 있으면 전용/도메인 예외 클래스로 둔다(catch 경계가 되고 로그에서 도메인 식별이 됨). 없으면 공통 예외 + 에러코드로만 세분화한다. 상황마다 예외 클래스를 새로 만드는 것은 안티패턴이다 — 예외 클래스 수는 "타입으로 잡아야 할 경계"의 수와 같고, 상황의 세분화는 에러코드가 담당한다.
  - 위 두 판단축("삼키느냐" / "타입 식별이 필요하냐")은 **직교하는 별개 질문**이다. 위 두 사례에서는 우연히 같이 정렬됐지만(삼키는 쪽이 전용 타입, 안 삼키는 쪽이 공통) 원리는 다르다. 예컨대 타입으로 잡아 로깅·보상만 하고 그대로 재전파하는 경우는, 전용 타입이 필요하면서도 끝단에서는 자동 매핑을 원할 수 있다.
- 원인 예외 보존: 공통 예외 베이스와 도메인 예외에 "(에러코드, 원인 예외)" 생성자를 추가해, 저장소가 던진 기술 원인을 예외 체인으로 실어 전파한다.

## 배운 것
- **adapter가 기술 예외를 변환하는 것 자체는 없앨 수 없지만, "무엇으로 변환하느냐"는 catch 여부로 갈린다.** 직접 정의한 아웃바운드 port(예: 캐시 인터페이스)는 그 계약에 프레임워크 기술 예외가 새어 나가면 추상화가 깨진다 → adapter가 반드시 도메인 예외로 변환해야 한다. 반면 프레임워크가 표준으로 관리하는 영속성 계층(예: ORM repository)은 그 추상 예외가 application에 노출돼도 되므로, 대개 변환 없이 그대로 전파해 전역 핸들러가 처리한다. 즉 "모든 인프라 예외를 잡아 변환"이 아니라 "직접 정의한 port만 변환하고, 표준 인프라 예외는 전파"가 기준이다.
- **데이터 접근 최상위 추상 예외는 특정 저장소 전용이 아니다.** 프레임워크의 데이터 접근 예외 최상위 타입은 관계형 DB와 캐시가 함께 공유하는 추상이라, 캐시 커넥션 실패 예외도 그 하위에 있다. 그래서 "이게 캐시 장애인가"를 예외 타입만으로는 가릴 수 없다. adapter의 catch가 안전한 이유는 try 블록 범위가 그 캐시 호출 하나뿐이라, 거기서 나는 예외는 캐시 발(發)임이 맥락으로 보장되기 때문이다(타입이 아니라 위치로 확신). 반대로 전역 핸들러는 잡는 범위가 넓어 DB 장애인지 캐시 장애인지 구분할 수 없다 → 저장소 장애를 특정 상태코드로 가르려면 그 지식을 공용 핸들러가 아니라 adapter 안에 가두는 게 맞다.
- **fallback으로 삼킬 예외를 "자동 응답 매핑되는 타입"으로 두면 안 된다.** 삼켜야 하는 예외를 자동 매핑 타입으로 두면 catch를 놓치는 순간 응답이 새어나간다. 자동 매핑 안 되는 unchecked 타입이면 실수해도 안전망(500)으로 흘러, 금전·정합성 경로에서 더 보수적이다. "넓은 타입으로 잡은 뒤 에러코드로 분기"하는 방식으로 대체하려는 시도는 이 안전성을 주지 못한다 — 타입 자체가 이미 자동 매핑 대상이면 소용없고, 넓게 잡아 나머지를 다시 던지는 것에 의존하는 것도 실수 여지가 크다.
- **로깅 역할 분담으로 스택 트레이스 중복을 피한다.** adapter가 원인을 ERROR + 전체 스택으로 남기고 예외에 원인도 실으면, 요청 끝단 핸들러가 5xx로 또 스택을 남겨 같은 스택이 로그에 두 번 찍힌다. 해결: adapter는 컨텍스트(식별자 등)만 WARN으로 간결히 남기고, 상세 스택은 끝단 핸들러가 ERROR로 한 번만 남긴다. "저장소 장애를 ERROR로 인지"는 catch 안 하는 경우 끝단 ERROR가 보장하므로 adapter가 WARN이어도 운영 인지가 가능하다. (처음엔 "adapter가 ERROR를 유지하고 이중 로깅을 감수"로 정했다가, 리뷰에서 역할 분담이 더 낫다고 판단해 전환했다.)

## 미해결·열린 질문
- 인프라 장애에 대한 자동 재시도(재시도·서킷 브레이커)는 이번에 도입하지 않았다. 필요해지면 트랜잭션 경계 밖(새 트랜잭션이 필요하므로)에서, 멱등성이 보장된다는 전제로, 프레임워크의 재시도 도구를 검토한다. 요청 처리 도중 즉시 재시도는 대개 무의미하다(방금 죽은 저장소는 곧바로 재시도해도 죽어 있음) → 빠르게 실패(503)시키고 클라이언트가 재시도하게 하는 방향이 낫다.
- fallback으로 삼키는 인프라 장애 사용처가 3곳 이상으로 늘면 그때 전용 타입의 공통 베이스 추출을 재검토한다.
