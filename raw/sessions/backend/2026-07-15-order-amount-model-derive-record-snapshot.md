# 주문 금액 모델 — 도출·기록·스냅샷 3분류와 청구액 vs 승인액 분리

부분취소 범위를 정하다가 "배송비는 주문이나 결제가 들고 있어야 하나, 배송 도메인이 관리해야 하나"라는 질문이 나왔고, 거기서 "주문 금액을 어떻게 모델링하나"라는 더 일반적인 원리로 번진 논의다. 배송·쿠폰·포인트가 아직 기획 범위 밖이라 지금 당장 만들 것은 없지만, 그것들이 들어올 때 어디에 무엇을 둘지를 미리 정리했다.

## 결정한 것

### 1. 금액은 성격에 따라 셋으로 갈린다 — 도출 / 기록 / 스냅샷

| 성격 | 처리 | 그래서 무엇이 달라지나 | 예시 |
|---|---|---|---|
| 계산으로 항상 복원됨 | **도출** | 저장하지 않는다. 매번 계산해도 같은 값 | 상품 총액 = `Σ(단가 × 수량)` |
| 외부에서 실제 일어남 | **기록** | 저장하고, **외부 응답과 대조 검증한다** | 결제대행사가 실제로 승인한 금액 |
| 정책이 바뀌어도 안 변해야 함 | **스냅샷** | 저장하고, **절대 재계산하지 않는다** | 상품 단가, 배송비, 적용된 쿠폰 할인액 |

기록과 스냅샷은 "저장한다"는 점에서 같아 보이지만 하는 일이 다르다. 기록은 대조할 상대가 있어야 의미가 있고(아래 3번), 스냅샷은 다시 계산하는 순간 존재 이유가 사라진다(아래 4번).

이 분류가 이 논의의 뼈대다. 어떤 금액을 저장할지 말지를 취향이나 성능으로 정하지 않고, 그 금액이 셋 중 무엇인지로 정한다.

### 2. 정책은 각 도메인이, 금액 스냅샷은 주문이 갖는다

배송비에는 성격이 다른 두 가지가 섞여 있다.

- **정책** — 배송비를 얼마로 매기는가, 무료배송 기준, 도서산간 추가요금, 반품 시 부담 주체. 이건 배송 도메인 소유이고 주문·결제가 몰라도 된다.
- **금액** — 주문이 스냅샷으로 가져야 한다. 배송 도메인에만 둘 수 없다.

금액을 주문이 가져야 하는 이유가 둘이다.

- **배송비는 고객이 실제로 내는 돈의 일부다.** 3만원 상품에 배송비 3천원이면 결제대행사에 보내는 승인액은 3만 3천원이다. 주문이 배송비 금액을 모르면 결제할 금액 자체를 계산할 수 없다.
- **매번 정책에 물어 계산하면 과거 주문 금액이 소급해서 달라진다.** 배송 정책이 바뀌면 작년 주문의 결제액이 바뀌어 버린다.

이건 이 코드베이스가 이미 상품 단가에 적용한 패턴과 똑같다. 상품 가격은 상품 도메인이 소유하지만, 주문 품목은 주문 시점 가격을 별도 컬럼에 스냅샷으로 저장한다. 나중에 상품 가격이 바뀌어도 과거 주문의 결제액이 그대로여야 하기 때문이다.

| | 정책 소유 | 금액 스냅샷 |
|---|---|---|
| 상품 가격 | 상품 도메인 | 주문 품목의 단가 컬럼 (이미 이렇게 함) |
| 배송비 | 배송 도메인 | 주문의 배송비 컬럼 (도입 시 같은 결) |

### 3. 청구액과 승인액은 분리한다 — 합치면 검증이 사라진다

"최종 결제액"이라는 한 단어에 성격이 다른 두 숫자가 들어 있다.

- **청구 의도** — 우리가 받아야 할 돈. 주문이 소유하고 주문 시점에 확정된다.
- **실제 과금** — 결제대행사가 실제로 뺀 돈. 결제 사건이 기록하며, 외부에서 일어난 사실이라 도출로 복원할 수 없다.

**둘을 합치면 안 된다.** 현행 코드는 승인 응답을 받을 때 우리가 기록한 금액과 응답 금액이 다르면 예외를 던져 검증한다. 두 숫자를 하나로 합치면 자기가 자기를 검증하는 꼴이 돼서 이 검증이 소멸한다. 현행 코드가 재요청 시 금액 불일치와 결제대행사 응답 검증을 애초에 두 갈래로 나눠 둔 것도 같은 이유다.

### 4. 최종액은 저장·도출 어느 쪽이든 무방하다 — 위험한 건 구성요소 재계산이다

"최종액을 저장해야 하나"의 답은 **구성요소를 스냅샷했는가에 달려 있다.**

```
상품 총액   = Σ(단가 × 수량) = 30,000   ← 이미 있음
배송비      =  3,000                    ← 배송 도입 시 스냅샷
쿠폰 할인액 =  5,000                    ← 쿠폰 도입 시 스냅샷
사용 포인트 =  1,000                    ← 포인트 도입 시 스냅샷

청구액 = 30,000 + 3,000 - 5,000 - 1,000 = 27,000   ← 도출
```

구성요소가 전부 얼어붙어 있으면 최종액은 매번 계산해도 항상 같은 값이다. 배송 정책이 바뀌든 쿠폰이 만료되든 이미 저장해둔 숫자를 더할 뿐이기 때문이다. 그래서 **최종액 자체는 저장해도 되고 도출해도 된다 — 이건 결정할 필요가 없는 문제다.**

**진짜 결정은 이것이다: 구성요소를 정책에서 다시 조회해 재계산하지 않는다.** 그러면 배송비 정책 변경, 쿠폰 만료·회수, 할인 행사 종료가 전부 과거 주문 금액을 소급해서 바꾼다.

주문 총액이 이미 이 패턴이다 — 품목 추가 시 `단가 × 수량`을 누적한 값이고, 단가가 스냅샷이라 불변이다.

### 5. 금액은 클라이언트가 계산해 보내지 않는다

금액을 클라이언트가 계산해 보내면 위변조된다. 3만 3천원짜리 결제를 100원으로 바꿔 보내면 그대로 결제된다. 서버가 계산하고, 서버가 기록하고, 결제대행사 응답과 대조한다. 현행 코드가 이미 이렇게 방어하고 있다.

### 6. 결제 시도 기록은 금액을 소유하지 않는다

결제창을 띄우려면 결제대행사에서 시도 단위 식별자를 미리 발급받아 저장해 두는데, 이 기록은 금액을 갖지 않는다. 같은 주문에 대해 이전에 만든 시도 기록을 다시 쓸 수 있는지 판정할 때만 주문의 총액을 넘겨받아 대조한다.

주문 하나에 이 기록이 여러 개 생길 수 있어서(결제수단별·재시도별), 금액을 거기 두면 "이 주문은 얼마짜리인가"의 답이 여러 개가 되어버린다.

## 배운 것

- **"저장할까 도출할까"는 취향 문제가 아니라 금액의 성격 문제다.** 도출 / 기록 / 스냅샷 셋 중 무엇인지를 먼저 묻고 나면 답이 자동으로 나온다. 헷갈리는 이유는 대개 한 단어(예: "최종액")에 성격이 다른 숫자가 섞여 있어서다.
- **스냅샷의 이유는 성능이 아니라 시간이다.** 캐싱하려고 저장하는 게 아니라, 정책이 미래에 바뀌어도 과거 사실이 안 흔들리게 하려고 저장한다. 그래서 "매번 계산하면 되지 않나"라는 반론은 정책이 불변일 때만 성립한다.
- **검증은 두 개의 독립적인 출처가 있을 때만 성립한다.** 청구액과 승인액을 하나로 합치면 대조할 상대가 없어져 검증이 조용히 사라진다. 중복처럼 보이는 두 값이 사실은 검증 장치인 경우가 있다.

## 미해결·열린 질문

- 배송비·쿠폰·포인트는 기획 범위 밖이라 지금 만들지 않는다. 현재는 구성요소가 상품 하나뿐이라 **상품 총액 = 청구액 = 승인액**으로 세 숫자가 우연히 같고, 그래서 구분이 코드에 드러나지 않는다.
- 쿠폰이 들어오면 **할인액의 품목별 안분을 주문 품목에 스냅샷해야** 부분취소가 가능해진다. "쿠폰 5천원 중 사과 몫이 얼마인가"를 모르면 사과 1개 취소 시 회수할 금액을 계산할 수 없다. 안분 규칙(단가 비례? 수량 비례? 반올림 잔여는 어디로?) 자체가 별도 설계 대상이다.
- 배송비는 품목처럼 비례 분할되지 않고 "전량 취소일 때만 환불"로 따로 노는 축이라, 도입 시 부분취소 잔액검증을 재검토해야 한다. 상세는 [[raw/sessions/backend/2026-07-15-partial-cancel-scope-item-based]] 참조.
