# PAID 주문 취소·환불 흐름 설계 — 단일 tx 환불 의도 + standalone CANCEL 대사로 환불을 보장

결제 완료(PAID) 주문을 사용자가 취소하면 전액 환불 + 재고 전체 복구가 일어나도록, 그동안 비어
있던 흐름을 채운 세션이다. 그전까지는 결제 전(INIT) 주문만 취소할 수 있었다 — 주문 도메인의
`Order.cancel()`이 INIT 상태에서만 취소를 허용했고, 환불은 시스템이 잘못 승인한 결제를 되돌리는
보상(compensation) 경로에만 존재했지 사용자가 주도하는 환불 경로는 없었다. 이 작업의 실제 무게중심은
"환불을 어떻게 **보장**하느냐"였고, 그 과정에서 초안 설계가 기대고 있던 안전망이 코드에 실재하지
않는다는 걸 발견해 standalone CANCEL 결제 대사를 새로 만든 것이 핵심이 됐다. (같은 PR에서 얻은
harness·AI 운영 교훈은 성격이 달라 별도 세션 메모로 분리했다.)

## 결정한 것

### 1. 환불 보장 — 단일 tx로 환불 "의도"를 영속화하고, 대사를 안전망으로

- **핵심 문제:** PG(결제대행사) 취소 호출은 외부 I/O라 주문 취소 트랜잭션 안에 넣을 수 없다. 그렇다고
  "주문을 CANCELED로 커밋한 다음 환불을 트리거"하는 순서로 짜면, 둘 사이에서 프로세스가 죽을 때
  주문은 취소됐는데 환불 기록이 없는 상태 — 돈을 안 돌려준 채 취소만 된 상태 — 가 남는다.
- **택한 방식:** 조율(orchestration) service가 한 RDB 트랜잭션 안에서 `CANCEL 결제 REQUESTED(=환불
  의도) 영속화 + 주문 취소 + 재고 복구`를 원자적으로 커밋한다. 실제 PG 환불 호출은 이 트랜잭션
  **밖**(커밋 이후)에서 best-effort로 실행한다. 어느 시점에 중단돼도 "이 결제는 환불해야 함"이라는
  durable 기록이 DB에 남고, 그 기록을 끝까지 마무리하는 책임은 아래 3번의 CANCEL 대사가 진다.
- **왜 이 구조가 되나:** 단일 DB라는 조건을 활용하면 이벤트/Outbox 없이 트랜잭션 하나로 order·payment
  두 aggregate에 걸친 정합(cross-aggregate consistency)을 확보할 수 있다.
- **검토한 대안 — Outbox 이벤트:** 주문 트랜잭션에 "환불 필요" 이벤트를 원자적으로 적고 별도 consumer가
  환불을 집행하는 방식. aggregate 경계는 더 깨끗해지지만, 환불 전용 이벤트·consumer를 새로 만들어야 해
  현재 스코프에 과하다고 봐 기각. 다만 결합이 커지면(부분취소·다채널) 그때 승격할 여지를 남겼다 —
  영속된 CANCEL REQUESTED 행이 이벤트와 사실상 같은 역할이라 전환이 자연스럽다.
- **응답 계약:** 취소 API 응답은 조율 service 트랜잭션 커밋(주문 CANCELED + 환불 의도 영속화) 시점에
  보장되는 "취소 접수"를 기준으로 끊는다. 커밋 후 인라인 best-effort PG 환불이 happy path에서 성공하면
  환불 결과까지 응답에 담고, UNKNOWN·실패면 "환불 처리중"으로 응답하고 나머지는 대사가 마무리한다.
  응답에 환불 진행 상태 필드를 두어 환불 없음(INIT 취소)/완료/처리중 세 값을 구분한다. 취소·환불 보장은
  영속된 의도 + 대사가 지므로 사용자가 PG 왕복을 끝까지 기다릴 필요가 없어, @Async·백그라운드 같은
  완전 비동기 인프라는 현재 불필요하다고 봤다(즉시 응답이 꼭 필요해지면 후속에서 가산적으로 도입).
- **트레이드오프:** 조율 service의 단일 트랜잭션이 order와 payment 두 aggregate의 테이블을 함께
  쓴다(경계 침범). 위 Outbox 승격을 미래 탈출구로 두고 지금은 감수했다.

### 2. append-only 원장 — 환불은 승인 행을 수정하지 않고 별도 CANCEL 레코드로

- **결정:** 환불을 "승인 행을 취소됨으로 mutate"가 아니라 "별도 CANCEL 레코드 append"로 표현한다. 대상
  APPROVE 결제의 성공(SUCCEEDED) 상태는 그대로 보존한다.
- **왜:** 결제 테이블은 사건을 쌓는 불변 원장이다. 승인 성공은 이미 일어난 사실이고 환불도 별개의
  사실이라, 승인 사실을 훼손하지 않아야 감사·분쟁 대응과 미래 부분취소 확장에서 일관된다. "이 결제를
  취소했는가"는 승인 행을 뒤집는 게 아니라 CANCEL 레코드의 존재·상태로 판단한다.
- **보상 경로를 재사용하지 않은 이유:** 기존 시스템 보상 경로(`CompensateApprovalUseCase`의
  `runPgCancel`)는 "애초에 승인되면 안 됐던" 결제를 되돌리느라 대상 APPROVE 결제를 FAILED로
  마킹한다(코드상 approve 결제에 `fail`을 호출). 사용자 주도 환불은 정당하게 성공한 승인을 되돌리는
  것이라 의미가 정반대다. 그래서 `runPgCancel`을 쪼개 공유하지 않고 **별도 환불 실행 경로**
  (`RefundExecutionUseCase`)를 뒀다 — 공유 코드를 건드려 보상 경로에 회귀를 내는 위험을 피하려는 것.
- **트레이드오프:** "이 주문 결제가 지금 유효한가"를 알려면 APPROVE·CANCEL 레코드를 집계해야 한다.
  단일 row를 mutate하는 모델보다 조회가 복잡하지만, append-only 원장이 치르는 일관된 비용으로 봤다.

### 3. standalone CANCEL 결제 대사 신설 (이번 작업의 진짜 핵심)

- **결정:** `type=CANCEL ∧ status∈{REQUESTED, UNKNOWN}`인 stale CANCEL 결제를 스캔해 PG 재조회·재실행으로
  종착시키는 대사(reconciliation) 경로를 신설한다. 1번에서 영속한 환불 의도가 PG 호출 전/중 중단으로
  남으면, 이 대사가 그 행을 집어 끝까지 마무리한다.
- **왜 굳이 새로 만드나 (아래 "막힌 점"의 발견에서 출발):** 후처리 대상·흐름을 정하는 정책 뼈대는 이미
  존재했다 — 후처리 대상 판정 정책에 CANCEL 분기가 있고, 흐름 정책에도 `CANCEL_RECONCILE` 매트릭스가
  있었다. 그런데 그걸 구동하는 배선만 죽어 있었다. 그래서 새 정책·새 PG 로직 없이, CANCEL 타입 stale
  후보를 뽑는 스캔 쿼리(`findStaleCancelPaymentsForReconciliation`)와 대사 루프의 CANCEL 처리 분기만
  추가해 죽은 정책을 live로 살렸다. 기존 취소 상태전이 service들과 PG 취소 어댑터·승인 이력 조회를
  그대로 재사용한다.
- **구동 규칙:** stale CANCEL(REQUESTED/UNKNOWN)마다 PG에 현재 상태를 물어 — PG에서 이미 취소됐으면
  CANCEL을 SUCCEEDED로 확정, 아직 승인 상태로 남아 있으면 취소를 재시도, PENDING·조회불가면 대기
  유지. CANCEL이 오래(환불 의도 기록 시점 기준 약 6시간) 안 풀리면 승인 대사와 동일하게 escalation
  통지로 사람에게 올린다.
- **확정적 실패(FAILED)는 통지로만 처리 — 두 가지 근거:**
  - (의미론) FAILED는 "취소 불가 기간·이미 정산·인증 오류"처럼 같은 요청을 재전송해도 안 풀리는
    거절이다. 같은 요청 반복이 무의미하다.
  - (구조) 뒤 4번에서 밝히듯 CANCEL은 4컬럼 unique 슬롯을 하나만 점유한다. FAILED CANCEL이 그 슬롯을
    차지하고 있으면 같은 결제에 새 CANCEL을 재생성하는 것 자체가 막혀, 전체취소 스코프에서는 자동
    재시도가 구조적으로 불가능하다.
  - 그래서 FAILED는 조용히 종착시키지 않고 escalation으로 surface해 환불 미집행이 묻히지 않게 한다.
    재시도 N회 + 백오프 같은 자동 재처리 엔진은 이번 스코프에서 빼고 별도 이슈(#208)로 분리했다.
- **트레이드오프:** 대사 스캔이 CANCEL 종류만큼 하나 늘어 PG 조회 부하가 증가한다. 승인 스캔과 동일한
  cutoff·페이징 정책을 따르게 해 통제했다.

### 4. 환불 멱등 — 5겹 방어, 그리고 알고 보니 이미 하드였다

- **5겹:** (1) CANCEL 단일 생성, (2) REQUESTED 상태일 때만 PG를 호출하는 상태 가드, (3) 결과 불명은
  성급히 실패로 보지 않고 UNKNOWN으로 보존, (4) 대사가 재전송하기 전에 PG에 현재 상태를 먼저 물어봄
  (query-before-retry — 모르면 다시 보내는 게 아니라 PG에 조회), (5) PG가 이미 취소된 건에는
  alreadyCanceled로 응답. (구현 중 "이미 성공한 환불 재요청에는 성공 결과를 그대로 반환"하도록 실행
  경로를 다듬어 재요청 안전성을 마무리했다.)
- **정정 — "DB unique 없음"은 오진이었다:** 논의 중 초안에는 "CANCEL 생성에 DB unique가 없어 주문 행
  잠금으로만 직렬화(소프트 보장)"라고 적었는데, 실제 스키마를 확인해 보니 틀렸다. 기존 결제 테이블의
  unique는 4컬럼 `uk_payment_merchant_pay_key_provider_pg_payment_id_type` —
  `merchant_pay_key`(어느 주문 결제에서 비롯됐는지 식별하는 키) / `provider`(PG사) /
  `pg_payment_id`(PG가 발급한 거래 ID) / `type`(결제 종류 APPROVE 또는 CANCEL) 이다. `type`이 키에 들어
  있어, 한 (merchantPayKey, provider, pgPaymentId)에 APPROVE 행 하나·CANCEL 행 하나만 존재할 수 있다(둘은
  type이 달라 서로 부딪히지 않는다). 즉 전체취소에서는 한 결제당 CANCEL이 하나로 **이미 DB가 하드
  보장**하고 있었다. 사용자가 "승인 REQUESTED는 중복 생성되나?"라고 물어서 실제 스키마를 따라가다
  발견했다. → 멱등 근거를 머리로 추론하지 말고 실제 제약을 확인할 것.
- **테스트 parity 문제:** 그 4컬럼 unique는 Flyway 마이그레이션(V6, 운영/로컬 MySQL)에는 있으나 Payment
  엔티티의 `@Table` 선언에는 없었다. 테스트 프로파일은 H2 `create-drop`으로 **엔티티에서** 스키마를
  생성하므로, H2에는 이 제약이 아예 없어 멱등을 테스트로 검증할 수 없는 상태였다. 엔티티 `@Table`에 이
  unique를 미러링해 H2에서도 멱등이 검증되게 했다(운영은 `validate` 모드라 스키마 변경 없이 무해).
  "테스트 통과"가 운영 MySQL 거동을 보장하지 않는 silent zone이라, 앞서 겪은 같은 결의 문제(#189)와
  이어진다.

### 5. 락 전략 — RTT 한 번보다 좁은 락 범위

- **결정:** 취소 흐름에서 주문을 잠글 때, 부모+자식을 한 번에 끌어오는
  `select distinct o … join fetch o.orderItems … FOR UPDATE`를 쓰지 않고, 주문 행 하나만 잠그는
  단일 행 락(`findByIdAndMemberIdForUpdate`) + orderItems는 aggregate를 통한 lazy 로드로 분리한다.
- **비관적 락인 이유:** 취소 service는 주문을 FOR UPDATE로 잠가 동시·중복 취소를 직렬화한다(먼저 든
  취소가 이기고, 둘째는 CANCELED 상태를 보고 거부). 한 트랜잭션에서 여러 aggregate를 쓰기 때문에 낙관적
  락이면 커밋 시점에야 충돌을 감지해 헛일 + 롤백이 되지만, 비관적 락은 앞에서 직렬화해 둘째가 헛일을
  안 한다.
- **리뷰 지적과 그 함정:** PR 리뷰에서 `distinct + join fetch + FOR UPDATE` 조합의 락 안전성이 도마에
  올랐다. 리뷰 봇은 "distinct 제거"를 제안했는데, 그건 join fetch의 row fan-out(주문 1건이 자식 아이템
  수만큼 행으로 복제됨)을 놓친 제안이라 그대로 따르면 단건 조회 매핑에서 결과가 여러 개가 되어
  `NonUniqueResultException`을 부른다. 진짜 문제는 따로 있었다 — join fetch를 락 쿼리에 합치면 락이
  자식(order_item) 행까지, 그것도 실행계획·인덱스 순서에 의존해 번져 락 범위가 넓어진다는 것.
- **택한 트레이드오프:** fetch join 한 쿼리는 주문+아이템을 DB 왕복(RTT) 한 번에 가져와 라운드트립을
  아낀다. 2단계로 분리하면 아이템 로드 쿼리가 하나 더 생겨 RTT가 1회 늘어난다. 하지만 취소는 사용자
  단발 동작(hot path 아님)이라 RTT 1회 추가는 미미한 반면, 락 범위를 주문 행 하나로 좁히는 이득(동시성
  안전 + 미래 데드락 예방, 돈 정합성 직렬화 락이라 더욱)이 크다. "약간의 RTT < 좁은 락 범위"로 보고
  분리를 택했다.
- **부수 이득:** distinct/단건 매핑 문제, distinct+FOR UPDATE의 SQL 생성 거동 의존(passthrough 설정·
  Hibernate 버전), 자식 락 순서의 실행계획 의존성 같은 모호함이 전부 사라져 락이 **검증 가능하게
  확실**해진다(H2·MySQL·Hibernate 버전 무관).
- **참고 (봇 제안이 맞을 수도 있던 경우):** Hibernate 6은 fetch join용 distinct를 SQL에 내보내지 않고
  메모리 내 중복제거로 처리할 수 있다 — 그렇다면 distinct를 유지하는 게 맞고 "제거" 제안이 틀린 게
  된다. 그러나 이건 버전·설정에 의존하는 거동이라, 돈이 걸린 락을 그런 거동에 기대는 것 자체가 취약해
  단일 행 락으로 아예 회피했다.

## 막힌 점·해결

### 기대고 있던 안전망이 코드에 실재하지 않았다

초안 설계의 환불 보장은 전적으로 "기존 CANCEL 대사가 영속된 CANCEL REQUESTED를 집어 재시도한다"는
전제 위에 서 있었다. 그런데 코드를 확인하니 기존 결제 대사(`ReconcilePaymentUseCase`)는 APPROVE 타입
결제만 스캔했고(`findStaleApprovePaymentsForReconciliation`), 후처리 대상 판정을 호출할 때 취소 결제
인자를 늘 비운 채(`resolvePostProcessTarget(payment, null, …)`) 부르며, `CANCEL_RECONCILE` 분기는
`SKIPPED`로 흘려보내고 있었다. **standalone CANCEL을 구동하는 경로가 코드상 아예 없었던 것.** 게다가
이번 설계의 CANCEL은 성공한(SUCCEEDED) 승인에 매달리는데, 기존 CANCEL은 전부 *스캔되는 APPROVE 실패*에
앵커링돼 구동됐으니, 어떤 기존 스캔에도 걸릴 수가 없었다. 안전망이 글로만 존재하고 코드엔 없었다.

리뷰 에이전트가 이 지점을 BLOCKER로 짚었고, 직접 코드로 재확인해 확정했다. 결국 이 발견이 위 3번(대사
신설)을 이번 작업의 핵심 축으로 만들었다. → 설계가 어떤 인프라에 기댈 때, 그 인프라가 *실제로* 그 일을
하는지 코드로 확인한다. "있을 것이다"라는 가정은 특히 돈 흐름에서 치명적이다.

### 멱등 근거를 추론했다가 실제 제약으로 정정

위 4번에 적은 대로, "CANCEL 생성에 DB unique가 없다"는 초안 서술이 오진이었다. 사용자의 "승인 REQUESTED는
중복 생성되나?"라는 질문을 따라 실제 스키마를 열어보고서야 4컬럼 unique의 `type`에 CANCEL이 포함돼 이미
하드 보장이라는 걸 확인했다. 검토 과정에서 나온 "UNIQUE 없음" 지적도 같은 오진이었다.

## 배운 것

- **기대고 있는 안전망이 실제로 존재하는지 코드로 검증하라.** 문서·정책 뼈대가 있어도 그걸 구동하는
  배선이 죽어 있으면 안전망은 없는 것이다. 특히 돈 흐름에서 "있을 것이다"라는 가정은 치명적이다.
- **멱등 근거는 추론하지 말고 실제 제약(스키마·unique)을 확인하라.** 여기서는 "unique 없음"이라는
  추론이 실제 4컬럼 unique로 뒤집혔고, 그게 FAILED를 자동 재시도가 아니라 escalation으로 처리해야
  하는 구조적 근거까지 됐다.
- **멱등은 성격이 다른 장치의 다층 방어다.** 멱등키(재시도 중복 방지)와 잠금 + 한도 검증(동시 과다취소
  방지)은 서로 못 막는 문제를 각각 막는 별개 장치라, 부분취소 같은 확장에서 둘 다 필요하다.
- **"테스트 통과"가 운영 거동을 보장하지 않는 silent zone이 있다.** H2 `create-drop`는 엔티티에서
  스키마를 만들기 때문에, Flyway에만 있고 엔티티엔 없는 제약은 테스트에서 통째로 사라진다.
- **append-only 원장에서 상태를 mutate하지 마라.** 승인 성공을 보존한 채 CANCEL 레코드를 append하면
  감사·분쟁·미래 부분취소에서 일관되고, 단일 tx 환불 의도 구조도 이 위에서만 성립한다.

## 미해결·열린 질문

- **부분취소는 이번 범위 밖.** 위 4컬럼 unique는 전체취소에선 `type=CANCEL`·`provider`가 고정이라 실질
  신원이 (merchantPayKey, pgPaymentId) 둘로 좁혀지지만, 부분취소는 같은 (merchantPayKey, pgPaymentId)에
  금액만 다른 CANCEL이 여럿이라 이 unique로 표현할 수 없다. amount를 unique에 끼워 넣는 건 답이 아니다
  (같은 금액을 두 번 취소할 수 있어 amount는 신원이 아니다). 올바른 모델은 취소 요청마다 고유 키(승인
  결제가 결제 단위로 멱등 키 merchantPayKey를 하나 갖듯, 취소 요청 단위로 하나 — 보통 클라이언트 발급
  또는 결정론적 파생)를 두고 unique를 그 키에 거는 것 + "동시에 다른 키로 같은 물건을 두 번 환불"은
  멱등키로 못 막으니 잠금 + "취소액 합 ≤ 승인액 한도 검증"으로 막는 것. 이 취소 요청 키 + 한도 검증
  모델로 별도 설계가 필요하다.
- **확정적 환불 실패(FAILED)의 자동 재시도 + 백오프 엔진은 미도입** — 이번엔 escalation으로 surface하는
  선까지만. 별도 이슈(#208)로 분리.
- **fetch join + FOR UPDATE의 자식 락 순서·데드락 가능성 검증은 후속(#259).** 가설은 order_id 인덱스
  순서대로 자식 행이 잠긴다는 것. 추후 다른 인덱스로 order_item에 락을 거는 로직이 생기면, 겹치는
  행 + 다른 락 순서 + 엇갈린 타이밍이 만나는 경우에 한해 데드락이 성립할 수 있다(항상이 아니라 그 조합
  에서만).
