# 모든 명령이 입출력 오류를 내는 장애의 추적, 그리고 모니터링이 자기 죽음을 못 남기는 문제

싱글보드 컴퓨터 홈서버의 루트 파일시스템이 USB로 연결된 SSD에 있다. 서버가 반복적으로
멈추는 증상이 있었고, 소거법으로 원인을 하드웨어의 특정 구간까지 좁혔다. 진단 절차와, 그 과정에서 드러난 모니터링의 구조적 사각지대를 남긴다.

## 막힌 점·해결

### 증상 — 셸은 살아 있는데 모든 명령이 실패한다

```
$ ls
-bash: /usr/bin/ls: 입력/출력 오류
```

셸 자체는 응답하는데 **디스크에서 실행 파일을 읽는 순간 실패**한다. 셸 내장 명령은
되고 외부 명령만 안 되는 형태다. 이건 프로그램이 깨진 게 아니라 **루트 디스크가
사라진 상태**다. 이미 메모리에 올라온 것만 돌아가고 새로 읽어야 하는 건 전부 실패한다.

루트가 USB 저장장치에 있으면 그 링크가 끊기는 순간 정확히 이 모습이 된다. 원격 접속은
유지되고(이미 떠 있는 프로세스라) 명령만 안 되니, 처음에는 권한이나 셸 문제처럼 보인다.

### 소거법 — 네 후보를 순서대로 지웠다

같은 증상을 만들 수 있는 원인이 여럿이라 하나씩 배제했다.

**① 전원 부족** — 이 하드웨어는 공급 전압이 떨어지면 플래그를 남긴다. 현재 값과 누적
로그를 모두 확인했다.

```
throttled=0x0
로그 전체에서 under-voltage 발생: 0회
```

한 번도 없었다. 전원은 후보에서 제외. **전원 문제라면 외부 전원 공급 장치를 사야 하는데,
그 비용을 안 써도 된다는 판단 근거가 됐다.**

**② 저장장치 수명** — SMART 정보를 읽었다.

```
Reallocated_Sector_Ct    0
Current_Pending_Sector   0
Offline_Uncorrectable    0
Wear_Leveling_Count      0
Available_Reservd_Space  100
```

불량 섹터도 마모도 없다. 낸드 자체는 새것이나 다름없다. 디스크 교체가 답이 아니라는 뜻.

**③ 드라이버 문제** — USB 저장장치는 두 가지 프로토콜로 붙을 수 있고, 일부 변환 칩은
빠른 쪽에서 오작동한다. 확인해보니 이미 안전한 쪽으로 붙어 있어서 해당 없음.

**④ 발열** — 온도는 확인 시점 기준 프로세서 53도, 드라이브 47~50도. 극단적이지 않지만
"발열이 오르면 멈춘다"는 사용자의 반복 관찰과 맞물려 마지막까지 남았다.

### 결정적 지표 두 개

전체 SMART 속성을 보고 나서야 원인이 특정됐다.

```
UDMA_CRC_Error_Count   571
Power_Cycle_Count      142
Power_On_Hours         124
```

**CRC 에러 571회.** 이 항목은 드라이브와 그 상위 컨트롤러(여기서는 USB 변환 칩) 사이
데이터 전송에서 깨진 패킷을 센 값이다. **건강한 하드웨어에서는 사실상 0으로 유지된다.**
케이블 접촉 불량, 커넥터 산화, 변환 칩 불량일 때만 올라간다. 낸드는 멀쩡한데 이 값이
크다는 건 **저장 매체가 아니라 그 매체로 가는 배선이 문제**라는 뜻이다.

**가동 124시간에 전원 사이클 142회.** 한 시간에 한 번꼴로 전원이 끊겼다 붙었다는 것으로,
정상 운영에서는 나올 수 없는 비율이다. 반복적인 비정상 차단을 뒷받침한다.

결론: 저장 매체와 변환 칩 사이의 물리적 연결 불량. 발열이 오르면 금속이 팽창해 아슬아슬한
접촉이 더 나빠지고 링크가 끊기는 것으로, 사용자의 관찰과도 맞는다.

조치는 재장착 → 그래도 재발하면 변환 어댑터 교체 순서로 잡았다. 판정 기준은 **현재 CRC
값을 기록해두고 하루 뒤 다시 읽는 것**이다. 늘지 않으면 접촉 문제가 해결된 것이고, 늘면
어댑터 불량이다. 추측이 아니라 숫자로 갈린다.

## 배운 것

- **"모든 명령이 입출력 오류"는 프로그램이 아니라 저장장치를 의심하는 증상이다.** 셸
  내장은 되고 외부 명령만 안 되면 거의 확실하다.
- **소거 순서를 전원 → 매체 수명 → 드라이버 → 링크로 잡으면 낭비가 적다.** 앞의 셋은
  각각 한 줄 명령으로 확인되고, 각각이 "사야 할 물건"을 다르게 만든다. 순서를 지키면
  불필요한 구매를 피한다.
- **SMART에서 매체 건강과 링크 건강은 다른 항목이다.** 종합 판정이 통과여도 CRC 에러가
  쌓여 있을 수 있다. 종합 판정만 보고 "디스크는 멀쩡하다"고 넘기면 원인을 놓친다.
- **가동 시간 대비 전원 사이클 비율은 좋은 이상 신호다.** 절대값이 아니라 비율로 봐야
  의미가 드러난다.

## 미해결·열린 질문 — 모니터링의 사각지대

이번 장애는 **모니터링이 잡아줬어야 할 사건인데 잡지 못했다.** 두 가지 구조적 한계가
드러났고, 확인이 남은 후속 하나가 있다.

**① 보는 온도가 다르다.** 여기서 말하는 모니터링은 **호스트 지표를 읽어 웹으로 노출하는
프로세스**다. 호스트에서 직접 돌면서 프로세서 사용률·메모리·디스크 사용량·온도를 주기적으로
표본화하고, 앞단 웹서버가 인증을 걸어 그 페이지를 서비스한다. 이 프로세스는 **프로세서
온도만 읽는다.**

이번에 문제가 된 건 저장장치와 변환 칩의 온도이고, 그건 SMART로 따로 읽어야 한다. 게다가 SMART 조회에는 상위 권한이
필요해서, 일반 사용자로 도는 모니터링 프로세스가 직접 읽을 수 없다. 권한 있는 주기 작업이
값을 파일에 적고 프로세스가 그 파일을 읽는 구조가 후보다.

**② 자기 죽음을 기록할 수 없다.** 더 근본적인 문제다. 기록도 지표도 전부 **죽어가는
그 디스크 위에** 있다. 링크가 끊기는 순간 로그를 쓸 수 없으니, 정지 직전 상태가 남지
않는다. 실제로 시스템 로그가 특정 시각에서 뚝 끊겨 있었고, 그래서 매번 원인을 추측만
하게 된다.

**해법의 방향은 지표를 그 기계 밖으로 내보내는 것이다.** 이 프로세스는 최신 표본을
JSON으로 돌려주는 조회 경로를 이미 갖고 있으니, 다른 기계에서 주기적으로 긁어 파일로
쌓아두면 서버가 죽어도 **마지막 값이 바깥에 남는다.** 정지 직전 온도가 치솟았는지
평온했는지가 보이면 발열 가설이 숫자로 검증된다.

**③ 판정을 위한 재측정이 아직 남아 있다.** 앞에서 세운 판정 절차(재장착 후 하루 뒤
CRC 값을 다시 읽어, 늘지 않으면 접촉 문제 해결·늘면 변환 어댑터 불량)의 결과를 아직
확인하지 않았다. 이 기록에서 유일하게 시한이 걸린 행동이라 여기 남긴다.

①②는 아직 적용 전이다. 특히 ②는 "지표를 만드는 곳과 보관하는 곳을 분리해야 한다"는
일반 원칙이라, 이 서버뿐 아니라 앞으로도 적용될 얘기다.
