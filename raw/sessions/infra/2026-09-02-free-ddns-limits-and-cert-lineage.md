# 무료 DDNS의 제약이 인증서와 URL 구조를 어디까지 결정하는가

가정용 회선의 홈서버에 무료 DDNS 서비스(no-ip)로 도메인을 붙여 쓰고 있다. 작업을
시작한 시점에 HTTPS가 완전히 죽어 있었고, 추적해보니 무료 플랜의 제약이 인증서 발급과
URL 설계까지 연쇄적으로 규정하고 있었다.

## 막힌 점·해결

### 도메인이 통째로 사라져 있었다

증상은 "인증서 만료"처럼 보였지만 더 근본적이었다. 도메인이 **어떤 IP로도 풀리지 않았다.**

```
status: NOERROR, ANSWER: 0
AUTHORITY: <상위 도메인> SOA ...
```

`NXDOMAIN`이 아니라 `NOERROR`에 답이 0개인 게 단서다. 상위 도메인은 살아 있는데 그 아래
호스트명만 없다는 뜻이다. 여러 공용 DNS에 물어봐도 같아서 캐시 문제도 아니었다.

원인은 **무료 호스트명의 주기적 확인 정책**이었다. 이 서비스는 무료 호스트명을 30일마다
확인하지 않으면 삭제한다. 서버가 장기간 꺼져 있는 동안 확인 메일에 응답하지 않아 호스트명이
지워졌다. 공유기의 DDNS 갱신 클라이언트가 계속 돌고 있어도 **호스트명 자체가 없으면
갱신할 대상이 없다.**

해결: 같은 이름으로 호스트명을 다시 등록하고, 공유기의 갱신 클라이언트 자격증명을
현재 계정 기준으로 다시 넣었다. 이름을 그대로 되찾았기 때문에 프록시 설정도 인증서
경로도 손댈 필요가 없었다.

교훈으로 남길 부분: **DNS 이름의 존재와 IP 갱신은 다른 층위다.** 갱신 클라이언트가
설정돼 있다는 사실만으로 "도메인은 괜찮다"고 가정하면 안 된다.

### 존재하지 않는 서브도메인 하나가 인증서 발급 전체를 막았다

인증서 발급 스크립트가 루트 도메인과 API용 서브도메인 두 개를 함께 요청하고 있었다.
그런데 무료 플랜에서는 서브도메인을 만들 수 없다 — **호스트명이 1개로 제한되고
와일드카드는 유료 기능**이다. 재등록 후에도 API 서브도메인은 DNS에 없는 상태였다.

certbot은 `-d`로 준 **모든 도메인을 각각 검증**하고, HTTP-01 방식은 인증 기관이 각
도메인에 실제로 접속해 토큰 파일을 확인한다. **하나라도 실패하면 인증서 전체가 발급되지
않는다.** 즉 쓰지도 않는 서브도메인 하나 때문에 루트 도메인 인증서까지 못 받고 있었다.

DNS-01 방식으로 우회할 수도 없다. 그것도 결국 해당 서브도메인 아래에 TXT 레코드를 만들
권한이 있어야 하는데, 그 권한이 없는 게 문제의 시작이기 때문이다.

해결: 발급 도메인 목록에서 서브도메인을 뺐다. **프록시 설정 파일은 지우지 않고 남겼다.**
DNS가 없어 아무도 도달하지 못하니 무해하고, 나중에 서브도메인을 확보하면 목록에 한 줄
더해 재발급하는 것만으로 되살아난다. 설정을 지웠다가 다시 쓰는 것보다 비용이 낮다.

### 도메인을 줄였더니 인증서가 새 경로에 저장됐다

이게 가장 놓치기 쉬웠다. 도메인 목록을 2개에서 1개로 줄여 재발급했더니 certbot이
기존 인증서 계보를 덮지 않고 **`live/<도메인>-0001/` 이라는 새 계보를 만들었다.**

```
Certificate is saved at: /etc/letsencrypt/live/<도메인>-0001/fullchain.pem
```

발급은 "성공"했는데 웹서버 설정은 `-0001` 없는 옛 경로를 가리키고 있으니, **웹서버는
만료된 옛 인증서를 계속 쓴다.** 로그에도 에러가 안 나고 발급 명령도 성공으로 끝난다.
발견 수단은 계보 목록을 직접 조회하는 것뿐이었다.

```bash
certbot certificates    # 계보 이름·도메인 목록·저장 경로·남은 기간
```

조용히 어긋나는 종류의 실패라 **발견 수단을 아는 것이 교훈의 절반**이다.

해결은 발급 시 계보 이름을 명시하는 것이다.

```bash
certbot certonly --cert-name <루트 도메인> -d <루트 도메인> ...
```

이러면 도메인 구성이 바뀌어도 **같은 경로에 덮어쓴다.** 웹서버 설정 경로가 고정되므로
이런 어긋남이 원천적으로 안 생긴다. 처음부터 넣어둘 옵션이었다.

발급·갱신 스크립트 정본: `{repo: commerce-infra, path: docker/scripts/cert-issue.sh}`,
`{repo: commerce-infra, path: docker/scripts/cert-renew.sh}`

## 결정한 것

### 서브도메인 대신 끝 슬래시를 붙인 서브패스로 붙이기로 했다

모니터링 페이지를 붙일 곳이 필요했는데 서브도메인을 만들 수 없었다. 선택지를 검토했다.

- **유료 전환** — 와일드카드가 열리지만 비용이 든다. 그리고 무료 호스트명의 30일 확인
  의무가 근본 위험이므로, 돈을 쓸 거면 차라리 도메인을 사는 게 낫다고 봤다.
- **도메인 구입 + 별도 DNS 제공자** — 서브도메인 무제한, 주기적 확인 없음. 가정용 회선의
  변하는 IP는 DNS 제공자의 API를 호출하는 갱신 스크립트로 해결. **장기적으로는 이쪽이
  정답**이지만 당장 필요한 게 아니어서 미뤘다.
- **채택: 루트 도메인의 서브패스.** 인증서를 새로 받을 필요가 없다는 게 결정적이었다.
  기존 루트 도메인 인증서를 그대로 쓴다.

주의할 함정이 하나 있다. 대상 페이지가 데이터를 **상대 경로로** 요청하면, 끝에 슬래시가
없는 주소에서는 요청이 한 단계 위로 새어 나가 깨진다.

```
/status/  →  fetch("api/status")  →  /status/api/status   정상
/status   →  fetch("api/status")  →  /api/status          깨짐
```

그래서 슬래시 없는 주소는 301로 슬래시를 붙여 보내고, 프록시 대상 끝에 슬래시를 두어
접두사를 떼어냈다. 서브도메인이었다면 겪지 않았을 문제라, **서브패스 선택의 숨은 비용**이다.

## 세 실패는 층이 다르다

이 세 가지가 한 사건처럼 보이지만 층이 다르다. 나중에 헷갈리지 않게 갈라 적어둔다.

1. **인증서가 만료된 것** — 자동 갱신이 서버에 등록된 적이 없어서. 운영 문서에는 주기
   실행으로 갱신한다고 적혀 있었는데 실제 등록은 비어 있었다. 문서와 서버의 어긋남.
2. **재발급이 실패한 것** — 위와 무관한 별개 원인. 도메인이 사라져 있었고, 존재하지
   않는 서브도메인이 목록에 남아 있었다.
3. **재발급이 반영되지 않은 것** — 또 별개. 계보 이름을 지정하지 않아 새 경로에 저장됨.

즉 "갱신이 안 돌아서 만료"와 "다시 받으려니 안 되더라"는 서로 다른 문제였다.

조치 결과: 주기 실행을 실제로 등록했다. 갱신 스크립트를 주 1회와 부팅 직후에 돌리고,
로그를 파일로 남기게 했다. 등록 내용과 각 옵션이 필요한 이유는 운영 문서에 적어뒀다 —
`{repo: commerce-infra, path: docs/cron.md}`. **문서에만 있고 서버에는 없던 상태가
이 장애의 출발점이었으므로, 이번에는 등록 여부를 확인한 뒤 문서를 고쳤다.**

## 배운 것

- **무료 DDNS는 "이름이 언제든 사라질 수 있다"는 전제로 다뤄야 한다.** 갱신 클라이언트가
  아니라 호스트명 자체의 생존을 감시 대상으로 삼아야 한다.
- **인증서 발급은 원자적이다.** 요청 목록에 쓰지 않는 도메인을 넣어두면, 그 하나가
  실패할 때 전체가 실패한다. 목록은 실제로 서비스하는 것만 담아야 한다.
- **명령이 성공했다고 반영된 게 아니다.** 인증서 발급처럼 "산출물의 경로"가 바뀔 수 있는
  작업은, 성공 메시지가 아니라 **소비하는 쪽이 보는 경로**를 확인해야 한다.
- 인증서 계보 이름을 명시하는 옵션은 처음부터 넣어두는 게 좋다. 도메인 구성이 바뀌는
  일은 드물지만, 바뀔 때 조용히 어긋나기 때문이다.

## 미해결·열린 질문

- 무료 호스트명의 30일 확인은 여전히 사람이 해야 한다. 놓치면 이번과 같은 일이 반복된다.
  자체 도메인 구입으로 넘어갈지, 넘어간다면 언제일지 미정.
- 서브도메인을 확보하면 서브패스로 붙인 페이지를 그쪽으로 옮기는 게 낫다. 상대 경로
  문제도 사라지고 가상호스트 분리도 깔끔해진다. 옮길 시점 미정.
