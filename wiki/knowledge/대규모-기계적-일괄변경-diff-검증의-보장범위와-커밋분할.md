# 대규모 기계적 일괄 변경 — diff로 무엇이 검증되고 무엇이 안 되는가

## 한 줄 정의

한 패턴을 18개 파일 44곳에서 걷어내며 쓴 검증 방법과, 그중 하나가 생각만큼 강하지 않다는 것. 대상이 무엇이었는지는 [[코드-주석에-문서-내부번호를-박지-않는다-재사용이-더-나쁘다]]에 있고, 여기서는 대상과 무관하게 성립하는 부분만 적는다 — import 정리든 deprecated API 치환이든 같은 얘기다.

## 삭제 줄만 보는 검사는 절반만 증명한다

파일이 많아 diff를 눈으로 다 확인하기 어려워서 이 명령으로 "의도한 것만 바꿨나"를 확인했다.

```bash
git diff -U0 | grep "^-" | grep -v "^---" | grep -v "<대상 패턴>"
```

결과가 0건이면 **삭제된 줄이 전부 대상 패턴을 포함한다**는 뜻이다. 여기까지는 맞다.

**그런데 이걸 "무관한 줄은 하나도 안 건드렸다"로 읽으면 틀린다.** 구멍이 둘이다.

1. **추가 줄(`^+`)을 전혀 안 본다.** 패턴이 든 44줄을 지우고 아무 내용이나 44줄을 넣어도 통과한다. **삽입·삭제 줄 수가 같다는 것(44/44)도 "각 줄이 제자리에서 치환됐다"를 증명하지 않는다.**
2. **같은 줄에서 패턴을 지우면서 다른 부분까지 고친 경우를 못 잡는다.** 그 줄에는 여전히 패턴이 들어 있으니 검사를 통과한다.

즉 이 검사가 보장하는 것은 **"대상과 무관한 줄을 통째로 지우지는 않았다"** 하나뿐이다.

**대칭 검사를 붙여야 제자리 치환까지 확인된다.**

```bash
# 삭제 줄에서 패턴만 지운 결과가 추가 줄과 같은지 비교
git diff -U0 | grep "^-" | grep -v "^---" | sed 's/<대상 패턴>//' | sed 's/^-//' > /tmp/before
git diff -U0 | grep "^+" | grep -v "^+++" | sed 's/^+//' > /tmp/after
diff /tmp/before /tmp/after   # 차이 0이면 각 줄이 제자리에서 치환됐다
```

(패턴 제거가 공백·구두점을 남기는 경우 `sed`를 실제 치환 규칙에 맞춰야 한다. 위는 뼈대다.) **커밋을 나눈 뒤에 확인하려면 범위를 줘야 한다** — `git diff`는 워킹트리만 보므로 커밋 후에는 `git diff <base>..HEAD`로 같은 검사를 돌린다.

> **일괄 변경의 diff 검증은 "삭제 쪽만 보는 검사"와 "삭제·추가를 대조하는 검사"가 보장 범위가 다르다.** 전자만 돌리고 "확인했다"고 말하면 과장이다. **리뷰어에게 검증 결과를 제시할 때도 어느 쪽을 돌렸는지 밝혀야 한다.** 검증 결과를 실제보다 강하게 말하는 것을 경계하는 결은 [[명세-자기검토의-한계와-인용한-규약의-실재성-검증]]과 같다. 소문자화 치환 검증에서 "로컬에서 열어본다"가 아니라 grep 전수 검색을 쓴 선례는 [[문서-코드-정합성-개념정본-심볼최소화]].

## 커밋 분할 기준에 하나를 더한다

목적이 다른 변경은 나눈다 — 이 기준은 그대로 둔다([[스코프-규율-한-pr-한-목적-인접부채-별도이슈-분리]]). 여기에 하나를 더한다.

> **목적이 하나여도, 리뷰어가 한 번에 훑기 어려운 규모면 나눈다.** 나누는 선은 리뷰 맥락을 따른다 — 같이 봐야 이해되는 것은 붙여 두고, 독립적으로 읽히는 경계에서 자른다.

이번에는 목적이 하나(식별자 제거)였지만 44곳이라 도메인 경계(주문 / 결제)로 둘로 갈랐다. 각 도메인의 운영 코드와 테스트 코드는 주석 변경의 맥락을 함께 봐야 하므로 나누지 않았다.

**다만 이 분할이 실제로 리뷰를 쉽게 했는지는 확인하지 못했다.** 리뷰 코멘트나 소요 시간 같은 신호를 보지 않았고, 둘로 나눠도 커밋당 22곳이라 여전히 적지 않다. **"그렇게 판단해서 나눴다"까지가 사실이고 효과는 미검증이다.**

## 열린 질문

- **위 대칭 검사는 이 작업 *이후에* 정리한 것이고 실제로 돌려보지는 않았다.** 다음 일괄 변경에서 검증해야 한다.
- 기계적 변경이 수백 곳 규모가 되면 커밋 분할만으로는 리뷰가 감당되지 않을 것이다. 그때 무엇을 근거로 "이 변경은 눈으로 안 봐도 된다"고 합의할지(검증 스크립트를 리뷰 대상으로 삼는 등)는 정하지 않았다.
