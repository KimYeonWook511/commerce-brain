# 하네스 프로세스 무게 조정과 문서-동작 정합 — 규칙은 기억이 아니라 정본으로 확인

**한 줄 정의.** 자체 개발 하네스(태스크 문서 탐색·논의·step 설계·구현·리뷰·커밋·문서 동기화를 묶은 9단계 workflow + `execute.py` 실행기)를 굴리며 굳힌 프로세스 무게·문서 정합 규율 — 진입 게이트는 제거가 아니라 경량화하되 근거를 정본 협업 규칙과 대조하고, 하네스 동작 기억이 문서와 어긋나면 방어 말고 검증하며, 작업 규모에 프로세스 무게를 맞춘다.

## 게이트는 제거가 아니라 경량화 — 정본 협업 규칙에 스킬 문서를 맞춤

실행기(`execute.py`)를 돌리기 직전의 게이트가 원래 "Plan Mode로 구현 계획 제시 → `ExitPlanMode`로 사용자 승인" 이라는 무거운 절차였는데, 이를 "File Drafting 결과·실행 계획을 보고하고 진행 의사를 가볍게 확인받은 뒤 실행 모델을 골라 바로 실행"으로 경량화했다(#223).

- **제거가 아니라 경량화로 정한 근거:** 팀 협업 규칙 정본 문서는 실행기에 대해 "진행 확인 후 실행"만 요구했지 Plan Mode + `ExitPlanMode`라는 무거운 의식을 요구하지 않았다. 그 의식은 스킬 문서가 자체적으로 격상시킨 것이었다. 그래서 가벼운 확인이 오히려 협업 규칙 원문과 더 정합했고, 정본 규칙 문서는 그대로 두고 스킬 문서만 원문 수준으로 내렸다.
- **게이트 자체를 없애지 않은 이유:** 실행기에는 자동 코드 검증 게이트가 없어 "진행 전 사용자 확인" 룰을 agent가 직접 지켜야 한다. 확인 단계는 남기되 형식만 가볍게 했다.

## 하네스 동작 기억이 문서와 어긋나면 방어 말고 검증

사용자는 이 하네스 버전(v2)을 "Plan Mode 게이트를 제거한 버전"으로 기억했다. 처음엔 스킬 문서를 인용하며 "규칙대로 한 것"이라 방어했는데, 사용자가 되짚어 스킬 문서를 grep해보니 **게이트가 그대로 남아 있었다.** v2는 실행기·agent 실행 계층만 다시 짰을 뿐 앞뒤 9단계 workflow(그 사이 진입 게이트 포함)는 이전 버전에서 계승한 것이었다. 즉 사용자 기억이 틀렸고 게이트는 살아 있었다 — 그리고 그 확인이 위 경량화 결정의 출발점이 됐다("어차피 살아 있으니 제거 대신 경량화가 실제 선택지").

- **규율:** 도구/하네스 동작에 대한 기억이 문서와 어긋날 땐 방어하지 말고 스킬 문서·코드로 검증한다. 이는 "규칙은 기억이 아니라 정본으로 확인"의 실물이며, [[설계단계-검증-정본·선례-확인실패와-전제의-적대적검증]]의 "harness에 지식을 박지 말고 정본 문서로 라우팅한다"는 통찰과 같은 정신이다.

## 작업 규모에 맞춘 프로세스 무게 — 작은 fix엔 경량 경로

PR #218의 변경은 사실상 1 step짜리(예외 catch 범위 축소)였다. 여기에 무거운 워크플로(task 문서 5종 + 다단계 실행기)를 태우는 건 과했다 — 산출물(문서·단계)이 변경보다 무거워진다.

- 소규모 변경은 경량 경로(worktree + plan + 직접 구현)로 충분하다. 무거운 워크플로 스킬은 여러 단계로 쪼개지는 큰 작업용으로 남긴다.
- **규율:** 작업 규모에 맞춰 프로세스 무게를 고른다 — 단일 스텝 fix에 다단계 실행기를 끌어오지 않는다.

## 커밋/기록 에이전트 순서와 문서-동작 drift

step 한 바퀴는 개발 → 리뷰 → 커밋(커밋 에이전트) → 상태 기록(기록 에이전트) 순이다. 기록 에이전트는 phase 상태 파일에 쓰기만 하고 git 권한이 없어 스스로 커밋하지 못한다. 그래서 한 step의 상태 파일 변경은 **다음 step의 커밋 에이전트**가 뒤늦게 함께 커밋한다 — git log가 뒤섞여 보이는 이유다.

- **문서 drift:** 하네스 레퍼런스 문서에는 "phase 상태 파일은 마지막 finalize 단계가 일괄 커밋하고 커밋 에이전트는 상태 파일을 건드리지 않는다"고 적혀 있는데, 실제로는 커밋 에이전트가 step별로 상태 파일을 커밋하고 있어 문서와 동작이 어긋난다.
- **처리:** 어느 쪽으로 정합화할지(커밋 에이전트 제약 강화 vs 문서 갱신)는 이번에 결정하지 않고, 하네스 자체를 고치는 PR이 난립하는 걸 피하려 별도 chore로 묶어 배치 처리하기로 미뤘다. 이는 하네스 개선 발견도 [[스코프-규율-한-pr-한-목적-인접부채-별도이슈-분리]]의 처리처 매핑을 따른 것이다.

### 도구 lifecycle을 미리 검증한다

`execute.py`가 worktree 안 파일을 못 찾는 ROOT 경로 계산 버그로 수동 구현 우회한 적이 있고(order-idempotency 작업 회고), worktree 작업 중 루트 문서를 메인 체크아웃에 잘못 편집한 실수, 존재하지 않는 마커를 무한 체크하는 빈 busy-loop로 CPU를 오래 점유한 실수도 있었다. 교훈은 도구를 쓰기 전에 그 동작 방식(ROOT 계산·worktree lifecycle)을 미리 검증하고, 백그라운드 완료는 자동 알림을 신뢰해 빈 폴링 루프를 쓰지 않는 것이다.
