# 문서 작성을 여러 작업자에게 병렬로 나눌 때 생기는 경계 구멍

## 한 줄 정의

큰 작업이 끝난 뒤 문서 정리(설계 결정 117,000자 → 영구 문서 28개 + 구조·계약·스키마 문서 병합)를 **LLM 에이전트 여럿에게 묶음별로 나눠 맡기고 사람 한 명이 취합·검수**한 기록. 순차로 하면 오래 걸리고, 한 작업자가 전부 쓰면 **맥락이 한계에 닿아 압축되면서** 앞서 쓴 것과 어긋날 위험이 있었다.

**다만 병렬로 얻은 시간은 재지 않았다.** 아래 비용(취합 항목 설계, 완료 판정 사고, 검수 부담)은 실제로 드러났는데 이득 쪽은 체감이고 측정이 없다 — **트레이드오프가 한쪽만 실측된 상태**다.

## 1. 병렬 작업자에게 "뒤집힌 결론"을 미리 알려 준다

가장 큰 위험은 **작업자가 원본 본문만 보고 옛 내용을 옮기는 것**이었다. 원본이 불변 원칙 때문에 본문을 안 고치고 상태 줄에만 정정을 적어 두는 관례를 쓰고 있었기 때문이다([[작업중-결정을-영구-adr로-승격하는-단위-개정사슬-접기]]).

공통 지시에 이걸 최우선으로 박고 **묶음마다 그 묶음에서 뒤집힌 사슬의 최종 상태를 구체적으로 적었다.**

```
묶음 A   "환불을 부모의 자식으로 둔다"  →  나중 결정이 독립 aggregate로 뒤집음
묶음 B   "시스템이 만드는 것은 키를 비운다"  →  나중 결정이 "비우지 않는다"로 뒤집음
묶음 C   "시각을 하나로 합친다"  →  나중 결정이 "셋으로"로 뒤집음
묶음 D   종결 상태 이름이 두 번 바뀜
묶음 E   "aggregate 경계로 가른다"  →  나중 결정이 "도메인 경계로"
```

이걸 안 적었으면 다섯 묶음이 각자 옛 내용을 옮겼을 것이다. **작업자는 자기 묶음만 보므로, 다른 묶음이 자기 것을 뒤집었다는 사실을 모른다.**

## 2. "담지 못한 것"을 스스로 보고하게 했다

지시 마지막에 이 항목을 넣었다.

> 원본에 있었지만 담지 못한 내용이 있으면 그것도 적어라(취합할 때 확인한다).

**이게 이번 방식에서 가장 효과가 컸다.** 실제로 잡힌 것들:

- 한 작업자가 "기각 대안 하나를 뺐다"고 보고 → 확인해 보니 **나중에 이 결정을 다시 열 때의 출발점**이라 되살렸다.
- 한 작업자가 "원본에 후속 결정이 없어 어느 갈래로 접는지 임의로 정하지 않았다"고 보고 → **코드에서 실제 매핑을 확인해** 채웠다. 지어냈으면 구현과 어긋났을 자리다.
- 한 작업자가 "이 항목은 다른 묶음 담당이라 안 썼다"고 인계 → 그 묶음이 실제로 담았는지 확인했다.

> **작업자가 "완벽하게 했다"고만 보고하면 취합자가 무엇을 확인해야 할지 알 수 없다.** 불완전함을 드러내게 하는 항목이 검수의 출발점이 된다.

## 3. 기존 내용 보존을 최우선 원칙으로 박았다

구조·계약·스키마 문서는 **여러 도메인이 함께 적힌 파일**이라 담당 도메인만 갱신하고 나머지는 한 글자도 건드리면 안 됐다.

```
1. 기존 파일을 전부 읽는다
2. 대응하는 작업 문서를 전부 읽는다
3. 기존 구조·목차·문체를 그대로 두고 담당 절만 갱신한다
4. 전체 완성본을 저장한다
```

**"기억으로 재작성하지 마라"를 명시**했다. 파일을 안 읽고 쓰면 안 건드릴 부분이 사라지거나 문체가 달라진다.

## 4. 스키마 문서에만 "작업 문서를 믿지 말라"고 지시했다

> 실제 DDL이 마이그레이션 스크립트에 있고 그것이 단일 출처다. 작업 문서는 설계 시점의 것이라 구현과 다를 수 있다. **반드시 실제 마이그레이션과 엔티티를 읽고 그것을 기준으로 써라.** 특히 컬럼 길이를 조심하라 — 작업 중에 여러 번 바뀌었다.

작업 중 멱등키가 96자에서 64자로, 다른 키가 64자에서 40자로 좁혀졌었다. **설계 문서를 그대로 옮겼으면 실제 스키마와 어긋났을 것이다.**

> **문서 종류마다 "정본이 어디인가"가 다르다.** 스키마는 마이그레이션이, 계약은 컨트롤러·DTO가 정본이다([[문서-코드-정합성-개념정본-심볼최소화]]). **병렬 작업자에게 그 정본을 지목해 줘야 한다.**

## 막힌 점 — 완료 알림을 안 기다리고 커밋했다

세 문서 중 둘은 완료 보고를 받고 커밋했는데 **하나는 파일이 바뀐 것만 보고 "끝났다"고 판단**했다. 그 작업자는 아직 편집 중이었다. 결과적으로 **중간 상태가 커밋됐고** 그 뒤 마지막 두 편집이 커밋 밖에 남았다.

```
로그 예시가 코드에서 이미 제거된 식별자를 그대로 쓰고 있었다
의존성 설명이 이번 작업에서 옮겨져 더는 존재하지 않는 패키지 경로를 가리키고 있었다
```

**둘 다 실제로 필요한 정정이었다.**

> **파일 변경 감지는 "쓰는 중"과 "다 썼다"를 구분하지 못한다.** 완료 판정은 명시적 신호로만 해야 한다.

**이것이 병렬 작업에서 특히 위험한 이유는 완료 신호가 여러 개이기 때문이다.** 순차로 하면 기다릴 신호가 하나라 놓칠 수가 없다. 병렬에서는 **그중 하나만 놓쳐도 부분 상태가 커밋되고**, 게다가 다른 작업자들이 이미 끝나 있어서 "이제 다 됐다"는 인상이 강해진다.

## 취합자가 검수할 것을 미리 정해 두었다

```
① 뒤집힌 옛 내용이 남았나        (뒤집힌 표현들을 문자열로 전수 검색)
② 이름·식별자가 겹치거나 넓지 않나
③ 서로 모순되지 않나
④ 분량이 기존 분포 안인가
⑤ 원본에만 있던 표기(편집 취소선, 내부 번호 참조)가 남았나
```

①과 ⑤는 기계로 전수 검사가 가능했다(결과 0건). ②는 파일명 목록을 훑어, ④는 글자 수를 재어 확인했다. **③(서로 모순되지 않는가)은 결국 제대로 못 했다** — 28개를 통독하는 것 말고 방법이 없어 인접해 보이는 것들만 골라 봤다. **다섯 항목을 세워 놓고 실제로 전수 검사한 것은 둘뿐이다.**

## 배운 것

- **병렬 작업의 실패는 "각자 잘못 쓴 것"보다 "경계가 빈 것"에서 나온다.** 각 작업자는 자기 범위를 성실히 하지만, 범위 사이에 걸친 것은 서로 상대가 할 거라고 생각하고 아무도 안 한다.
- **작업자가 모르는 것을 지시가 알려 줘야 한다.** 뒤집힌 결론, 정본의 위치, 다른 묶음과의 관계는 작업자가 자기 범위만 봐서는 알 수 없다.
- **작업자가 "임의로 정하지 않고 남긴" 판단은 존중할 만하다.** 원본에 답이 없는 자리를 그럴듯하게 메우면 나중에 구현과 어긋난다.
- **기존 내용이 함께 사는 파일을 갱신할 때는 "무엇을 건드리지 마라"가 "무엇을 써라"보다 중요하다.**

## 열린 질문

- **병렬 작업자 사이의 인계를 구조적으로 보장할 방법이 없다.** 묶음이 더 많아지면 취합 부담이 그만큼 커진다.
- **취합자가 검수할 항목을 미리 다 알 수 있는가.** 이번에는 뒤집힌 결론을 알고 있어서 전수 검색이 가능했다. 그걸 모르는 상황이라면 무엇을 찾아야 할지도 모른다.
- **작업자가 스스로 "뺐다"고 보고한 것 외에, 보고조차 안 한 누락은 어떻게 잡나.**
