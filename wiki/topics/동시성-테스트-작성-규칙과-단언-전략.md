# 동시성 테스트 작성 규칙 — "타이밍을 운에 맡기지 않는다"

한 줄 정의: 동시성 테스트는 자연 race를 *어쩌다 일어나게* 하고 그 순간을 단언하는 게 아니라, **인터리빙과 무관하게 성립하는 불변식만 단언**하거나(제거) **인터리빙을 결정론적으로 확정**한다(통제).

## 정본 위치 — 프로젝트 테스트 컨벤션 문서 (규칙 본문 복사 금지)

규칙 본문 자체의 정본은 코드 repo(commerce-backend)의 테스트 컨벤션 문서 "동시성 테스트 작성 규칙" 섹션(PR #187에서 신규 추가, 정확한 path는 side-repo가 채움)이다. 이 노트는 규칙 본문을 복사하지 않고, 그 규칙에 이른 *사고 과정과 왜*를 companion으로 담는다.

## 트리거 — AI 안티패턴 반복 (Thread.sleep, race 무대 stub 강제)

AI에게 테스트 작성을 맡겼을 때 `Thread.sleep`으로 타이밍 맞추기, race 무대 컴포넌트의 분기 결과를 stub으로 강제하기 같은 안티패턴이 반복 출현한 게 컨벤션화 트리거였다. 한두 번은 일회성 지시로 잡지만, 같은 패턴이 계속 보이면 매번 같은 토론을 되풀이하지 않도록 컨벤션으로 박아야 한다. 이슈 #186을 메타이슈로 열고 PR #187에서 문서에 규칙을 신규 추가하며 위반 테스트를 정리했다. (같은 결의 AI 협업 안티패턴 대응은 [[코드베이스-패턴-우선-설계판단-미사용api-방어가드-자동리뷰]]·[[ai-코드리뷰-종합-층위통합과-심각도-도메인보정]] 참조.)

## 핵심 원칙 두 갈래 — 제거(invariant) / 통제(seam·latch)

처음엔 "타이밍을 제거한다"만 헤드라인으로 잡았는데, 그러면 latch/seam으로 인터리빙을 의도적으로 통제하는 접근과 어긋난다는 다른 AI 검토 피드백을 받아 원칙을 두 갈래로 나눴다.

- **제거** — 결과를 인터리빙과 무관하게 만든다. N thread를 동시에 던지고, 어떤 순서로 섞이든 성립하는 **불변식만 단언**한다("재고는 음수가 안 됨", "성공은 정확히 1건"). 기본이자 광범위 race 검증용.
- **통제** — 인터리빙을 결정론적으로 확정한다. *알려진 race 버그를 회귀로 박제*할 때만 쓰는 예외 패턴. seam/hook으로 순서·타이밍을 고정한다.

자연 race에 의존하기(`Thread.sleep`으로 타이밍 맞추기, latch로 thread 간 *속도* 맞추기, 그냥 동시에 돌려 어쩌다 일어난 걸 단언하기)는 전부 안티패턴이다. 위험한 인터리빙은 테스트로 잡을 게 아니라 락/유니크 제약/원자적 UPDATE/트랜잭션 경계 재설계로 애초에 *불가능*하게 만들고, 테스트는 그 설계가 작동하는지 invariant로 확인한다([[도달불가분기-방어금지-불변식테스트-돈정합성-통합테스트]]와 같은 철학).

## stub 기준 — '컴포넌트 종류'가 아니라 'race의 무대인가'

초안에서는 "DB, 락, application service는 stub하지 않는다"처럼 **컴포넌트 종류**로 기준을 잡았다. 사용자 피드백으로 **"검증하려는 race가 그 컴포넌트에서 일어나는가"**라는 기준으로 전환했다.

- 그 컴포넌트가 race의 무대면 진짜를 쓴다 — stub하는 순간 무대가 사라져 검증이 무의미해진다.
- 무대 밖이면 mock한다 — 예: PG gateway는 그 race의 무대가 아니라 mock 가능, idempotency store 같은 인프라도 race 검증 대상이 아니면 mock 가능.

판단은 컴포넌트 종류가 아니라 "무대인가"로 한다.

## willAnswer의 관찰 vs 결정 경계

받은 검토 피드백 중 가장 정확했던 지적. 같은 `willAnswer`라도 무엇을 하느냐로 갈린다.

- **관찰 (OK)**: `AtomicInteger`로 호출 횟수를 세는 것 — 외부 호출을 *기록*만 한다.
- **결정 (금지)**: `doReturn(false).when(service).hasStock()` — race 무대의 결과를 *가짜로 정한다*.

이 한 줄이 "mock 응답은 thread-safe하게 작성하라(권장)"와 "race 무대 컴포넌트의 분기 결과를 stub으로 강제하지 마라(금지)"의 양립을 명확하게 했다. mock이 race를 관찰만 하면 되고, 결과를 대신 결정하기 시작하면 그건 이미 동시성 검증이 아니다.

## 통제의 결과 단언 한계 — window는 강제, 결과는 invariant

데드락이나 락 타임아웃처럼 결과가 DB 스케줄러에 달린 경우, 어느 thread가 winner가 될지는 결정론으로 단언할 수 없다. 그래서 **인터리빙 window 자체는 결정론적으로 강제하되, 결과는 invariant로만 단언**하는 hybrid가 정상이다. 주문 생성 비관적 락 데드락 통합 테스트(`OrderConcurrencyServiceDeadlockTest`)의 latch hook 예시가 이 형태다.

- 재고 감소 서비스(`DecreaseStockService.decrease` — 주문 생성 시 비관적 락을 잡는 지점)에 `willAnswer`를 걸되 `callRealMethod()`로 실제 로직은 그대로 실행하고, 개수 2짜리 `CountDownLatch`로 양쪽 thread가 각자 첫 락을 잡을 때까지 서로 대기시켜 "반대 순서로 락을 잡는 window"를 결정론적으로 강제한다. (응답을 강제하는 게 아니라 순서만 확정한다.)
- 결과는 `errors.isNotEmpty()`(적어도 하나는 실패)와 `orderCount < 2L`(둘 다 성공할 수는 없음) 같은 invariant로 단언한다. DisplayName도 불변식을 서술하도록 맞췄다. `assertThatThrownBy`로 특정 예외를 못박으면 flaky가 된다.

이 window-강제/결과-invariant 구도는 [[하네스-ac-검증범위-격리테스트와-위험경로-결정적강제]]의 "위험 경로 결정적 강제"와 같은 골격이다.

## PR #179에서 나온 단언 전략 — race 발생 자체는 포기

PR #179(payment_attempt unique 회귀 복구, 세부는 [[multi-column-unique-length-명시-컨벤션]])에서 동시성 테스트의 단언 전략이 실사례로 다듬어졌다.

- **"race가 실제로 났는지" 자체를 단언하지 않는다.** `errors.anyMatch(DataIntegrityViolationException)`로 race 발생을 강제하던 단언을 제거했다. race 발생 여부는 환경 의존적이다 — CPU 코어가 적거나 CI 부하가 크면 첫 스레드 커밋 후 나머지가 사전 `find` 분기로 빠져 race가 아예 안 날 수 있다. 이게 CI flake의 원천이었다. 잃는 건 "race 발생 가시화"뿐이고, 데이터 invariant(`count == 1`)와 발생 예외 분류(`assertRaceOrPaymentError` helper)는 환경 독립적으로 남는다.
- **latch barrier로 anyMatch를 살리려던 실험은 revert했다.** `@MockitoSpyBean`으로 repository에 latch를 건 결과, `@Repository` Adapter가 이미 Spring CGLIB proxy인데 Mockito spy로 이중 wrapping되며 `callRealMethod`의 reflection 경로에서 unchecked 예외가 `InvocationTargetException` → `UndeclaredThrowableException`으로 포장돼 기대한 예외가 안 잡혔다. spy로 동시성을 제어하려면 interface가 아니라 service 레이어에서 직접 hook하거나 test-specific 진입점을 두는 게 안전하다.
- **HikariCP pool은 동시성 테스트 클래스 단위로 inline 명시.** 20 thread + 보상 흐름(REQUIRES_NEW 별도 커넥션)은 기본 pool size 10을 초과해 `CannotCreateTransactionException`을 낸다. `@SpringBootTest(properties = {...})`로 `maximum-pool-size=30` 등을 박았다. 다른 동시성 테스트가 이미 같은 컨벤션을 써 그에 맞췄다 — 새 동시성 테스트 추가 시 기존 컨벤션 search가 reflex여야 한다.

## stress/soak는 컨벤션 범위 밖

부하·성능 측정은 JUnit/Spring 영역이 아니라 k6, Gatling 같은 전용 부하 도구의 영역이다. 별도 트랙으로 분리하고, 이 컨벤션은 결정론적 동시성 검증만 다룬다.

## 위반 케이스 처리 — 분기 시뮬레이션이라 삭제

네이버페이 결제 승인 흐름 동시성 통합 테스트(`NaverPayServiceConcurrencyTest`)에서 새 규칙을 어기는 케이스 2건을 삭제했다. 둘 다 race 무대인 결제 승인 서비스(`PaymentApprovalService`)를 spy로 잡아 결과를 강제하고 있었다.

- `completeApprovedPayment`를 `doThrow`로 강제하던 케이스(동시 중복 결제 보상 취소 경로에서 cancel attempt가 하나만 생성되는지) → 자연 race로 발생하는 DUPLICATE 시나리오는 같은 클래스의 다른 테스트가 이미 커버.
- `isCompensationRequired`를 `doReturn(false)`로 강제하던 케이스(다른 thread가 이미 Payment를 완료해 보상 cancel이 skip되는지) → 같은 시나리오를 보상 로직 단위 테스트(`PaymentApprovalCompensationServiceTest`)가 mock으로 검증.

진짜 race 시나리오로 재설계하는 것도 가능하지만(다른 thread가 먼저 Payment를 commit하는 timing 통제 필요), 단위 테스트가 이미 검증하는 시나리오라 동시성 테스트로서의 가치가 낮아 삭제를 택했다. 이 삭제한 두 테스트 파일 자체는 코드 정본(repo)에 있다. 결제 승인 보상의 계층 분리·결정적 검증 배경은 [[payment-낙관락-충돌처리-3계층-흡수는-트랜잭션-밖]] 참조.

## 배운 것

- **flaky의 본질 재정의.** 처음엔 "자연 race = flaky"로 단정했으나 정정했다 — flaky의 원인은 **인터리빙에 의존하는 단언**이지 자연 race 자체가 아니다. 인터리빙과 무관한 invariant를 단언하면 자연 race로도 안정적이다.
- **진짜 race-safety vs 분기 시뮬레이션.** 삭제한 위반 케이스들은 *분기 결과 시뮬레이션*이었지 동시성 검증이 아니었다. 이런 건 단위 테스트가 더 적합하다. 동시성 자원(DB, 락)이 살아있는 상태에서 N thread를 던지고 invariant를 보는 게 진짜 race-safety 검증이다.
- **테스트로 잡을 일이 아닌 것.** 타이밍에 따라 결과가 달라진다는 건 로직이 race에 노출됐다는 신호다. 답은 "모든 타이밍을 테스트하자"가 아니라 "타이밍과 무관하게 설계하자"다.
