# 서블릿 필터의 예외 처리·에러 디스패치 — 전역 핸들러 경계와 OncePerRequestFilter

## 한 줄 정의

Spring Security 없이 `OncePerRequestFilter`로 자체 인증을 구현할 때, 필터 계층의 예외가 전역 예외 핸들러(`@RestControllerAdvice`)에 닿지 않는다는 사실에서 파생되는 예외 처리 규칙들.

## 범위 — OncePerRequestFilter 기반 자체 인증

이 백엔드는 Spring Security를 쓰지 않고 평범한 서블릿 필터(`OncePerRequestFilter`)로 자체 JWT 인증을 구현한다(그 인증/인가 진입점의 패키지 구조는 [[security-common-leaf-재편과-토큰-포트-네이밍]]). 아래는 그 리팩터 중 정리한, 다른 백엔드에도 그대로 써먹을 수 있는 일반 지식이다.

## 서블릿 필터 예외는 전역 핸들러(@RestControllerAdvice)에 닿지 않는다

`@ControllerAdvice`/`@ExceptionHandler`는 요청을 컨트롤러로 라우팅하는 프론트 컨트롤러(DispatcherServlet) **안에서** 핸들러가 던진 예외만 처리한다. 서블릿 필터는 그 프론트 컨트롤러 **앞**에서 돈다. 그래서 필터 자체에서 던진 예외는 전역 핸들러가 절대 못 본다.

따라서 필터 단계의 인증 실패 응답은 **필터가 직접** 써야 한다(전역 핸들러가 대신 못 해줌). 반대로 컨트롤러/서비스가 던진 예외는 프론트 컨트롤러 안이라 전역 핸들러가 정상 처리한다. 바로 이 경계 때문에 [[도메인-예외-httpstatus-제거-errorcategory]]의 카테고리→HttpStatus 매핑을 전역 핸들러의 private 메서드로 둘 수 없고, 필터·인터셉터가 공유하는 별도 유틸로 빼야 했다.

## doFilter()를 인증 try-catch 밖으로 — 하류 예외 오처리 방지

처음 필터는 `filterChain.doFilter()`(=이후 필터 체인 + 컨트롤러 전체 실행) 호출을 인증 try-catch **안에** 두고 있었다. 그래서 하류 컨트롤러/서비스에서 난 예외까지 필터의 `catch`에 잡혀 401로 오처리될 수 있었다.

해결: 토큰 인증 호출만 try-catch로 감싸고(인증 실패만 401), `doFilter()`는 그 catch **밖**으로 빼서 하류 예외가 정상 전파되게 했다.

## 필터 catch(Exception) 안티패턴과 프레임워크 기본 에러 처리(포맷 차이)

필터에서 예상 못한 예외를 잡아 직접 응답하려는 유혹이 있지만, 그러면 필터마다 `catch(Exception)`을 달아야 하는 안티패턴이 된다. 실제로 이 프로젝트의 다른 필터들(요청 추적 ID 필터, 접근 로그 필터)은 catch 없이 `try { doFilter } finally { 정리 }`만 두고 예외를 그대로 전파한다.

전파된 예외는 서블릿 컨테이너가 받아, Spring Boot가 자동 등록한 기본 에러 엔드포인트(`/error`, `BasicErrorController`)로 내부 forward → 500 응답 + 로그를 프레임워크가 일괄 처리한다. 단 그 500 응답 포맷은 프레임워크 기본(`{timestamp,status,error,path}`)이라, 컨트롤러 예외가 전역 핸들러를 거쳐 나가는 우리 표준 포맷(`{code,message,data}`)과 다르다. 이 포맷 차이는 필터 계층 전체에 공통이지 특정 필터만의 문제가 아니다.

결론: 인증 필터의 제네릭 `catch (Exception)`(예상 못한 예외를 401로 삼키던 것)을 제거했다. 토큰 검증기는 상태 없는 JWT 파싱이라 정상적으로는 구체 인증 예외만 던지므로, 그 제네릭 catch는 사실상 **도달 불가한 죽은 코드**였고 오히려 예상 못한 예외를 401로 위장했다. (JWT 파싱 예외를 라이브러리 베이스로 제대로 잡게 고친 뒤 — [[jwt-예외-catch-footgun-bare-securityexception]] — 위조 토큰조차 구체 인증 예외가 되므로 이 제네릭 catch는 완전히 도달 불가가 된다.) 정말로 필터 계층 500까지 표준 포맷으로 통일하려면 "필터마다 catch"가 아니라 "최외곽 에러 처리 필터 하나"가 올바른 방법이다 — 이번엔 도달 불가 경로라 불필요.

## /error 재인증 방지 — shouldNotFilterErrorDispatch vs Spring Security 인가 필터

걱정했던 시나리오: 예외가 `/error`로 forward되면 그 요청이 인증 필터를 **다시** 타서, `/error`가 인증 화이트리스트가 아니니 401로 뒤바뀌는 것 아닌가?

실제로는 안 그렇다. `/error`로 가는 건 일반 요청이 아니라 **ERROR 디스패치**다. `OncePerRequestFilter`에는 `shouldNotFilterErrorDispatch()`가 있고 **기본값이 true**라, ERROR 디스패치일 때는 필터 본체 로직(토큰 검증)을 **건너뛴다**. 핵심은 필터가 어느 디스패치 타입에 등록되느냐가 아니라 이 스킵 메서드다 — 설령 ERROR 디스패치에서 실행되더라도 본체 로직을 건너뛰게 하므로 안전하다.

대조(중요한 실무 지식): **Spring Security**를 쓸 때는 달랐다. Spring Security의 인가 필터(`AuthorizationFilter`, Security 5.7/6.0 기준)는 ERROR·FORWARD 디스패치에도 적용되기 때문에, `/error`로 forward되면 인가를 다시 타 막혔다. 그래서 예전엔 `.requestMatchers("/error").permitAll()`로 `/error`를 열어줘야 했다. 우리는 평범한 `OncePerRequestFilter`라 그 스킵 메서드 덕분에 `/error`를 따로 허용할 필요가 없다. MVC 계층도 안전하다 — 기본 에러 컨트롤러엔 우리 권한 애너테이션(`@RequireRole`)이 없어 권한 인터셉터도 no-op으로 통과.
