# payment 도메인 현재 구조 (2026-08 부분환불 재설계 이후)

## 한 줄 정의

**결제와 환불이 각자 aggregate이고, 그 둘을 묶는 불변식은 "환불 총액이 결제 승인액을 넘지 않는다" 하나다.** 그 불변식을 먼저 확정하니 무엇이 한 덩어리여야 하는지, 어떤 값이 어디 있어야 하는지가 거의 자동으로 정해졌다.

이 문서는 **개념 지도**다. 각 판단의 근거는 링크된 결정 노트에 있고 여기서 반복하지 않는다. 코드 심볼·클래스 목록은 담지 않는다([[문서-코드-정합성-개념정본-심볼최소화]]). 2026-05 시점 스냅샷은 [[payment-도메인-구조-개요]]에 남아 있다.

## 어휘 — 먼저 갈라야 하는 말들

```
결제대행사 vs 간편결제   네이버페이는 간편결제다.  우리는 가맹점 쪽 조율자이지 PG 서버가 아니다
승인 vs 인증            인증은 사용자가 결제사 화면에서 본인 확인.  승인은 우리 서버가 돈을 청구
취소 vs 환불            취소는 주문에 가하는 행위.  환불은 그 결과로 돈이 돌아가는 것
회수(대사)              결과를 못 받은 건을 주기적으로 다시 집어 확인·재전송하는 것
```

전체 어휘와 세 층의 역할은 [[결제사-간편결제-구분과-세-층-역할-결과불명-재시도-모델]], 취소/환불/반품 용어 축은 [[부분취소-스코프-배송전-품목수량-기반-금액입력-기각]].

## 표 넷과 각자의 역할

```
결제        한 시도 = 한 행.  활성 슬롯으로 "그 주문에 살아 있는 결제 하나"를 강제
환불        독립 aggregate.  자기 상태 기계와 자기 낙관 락을 가진다
주문 품목    취소수량을 누적.  부분취소 잔액의 정본
호출 기록    결제사에 보낸 것·받은 것을 원본째 쌓는다.  판정에 쓰지 않는다
```

- **결제는 시도 원장이다.** 시도마다 새 행을 쌓고 기존 행을 재사용하지 않는다 — 몇 번 시도했고 각각 왜 실패했는지가 남아야 한다([[payment-append-only-원장과-exists-완료판단]]·[[유일슬롯-비우고-같은값-재점유-쓰기순서와-메서드이름-신호]]).
- **결제창을 띄우기 위한 예약 테이블은 없다.** 이중결제 차단이 두 곳에 흩어지는 것을 피해 결제 행의 활성 슬롯 하나로 모았다([[예약테이블-폐지-결제행-활성슬롯-단일화와-사라지는-방어]]).
- **호출 기록은 aggregate 밖이고 낙관 락이 없다.** 어떤 불변식에도 참여하지 않으므로 부모를 통해 저장할 이유가 없다([[외부-호출기록-aggregate-밖-낙관락-없는-쌓기전용]]).

## 금액이 어디 사는가 — 셋을 구분한다

| 무엇 | 어디 | 왜 |
|---|---|---|
| 주문 금액 스냅샷 | 주문·주문 품목 | 정책이 바뀌어도 과거 주문이 안 흔들려야 한다 |
| **결제사가 실제로 승인한 금액** | 결제 행 (별도 컬럼) | 우리 기록과 갈릴 수 있고, **한도의 기준은 이쪽이다** |
| 누적 환불액 | 결제 행 | 한도 판정이 읽는 유일한 값 |

**우리가 기억하는 값과 상대가 실제로 처리한 값을 같은 컬럼에 두지 않는다** — 합치면 어긋났을 때 대조할 방법이 사라진다([[한도-기준은-결제사가-실제로-승인한-금액]]). 이 구분의 일반 원리는 [[주문-금액-모델-도출·기록·스냅샷-3분류와-청구액-승인액-분리]].

## 불변식을 누가 지키는가

- **환불 한도는 결제가 판정한다.** 환불이 독립 aggregate인데도 그것을 만드는 것은 결제의 도메인 메서드다 — **불변식을 지키는 주체와 생명주기를 가진 주체가 다를 수 있다**([[환불-독립-aggregate-한도판정은-결제가-누적액-컬럼]]).
- **한도 계산에 상태로 예외를 두지 않는다.** 성공·요청됨·결과불명 환불을 전부 센다. **덜 세면 돈이 나가고 더 세면 회원이 잠시 기다린다.**
- **부분취소 잔액의 정본은 주문 품목의 취소수량이다.** 사건을 집계한 값은 사건의 상태에 딸려 있어 상태가 전이하면 집계가 움직이는데, 취소수량은 상태와 무관하게 누적된다([[부분취소-잔액-정본-수량기준-상태무관-누적]]).

## 동시성 — 무엇이 무엇을 막나

```
같은 주문에 살아 있는 결제 하나   결제 행의 활성 슬롯 (DB 유일 제약, NULL 로 비움)
동시에 환불을 만드는 것           결제의 누적 환불액이 실제로 바뀌어 낙관 락 버전이 오르는 것
환불 하나를 고치는 것             환불 자신의 낙관 락 (부모 버전을 흔들지 않는다)
같은 주문의 동시 취소             주문 행 비관 락
커밋 전에 도착한 같은 키          분산 선점 층 → "처리 중" 전용 응답
같은 키의 중복 처리(최종)         DB 유일 제약
```

- **한도를 판정하는 메서드는 부모 값을 바꾸지 않으므로 그 자체로는 버전을 올리지 못한다.** 누적액이 실제로 바뀌기 때문에 비로소 버전이 오르고 진 쪽이 물러난다 — **동시에 환불을 만드는 것에 대한 유일한 방어가 이 갱신이다**([[자식-환불-자기-낙관락-부모버전은-불변식이-바뀔때만]]).
- **잠금은 주문 행 하나만.** 품목 행까지 잠그면 두 요청이 겹치는 행을 다른 순서로 잠가 교착이 난다([[부분취소-동시성-주문행-단일잠금과-캐시겹-미도입]]).
- **커밋 전 중복에게 성공으로 답할 수 없다** — 앞 요청이 커밋에 성공할지 아직 모른다([[동시도착은-선점층이-받고-처리중-전용응답]]).

## 멱등키가 셋이다

| 값 | 누가 발급 | 바뀌나 | 유일 범위 |
|---|---|---|---|
| 사건 키 | 우리 도메인 | 안 바뀜 | — (외부 이력에서 우리 건을 집는 값) |
| 요청 멱등키 | 호출자 | 안 바뀜 | (부모, 요청자, 키) — **찾는 범위와 같게** |
| 결제사 호출 멱등키 | 우리 도메인 | 재시도 가능 실패에만 | 전체 — 겹치면 코드 버그다 |

**하나로 겸하게 하면 셋 중 하나는 반드시 깨진다**([[멱등키-세-값-분리와-요청멱등키는-호출자가-발급]]). 검증 전에 채우는 외부 값에는 유일 제약을 걸지 않는다 — 그 제약이 공격 수단이 된다([[검증-전에-채우는-외부값에-유일제약-금지]]).

## 트랜잭션 경계 — 원칙을 어긴 자리 셋

```
승인 확정        주문 + 결제              ★ 도메인 경계도 넘는다
승인 반려        결제 + 환불                 같은 도메인 안이다
결제된 주문 취소  주문 + 결제 + 환불 + 재고   ★ 도메인 경계도 넘는다
```

**돈이 걸린 자리에 틈을 만드는 위험이 원칙을 지키는 이득보다 크다**고 보고 허용했고, 대신 도메인 경계를 넘는 것만 별도 클래스로 갈라 **파일 단위로 셀 수 있게** 했다([[돈정합성-우선-경계넘는-트랜잭션-셋-허용과-셀-수-있게]]). 재고 복구는 최소 집합에 들지 않지만 안에 두고 **맨 뒤에** 배치했다 — 락 보유 시간을 줄이려는 것이고 순서가 계약이 된다([[재고복구-트랜잭션-맨뒤-배치와-비관락-경합-계측갈래]]).

## 결과를 모를 때

**결과 어휘가 넷이다** — 됐다 / 모른다 / 다시 시도할 수 있는 실패 / 다시 시도할 수 없는 실패. 응답 코드 표보다 **전송 계층 판정을 먼저** 보고, 서버 오류와 모르는 코드는 "모른다"로 접는다([[외부-돈-호출-결과어휘-넷과-전송계층-판정-우선]]).

```
회수 수단 순서   ① 이력 조회  → ② 같은 멱등키 재전송.  둘 중 하나만 쓰지 않는다
승인 확정        이력이 비면 승인 API 를 다시 부른다.  이 호출로 돈이 움직인다
환불 종착        성공 하나뿐.  자동으로 도달하는 실패 종착이 없다
회수 상한        없다.  회차마다 간격만 벌린다 (10초·30초·2분·5분·10분)
```

- **결과를 모르는 동안은 같은 멱등키로 다시 부른다.** 새 키는 상대의 중복 방지 보호를 스스로 포기하는 것이다([[결과불명-재호출은-같은-멱등키로-새키-결론-뒤집힘]]).
- **자동 회수를 멈추지 않는다** — 멈추면 받아서 처리할 경로가 없어 방치와 같다([[결과회수-상한-폐지와-백오프-표-통지-반복]]).
- **결제 실패는 정상 종료지만 환불 실패는 아니다.** 상태 기계를 복사하기 전에 그것부터 본다([[승인은-다시-물어-확정-환불에는-실패-종착이-없다]]).
- **회수 배치는 "그 주문 정말 취소됐어?"를 묻지 않는다** — 환불이 만들어지는 자리를 정당한 조건과 같은 트랜잭션으로 묶어 **확인이 필요 없게** 만들었다([[회수배치가-주문상태를-묻지-않는다-확인대신-전제를-지킨다]]).

## 결제사 경계

**나가는 인터페이스 하나 + 결제사마다 어댑터 하나.** 어댑터는 예외를 던지지 않고 타임아웃·서버 오류·모르는 응답을 전부 정해진 결과로 접는다. 나가는 호출 전부에 읽기 제한 시간을 걸고, **회원이 기다리는 자리보다 짧게** 둔다(기준은 화면이 아니라 배치 스레드를 오래 잡지 않는 것) — [[결제사-연동타입-인프라-격리와-나가는-호출-읽기제한시간]].

결제사 명세가 말하지 않아 실측으로 메운 것들은 [[네이버페이-환불-api-실측-기록]]에 있다. **회수 전략 전체가 그중 한 관측에 기대고 있다** — 요청에 실은 시도 키가 이력 행에 실려 돌아온다는 것([[네이버페이-환불-이력-지목근거-보내기전-우리가-정하는-값]]).

## 지금 감수 중인 것

- **끝내 확정되지 않는 환불이 있으면 그 금액만큼 추가 환불이 계속 막힌다.** 사람이 봐야 할 건임을 상태와 검토 코드로 표시하는 데까지는 왔지만 **그것을 다룰 관리자 화면이 없어 실제로는 아무도 풀지 못한다.**
- **결제사 정산 데이터와 대조하는 장치가 없다.** 우리 기록과 결제사 기록이 어긋난 것을 **이미 나간 뒤에** 발견하는 수단이 없고, 회원이 다음 환불을 요청할 때 한도 초과로 드러날 뿐이다.
- **결과 불명이 얼마나 자주 나는지 재지 않았다.** 활성 슬롯 시점 비교도 대가의 크기만 봤고 빈도는 재지 않았다([[배타점유-슬롯-미리잡기-vs-성공시-감지·되돌리기]]).
- **재고 락 대기 실패 빈도를 모른다.** 계측 갈래만 만들어 뒀고 데이터가 없다.
- **호출 기록에 마스킹된 카드번호·영수증 주소가 원본째 담긴다.** 보관 기간과 접근 제한을 정하지 않았다.
- **한 주문에 여러 건일 때 특정 취소의 외부 집행 여부**는 실측으로 판정 근거를 얻었으나, 그때 "이 상태로 내보내도 되는가"에 답하지 않고 넘어간 절차 공백이 남아 있다([[부분취소-외부취소와-우리-기록-사이-대응관계-부재]]).
