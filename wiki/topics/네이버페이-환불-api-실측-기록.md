# 네이버페이 환불 API 실측 기록 — 명세가 말하지 않는 것들

## 한 줄 정의

결제대행사 없이 네이버페이를 직접 연동한 백엔드에서 부분환불 모델을 설계하며, **명세로 알 수 없는 동작을 개발 환경에서 직접 확인한 기록**이다. 재현 비용이 크다 — 결제창 인증에 사람이 직접 네이버 로그인과 결제 비밀번호를 넣어야 해 자동화로 다시 만들 수 없다.

## 실측 조건 (결론의 적용 범위를 가른다)

- 2026-08-09, 네이버페이 **개발 환경**(API `dev-pay.paygate.naver.com`, 결제창 `test-m.pay.naver.com`)
- 100원 결제 → 30원·30원·40원으로 나눠 환불하며 관측
- **포인트 전액 결제였다.** 카드·머니 충전계좌가 모두 점검 중이었다. 응답이 카드·계좌 금액(`primaryPay*`)과 포인트 금액(`npoint*`)을 나눠 다루고 카드에는 취소 기한 제약(`CancelDeadlineExpired`)이 따로 있으므로 **카드 결제의 부분취소도 같다는 보장은 없다.**
- 운영 환경도 같다는 보장은 명세에 없다.

## 관측 6건

**1. 취소 요청에 실은 `merchantPayTransactionKey`가 그 취소 이력 항목에 되돌아온다.** 환불마다 다른 값을 넣으니 그대로 구분되어 돌아왔다. 승인 항목에는 결제 시작 때 보낸 값이 실려 있다. → 명세는 필드의 존재만 말하고 항목별로 어느 값이 실리는지는 말하지 않는다. **이 관측에 회수 전략이 통째로 기대고 있다** — [[네이버페이-환불-이력-지목근거-보내기전-우리가-정하는-값]].

**2. 나눠 환불하면 마지막 잔액을 남김없이 턴 건까지 전부 부분취소 유형(`04`)으로 기록된다.** 전체취소 유형(`03`)은 처음부터 전액을 한 번에 취소할 때만 나오는 것으로 보인다. 명세는 두 코드의 의미만 적고 어느 쪽이 붙는지 선택 규칙을 말하지 않는다. → **전체취소 유형만 찾는 코드는 부분환불이 한 번이라도 섞이면 그 결제의 취소를 하나도 인식하지 못한다. 여섯 중 가장 값어치 있는 관측이다.**

**3. 잔액 대조 거절 응답에 결제사가 계산한 잔액이 실려 온다.** 일부러 틀린 예상 잔액(999원)을 보내니 `RestAmountDiff`로 거절되며 메시지에 `naverExpectedPayRestAmount:40` 형태로 담겨 왔다. 파라미터와 실패 코드 자체는 명세에 있고 문서가 연동을 권장하기까지 한다. **새로 안 것은 "거절당했을 때도" 결제사 쪽 잔액을 얻는다는 것**이다.

**4. 같은 멱등키 재전송에서 환불이 두 번 일어나지 않는다.** HTTP 409와 이전 응답 본문 재전달, 응답 헤더로 같은 키 반환은 명세에 그대로 있다. 실측으로 확인한 것은 **잔액이 유지되어 실제로 중복 집행이 없었다**는 것. → **409를 확정적 실패로 처리하면 성공을 실패로 뒤집는다** — 본문이 이전 성공 응답 그대로이기 때문이다. 이 관측이 "결과를 모르는 동안은 같은 키로 다시 부른다"의 근거가 됐다([[결과불명-재호출은-같은-멱등키로-새키-결론-뒤집힘]]).

**5. 요청 검증 단계에서 거절된 시도는 이력에 남지 않는다.** 잔액 불일치로 튕긴 요청이 이력에 흔적이 없었다(성공 4건만). 명세는 항목 상태(`admissionState`)에 `FAIL` 값이 **있다고만** 하고 언제 생기는지는 말하지 않는다. → "실패한 시도도 이력에 한 줄 남는다"는 가정이 적어도 파라미터 검증 실패에는 해당하지 않는다.

**6. 이력 목록 순서는 이번 관측에서 시간 오름차순이었다.** → **설계 근거로 쓰지 않았다.** 명세에 순서 보장 서술이 없고 관측이 한 번뿐이다. "순서에 의존하지 않는 판정"이라는 방침을 그대로 유지했다.

## 연동 방법 중 명세를 봐도 잘 안 풀리는 것

- **이력 조회만 요청 형식이 다르다.** 승인·취소는 form 형식인데 이력 조회는 JSON이고 결제번호를 URL 경로에 넣는다(`POST .../v2.3/list/history/{결제번호}`, 본문 `{"pageNumber":1,"rowsPerPage":50}`).
- **틀리면 원인을 짐작할 수 없다.** form으로 보내거나 경로에서 결제번호를 빼면 EUC-KR HTML로 "서버에러"만 돌아온다. 경로에 번호가 없으면 기간 조회 엔드포인트로 해석되어 필수 파라미터 부재로 실패하는 것이다.
- **취소 API 타임아웃을 최소 60초로 두라고 명세가 경고한다.** 취소 완료까지 시간이 걸린다는 뜻이고, "결과가 불확실한 건"이 어디서 오는지 알려주는 문장이다.

## 이번에 만들어 보지 못한 것 (명세에는 있다)

다음 사람이 이미 답이 있는 것을 다시 실측하지 않도록 남긴다.

- `CancelNotComplete` — "취소 처리가 완료되지 않았지만 자동 재처리 예정. **가맹점은 재시도 필요 없이 취소 성공 상태로 변경**하면 된다"
- `PreCancelNotComplete` — 위와 지시가 정반대다. 이전에 요청한 취소 정보로 재시도하라고 한다
- `AlreadyOnGoing`, `AlreadyCanceled`("이미 **전체** 취소된 결제"), `CancelDeadlineExpired`

앞의 둘은 지시가 반대인데 이름이 비슷해 같은 실패로 묶기 쉽고, 재시도 안전성과 직결된다. 또 **환불이 동기적으로 완료되는가**(응답 시점에 이미 이력에 반영돼 있었는지)를 검증하지 않았다 — 회수 설계에 직결된다.

## 필드 이름 대응표

| 이 글에서 부르는 말 | 실제 |
| --- | --- |
| 환불 식별자를 싣는 자리 | 취소 요청 `merchantPayTransactionKey` (128바이트, 선택). 이력 항목에도 동명 필드 |
| 결제사가 발급한 이력 번호 | `payHistId` |
| 취소 유형 | `admissionTypeCode` — `01` 원결제 승인 / `03` 전체취소 / `04` 부분취소 |
| 이력 항목 상태 | `admissionState` — `SUCCESS` / `FAIL` |
| 예상 잔액 대조 | `doCompareRest=1` + `expectedRestAmount`, 거절 코드 `RestAmountDiff` |
| 멱등키 | 요청·응답 헤더 `X-NaverPay-Idempotency-Key` (64자 이내) |
| 결제창 시간 초과 | `TimeExpired` (예약 번호 생성 후 30분) |

## 열린 질문

- **멱등키 보관 기간.** 명세에 숫자가 없고 실험 설계가 성립하지 않는다. "언제든 만료됐을 수 있다"를 전제로 삼았다.
- **실패 상태 이력 항목이 언제 생기는가.** 파라미터 검증 실패는 안 남는 것을 확인했으나 결제사 내부 처리까지 갔다가 실패하는 경우를 만들지 못했다. 그래서 "실패 항목만 있으면 완료로 보지 않는다"는 보수적 규칙을 유지했다.
- **카드 결제에서도 같은가.** 위 관측은 전부 포인트 전액 결제다.
- **개발 환경과 운영 환경의 동작이 같은가.** 다르다는 서술도 같다는 보장도 명세에 없다.
