# 결제대행사와 간편결제의 구분, 세 층의 역할, 결과 불명과 재시도 모델

## 한 줄 정의

부분환불 재설계에 들어가기 전에 결제 도메인의 어휘와 상태 모델을 정리한 세션. **결정을 내린 것이 아니라 기존 결정들이 왜 그 모양인지를 다시 세운 것**이며, 그 위에서 "결과 불명을 명시 상태로 유지한다"를 재확인했다.

## 결제대행사(PG)와 간편결제 서비스는 다르다

- **네이버페이는 카드 승인을 중개하는 결제대행사가 아니라 간편결제 서비스다.** 우리 시스템은 그런 외부 결제 서비스에 요청을 보내는 **가맹점 쪽 결제 조율자**이지, 남의 결제를 대행하는 PG 서버를 만드는 게 아니다.
- **토스페이먼츠는 진짜 결제대행사다**(토스페이라는 간편결제와 다름).
- 여러 간편결제를 직접 통합하더라도 **우리 결제만 처리하는 한 우리는 가맹점이지 결제대행사가 되지 않는다.**

이 구분이 [[payment-order-도메인분리와-pg격리]]의 "PG 격리"가 무엇을 격리하는지를 정확히 만든다 — 격리 대상은 결제대행사가 아니라 **외부 결제 서비스 일반**이다.

## 세 층의 역할

```
주문           무엇을 사는가
결제창 준비물   이번 결제 시도를 대표.  결제수단당 재사용되고 만료 시간이 있음
결제 사건       외부에 실제로 보낸 요청 기록.  append-only, 승인·취소 종류가 있음
```

**앞의 둘은 결제가 일어나기 전의 세계이고, 결제 사건은 외부 경계에서 실제 벌어진 일이다.** 이 세 층이 실제로 예약 테이블 + 사건 테이블로 구현된 경위는 [[payment-reserve-예약테이블-분리-a안-b안]]이고, 나중에 예약 층이 결제 행 자체로 흡수됐다([[예약테이블-폐지-결제행-활성슬롯-단일화와-사라지는-방어]]).

## 도메인 주문 식별자 ≠ 외부 결제 식별자

우리 주문은 하나로 유지되지만, 외부 결제사로 보내는 결제 식별자는 **재시도마다 새로 발급한다**(외부 결제사가 같은 식별자 재사용을 막기 때문). 둘의 생명주기가 달라서 이 매핑과 재시도 단위를 대표하는 계층이 필요하다. 그래서 **재시도해도 주문을 새로 만들지 않고 외부 결제 식별자만 새로 발급한다.**

> 이 "시도마다 새로 발급"이라는 성질이 나중에 열린 질문으로 되돌아온다 — 주문마다 고정 키를 쓰면 배타성을 결제사에 맡길 수 있는데 그 대안이 검토돼서 탈락한 것인지조차 알 수 없었다([[배타점유-슬롯-미리잡기-vs-성공시-감지·되돌리기]]).

## 결과 불명은 성공도 실패도 아닌 제3의 상태다

외부에 승인 요청을 보냈는데 timeout이나 네트워크 단절로 응답을 못 받아 **"돈이 나갔는지 모르는"** 상태. **정상 대기(요청을 보내고 응답을 기다리는 중)와는 다르다** — 정상 대기는 기다리면 되지만, 결과 불명은 확인 전까지 재결제를 막아야 이중청구를 방지한다([[payment-unknown-결과불명-처리와-예외분류]]).

## 재시도 두 종류

1. **같은 결제 건의 승인확정을 다시 요청** — 외부 결제사의 승인확정이 멱등적이라 이미 승인된 건은 중복 승인되지 않는다. **외부 결제사가 이중청구를 막아준다.**
2. **새 식별자로 새 결제** — 외부 결제사는 별개 건으로 보므로 막지 못한다. **우리 시스템이 "결과 불명 건이 있으면 새 결제를 차단"해서 막아야 한다.**

이 구분이 나중에 "결과를 모르는 동안은 같은 멱등키로 다시 부른다"의 뼈대가 된다([[결과불명-재호출은-같은-멱등키로-새키-결론-뒤집힘]]).

## append-only가 필요한 이유

시도마다 결제 사건 행을 새로 쌓으면(재시도 = 새 식별자 = 새 행) 이전 시도 흔적이 덮이지 않는다. **결과 불명 흔적이 보존돼야 (1) 추적·확정과 (2) 새 결제 차단이 둘 다 가능하다.** 한 행을 재사용(수정)하면 결과 불명 흔적이 덮여 이중청구 방어 근거가 사라진다 — [[payment-append-only-원장과-exists-완료판단]], 그리고 같은 이유로 시도마다 새 행을 쌓기로 한 물리 설계는 [[유일슬롯-비우고-같은값-재점유-쓰기순서와-메서드이름-신호]].

## 검토한 대안 — 결과 불명을 명시 상태로 둘지

논점: "결과 불명"을 별도 상태로 둘지, 아니면 "처리 중" 하나로 두고 경과 시각으로 구분할지.

- **통합 논거(별도 상태 없이 처리중 + 시각):** 서버 크래시로 확정하지 못하고 멈춘 "처리 중" 행도 어차피 시간 기반으로 확인해야 하니 **"미종료 = 확인 대상"이라는 단일 조건이 단순하다.** 별도 상태를 둬도 크래시 케이스는 처리중에 남아 확인 대상이 두 갈래가 된다.
- **이 프로젝트에서 명시 상태 유지가 나은 이유:** 현행은 결과 불명 건만 즉시 재결제를 차단하고 확인 주기를 빠르게(1분) 돌리며, 정상 요청 흔적은 느린 주기(15분)로 확인한다([[미확정차단-대사스캔-정합성-starvation-escalation]]). 크래시로 요청 흔적 상태에 멈춘 행도 시간 기반 확인으로 스스로 복구된다. 즉 **이 프로젝트는 위험도별로 대응을 차등하기 때문에 명시 상태가 유리하다. 통합 논거의 "처리가 동일하다"는 전제가 이 프로젝트엔 맞지 않는다.**
- **로그로는 대체 불가:** 로그는 "왜 불명이 됐나"(사후 디버깅)를 남기고, 상태는 "지금 이 주문을 막을까"(실시간 정합성 판단)에 쓰인다.

## 열린 질문

- 결과 불명 표현은 이 프로젝트에선 명시 유지가 결론이나, **새 결제를 백지에서 설계한다면 "처리 중 + 시각" 통합도 선택지로 열려 있다.**
- 결제사 연동 방식 자체의 트레이드오프는 [[간편결제-직접연동-vs-결제대행사-하이브리드-전략-검토]].
