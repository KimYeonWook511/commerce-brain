# 인증/인가 진입점을 common.security leaf로 재편 + 토큰 포트/어댑터 네이밍

## 컨텍스트 — 실재한 패키지 순환과 안정 의존성 원칙

백엔드는 JWT 기반 인증을 쓴다. HTTP 요청의 인증/인가를 웹 진입점에서 강제하는 코드(토큰을 검증하는 서블릿 필터, 권한을 검사하는 MVC 인터셉터, 인증된 신원을 요청 스코프에 보관하는 컨텍스트, 컨트롤러 파라미터에 회원 id를 주입하는 argument resolver)가 원래 top-level 독립 `security` 패키지에 있었다.

패키지 순환이 실재했다: 공통 웹 설정이 security를 빈으로 등록 → security가 인증 도메인(auth)을 호출 → auth의 예외가 공통 예외 베이스를 상속 → **`공통 → security → auth → 공통` 3-패키지 순환.** 또한 권한 애너테이션(`@RequireRole`)과 인증 컨텍스트는 거의 모든 도메인 컨트롤러가 import한다. 이렇게 "많은 곳이 의존하는" 패키지일수록 leaf(아무것도 의존 안 함)여야 안정적이다(안정 의존성 원칙). 외부 동작(HTTP 응답·에러코드·DB 스키마)은 바뀌지 않았다. (auth/member/security 도메인 경계 자체는 [[인증-패키지-경계-auth-member-security-분리]]·[[auth-member-security-도메인-구조-개요]] 참조.)

## 결정 1 — security를 common.security로 옮겨 leaf로

인증/인가 진입점 전체를 공통 인프라 패키지 하위(`common.security`)로 이동해 "아무것도 의존하지 않는 leaf"로 만든다. 공통 패키지는 이미 전역 예외 처리·로깅 필터 같은 웹 인프라를 품고 있어 인증/인가 필터·인터셉터도 같은 부류다. 옮기면 순환이 사라지고 새 패키지 간 의존이 0이다(관련 패키지들이 이미 공통 패키지를 의존하므로). 이 leaf의 필터가 곧 [[서블릿-필터-예외-처리와-에러-디스패치]]와 [[jwt-예외-catch-footgun-bare-securityexception]]에서 다룬 필터·토큰 검증 코드다.

## 결정 2 — 토큰 검증만 포트로 역전 (security는 JWT를 모른다)

leaf는 토큰 기술(JWT)을 몰라야 한다. 그래서 "토큰 문자열 → 누구인가(신원)"라는 단 하나의 호출만 포트 인터페이스로 두고(`common.security`에 위치), 인증 도메인이 JWT로 그 포트를 구현한다. 방향은 "구현체 → 공통" 한 방향뿐이라 순환이 안 생긴다.

검증 실패 전파: 구현체(인증 도메인)가 던지는 예외는 앱 전역 공통 예외 베이스를 상속한다. 필터는 그 예외를 **공통 베이스 타입으로** 잡아 안에 실린 에러코드를 응답에 쓴다. 필터가 인증 도메인의 구체 예외 타입을 이름으로 부르지 않으므로(다형성) 컴파일 타임 의존이 안 생겨 leaf가 유지된다 — 이는 [[persistence-exception-노출-경계-추상수준]]의 "추상 상위 catch → 구현체 이름을 안 부른다"와 같은 기법이다.

## 결정 3 — 인가용 역할 enum을 도메인 역할과 분리 (JWT 문자열 경계)

회원 도메인에는 "관리자/일반" 역할 enum이 원래 있고, 인가 판정에도 같은 역할 개념이 필요하다.

- **대안 A(기각)**: 회원 도메인 역할 enum을 인가 leaf로 옮겨 하나로 통일. 단점 — 회원 도메인이 인가 패키지를 역으로 의존하게 되어, 이 리팩터의 목적(의존 방향 바로잡기)과 정면으로 어긋난다.
- **대안 B(채택)**: 회원 도메인은 자기 역할 enum을 그대로 두고, 인가 leaf에 **별도** 인가용 역할 enum을 신설. 두 enum은 서로 참조하지 않고 **JWT의 role 문자열로만** 오간다(발급 시 enum 이름 → 문자열, 검증 시 문자열 → enum 복원). 상수 이름이 같아 문자열이 그대로 왕복한다.

통일 안 한 진짜 이유: "중복 비용"이 실제로 낮다. 두 enum 사이에 이미 JWT 문자열 경계가 있어 enum↔enum 변환 매퍼가 생기지 않는다(발급=문자열화, 검증=문자열→enum은 JWT를 쓰는 한 원래 존재하던 코드). 유일한 대가: 역할 추가 시 두 enum에 다 넣어야 한다. 하지만 빠뜨리면 문자열→enum 변환이 예외를 던져 시끄럽게 드러나므로(조용한 버그 아님) 감수 가능.

## 결정 4 — 에러코드 접두는 문제영역이 결정 (인증 계약 code 보존, PG 현업 근거)

leaf가 인증 도메인 에러코드를 import하면 다시 의존이 생기므로, 인가 진입점 자체의 에러코드 타입을 새로 만들었다. 단 "토큰 없음(401)"·"권한 부족(403)"의 code/message 문자열은 기존 인증 계약(`AUTH-401`·`AUTH-403`)을 그대로 쓴다.

**핵심 원칙: 에러코드는 "어느 클래스가 던졌나"가 아니라 "클라이언트에게 이게 무슨 종류의 문제인가"로 분류하는 계약이다.** 인가 진입점의 에러코드 클래스는 leaf를 지키려고 코드를 정의하는 자리일 뿐, 그 코드가 가리키는 문제 영역은 여전히 "인증/인가"다. 그래서 클래스가 security에 있어도 코드는 인증 접두를 쓴다.

새 접두(`SECURITY-401`)를 안 쓴 이유 둘: (1) 인증 실패 코드가 이미 API 스펙에 계약으로 게시돼 클라이언트가 그 문자열로 분기한다 → 바꾸면 계약 파괴. (2) 토큰 만료·무효 세부 코드는 인증 도메인이 던져 포트로 전파되므로 여전히 인증 접두다. 새 접두를 쓰면 같은 401 경계에서 접두가 갈라져 더 나쁘다.

현업 근거: 실제 결제 게이트웨이(PG) 응답을 보니 실패 사유마다 **고유 code**를 주고 message는 사람용 설명이었다(백엔드가 그 code로 프로그램 분기까지). "사유마다 고유 code, message는 설명"이 업계 표준이고, code를 공유하고 message로만 구분하는 방식은 실무 표준이 아니다(message는 문구가 바뀌고 다국어가 되니 계약이 아님). 이 code/계약 보존은 [[도메인-예외-httpstatus-제거-errorcategory]]의 "외부 계약 불변" 전제와 결이 같다.

## 결정 5 — 포트↔어댑터 네이밍 짝맞춤 + 하나의 JWT 어댑터로 병합

네이밍 원칙: 포트(인터페이스)는 기술을 모르는 추상 이름, 어댑터(구현체)는 `<기술>+<포트명>`으로 시각적 짝을 맞춘다(이미 쓰는 패턴: 토큰 발급 포트↔JWT 발급 어댑터, refresh 저장 포트↔Redis 어댑터, 비밀번호 해시 포트↔Bcrypt 어댑터).

- access 토큰 검증 포트를 `TokenValidator`, JWT 구현을 `JwtTokenValidator`로 통일(처음 `TokenAuthenticator`류를 썼다가 어댑터와 1:1 짝이 맞고 "검증기" 어휘가 자연스러워 Validator로).
- **"왜 AccessTokenValidator는 없나"**: access 검증기가 곧 그 포트(`TokenValidator`, 신원 반환)다. `AccessTokenValidator`/`RefreshTokenValidator` 대칭 쌍이 될 수 없는 이유는 leaf 경계 — access 인증은 인가 진입점(leaf) 소관이라 포트가 leaf에, refresh 검증은 재발급이라는 인증 도메인 내부 소관이라 포트가 인증 도메인에 있다. 한 포트로 합칠 수도 없다(leaf에 두면 security가 refresh를 알고, 도메인에 두면 필터가 도메인을 의존해 다시 순환).
- **어댑터 병합**: 처음 access/refresh 어댑터를 두 클래스로 쪼갰더니 둘이 똑같은 "JWT 서명·만료·타입 검증 + claims 추출" 코드를 공유하려 별도 헬퍼 클래스가 하나 더 생겼다. "쪼갠 뒤 다시 공유하려 헬퍼를 만든" 꼴이라, **하나의 JWT 어댑터가 두 포트를 모두 구현**하고 공통 파싱은 private 메서드로 두는 쪽으로 병합(헬퍼 제거). 교훈: 두 포트가 한 기술을 공유하면 억지로 두 어댑터로 쪼개지 말고 어댑터 하나가 두 포트를 구현하는 게 자연스럽다.

## 결정 6 — 토큰 실패 코드를 인증 도메인 예외가 실어나르는 이유

만료·무효·빈 토큰을 서로 다른 코드로 구분해 유지하기로 했다. 그러면 "어떤 종류의 토큰 실패인가"를 아는 쪽 = 인증 도메인(JWT를 실제로 파싱하는 쪽)이 그 코드를 소유해야 한다(leaf는 토큰 기술을 모르니까). 그래서 코드를 실은 예외는 인증 도메인의 예외 타입이고, 이건 "도메인 모델링"이 아니라 앱 전역의 "에러코드를 실어 응답으로 매핑되는" 공통 예외 베이스를 상속한 것뿐이다(모든 모듈 공통 방식). 필터는 이를 공통 베이스로 받아 코드만 전파한다. 이 만료/무효/위조 구분이 바로 [[jwt-예외-catch-footgun-bare-securityexception]]에서 footgun이 무력화한 그 코드 경로다.

## 참조한 다른 서버 구현 — 가져온 것/안 가져온 것

- **가져옴**: 인가 골격을 공통 패키지 security 하위에 두는 방향, 토큰 검증을 포트로 역전, 포트가 신원 값 객체(record)를 반환하는 형태.
- **안 가져옴**: (a) 에러코드를 enum 이름 그대로 내보내는 방식 — 우리는 명시적 code 문자열 컨벤션이라 그대로 쓰면 계약이 깨짐. (b) 모든 토큰 실패를 단일 401로 뭉개는 것 — 우리는 만료/무효 구분 유지(그 서버는 구분이 없어 포트를 인가 leaf에 둘 수 있었다). (c) 비밀번호 해시를 인가 패키지에 두는 것 — 우리는 로그인/가입만 쓰는 인증 도메인 관심사라 거기 유지. (d) 인가 패키지를 전부 평평하게 — 우리는 역할별 하위 패키지(필터/인터셉터/resolver/컨텍스트/포트/에러/설정) 유지.

## 트레이드오프·미해결(만료/무효 구분 스펙 부재, 로그 레벨 정리 보류)

- 토큰 만료(`AUTH-401-2`)·무효(`AUTH-401-3`) 구분 코드는 코드가 내보내지만 **API 스펙 문서엔 없다**(스펙엔 `AUTH-401`만). 클라이언트가 실제로 그 구분에 의존하는지 불명확 — 구분 유지가 정말 필요한지 재논의 여지(현재는 유지).
- 토큰 검증 경로의 로그 레벨 정리(만료·빈 토큰은 운영 로그 스팸이라 warn→무로그/debug, 위조는 warn 유지, "어댑터 직접 로깅 vs 중앙 일괄" 경계)는 이 리팩터 범위 밖이라 분리해 보류. 이 로깅 역할 분담 논점은 이후 [[인프라-일시장애-503-예외-매핑-판단축]]에서 adapter WARN / 끝단 ERROR로 구체화됐다.
