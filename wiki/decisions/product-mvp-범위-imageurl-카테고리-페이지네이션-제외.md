# Product MVP 범위 — imageUrl 문자열 저장 + 카테고리·페이지네이션·초기재고 제외

## 컨텍스트·문제(MVP 기능 경계)

상품 관리·조회 기능의 요구사항 문서가 명시적 **제외 범위**를 뒀다: 페이지네이션 / 검색·필터·카테고리 / 파일 업로드 / 상품 생성 시 초기 재고 생성 / 관리자 UI / 목록 응답의 재고 정보. 각 제외는 "지금은 안 한다"가 아니라 "왜 지금 넣으면 기능이 폭발하는가"의 판단이 붙어 있다.

## imageUrl 문자열 저장 근거

상품 이미지는 URL 문자열 컬럼(`image_url`)으로만 저장한다. 파일 업로드·외부 스토리지 연동은 범위 밖.

- 파일 업로드를 넣으면 외부 저장소(S3 등) 선택, 업로드 정책, presigned URL, 권한 모델까지 딸려와 기능 크기가 폭발한다.
- 백엔드 책임을 "URL을 저장한다"로 좁히면 클라이언트가 어디서든 URL을 대주면 되고, **CDN 전환·이미지 서버 교체에도 백엔드 변경이 없다**.
- **트레이드오프**: URL 유효성 검증이 없다. `imageUrl`은 아무 제약도 없는 선택 필드로 요청 DTO에도 `@NotBlank`가 없고 엔티티 생성자도 이름·가격·상태만 검증한다. 깨진 URL·호스팅 만료를 백엔드가 인지하지 못하고, 이미지 소유권·보안은 백엔드 책임 밖이다.
- **도입 시점**: 어드민 화면 작업 시 저장 방식(S3 vs server storage)도 함께 정한다. server storage는 리스크가 커 S3로 기울 가능성이 높지만 구체 결정은 그 task로 미룬다(향후 frontend/infra 크로스).

## 왜 카테고리 제외(도메인 미확정)

- 카테고리는 별도 엔티티/테이블 + 다대다 + 트리 구조 결정까지 큰 변경이다.
- 더 본질적인 이유 — **어떤 카테고리를 도입할지 비즈니스 도메인 자체가 아직 안 정해졌다**. 지금은 큰 "commerce" 컨셉이고 옷/화장품/기타 같은 세부 분류가 미확정이다. 정해지지 않은 분류 체계에 코드를 먼저 맞추지 않는다.
- "상품을 찾아본다"는 기본 시나리오는 카테고리 없이 목록 + 상세로 충분하다.

## 왜 페이지네이션 제외 + 도입 트리거

- MVP 데이터 규모(수십~수백 row)에서는 전체 조회로 충분하다.
- 페이지네이션을 넣으면 정렬·필터 조합 정책까지 딸려와 범위가 커진다.
- "기본 정렬은 `createdAt DESC` 고정"으로 **의사결정 부담만 미리 잠가**뒀다.
- **도입 트리거**: 등록 상품 전체를 한 번에 조회/구성하는 게 부담이 되는 시점부터. 구체 row 임계는 미정 — 운영하며 체감으로 판단한다.

## 왜 초기 재고를 함께 안 만드나

- 재고는 동시성·이력 등 별도 설계 부담이 있어 상품 관리 기능 안에 끼우면 기능 크기가 폭발한다.
- 관리자 흐름은 "상품 생성 → 별도 API로 재고 초기화" **2단계**다([[관리자-재고조작-별도api-이력-감사-분리]]). UX 부담을 감수하고 도메인 분리를 우선했다.
- 이 정책이 곧 "상품은 있는데 stock row 없음"을 정상 상태로 만들고, 그래서 상세 조회가 재고 누락을 0으로 정규화하는 인과가 성립한다 → [[product-상세조회-stock-의존-재고누락-0-정규화]] · [[stock-도메인-구조-개요]].

## 트레이드오프(엔티티 생성 계약 변경 파급 회귀)

- 상품 조회 회고의 회귀 사례: step 범위가 좁아 `Product.builder()` 사용처(주문·결제·재고 테스트 fixture)가 깨지는 걸 처음엔 못 잡았고 전체 테스트 보정이 필요했다.
- **교훈**: 엔티티 생성 계약 변경은 작은 도메인 변경이 아니라 **전체 fixture 변경**으로 봐야 한다(shared domain 엔티티 계약 변경은 전체 테스트 실행이 AC에 포함돼야 한다). 이 파급 인식은 [[ddd-이관-컨벤션-adapter-command-query-네이밍]]의 이관 교훈과 맞물린다.
