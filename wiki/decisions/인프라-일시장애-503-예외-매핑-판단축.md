# 인프라 일시 장애를 503으로 — 예외 상속 전략의 두 직교 판단축

## 컨텍스트 — 저장소 일시 장애에 500은 부정확

외부 캐시·저장소가 잠깐 죽는 것은 재시도 가능한 일시 장애다. 500은 "예상 못한 서버 버그"를 뜻하므로 이 경우 부정확하다. 그래서 도메인 예외가 HTTP 상태 대신 드는 의미 분류 체계([[도메인-예외-httpstatus-제거-errorcategory]]의 `ErrorCategory`)에 "일시적 사용 불가(→503)"를 신설한다. 이 노트는 그 ErrorCategory 체계를 확장하면서, 인프라 장애 예외의 상속 전략을 두 판단축으로 정리한 결정이다.

## 결정 1 — 503 카테고리 신설 (외부 계약 변경 vs 정확성)

외부 캐시·저장소의 일시적 사용 불가 장애를 500이 아니라 **503(Service Unavailable)**으로 응답한다. `ErrorCategory`에 "일시적 사용 불가(→503)"를 추가한다. [[도메인-예외-httpstatus-제거-errorcategory]]는 "외부 계약 불변" 전제로 저장소 장애를 현행 500으로 뒀지만, 여기서는 재시도 가능성을 클라이언트에 정확히 알리는 정확성 이득이 계약 변경(500→503)을 감수할 값어치가 있다고 판단했다. `getCategory()` 인터페이스와 default 없는 switch 매핑 유틸 덕에 새 카테고리 추가가 컴파일 타임에 안전하게 강제된다.

## 결정 2 — 공통 인프라 베이스 예외는 안 만든다 (사용처 2곳, YAGNI)

원래 제안은 "공통 인프라-사용불가 베이스 예외를 만들어 도메인별 인프라 장애 예외를 그 아래로 통합"이었으나 기각했다. 이유: (1) 사내 예외 전략 문서가 "베이스 추출은 사용처가 3곳 이상이고 공통 catch 시나리오가 실제 필요할 때"라 미리 정해뒀는데 현재 사용처가 2곳뿐이고, (2) 두 사용처의 처리 방식이 근본적으로 달라 하나의 베이스로 묶어도 실질 이득이 적다. 선례상으로도 공통 베이스 없이 도메인별로 처리하는 패턴이 문제없이 운영된다.

## 판단축 A — application이 삼키느냐: 자동 매핑 공통 베이스 vs 전용 unchecked

예외 상속 전략은 "**application 계층이 그 예외를 catch해서 삼키느냐**"로 갈린다.

- **catch하지 않고 요청 끝단까지 전파** → 자동 응답 매핑되는 공통 예외 베이스 계열로 던진다. 전역 핸들러가 "의미 카테고리 → HTTP 상태" 규칙으로 자동 매핑(동시성 충돌 409, 인프라 일시 장애 503). 도메인마다 전용 응답 핸들러가 불필요하다.
- **catch해서 fallback/보상** → 자동 매핑을 **회피**해야 하므로 자동 매핑되지 않는 unchecked 전용 예외 타입으로 던진다. 이 예외는 삼켜서 대체 경로로 흘리는 게 정상 흐름인데, 자동 매핑 타입으로 두면 catch를 놓치거나 범위가 어긋나는 순간 원치 않는 응답이 클라이언트로 샌다. 자동 매핑 안 되는 unchecked면 실수해도 안전망(500)으로 흘러 금전·정합성 경로에서 더 보수적이다.

## 판단축 B — 타입 식별이 필요하냐 (A와 직교)

"도메인 예외 클래스를 따로 두느냐 vs 공통 예외를 그대로 던지느냐"는 별개 질문이다: **"그 예외를 타입으로 catch해서 구분·처리할 일이 있는가."** 있으면 전용/도메인 예외 클래스로 둔다(catch 경계가 되고 로그에서 도메인 식별이 됨). 없으면 공통 예외 + 에러코드로만 세분화한다. 예외 클래스 수는 "타입으로 잡아야 할 경계"의 수와 같고, 상황의 세분화는 에러코드가 담당한다 — 상황마다 예외 클래스를 새로 만드는 건 안티패턴이다.

판단축 A("삼키느냐")와 B("타입 식별이 필요하냐")는 **직교하는 별개 질문**이다. 아래 두 사례에서는 우연히 같이 정렬됐지만 원리는 다르다(예: 타입으로 잡아 로깅·보상만 하고 그대로 재전파하면, 전용 타입이 필요하면서도 끝단에선 자동 매핑을 원할 수 있다).

## 두 사례 대비 — refresh 토큰 저장소 vs 주문 멱등성 저장소

> [!warning] 전환(supersede) — refresh 토큰 저장소 처리가 이전 결정을 반전
> **인증 refresh 토큰 저장소**(캐시가 곧 저장소 자체라 원본으로 대체 불가): 아무도 catch하지 않는다 → 공통 도메인 예외로 던져 **503 자동 매핑**. 기존 [[auth-redis-장애-도메인예외-매핑-도메인전용-어드바이스]](pr-197)가 두었던 "이 저장소 전용 예외 클래스 + 이 도메인 전용 @RestControllerAdvice"를 **폐기**한다. 응답도 500 → 503으로 바뀐다. 도메인이 늘 때마다 전용 응답 핸들러(우선순위 지정·핸들러·단위 테스트)가 반복 증가하던 부담이 사라진다. → 그 이전 결정은 이 노트로 대체됨(양방향 supersede).

- **주문 멱등성 저장소**(캐시는 성능 최적화 레이어일 뿐 원본 DB로 대체 가능): application이 catch해서 DB 유니크 제약 안전망 경로로 fallback한다 → 자동 매핑을 피하는 전용 unchecked 예외를 유지한다. 이 이중 방어의 fallback 경로는 [[주문-멱등성-redis-setnx-plus-rdb-unique-이중방어]]·[[redis-장애-멱등캐시-fallback-boolean-예외분리]]와 같은 구조다.

원인 예외 보존: 공통 예외 베이스와 도메인 예외에 "(에러코드, 원인 예외)" 생성자를 추가해, 저장소가 던진 기술 원인을 예외 체인으로 실어 전파한다.

## 직접 정의한 port만 변환, 표준 인프라 예외는 전파

adapter가 기술 예외를 변환하는 것 자체는 없앨 수 없지만 "무엇으로 변환하느냐"는 catch 여부로 갈린다. 직접 정의한 아웃바운드 port(예: 캐시 인터페이스)는 그 계약에 프레임워크 기술 예외가 새면 추상화가 깨지므로 adapter가 반드시 도메인 예외로 변환한다. 반면 프레임워크가 표준으로 관리하는 영속성 계층(ORM repository)은 그 추상 예외가 application에 노출돼도 되므로 대개 변환 없이 전파해 전역 핸들러가 처리한다. 즉 **"직접 정의한 port만 변환하고, 표준 인프라 예외는 전파"** — 이는 [[persistence-exception-노출-경계-추상수준]]의 "추상 vs 구현 구체" 선별 번역과 동일 원리다.

부연: 프레임워크의 데이터 접근 예외 최상위 타입은 관계형 DB와 캐시가 공유하는 추상이라, 캐시 커넥션 실패도 그 하위에 있다. 그래서 "이게 캐시 장애인가"를 예외 타입만으로는 못 가린다. adapter의 catch가 안전한 이유는 try 블록 범위가 그 캐시 호출 하나뿐이라 거기서 나는 예외는 캐시 발(發)임이 위치로 보장되기 때문이다(타입이 아니라 위치로 확신). 전역 핸들러는 범위가 넓어 DB/캐시 장애를 구분 못 하므로, 저장소 장애를 특정 상태코드로 가르는 지식은 공용 핸들러가 아니라 adapter 안에 가둔다.

## 로깅 역할 분담 (adapter WARN 컨텍스트 / 끝단 ERROR 스택)

adapter가 원인을 ERROR + 전체 스택으로 남기고 예외에 원인도 실으면, 끝단 핸들러가 5xx로 또 스택을 남겨 같은 스택이 로그에 두 번 찍힌다. 해결: adapter는 컨텍스트(식별자 등)만 WARN으로 간결히 남기고, 상세 스택은 끝단 핸들러가 ERROR로 한 번만 남긴다. "저장소 장애를 ERROR로 인지"는 catch 안 하는 경우 끝단 ERROR가 보장하므로 adapter가 WARN이어도 운영 인지가 가능하다. (처음엔 "adapter가 ERROR 유지 + 이중 로깅 감수"로 정했다가 리뷰에서 역할 분담이 낫다고 판단해 전환.)

## 미해결 — 재시도·서킷브레이커, fallback 3곳+ 시 베이스 재검토

- 자동 재시도(재시도·서킷 브레이커)는 이번에 도입 안 함. 필요해지면 트랜잭션 경계 밖(새 트랜잭션 필요)에서 멱등성 전제로 프레임워크 재시도 도구를 검토. 요청 처리 도중 즉시 재시도는 대개 무의미(방금 죽은 저장소는 곧바로 재시도해도 죽어 있음) → 빠르게 실패(503)시키고 클라이언트가 재시도하게 하는 방향이 낫다.
- fallback으로 삼키는 인프라 장애 사용처가 3곳 이상으로 늘면 그때 전용 타입의 공통 베이스 추출을 재검토한다(현재 YAGNI로 보류).
