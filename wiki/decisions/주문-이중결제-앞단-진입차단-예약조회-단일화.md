# 주문 이중결제 앞단 진입 차단 + 예약 조회 단일화·미발견 코드 분리

PR #235의 나머지 두 결정. (1) 예약 동시 소비 가드는 [[예약-동시소비-가드-version-vs-cas]]로 분리했다.

## 컨텍스트 — 앞단 빈도 저감 vs 최종 보루

이중 PG 청구를 막는 **최종 보루** — 같은 주문의 두 번째 성공 결제를 DB unique(`uk_payment_approved_order_key`) 위반으로 막고 보상으로 정리하는 앞선 작업(#230) — 은 그대로 두고, 그 **앞단**에서 PG 청구 도달 빈도를 낮추는 심층 방어다. 여기 두 결정은 "정합성의 대체가 아니라 빈도 저감"이라는 위치를 공유한다.

## 주문 기준 진입 사전 차단 (existsApprovedByOrderId → PAYMENT_DUPLICATE)

그동안 진입에서 UNKNOWN 결제가 걸린 주문만 차단하고 "이미 성공한 승인 결제가 있는 주문"은 차단하지 않아, 한 주문을 다른 예약(다른 merchantPayKey)으로 재결제하는 새 승인이 PG 호출까지 가서 최종 보루(주문당 성공결제 unique 위반)에서 보상으로 처리됐다.

- 이를 앞당겨, "그 주문에 이미 성공한(APPROVE·SUCCEEDED) 결제가 있는가"를 EXISTS로 묻는 `existsApprovedByOrderId`를 추가하고, 승인 진입에서 새 승인(RESERVED 신규 승인)을 PG 호출 전에 `PAYMENT_DUPLICATE`("이미 다른 결제가 완료된 주문입니다", 409)로 차단한다. 기존 UNKNOWN 차단(`existsUnknownByOrderId`)과 동형.
- 진입 차단 위치는 예약이 이미 USED인 분기(같은 키 redirect 멱등 응답 경로) 이후·`create()` 전. USED 예약의 같은 키 멱등 응답을 가로채지 않도록 진입 차단은 RESERVED 신규 승인에만 적용한다.

### 앞단·뒷단 같은 코드 공유 — PAYMENT_DUPLICATE(주문 단위) vs ALREADY_USED(예약 단위)

- 최종 보루(주문당 성공결제 unique 위반 → 같은 `PAYMENT_DUPLICATE`로 번역)와 진입 차단은 **같은 "주문 이중 결제" 사실을 PG 호출 전/후 다른 시점에 감지**하는 앞단·뒷단 관계라, 같은 코드를 공유하는 게 일관적이다.
- 두 예약 전용 코드의 네이밍 스타일이 달라 보이지만 **막는 단위가 다르다.** `PAYMENT_RESERVATION_ALREADY_USED`는 **예약 단위**(한 예약을 다른 pgPaymentId가 경합 소비, [[예약-동시소비-가드-version-vs-cas]]), `PAYMENT_DUPLICATE`는 **주문 단위**(주문에 이미 성공 결제 존재). 진입 차단은 주문 기준(`existsApprovedByOrderId`)이라 DUPLICATE가 맞다.

## 'RESERVED 예약 + SUCCEEDED 결제 공존'은 다른 reservation 간에만

- 같은 reservation에서는 **발생 불가능**하다. 승인 기록(`create()`)이 예약 소비와 결제 INSERT를 한 트랜잭션에서 원자적으로 하므로, 결제가 존재하면 그 예약은 반드시 USED다.
- 진입 차단이 실제로 잡는 건 **다른 reservation 간**이다: 주문 O를 예약 R1(USED)로 결제 성공한 뒤, 같은 주문에 새 예약 R2(RESERVED, 다른 merchantPayKey)를 발급해 재결제하는 경우 — orderId를 공유하는 SUCCEEDED 결제가 있어 진입 차단이 동작한다.

## 예약 조회 단일화 — 회원 검증 흡수, 키 존재 비노출(403→404)

기존 예약 역조회는 merchantPayKey 단독이라 회원 검증이 별도 분기로 남았고, 남의 키가 존재하면 403(`PAYMENT_MEMBER_MISMATCH`)이 반환되어 키 존재 여부가 노출됐다.

- 승인 진입 역조회를 `findByMemberIdAndMerchantPayKey(memberId, merchantPayKey)`로 단일화해 회원 검증을 조회 조건에 흡수했다. "키 조회 후 memberId 불일치 시 403" 분기를 제거하고(에러코드 `PAYMENT_MEMBER_MISMATCH` 자체 삭제), 남의 키·없는 키를 모두 예약 미발견으로 흡수 — 키 존재를 비노출(보안). 응답 의미 변화(403 → 404)는 의도한 것이다.

## 미발견 코드 분리 — PAYMENT_RESERVATION_NOT_FOUND, 순차 USED 경로도 ALREADY_USED로 일관화

- 예약 미발견이 결제(Payment) 미발견과 같은 `PAYMENT_NOT_FOUND`로 응답되어, 결제창 준비물(Reservation)과 PG 사건(Payment)의 미발견 의미가 섞였다. 예약 미발견 전용 `PAYMENT_RESERVATION_NOT_FOUND`("결제 예약을 찾을 수 없습니다", 404)를 신설해 승인 진입 역조회 실패만 교체(PG·history 경로의 `PAYMENT_NOT_FOUND`는 유지). **일반화: 도메인 엔티티(Reservation vs Payment)가 다르면 미발견 코드도 분리한다.**
- 한 가지 더 일관화(리뷰 지적): USED 예약에 다른 pgPaymentId로 온 요청이 그동안 `PAYMENT_NOT_FOUND`로 응답됐는데, 이는 실은 "이미 소비된 예약을 다른 pgPaymentId로 재사용하려는 중복 요청"이다. 이 순차 경로도 `PAYMENT_RESERVATION_ALREADY_USED`로 바꿔, 같은 race(다른 pgPaymentId 재사용)가 동시(`saveUsed` 낙관 락)·순차(USED 분기) 경로에서 같은 코드로 일관 차단되게 했다.

## 막힌 점 — 진입 차단이 동시성 테스트 깨뜨림, AC에 동시성 테스트 누락

진입 차단(`PAYMENT_DUPLICATE`)이 "같은 주문 동시 요청"의 race 결과에 새 에러코드를 추가했는데, 그 동시성 테스트가 이를 반영하지 못했다. PR 리뷰 처리 중 전체 동시성 테스트를 돌려서야 드러났다.

- **같은 pgPaymentId 동시 멱등/AlreadyComplete 시나리오:** winner가 성공 commit한 뒤 RESERVED로 읽은 패자가 진입 차단에 걸리는 **현실적 flaky race**. race 허용 목록에 `PAYMENT_DUPLICATE`를 추가해 해결.
- **"이미 SUCCEEDED 결제 있으면 동시 요청도 멱등" 시나리오:** setup이 예약 소비(`use()`)를 빼고 결제만 SUCCEEDED로 만든 **비현실적 상태**(같은 예약에선 불가능)였다. 진입 차단이 이를 막아 결정적 실패. → setup을 예약 USED로 현실화해 멱등 경로 복원.
- **원인: 진입 차단을 추가한 단계의 수용 기준(AC)에 동시성 테스트가 없었다.** 동시성 테스트는 분리 태스크라 기본 테스트 실행에서 빠지는데, 그걸 AC에 안 넣어서 자동 검증이 회귀를 못 잡고 통과해버렸다. 이 함정은 [[동시성-테스트-작성-규칙과-단언-전략]]의 "새 진입/상태 가드 추가 단계는 AC에 동시성 테스트를 반드시 포함" 규칙의 실사례다.

## 미해결 — 진입 차단은 정합성 대체가 아니라 빈도 저감

진짜 동시 race는 100% 못 막으므로, 주문당 성공결제 unique + 보상이라는 최종 보루(#230)가 계속 필수다. 진입 차단은 그 앞단에서 PG 청구 도달 빈도를 낮출 뿐이다. find-first + unique 최종보장, 시간차 중복 vs 동시 race 격리는 [[find-first-write-not-check-db-unique-멱등]] 참조.
