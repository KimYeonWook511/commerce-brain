# 결제 status는 '일어난 사실'만 담고 후처리 분류는 정책이 계산 — MANUAL_REVIEW 새 상태 철회

> [!note] 적용 범위 정정 (2026-08) — 이 규칙이 막는 것은 "분류의 상태 승격"이고, 사실은 상태로 둘 수 있다
> 결제·환불 모델 재설계에서 이 결정을 근거로 새 상태를 두 번 되돌렸다가 두 번 다 결국 상태를 두는 쪽으로 갔다. **규칙을 뒤집은 것이 아니라 적용 범위를 잘못 읽었던 것이다.**
> - **"돈이 나갔다 돌아오는 중"을 전용 종결 상태로 뒀다**([[전용-종결상태-돈이-나갔다-돌아오는-중]]). 아래가 기각 근거로 든 **YAGNI("소비처 없는 상태를 만들지 마라")의 그 소비처가 생겼다** — 운영자가 가장 먼저 찾는 목록이 그것인데 상태로 고를 수 없었다. 아래가 미해결로 남긴 "결론 축 / 과금·보상 축의 직교 분해"에 대한 부분적 답이기도 하다.
> - **"자동 처리가 더 못 간다"도 매번 계산이 아니라 상태로 저장한다**([[승인은-다시-물어-확정-환불에는-실패-종착이-없다]]). 계산으로 두면 정책 값을 바꾸는 순간 이미 멈춘 건들이 일제히 부활해 **배포 한 번이 이중환불이 된다.**
> - **escalation을 스캔 시간 윈도우로 표현한다는 방침은 폐기됐다** — 그 상한 자체가 없어졌다([[결과회수-상한-폐지와-백오프-표-통지-반복]]).
>
> 정리하면 이 규칙이 막는 것은 *"후처리 분류를 상태로 승격하는 것"*이지 *"어떤 사실도 상태로 두지 말라"*가 아니다. **그 범위를 너무 넓게 읽어 정당한 선택지를 스스로 지운 경위는 [[명세-반복검사-건수도-심각도도-수렴지표가-아니다]]에 있다.**

## 컨텍스트·문제 — MANUAL_REVIEW 도입했다 철회한 과정

PR #237(UNKNOWN 결제 대사 루프 + 주문 만료 타이밍 가드)에서 결제 상태 모델을 정한 세션이다. 대사(reconciliation) 종착과 보상 종착을 표현하려고 `PaymentStatus`에 `MANUAL_REVIEW`(자동 처리 포기·운영자 확인) 새 상태를 넣었다가, 이미 내려져 있던 반대 방향 결정을 뒤늦게 발견하고 철회한 과정이 핵심이다. 결론은 "status는 사실만, 분류는 정책이 매번 계산"으로 수렴했다.

이 세션에서 승격을 시도한 `MANUAL_REVIEW`는 원래 [[결제-후처리-대상식별-status중심-재설계]]가 도입한 정책 **분류값**이었다. 그 노트에서 mismatch·환불거절·escalation 초과를 모으던 "수동검토" 분류를 status enum으로 올리려 한 것이 이 세션이고, 여기서 철회된다.

## 결정: status는 사실만, 후처리 분류는 정책이 계산

`PaymentStatus`는 결제에 실제로 일어난 **사실**만 담는다 — `REQUESTED`·`SUCCEEDED`·`FAILED`·`UNKNOWN` 네 값뿐이다. "이 결제가 후처리 대상이냐, 어떤 대상이냐"(자동 대사 / 보상 / 수동 확인 / 없음)는 status에 박지 않고, 정책이 `(status + 실패코드 + 경과 시간 + 연계된 취소 행)` 조합으로 매번 계산한다.

- **핵심 원칙:** 분류 결과를 status에 박으면 "일어난 사실"과 "그로부터 파생된 판단"이 한 값에 섞여 상태의 의미가 흐려진다. status는 사실 축에 고정, 파생 분류는 정책 계산으로 분리.
- **철회한 것 = 상태이지 정책 분류값이 아니다.** 넣었다가 뺀 건 `PaymentStatus.MANUAL_REVIEW`라는 *상태값*이다. 정책이 후처리 대상을 가릴 때 쓰는 분류값 중 "수동 확인"은 그대로 살아 있다 — status가 아니라 정책이 계산해 내놓는 결과값이라 사실/파생 혼선을 일으키지 않는다. 승격을 막은 대상은 정확히 "이 분류를 status enum으로 올리는 것"이다.

## MANUAL_REVIEW 새 상태 기각 근거 (무손실 복원 / YAGNI / 되돌리기 쉬움)

처음엔 자동 처리를 포기한 건과 보상 종착을 상태로 드러내려고 `MANUAL_REVIEW`를 도입했다. 사용자가 "보상된 승인 결제 상태를 어떻게 표현할지는 이미 정한 결정이 있다"고 짚어줘서 그 결정을 다시 읽고 철회했다.

- **이미 있던 반대 방향 결정:** PG가 승인(과금)했으나 우리가 중복·금액불일치로 거부하고 보상(환불)한 승인 결제는, "과금됐지만 보상 대상"이라는 새 상태로 표현하지 않는다. 대신 기존대로 `FAILED` + 실패코드(중복결제 / 금액불일치) + 같은 PG결제ID를 가진 취소(CANCEL) 행으로 표현한다. 이 표현 규약은 [[이중결제보상-완료가드-제거-pgpaymentid-무조건취소]]·[[결제승인완료-보상-완료우선-이중결제-adapter매핑]]·[[대사-확정-검증보상-대칭-재승인없음]]이 공유한다.
- **기각 근거 1 — 무손실 복원:** "과금 후 보상" 여부는 `실패코드 ∈ {중복결제, 금액불일치}` + 같은 PG결제ID의 취소 행 존재로 결정적으로 되살릴 수 있다. FAILED가 표현상 부정확할 뿐(과금된 거부 건을 실패로 표기) 데이터를 잃지는 않는다.
- **기각 근거 2 — YAGNI:** "clean fail vs 과금 후 보상"을 구분해 실제로 소비하는 기능(정산 대조 / 분쟁 자동화 / 운영 대시보드)이 아직 없다. 소비처 없는 상태를 미리 만드는 건 가정된 미래 요구를 위한 부채다.
- **되돌리기 쉬움:** 새 상태를 나중에 추가하는 비용이 지금 추가하는 비용과 거의 같고(enum 값 추가 + 소비처 재검토), 과거 데이터도 `FAILED ∧ 실패코드 조건` 일괄 UPDATE로 결정적 backfill이 가능하다. 미뤄도 이자가 붙지 않는 결정이라 미루는 쪽이 안전하다.

## escalation은 새 상태 대신 스캔 시간 윈도우로

PG가 정해진 시간을 넘도록 결론(승인/거부)을 못 내는 건(escalation)도 새 상태로 표현하지 않는다. 자동 대사 스캔 쿼리를 시간 윈도우로 제한해, 상한을 넘긴 미확정 건을 자동 대사 대상에서 자연히 빼는 방식으로 처리한다.

- **윈도우:** 하한은 진입 지연(UNKNOWN ~1분, REQUESTED ~15분 = 승인 가능 10분 + 마진 5분), 상한은 escalation 기준 ~6시간. 정책 상수로 확정(운영 config화는 추후). 이 값들의 파생 근거는 [[결제-후처리-대상식별-status중심-재설계]]이다.
- **"자동 대사 대상이냐"를 status가 아니라 시간 윈도우가 정의한다.** 상한을 넘긴 건은 스캔에서 빠지고 상태는 그대로 `UNKNOWN`/`REQUESTED`로 남는다. 상태 enum을 늘리지 않고도 "더 이상 자동으로 손대지 않는다"를 표현한다. 이 윈도우가 만료 차단과 맞물려 만드는 over-blocking/starvation 정합성은 [[미확정차단-대사스캔-정합성-starvation-escalation]]에서 구조로 다룬다(그쪽은 정합성 구조, 여기는 상태 표현 관점).
- **하한을 상태별로 가른 이유:** 공통 하한을 두면 진입 지연이 긴 REQUESTED가 정렬 앞단을 차지해 뒤 후보가 고사(starvation)한다.

## 막힌 점 — 루트 ADR 로그 미확인으로 반대 결정을 재발명

같은 문제(보상된 승인 결제를 어떻게 표현할지)를 이미 내려진 결정과 정반대 방향으로 다시 풀었다. 이 PR의 task 문서만 보고, 그 위 층에서 최신 결정들이 번호순으로 누적되던 루트 ADR 로그를 안 봤기 때문이다. 거기에 "보상된 승인은 새 상태 대신 FAILED + 실패코드 + 취소 행"이 이미 있었는데 못 보고 `MANUAL_REVIEW` 새 상태를 도입하는 정반대 선택을 했다. 사용자가 짚어줘서 다시 읽고 철회했다.

- **교훈으로 굳힌 것:** 상태·도메인 정책을 바꾸려 할 땐 탐색 단계에서 task 범위 문서에 갇히지 말고, 최신 결정이 쌓이는 루트 ADR 로그를 변경 키워드로 먼저 grep해 "이미 반대 결정이 있나"를 확인해야 한다. 이 "정본·선례 확인 실패"는 [[설계단계-검증-정본·선례-확인실패와-전제의-적대적검증]]과 같은 결의 실패 사례다.

## 배운 것 (직교 축 분리, 소비처 없는 상태 금지)

- **"상태"와 "그 상태로부터의 분류"를 한 enum에 섞지 마라.** status는 사실 축에만 고정하고, 파생 판단은 정책이 사실 + 실패코드 + 시간 + 연계 행으로 계산하게 둔다.
- **소비처 없는 상태값은 만들지 마라.** 새 상태의 정당화는 "그 구분을 실제로 읽어 쓰는 기능"이 생길 때다. 되돌리기 쉽고 backfill이 결정적이면 미루는 쪽이 부채가 적다.
- **직교하는 두 축을 한 값에 뭉개면 애매함이 생긴다.** `MANUAL_REVIEW`의 애매함은 "결론이 났나(확정 vs 미상)"와 "과금됐나 / 보상됐나"라는 직교 두 축을 한 상태값에 섞은 데서 나왔다. 분해한다면 status는 결론 축만 담고, 보상 여부는 별도 필드나 취소 행으로 직교하게 표현하는 게 맞다.

## 미해결 (결론축/보상축 명시적 직교 분해, escalation 운영 가시성 #238)

- **결론 축 / 과금·보상 축의 명시적 직교 분해는 아직 안 했다.** 지금은 "과금 후 보상"을 FAILED + 실패코드 + 취소 행으로 복원하는 데 그친다. 명시적 직교 분해는 그 구분을 실제로 소비하는 기능이 생길 때 재검토한다.
- **escalation 상한 초과 건의 운영 가시성**(통지·조회 종착)은 후속 #238로 미뤘다. 지금은 자동 대사에서 빠지고 UNKNOWN/REQUESTED로 남을 뿐, 사람이 봐야 할 것으로 드러나지 않는다. escalation 시점을 담는 직교 필드 접근은 [[결제-escalation-종착통지-escalatedAt-직교필드]] 참고.
- 새 상태(정산 대조 / 분쟁 자동화 / 운영 대시보드가 요구할 때) 도입은 그 소비 기능이 생기는 시점의 재검토 trigger로 남긴다.
