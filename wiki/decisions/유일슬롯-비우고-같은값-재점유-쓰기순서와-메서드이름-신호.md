# 유일 제약을 비웠다가 같은 값으로 다시 잡을 때의 쓰기 순서

## 컨텍스트 — 어떤 설계에서 이 문제가 나오나

"한 주문에 살아 있는 결제는 최대 하나"를 DB 유일 제약으로 지키기로 했는데, 결제는 실패하면 다시 시도할 수 있어야 한다. 그러면 **한 번 잡았던 값을 놓았다가 같은 값으로 다시 잡는** 흐름이 생긴다.

이 모양은 결제에만 있는 게 아니다 — "**어떤 자원을 한 번에 하나만 점유하되, 점유를 풀고 다시 잡을 수 있어야 한다**"는 조건이면 좌석 선점·배타적 작업 잠금·예약 슬롯에서 같은 문제가 나온다.

## 결정 1 — 점유 컬럼을 따로 두고 비울 때 NULL로 만든다

| 컬럼 | 성질 | 무슨 일을 하나 |
| --- | --- | --- |
| 자원 참조 | `NOT NULL` | **이력.** 이 행이 어느 주문의 시도였는지. 끝나도 안 지운다 |
| 점유 표시 | `UNIQUE`, NULL 허용 | **배타 점유.** 살아 있으면 자원 식별자, 끝나면 NULL |

**이 둘을 하나로 합치지 않는 것이 이 설계의 절반이다.** 합쳐서 끝날 때 NULL로 만들면 **끝난 행이 어느 자원의 것이었는지가 사라져** "이 주문에 지난 시도가 몇 번 있었나"를 영영 못 찾는다.

살아 있는 동안 두 컬럼에 같은 값이 중복으로 들어간다. 정규화 관점에서는 중복이지만 **한쪽은 사실을 기록하고 다른 쪽은 제약을 표현하는 것**이라 목적이 다르다.

## 결정 2 — "살아 있는 것만 유일"을 NULL 허용으로 표현한다

MySQL은 유일 제약에서 **NULL을 중복으로 치지 않는다.** 끝난 행이 아무리 쌓여도 NULL끼리는 충돌하지 않는다. 이 저장소가 이미 쓰던 트릭이며([[payment-이중결제-reserve따닥-mysql-null트릭-unique]]) 그 이유도 같다 — PostgreSQL이면 부분 인덱스(`CREATE UNIQUE INDEX ... WHERE status = 'ALIVE'`)로 조건부 유일을 직접 표현하지만 **InnoDB에는 그게 없어 조건을 인덱스가 아니라 값에 담는 우회를 쓴다.**

**DBMS마다 다르므로 옮길 때 확인해야 한다** — SQL Server는 유일 제약에 NULL을 **하나만** 허용해 이 방법이 아예 안 통하고, PostgreSQL 15+는 `NULLS NOT DISTINCT`로 이 성질을 끌 수 있어 무심코 켜면 조용히 깨진다.

**대가:** 점유 컬럼 하나가 두 가지를 겸한다 — 무엇을 가리키는 값이면서 "살아 있는가"의 표시. 상태 컬럼과 어긋날 수 있어 **둘을 같은 UPDATE에 묶어** 도메인 객체 안에서만 바뀌게 했다.

## 결정 3 — 시도마다 새 행을 쌓는다

재점유를 **기존 행의 UPDATE로** 처리하면 아래 4번의 쓰기 순서 문제가 **아예 안 생긴다.** 그래도 새 행을 쌓기로 했다 — 이 테이블이 **시도 원장**이라 몇 번 시도했고 각각 왜 실패했는지가 남아야 한다([[payment-append-only-원장과-exists-완료판단]]). **순서 문제는 해결할 수 있는 것이고 잃은 이력은 되찾을 수 없다.**

검토하고 버린 것:

- **끝난 행을 DELETE** — 이력이 사라지는 데다 **ORM의 쓰기 순서상 DELETE가 INSERT보다 뒤라 순서 문제가 오히려 악화된다.**
- **유일 키에 시도 회차를 넣어 값이 안 겹치게** — 그러면 같은 주문에 살아 있는 결제가 여럿 서도 제약이 안 막는다. **막으려던 것 자체가 사라진다.**
- **비움과 재점유를 두 트랜잭션으로 나누기** — 순서는 확실해지지만 사이에서 끊기면 **아무도 점유하지 않은 채로 남는다.**

## 결정 4 — 비우는 쪽이 새로 잡는 쪽보다 먼저 DB에 닿게 만든다

**DB 층 — 순서만 맞으면 문제가 없다.**

| 보낸 순서 | 결과 |
| --- | --- |
| UPDATE(비움) → INSERT | 통과 |
| INSERT → UPDATE(비움) | 위반 |

- MySQL은 유일 제약을 **행을 쓰는 그 순간마다** 검사하고 커밋까지 미룰 수 없다. 표준 SQL의 `DEFERRABLE INITIALLY DEFERRED`를 지원하지 않는다.
- **"문 단위"가 아니라 "행 단위"인 것이 중요하다.** 한 문으로 값을 밀어 올리는 `UPDATE t SET slot = slot + 1`은 **최종 상태가 유일해도 중간 행에서 위반이 난다.** "한 문으로 처리하면 되지 않나"는 안 통한다.
- `unique_checks = 0`은 유예처럼 보이지만 **검사를 미루는 게 아니라 건너뛴다.** 대안이 아니다.
- **옵티마이저가 문과 문 사이 순서를 바꾸는 일은 없다.** 옵티마이저가 고르는 것은 *한 문 안에서* 어떤 인덱스를 탈지다.

**ORM 층 — 코드에 적은 줄 순서는 아무 보장이 아니다.** 두 경로가 있고 둘 다 같은 결론으로 간다.

- **기본키를 DB가 매기는 전략**(`IDENTITY`/AUTO_INCREMENT): 키 값을 얻으려면 INSERT를 보내야 하므로 **미룰 수가 없다.** MySQL은 시퀀스가 없어 현실적으로 이 경로가 지배적이다.
- **그 밖의 전략**: Hibernate가 flush할 때 코드 순서가 아니라 작업 종류별로 정해진 순서로 내보낸다.

```
OrphanRemoval → INSERT → UPDATE → (컬렉션 작업들) → DELETE
                ^^^^^^   ^^^^^^   이 순서가 고정.  코드에 무엇을 먼저 적었든 무관
```

→ **비우는 갱신을 명시적으로 먼저 flush해야 한다.** 어느 전략을 쓰든 성립하도록 방어했다(기본키 전략을 아직 문서에 못 박지 않았기 때문).

**단, 먼저 flush한다고 저절로 되는 게 아니다.** `flush()`는 그 엔티티만이 아니라 **영속성 컨텍스트 전체**를 내보낸다. 새 점유 엔티티를 이미 영속화해 둔 뒤에 비우는 갱신을 flush하면 **그 flush 안에서 INSERT가 UPDATE를 앞질러** 원래 버그가 재현된다. 이 해법은 **"비우는 flush 시점에 새 엔티티가 아직 영속화되지 않았을 것"**이라는 조건 위에서만 성립한다.

## 결정 5 — 그 순서 의존을 메서드 이름으로 드러낸다

| 성격 | 무엇에 기대나 |
| --- | --- |
| 평범한 저장 | 아무것도. 커밋 시점에 나가면 된다 |
| 충돌 확정용 저장 | 낙관 락 충돌을 이 호출 안에서 확정하는 것 |
| 순서 보장용 저장 | 이 저장이 뒤엣것보다 먼저 DB에 나가는 것 |

셋 다 안에서는 똑같이 즉시 flush를 부른다. **안이 같으니 이름 말고는 구분이 안 드러난다** — 그러면 나중에 누가 "여기는 충돌을 안 잡네" 하고 평범한 저장으로 바꾸는 순간 **쓰기 순서가 조용히 깨진다.** 주석은 리팩터에서 지워지지만 **이름은 남는다.** 즉시 flush를 계약으로 못 박는 결은 [[unique-위반-예외번역-infra-adapter-경계와-flush-타이밍]]과 같다.

**이름은 방어선이 아니라 신호다.** 실제 방어는 *비우고 같은 값으로 다시 잡는 경로를 진짜 DB로 도는 통합 테스트*다. 이름의 역할은 **그 테스트가 왜 있는지를 읽히게 하는 것**이고, 둘 중 하나만 두면 안 된다([[도달불가분기-방어금지-불변식테스트-돈정합성-통합테스트]]).

## 배운 것

- **"동시에 나가나?"는 잘못된 질문이었다.** 한 커넥션에서 SQL은 언제나 하나씩 순차로 나간다(JDBC 배치로 묶여도 순서는 보존된다). 진짜 질문은 **"어느 쪽이 먼저 나가나"**다.
- **제약 검사 시점은 DBMS마다 다르다.** "커밋할 때 한꺼번에 보겠지"라는 직관은 MySQL에서 틀린다.
- **이 버그가 늦게 발견되는 이유는 flush 순서가 흔들려서가 아니다** — 그건 결정적이다. 진짜 이유는 (가) 비우고 *같은 값으로* 다시 잡는 경로를 테스트가 안 덮고, (나) **중간에 조회 쿼리 한 줄이 끼면 auto-flush가 일어나 우연히 통과하고**(그 쿼리를 지우거나 옮기는 순간 아무 상관없어 보이는 변경에서 깨진다), (다) 제약이 안 걸린 스키마나 인메모리 DB로 도는 테스트다([[silent-schema-drift-패턴]]).
- **"비우고 다시 잡기" 사이의 틈은 다른 트랜잭션에 안전하다** — 비우는 UPDATE가 배타 락을 걸어 다른 트랜잭션이 우리 커밋까지 대기한다. **다만 그 대기가 락 타임아웃과 데드락 두 가지로 끝날 수 있고 둘은 다르게 다뤄야 한다** — InnoDB의 중복 키 검사는 공유 락·갭 락을 잡아 데드락의 고전적 원천이다. **두 예외를 받는 자리가 있어야 하고 낙관 락 충돌과도 구분해야 한다**([[재고복구-트랜잭션-맨뒤-배치와-비관락-경합-계측갈래]]).

## 미해결

- **생성 컬럼(또는 함수 인덱스)으로 조건부 유일을 표현하는 방법을 검토하지 않았다.** MySQL 5.7+ 생성 컬럼, 8.0.13+ 함수 인덱스로 `CASE WHEN status='ALIVE' THEN 자원식별자 END`를 만들어 유일 제약을 걸 수 있다. **DB가 스스로 파생시키므로 애플리케이션이 점유 컬럼을 손으로 채우고 비울 필요가 없어져** 위 결정 2의 대가가 사라진다. 대신 인덱스가 상태 값에 묶인다. **이번엔 아예 검토 대상에 안 올렸다는 게 정확한 상태다.**
- **락 대기 시간과 데드락 빈도를 재보지 않았다.**
- **기본키 생성 전략을 문서에 명시할지 정하지 않았다.** 지금은 어느 쪽이든 성립하게 방어해 뒀다.
