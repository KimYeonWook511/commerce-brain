# 관리자 재고 조작 별도 API + 변경만 이력에 남긴다 (감사 목적 분리)

## 컨텍스트·문제 — 무엇을 이력에 남기나

관리자의 초기 재고 생성·수동 증감을 어디에 붙일지(상품 API vs 별도 재고 API), 그리고 재고 변경 중 무엇을 이력 테이블에 남길지를 정해야 했다. 재고 변경원은 둘이다 — 관리자 조작과 주문 차감/복구. 이력에 둘 다 남길지, 관리자 것만 남길지가 쟁점이었다. 이 결정은 [[stock-도메인-구조-개요]]의 세 축 중 "관리자 조작·이력 분리"에 해당한다.

## 결정

- 관리자 초기 재고 생성·수동 증가/감소는 **상품 API가 아니라 별도 재고 API**로 제공한다.
- 그 변경만 `tbl_stock_history`에 감사 데이터로 남긴다. 이력의 핵심 컬럼은 *변경 수량(`quantityChange`) + 변경 사유 + 관리자 member id + 시점*이다.
- **주문 차감/복구는 이력에 남기지 않는다.**

## 왜 주문 차감/복구는 이력에 안 남기나 (목적·SoR·성격)

"테이블 폭증" 우려보다 *테이블 목적 자체*가 이유다.

- **`tbl_stock_history`는 관리자 감사용으로 설계됐다.** 핵심 컬럼이 관리자 member id와 변경 사유다. 주문 차감은 관리자가 없고 사유도 단조로워, 같은 테이블에 끼우면 NULL/sentinel 값이 늘고 "감사"라는 의미가 흐려진다.
- **주문 흐름은 이미 다른 도메인이 기록한다 — SoR 이중화 회피.** 주문 생성/취소/만료는 order 도메인이, 재고 복구는 outbox 이벤트(Kafka payload 포함)가 기록한다. 게다가 HTTP 요청에서 발급한 traceId가 Kafka·Outbox 경계를 지나 주문→재고 복구 전체를 단일 traceId로 잇는다. 같은 사실을 이력에 또 적으면 기록의 원천(source of record)이 둘이 되어 일관성 부담만 는다.
- **변경의 성격이 다르다.** 관리자 변경은 *수동·의도적·외부 입력*이고, 주문 차감은 *자동·시스템 결과*다. 한 테이블에 섞으면 조회할 때마다 성격별 case-split이 필요해진다.

→ 이력 테이블의 *목적*과 *조회 동기*가 "관리자 책임 추적" 하나로 좁아, 다른 변경원은 의도적으로 배제했다.

이 분리는 메서드 시그니처 레벨에서도 강제된다 — 관리자 경로 `AdminStockService.increaseByAdmin(...)`(이력 기록)과 주문 취소 경로 `StockInventoryService.increase(...)`(이력 미기록)는 같은 이름의 분기 메서드가 아니라 **애초에 별도 메서드**다. 이름부터 다르니 호출 시점에 책임이 자연스럽게 강제된다(order 측 보강 근거는 [[재고복구-동기취소-vs-outbox-비동기만료-비대칭]]). 주문→재고 복구를 잇는 traceId 전파 결의 뿌리는 [[주문-멱등성-캐싱-after-commit-이벤트-분리]]와 [[mdc-정리-스코프-오너십-2규칙]]에 있다.

## 요구사항 충돌 봉합 — 초기 재고 0 vs quantityChange 0

관리자 재고 관리 기능을 구현하는 중에 두 요구사항이 정면으로 부딪혔다.

- **충돌:** 요구사항은 초기 재고 수량 `0`을 허용한다. 동시에 이력의 변경 수량(`StockHistory.quantityChange`)은 `0`을 허용하지 않도록 설계돼 있었다. 초기 재고를 0으로 만들면 이력에 `quantityChange = 0`을 남겨야 하는데 그게 금지라 막혔다.
- **해결:** "초기 재고가 0이면 재고(stock) row만 생성하고 이력(history)은 저장하지 않는다"는 예외 정책으로 봉합했다.

이렇게 만들어진 "stock row는 있으나 이력은 없는" 상태, 그리고 넓게는 "재고 row가 아직 없을 수도 있는" 비대칭은 상품 조회 쪽에서 재고 누락을 0으로 정규화하는 [[product-상세조회-stock-의존-재고누락-0-정규화]]와 연결된다.

## 교훈 — 충돌은 계획 단계에서 잠근다

이 충돌은 구현 단계에서야 드러나 그 자리에서 임시 예외 정책으로 봉합했다. 서로 충돌할 수 있는 요구사항·정책은 *구현 전 계획 단계*에서 먼저 명시하고 잠가야 한다. 구현 중에 부딪히면 임시 예외로 봉합하게 되고, 그 예외가 문서화되지 않으면 나중에 놀란다. (요구사항 충돌 예방이라는 일반 교훈은 knowledge 노트 승격 후보.)

## 미해결 — 이력 pagination 부재

이력 조회 첫 버전은 pagination 없이 상품별 전체 목록을 반환한다. 관리자 재고 분리의 트레이드오프로 명시해 둔 것으로, 데이터가 늘면 후속으로 pagination을 붙여야 한다.
